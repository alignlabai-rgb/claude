定期・イベント自動実行 — Routinesとローカル処理を分ける

いつ、どこで、何を実行し、どの結果を確認するかを設計します。

旧情報は固定旧版の全文へ分離しています。以下の例・試験案は未実行の教材です。

三つの仕組みを同じcronと呼ばない

Codeのcloud Routinesはresearch previewで、schedule、API、GitHub event等から実行できます。Routines。Desktop scheduled taskは端末側、/loopとCronCreate／CronList／CronDeleteはsession内の仕組みです。一方、CLIの/schedule（alias /routines）はv2.1.225以降でcloud routineを作成する入口です。/schedule list／update／runなどの管理にはv2.1.227以降が必要です。CLIで設定しても実行先がローカルになるわけではありません。

最初に選ぶのは時間間隔ではなく完成物です。「毎日何か報告」より「変更したAPI記述の候補を差分と出典付きで出す」と決めます。変化がないなら静かに終える、重大な不足なら解消条件を返す、という通知の意味も別に設定します。

cloudと端末の前提

cloud routineは選んだrepositoryやconnector等へアクセスして実行し、端末を閉じても続きます。ただし端末内の全資料を自動で読める意味ではありません。local Desktop taskは端末の稼働が条件になり、/loopなどのsession内の繰り返しはCodeが動作中かつidleであることが条件です。CronCreateの未期限切れtaskは--resume等で復元される場合がありますが、期限切れや予定時刻を過ぎた一回task、self-paced loop等は例外です。session継続とcloud routineの独立した永続実行を混同しません。Desktop tasks／Session scheduling。

例の自動記事候補は公開資料だけを入力にし、未公開の内部folderをcloudへ渡さない設計にします。個別の契約やデータ条件を確認せず、便利な接続があるからと読み込みを拡大しないでください。実行場所とデータの境界を短い票へ残します。

eventは依頼の権限を増やさない

API triggerやGitHub eventには外部の文字列が含まれます。routineの保存済み目的と、event本文の指示を分けます。攻撃的な命令や無関係な依頼がpayloadにあっても、それを新しい許可として実行しません。

公式はAPIのtextやRun nowの追加入力をroutine-fire-payloadのuntrusted dataとして扱う構造を説明しています。保存済みのroutine promptは現在、実行する割当taskとして渡され、追加のfire textとは別です。その保存済みpromptも、実行中の新しい承認や同意の代わりにはなりません。API triggerのpayload。ただしwrapperだけで業務の安全を保証するわけではありません。接続先、network、tool、環境変数のscopeを最小化し、自律実行する前に人工eventで試験します。

未実行例：文書の鮮度候補を作る

公開repositoryの仕様ページについて、前回確認後の変更を読み、対象ページ・根拠URL・変更理由・確認不能を候補一覧にするroutineを想定します。公開反映は別のownerが確認し、routineはPR候補やローカル候補で止めます。日次件数を満たすために無意味な記事を作りません。

人工eventは正常更新、同じeventの再送、空差分、削除された資料、取得拒否を含めます。重複eventは同じ候補を増殖させないよう入力IDと状態を照合します。時刻だけを記録するのでなく、どの資料版を確認したかを残すと次回の差分が再現できます。

緑のstatusは業務成功ではない

公式routine案内は、緑のstatusがsessionのinfrastructure errorなしの開始・終了を示し、promptの仕事の成功を意味しないと明記します。Runsの確認。成功の判定は実成果、入力不足、permission拒否、tool結果と照合します。

そのため監視は起動回数でなく、完成物があるか、予定した範囲を満たすか、重要な失敗が通知されたかを見ます。結果不明の外部操作があれば無確認再送せず照合します。自動生成された「成功しました」という文だけを記録へ転載しないようにしてください。

停止と縮小までを運用に含める

通知が増えて読まれない、同じ未解決を繰り返す、利用枠を超える、対象がなくなった場合は頻度やscopeを縮小する条件です。停止には原因、解消owner、次に何を確認すれば再開するかを付けます。無限retryや、quotaを消費するための実行を目的にしません。

導入の受入は設定保存、最初の正常実行、失敗eventの検出、結果の利用という段階を分けます。旧scheduleを残したまま新routineを追加して二重実行しないよう、既存設定を確認します。本記事はroutine作成、token発行、GitHub連携、定期設定を実行していません。

日次起動より先に一回を評価する

合成の更新一覧に、新しい項目、既知の項目、根拠のない項目を混ぜ、何を採用し何を保留するかを試します。その一回が評価できないまま毎日起動すると、判断の曖昧さも毎日再生産されます。起動頻度を決める前に、重複判定と人が読む差分を設計します。

定期実行の最終記録には、対象期間、読めた入力、未取得の入力、採用候補、保留理由を短く残します。何も変化していない回を失敗として記事で埋める必要はありません。起動の緑表示、出力ファイルの存在、内容の受入を分けることで、『毎日動いた』を『毎日価値が出た』と読み違えることを防げます。
