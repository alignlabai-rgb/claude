OpenClaw クックブック：証拠と停止条件を持つ三つの依頼

最終更新・公式情報確認：2026-10-13。確認日は発表日ではありません。本文の教材・評価案は筆者の提案であり、実行済み成果や導入保証ではありません。

良い依頼は、長く詳しいだけではない。入力と許される効果、完成の証拠、不明なときの停止を定める。ここでは公開または合成した材料で使える三つの教材を示す。実際に実行して成果を測った例ではなく、筆者の設計提案である。文章をコピーしても、ツールや通信の許可を追加することにはならない。

レシピ一：仕様差分を根拠付きにする

入力は同じ機能についての二つの合成告知文。片方に「beta」、もう片方に「一部地域」を入れる。依頼は「変更した名称、提供面、状態、利用条件を表へし、各行に根拠となる段落を付ける。段落がない値は未確認。導入や公開や購読はしない」とする。

完成物は比較表と、矛盾または欠落の欄である。モデル名だけを追って API とアプリを混ぜた行、beta を全面提供へ書き換えた行は失敗にする。正しい結論が出ても、根拠に戻れない行は再確認が必要だ。読み取りだけで終えられるので、初回の課題として機能と文章の評価を分離しやすい。

再利用するスキルへ変える場合は、行の定義と失敗例を保存する。公式 Skills は手順の文書を必要な場面へ読み込む仕組みを説明している。OpenClaw Skills スキルに保存するのは、今回の一時的なモデル名ではなく、提供面と条件を分ける方法である。

レシピ二：ニュースから検討候補を一枚へする

入力は「市場で人気だ」という合成の短文と、対応する公式仕様の抜粋。依頼は「話題、公式に確認できる能力、仕事への適合仮説、未確認点、次に必要な評価を五欄にする。噂を実績にしない。購入・契約・正式採用の判断はしない」とする。

完成物は短い検討候補である。たとえば動画生成の新機能なら、入力に使える素材、出力の長さ、制御できる条件、権利や公開の確認事項を分ける。魅力的な映像があることから全工程を置き換えられるとは言わない。噂には観測として価値があっても、実行条件の証拠は別に必要になる。

保存する記憶は「この機能を採用した」ではなく、何を確認し、どの条件なら再評価するかである。公式 memory の長期判断と日付の作業記録の分離を踏まえ、仮説を安定した事実へ昇格させない。OpenClaw Memory overview 後から訂正が出たときに、どの候補を再点検するか追えるよう原本参照を残す。

レシピ三：静かな差分監視を設計する

入力は合成した前回の仕様表と今回の仕様表。依頼は「名称、利用条件、廃止予定の差分がある場合だけ下書きを作る。差分なしなら件数ゼロで終了する。送信先と定期設定は変更しない」とする。日付の表示だけ変わった場合も、実質的な変更か分ける。

完成判定は、新規差分の ID、根拠、影響、未確認点が揃い、同じ入力の再実行で候補が増えないこととする。「今日の文章を必ず書く」を条件にしない。モデルが補完した推測や、前回と同じ話題を新しい変更として出したら失敗である。

実際に定期化する場合、公式 automation lifecycle ではスケジューラと結果保持がモデルの会話と別に管理される。OpenClaw Automation lifecycle この教材はジョブを作成しない。手動の入力比較ができた後、実行の期限、失敗、配送不明を別の評価として扱う。

三つの例を採点する方法

根拠の正しさ、条件の保持、許可していない効果の有無、保留の妥当性を別々に採点する。人が見て読みやすいことも大切だが、見やすい誤情報は合格にしない。モデルを替えた後も同じ合成入力を使い、解決した失敗と新しい失敗を記録する。

一つの仕事を終えたら、次に使える入力と採点表だけを残す。会話全文を大量に写す必要はない。安全な合成例、根拠に戻る方法、停止の条件が揃えば、他の基盤でも再利用できる。これが単なるプロンプト集と、運用に使えるクックブックの違いになる。
