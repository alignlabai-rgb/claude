Docker Essentials

The Universal Shipping Container for Code — AI Agent Sandbox として使いこなす

What is Docker?

Dockerは、あなたの作ったプログラムを「どこでも動くケース」に閉じ込める技術です。
AIエンジニアにとって、これは単なるツールではなく「自律型エージェントの檻（Cage）」として機能します。

The Shipping Container Analogy

昔 (Before Docker):
引っ越しのとき、家具や食器をそのままトラックに放り込んでいました。
「Aさんのトラックでは運べたけど、Bさんのトラックだと不安定で壊れる」という問題が起きました。
(＝ PCが変わると動かない "It works on my machine" 問題)

今 (With Docker):
家具も食器も空気も、全て規格化されたコンテナに詰め込みます。
トラックの運転手（Windows, Mac, Linux）は、中身を気にせず「コンテナ」を運ぶだけ。
開ければどこでも全く同じ部屋が再現されます。

Core Concepts

🖼️ Image（設計図）

コンテナに何が入っているかの定義ファイル。
「Ubuntu + Python 3.12 + このコード」という不変のデータ。CD-ROMのようなもの。

📦 Container（実体）

Imageから生成された、実際に動いているプロセス。
1つのImageから何個でも作れる。使い終わったら捨てて跡形なく消える（Disposable）。

📝 Dockerfile（レシピ）

Imageの作り方を記述したテキストファイル。
「FROM ubuntu → RUN apt install → COPY ソースコード」という手順書。

🗂️ Volume（永続ストレージ）

コンテナを削除してもデータが残る永続化領域。
DBのデータやアップロードファイルはVolumeに保存する。

🌐 Network（仮想LAN）

コンテナ間の通信路。同じnetworkに属するコンテナはコンテナ名でアクセス可能。

🎻 Docker Compose（指揮者）

複数コンテナを1つのYAMLで定義・管理するツール。App + DB + Redisを同時起動できる。

Dockerfile の書き方

Dockerfileは上から順に実行され、各命令が「レイヤー」を積み重ねます。

基本構文

FROM python:3.12-slim # ベースイメージ指定 WORKDIR /app # 作業ディレクトリ設定 # 依存関係を先にコピー（キャッシュ効率化） COPY requirements.txt . RUN pip install -r requirements.txt # ソースコードをコピー COPY . . EXPOSE 8000 # ポート宣言（情報提供のみ） CMD ["python", "-m", "uvicorn", "main:app", "--host", "0.0.0.0"]

Multi-stage Build BEST PRACTICE

ビルド用コンテナと実行用コンテナを分離。本番イメージを劇的に小さくできる。

# Stage 1: Build FROM node:20 AS builder WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . RUN npm run build # Stage 2: Production (node_modulesのdevDepsを含まない) FROM node:20-slim WORKDIR /app COPY --from=builder /app/dist ./dist COPY --from=builder /app/node_modules ./node_modules EXPOSE 3000 CMD ["node", "dist/index.js"]
Tip — .dockerignore プロジェクトルートに .dockerignore を置いて node_modules/・.git/・*.env を除外すると、イメージが小さくなりビルドも速くなる。

Docker Compose — 複数コンテナ管理

Webアプリ + DB + Cacheなど複数サービスを1ファイルで宣言的に管理します。

compose.yaml の基本構造

services: api: build: . # Dockerfile からビルド ports: - "8000:8000" environment: DATABASE_URL: postgresql://postgres:pass@db:5432/mydb depends_on: db: condition: service_healthy # DBのヘルスチェック後に起動 volumes: - ./src:/app/src # ホットリロード用バインドマウント db: image: postgres:16-alpine environment: POSTGRES_PASSWORD: pass POSTGRES_DB: mydb volumes: - pgdata:/var/lib/postgresql/data # 名前付きVolume（永続化） healthcheck: test: ["CMD-SHELL", "pg_isready -U postgres"] interval: 5s timeout: 5s retries: 5 redis: image: redis:7-alpine ports: - "6379:6379" volumes: pgdata: # 名前付きVolumeの宣言（docker管理・ホストから隔離）

Compose コマンド

コマンド 説明
docker compose up -d全サービスをバックグラウンドで起動
docker compose up --buildイメージを再ビルドして起動
docker compose down全サービス停止・コンテナ削除
docker compose down -vVolumeも含めて完全削除
docker compose logs -f apiapiサービスのログをフォロー
docker compose exec api bashapiコンテナにシェル接続
docker compose ps各サービスのステータス確認
docker compose restart apiapiサービスのみ再起動
docker compose run --rm api pytest一時コンテナでコマンド実行
Tip — 複数環境の管理 compose.yaml（共通）+ compose.dev.yaml（開発用オーバーライド）の2ファイル運用が定番。 docker compose -f compose.yaml -f compose.dev.yaml up でマージ起動。

Volumes — データ永続化

コンテナを削除してもデータを残すための仕組み。3種類の使い分けを把握する。

種別 記法 用途 管理
Named Volume pgdata:/var/lib/postgresql/data DBデータ・永続ストレージ Docker管理（隔離）
Bind Mount ./src:/app/src 開発中のホットリロード ホストOS管理
tmpfs Mount --tmpfs /tmp 一時ファイル・セキュア処理 メモリ（再起動で消える）
# Named Volume の操作 docker volume ls # 一覧 docker volume inspect pgdata # 詳細（マウントパス確認） docker volume rm pgdata # 削除 docker volume prune # 未使用を一括削除 # バックアップ（Named Volume → tar） docker run --rm \ -v pgdata:/data \ -v $(pwd):/backup \ alpine tar czf /backup/pgdata.tar.gz /data

Network — コンテナ間通信

Docker Compose内のサービスはデフォルトで同一ネットワークに属し、サービス名でDNS解決できます。

ネットワーク種別 特徴 用途
bridge（デフォルト） 同一ホスト内の仮想LAN。コンテナ名でアクセス可 通常の開発・本番
host ホストのネットワークをそのまま使用 高パフォーマンスが必要な場合（Linux限定）
none ネットワーク完全遮断 エージェントのセキュアサンドボックス
overlay 複数ホスト間のコンテナ通信（Swarm） 分散デプロイ
# ネットワーク操作コマンド docker network ls docker network create mynet docker network inspect mynet # コンテナをネットワークに接続 docker run --network mynet --name app1 myapp docker run --network mynet --name db1 postgres:16 # app1 から db1 へ: ホスト名 "db1" でアクセス可能

AI Agent Sandbox パターン OPENCLAW

自律型エージェント（Claude Code / OpenClaw）に危険なコード実行をさせる場合は、 必ずDockerコンテナで隔離します。

基本的なエージェント実行コンテナ

FROM python:3.12-slim # 最低限のツールのみインストール RUN apt-get update && apt-get install -y \ git curl jq \ && rm -rf /var/lib/apt/lists/* # セキュリティ: root以外のユーザーで実行 RUN useradd -m -u 1000 agent USER agent WORKDIR /workspace # エージェントが使うPythonパッケージ COPY requirements.txt . RUN pip install --user -r requirements.txt # エントリーポイント: エージェントコードを実行 CMD ["python", "agent_runner.py"]

Claude Code をサンドボックス実行する compose.yaml

services: claude-sandbox: build: context: . dockerfile: Dockerfile.agent volumes: - ./workspace:/workspace # 作業対象のコードをマウント - /var/run/docker.sock:/var/run/docker.sock # Docker-in-Docker不要の場合は外す environment: ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY} network_mode: "none" # ネットワーク完全遮断（外部通信禁止） mem_limit: 2g # メモリ上限 cpus: "1.0" # CPU上限 read_only: false # 作業用に書き込み許可 security_opt: - no-new-privileges:true # 権限昇格禁止 tmpfs: - /tmp:size=500m # tmpfsで一時ファイル管理
⚠️ セキュリティ注意 エージェントに --dangerously-skip-permissions を渡す場合は特に隔離が重要。 network_mode: none を設定してもAPIキーが漏れる可能性があるため、 最小権限原則を守り、実行後はコンテナを即削除する。

コンテナ内でのエージェント実行パターン

# パターン1: 使い捨てコンテナで1タスクだけ実行（推奨） docker run --rm \ --network none \ --memory 2g \ --cpus 1.0 \ -v $(pwd)/task:/workspace \ -e ANTHROPIC_API_KEY=$ANTHROPIC_API_KEY \ claude-agent:latest \ claude --print "README.md を読んで要約して" > output.txt # パターン2: 対話型開発（デバッグ用） docker run -it --rm \ --network bridge \ # 開発時はネットワーク許可 -v $(pwd):/workspace \ -e ANTHROPIC_API_KEY=$ANTHROPIC_API_KEY \ claude-agent:latest bash # パターン3: Compose で継続実行 docker compose run --rm agent claude "タスクを実行して"

本番運用のベストプラクティス

✅ イメージサイズを最小化する

  • -slim や -alpine ベースイメージを使う（ubuntu full は避ける）
  • Multi-stage build でビルドツールを本番イメージに含めない
  • .dockerignore で node_modules/・.git/・テストファイルを除外
  • RUN 命令を && で連結してレイヤー数を減らす

✅ セキュリティを固める

# rootユーザーで動かさない RUN useradd -m -u 1000 appuser USER appuser # イメージを定期的に更新してパッチを当てる FROM python:3.12.4-slim # タグはfloating(:latest)ではなく固定バージョンで # 機密情報をイメージに焼き込まない # ❌ 悪例: ENV API_KEY=sk-xxxx # ✅ 良例: docker run -e API_KEY=$API_KEY または --env-file .env

✅ ヘルスチェックを設定する

HEALTHCHECK --interval=30s --timeout=10s --retries=3 \ CMD curl -f http://localhost:8000/health || exit 1

✅ ログ設計

アプリはstdout/stderr にログを出力するだけでよい。 ファイルに書かない。Dockerが docker logs で収集し、 クラウドのロギングサービスが自動集約する。

Tip — Docker Desktop vs Rancher Desktop macOS / Windows では Docker Desktop（有償）か Rancher Desktop（無償・MIT）が2択。 企業利用なら Docker Desktop の有償ライセンスが必要。個人・OSS開発なら Rancher Desktop で十分。

OpenClaw との連携

なぜ自律型エージェント（OpenClaw）にDockerが必要なのか？ 理由は「安全性（Safety）」と「再現性（Reproducibility）」です。

  • Sandbox（砂場）: エージェントが暴走して rm -rf / を実行しても、消えるのはコンテナの中だけ。ホストPCは無傷。
  • Consistency: 「私のMacでは動いたのに、サーバーではエラー」という事故をDockerなら防げる。
  • Rollback: イメージをバージョン管理すれば、エージェントの動作環境をいつでも過去に戻せる。
  • Resource Control: CPUとメモリの上限を設定して、暴走タスクからホストを守る。

詳細な連携設計は OpenClaw アーキテクチャ を参照。
