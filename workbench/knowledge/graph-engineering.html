1. Graph Engineering とは何か？ — 進化の第5段階

LLMを実務システムや自律コンテンツ制作に組み込むエンジニアリング手法は、この数年で急速な進化を遂げてきました。 単にプロンプトを工夫する「Prompt Engineering」から始まり、コンテキストや検索を制御する「Context Engineering」、テスト・ガードレールで囲む「Harness Engineering」、そして試行錯誤を回す「Loop Engineering」へと発展しました。

しかし、大規模なマルチエージェント協働や、人間が途中で介入する業務プロセス、あるいは数万ファイルに及ぶプロジェクト全体の知識検索では、**「単一のループ」すら破綻**します。ここで登場したのが第5の体系**「Graph Engineering（グラフエンジニアリング）」**です。

Gen 1: Prompt Engineering
単一指示と文脈表現の最適化
Few-shot、Chain-of-Thought（CoT）、Role Prompting。入力文字列の工夫でLLMの出力を制御。
Gen 2: Context Engineering
外部知識注入とRAG
Vector DB、Semantic Search、Chunking、Memory Window。必要な文脈のみを動的に構築。
Gen 3: Harness Engineering
評価基盤と安全ガードレール
Eval Suite、Input/Output Sanitizer、サンドボックス実行、LLM-as-a-Judge による品質境界の固定。
Gen 4: Loop Engineering
自律試行錯誤と自己修復ループ
ReAct、Reflexion、Auto-debug、無制限ループの防止。失敗原因を自己観察して改善。
Gen 5: Graph Engineering (本体系)
状態遷移グラフ (State Graph) & 構造化ナレッジ (GraphRAG)
ノード（処理）とエッジ（条件分岐）による決定論的状態管理、サブグラフ並列化、Time Travel（過去状態への巻き戻し）、GraphRAGによる概念グラフ統合。

2. Graph Engineering の 2 大柱

Graph Engineering は大きく分けると**「A. 制御構造のグラフ化（State Graph）」**と**「B. 知識構造のグラフ化（GraphRAG）」**の2本の柱で構成されます。これらが融合することで、AIシステムは**高い信頼性**と**ディープな文脈理解**を両立します。

柱 A: State Graph Engineering（状態遷移型制御）

エージェントの全実行フローを、共有される「State（状態データ）」と、それを変更・判断する「Node（処理単位）」および「Edge（条件分岐）」からなる状態遷移機械（State Machine）としてモデル化します。

  • State（状態）: TypedDict や Pydantic で厳格に定義された共通変数空間。
  • Node（ノード）: LLMの呼び出し、ツール実行、外部API連携などを行う独立した関数。
  • Edge（エッジ）: 次のノードへ進む条件分岐ロジック（Router）。
  • Checkpoint（チェックポイント）: 状態の履歴をDBに永続化し、中断・人間介入・タイムトラベル（過去への復元）を可能にする。

柱 B: Knowledge Graph Engineering (GraphRAG)

単なるテキストのベクトル検索（通常のRAG）ではなく、テキストから「主体・述語・客体（Entity & Relationship）」を抽出してグラフデータベースを構築し、コミュニティ検出（Leiden法等）を用いて文脈全体を要約・検索します。

  • Entity & Relation Extraction: 高性能LLMで概念同士の関係性をグラフ化。
  • Community Summarization: グラフのクラスタごとに階層的なサマリーを自動生成。
  • Global / Local Query: 全体像の質問（Global）と特定の詳細質問（Local）の両方を高精度に回答。
  • HippoRAG / LightRAG: 連想記憶（Personalized PageRank）を用いた超高速知識探索。

3. 6大グラフエンジニアリング・デザインパターン

実務で頻出する、検証済みの「グラフ構造パターン」です。これらを組み合わせることで、直列のコードでは記述困難な高度なエージェントシステムを直感的に構築できます。

Pattern 1: Router & Dynamic Dispatcher（動的ルーティング型）

入力クエリの意図や分類結果に応じて、適切な専門ノード（またはサブグラフ）へ分岐する基本パターン。

State: { "query": str, "category": str, "result": dict }

START ➔ [Classify Node] ➔ Conditional Edge
          ├── category=="code"  ➔ [Coder Subgraph]
          ├── category=="art"   ➔ [Visual Subgraph]
          └── category=="other" ➔ [General Node] ➔ END

Pattern 2: Supervisor & Subgraph Orchestrator（監督＆サブグラフ型）

中央の Supervisor エージェントが全体の目標を把握し、タスクを割り振って各 Subgraph を並列または順次実行制御する構造。

START ➔ [Supervisor Node]
          ├──> [Research Subgraph] ──┐
          ├──> [Design Subgraph]   ──┼─> [Supervisor Merge]
          └──> [Audit Subgraph]    ──┘       │
                                             └─> Finish? ➔ END / Loop

Pattern 3: Parallel Fan-out / Fan-in (Map-Reduce)（並列拡張・集約型）

1つの巨大なタスクを多数の独立したサブタスクへ分割（Map/Fan-out）し、複数のノードで並列処理したのち、1つの集約ノード（Reduce/Fan-in）で統合するパターン。

[Split Tasks Node] ➔ Send() (Parallel Fan-out)
  ├── Workers[0] (e.g. Chapter 1 Generation)
  ├── Workers[1] (e.g. Chapter 2 Generation)
  └── Workers[2] (e.g. Chapter 3 Generation)
  ➔ [Reduce Node] (Combine & Deduplicate) ➔ END

Pattern 4: Evaluator-Optimizer Stateful Loop（評価・自己修復グラフ）

生成（Generate）と評価（Evaluate）の間に条件エッジを配置し、合格基準に達するまで「状態（State）」にフィードバックを溜めながら反復修正する構造。

[Generator Node] ➔ [Evaluator Node] ➔ Conditional Edge
  ├── Score >= 90 ➔ [Finalize Node] ➔ END
  └── Score < 90  ➔ [Append Critique to State] ➔ [Generator Node]

Pattern 5: Human-in-the-Loop Interruption（人間介入・状態待機型）

高リスクなアクション（資金移動・本番デプロイ・SNS投稿）の手前に `interrupt()` を配置。グラフの状態をチェックポイントDBに保存して一時停止し、人間の承認後に再開するパターン。

[Draft Plan Node] ➔ [Checkpoint Persistence] ➔ [INTERRUPT (Human Approval)]
  ├── Approved ➔ [Execute Production Node] ➔ END
  └── Rejected ➔ [Revise Plan Node] ➔ [Draft Plan Node]

Pattern 6: GraphRAG + Vector Hybrid Pattern（ハイブリッドナレッジ検索）

構造化グラフ（Entity-Relation Graph）による全体俯瞰検索と、従来のベクトル検索（Dense Vector）による局所詳細検索を並行して行い、Rerankerで統合するナレッジパターン。

Query ➔ Parallel Branch:
  ├── [GraphRAG Global Search] (Community Summary) ──┐
  └── [Vector Local Search]    (Chunk Similarity)   ──┼─> [Reranker] ➔ Context ➔ LLM

事例 1: クエイター・制作系
Ex 01 全自動マルチモーダル漫画・アニメ制作パイプライン（State Graph + Map-Reduce） 制作自動化

ストーリーの脚本から、コマ割りネームの生成、画像生成AIによるコマ画像生成、キャラクター整合性の検品、動画化（V2V/I2V）までを単一の「状態遷移グラフ」として管理。画像生成に失敗したコマだけを個別ノードで修正ループさせ、全コマが揃った段階で Fan-in して動画化します。

from typing import TypedDict, List, Annotated
import operator

class MangaProductionState(TypedDict):
    title: str
    script_pages: List[str]
    panel_prompts: List[dict]
    generated_panels: Annotated[List[dict], operator.add] # Reducerで並列追加
    audit_verdicts: dict
    approved_for_render: bool

# ノードと条件エッジの配置
# Node 1: Script Splitter
# Node 2: Parallel Fan-out -> Panel Image Generator (Send API)
# Node 3: Character Consistency Auditor (Evaluator)
# Interrupt Node: Human Director Approval (チェックポイント保存)
# Node 4: Final Video Composite
成果: 1エピソード制作時間が 14時間 ➔ 45分に短縮。壊れたコマだけのピンポイント自動リトライ率 100%
事例 2: エンジニアリング・リファクタリング系
Ex 02 大規模コードベース依存グラフ修正 & セキュリティ監査エージェント コードベース修復

10万行を超えるコードベースで依存関係を Graph（Call Graph / AST Graph）として抽出し、共通ライブラリの非推奨API置き換えを影響範囲の葉ノード（Leaves）から根ノード（Root）へと順番に伝播修復。修正ごとに自動テストノードを実行し、失敗時は該当ノードの直前状態へタイムトラベル復元します。

5. Graph Engineering 5大アンチパターンと回避策

状態グラフやナレッジグラフを設計する際に陥りがちな失敗パターンと、その解決策です。

Anti-Pattern 1: Infinite Cycle Sink（デッドロック無限循環グラフ）

Evaluator ノードの合格基準が厳しすぎる、または修正ノードが同じ出力を繰り返すことで、グラフが特定の循環（Node A ⇄ Node B）から永遠に抜け出せなくなる現象。

✅ 解決策: State に `recursion_count` または `step_history` を保持し、特定閾値（例: 5回）を超えたら強制的に `human_escalation_node` や `fallback_node` へ誘導する条件エッジを必須化する。

Anti-Pattern 2: Monolithic State Bloat（モノリシック状態肥大化）

すべてのノードの出力や中間データ、全巨大テキストを単一の `State` オブジェクトに詰め込み、毎ステップのコンテキストやトークン消費量が指数関数的に増大する設計。

✅ 解決策: サブグラフごとに独立した `SubState` を定義するか、State には参照ID（Key/URL）のみを持たせ、重い実データは外部キャッシュやストアに置く。

Anti-Pattern 3: Orphan Node & Unreachable State（孤立ノードと到達不能状態）

条件エッジの判定ロジック（Router）に想定外の返り値が含まれており、どのエッジにもマッチせずエラー終了、またはどのパスからも呼び出されない孤立ノードが存在する設計。

✅ 解決策: グラフコンパイル時（`.compile()`）に全ノードの到達可能性を検証する静的アナライザーを導入し、条件エッジには必ず `else` や `DEFAULT` パスを設定する。

Anti-Pattern 4: Over-Graphing Simple Logic（単純処理の過剰グラフ化）

直列の `for` ループや関数呼び出し1回で済む単純な処理まで、無理やり5つのノードと条件エッジでグラフ化し、オーバーヘッドとデバッグ複雑性を増大させる設計。

✅ 解決策: 「条件分岐が存在するか」「状態の保存/人間介入が必要か」「並列実行があるか」のいずれも満たさない単一線形処理は、通常の1つの Node 内部にカプセル化する。

Anti-Pattern 5: Non-deterministic Edge Condition（非決定論的エッジ条件）

エッジの分岐条件（次に行くノードの選択）をLLMの自由形式テキスト出力に頼り、表記ゆれ（例: `"yes"` / `"Yes."` / `"APPROVED"`）で分岐に失敗する現象。

✅ 解決策: 条件分岐ノードでは Structured Output（Pydantic / Enum / JSON Schema）を強制するか、決定論的なPythonコード（`if score > 0.8:`）で判定する。

6. 実践コード: Python + LangGraph 決定版実装例

以下は、実際に動作する State Graph の完全なコード構造です。状態の定義、ノード関数、条件分岐、チェックポイント永続化、人間介入（Interrupt）のすべてが含まれています。

from typing import TypedDict, Literal, Annotated
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver

# 1. 厳格な State（状態）の定義
class SystemState(TypedDict):
    user_goal: str
    code_draft: str
    review_score: float
    feedback: str
    attempt_count: int
    is_approved: bool

# 2. ノード関数の実装 (Nodes)
def generator_node(state: SystemState) -> dict:
    print(f"--- GENERATOR (Attempt {state.get('attempt_count', 0) + 1}) ---")
    current_attempts = state.get("attempt_count", 0) + 1
    # LLM生成ロジックのシミュレーション
    code = f"# Code generated for: {state['user_goal']}\ndef solution(): return True"
    return {"code_draft": code, "attempt_count": current_attempts}

def evaluator_node(state: SystemState) -> dict:
    print("--- EVALUATOR ---")
    # 評価ロジック（スコアとフィードバック）
    score = 0.95 if state["attempt_count"] > 1 else 0.60
    feedback = "Good quality." if score >= 0.8 else "Needs error handling."
    return {"review_score": score, "feedback": feedback}

def human_approval_node(state: SystemState) -> dict:
    print("--- HUMAN APPROVAL GATE ---")
    # 人間介入ステップ（承認フラグの設定）
    return {"is_approved": True}

# 3. 条件付きエッジの判定関数 (Conditional Router)
def route_evaluation(state: SystemState) -> Literal["human_approval_node", "generator_node", "fallback_node"]:
    if state["review_score"] >= 0.8:
        return "human_approval_node" # 合格 ➔ 人間承認へ
    elif state["attempt_count"] >= 3:
        return "fallback_node"       # 3回失敗 ➔ エスカレーション
    else:
        return "generator_node"      # 不合格 ➔ リトライ

def fallback_node(state: SystemState) -> dict:
    print("--- FALLBACK (MAX ATTEMPTS EXCEEDED) ---")
    return {"feedback": "Escalated to human engineer."}

# 4. グラフの構築とコンパイル
builder = StateGraph(SystemState)

# ノードの追加
builder.add_node("generator_node", generator_node)
builder.add_node("evaluator_node", evaluator_node)
builder.add_node("human_approval_node", human_approval_node)
builder.add_node("fallback_node", fallback_node)

# エッジの接続
builder.add_edge(START, "generator_node")
builder.add_edge("generator_node", "evaluator_node")

# 条件付きエッジ
builder.add_conditional_edges(
    "evaluator_node",
    route_evaluation,
    {
        "human_approval_node": "human_approval_node",
        "generator_node": "generator_node",
        "fallback_node": "fallback_node"
    }
)

builder.add_edge("human_approval_node", END)
builder.add_edge("fallback_node", END)

# チェックポインタの設定（状態の永続化と割り込み用）
memory_checkpointer = MemorySaver()
graph = builder.compile(
    checkpointer=memory_checkpointer,
    interrupt_before=["human_approval_node"] # 承認ノードの手前で自動一時停止
)

print("✅ State Graph Compiled Successfully!")

7. チェックリスト & 重要文献 (Papers & References)

📋 グラフ設計・運用前チェックリスト

  • State Schema: `State` の型定義と `Reducer`（リストの結合等の動作）は明確に宣言されているか？
  • Recursion Limit: 無限ループ防止用の最大ループカウンターと条件分岐エッジが備わっているか？
  • State Isolation: サブグラフ間で不要な状態変数が漏れ出さず、分離されているか？
  • Checkpointer: 本番運用環境で状態をDBに永続化し、エラー復旧や中断再開ができるか？
  • Human-in-the-loop: 不可逆なアクションの手前に明示的な Interrupt パスを配置しているか？
  • GraphRAG Alignment: 全体俯瞰（Global）と局所詳細（Local）のクエリ振分けロジックが決定論的か？
