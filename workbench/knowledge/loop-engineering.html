ループエンジニアリングとは何か

「You don't prompt a coding agent once. You design loops that run autonomously. A loop with nothing to push back is the agent just agreeing with itself.」
── Loop Engineering の核心原則（Boris Cherny / Anthropic, 2026）

プロンプトエンジニアリングが「1 回の指示をどう書くか」、コンテキストエンジニアリングが「何を見せるか」だとすれば、ループエンジニアリングは 「エージェントがどう反復するか」 を設計します。

4 つの規律の進化を振り返ると：

規律問い確立時期設計対象
Prompt Engineeringどう頼むか2020〜1 回の指示文
Context Engineering何を見せるか2025年6月〜コンテキストウィンドウの中身
Harness Engineeringどう組むか2026年2月〜ツール・メモリ・検証の環境
Loop Engineeringどう回すか2026年6月〜自律反復サイクル全体

「ループ設計のないエージェントは、タスクを受け取り、1 回実行し、終わる ── つまり自動化スクリプトと変わらない。本当の意味でのエージェントは、フィードバックを受け取り、自分で判断し、次の行動を決める」という思想が基盤にあります。

「Reflect → Plan へのフィードバック」がループを閉じます。フィードバックゲートがないループはエージェントが自己承認を繰り返すだけです。終了条件（done-condition）の設計も同様に重要です。

軍事・認知科学から来た OODA ループとの対応

OODA（John Boyd, 1970s）Agent Loop（2022〜）役割
Observe（観測）Observe（ツール出力・環境状態）現実を知覚する
Orient（方向付け）Reflect（評価・判断）状況を解釈する
Decide（決定）Plan（次アクション決定）行動を選択する
Act（行動）Act（ツール実行）環境に影響を与える

AI エージェントループは OODA の直接の派生ではなく並行発展ですが、構造的に一致しています。

学術的系譜 ── 論文で辿るループの進化

ReAct: Synergizing Reasoning and Acting in Language Models
Yao et al. (Princeton / Google Research), arXiv 2022年10月
LLM に「思考（Reason）+ 行動（Act）を交互に実行させる」設計を提案。Thought → Action → Observation のサイクルが現在のエージェントループの原型。HotpotQA・ALFWorld で従来手法を上回る精度を実現。
Reflexion: Language Agents with Verbal Reinforcement Learning
Shinn et al. (Northeastern / MIT), arXiv 2023年3月
「言語フィードバックによる自己改善」を実現。タスク失敗後に自然言語で反省文を生成し、次のループに注入することで精度を向上。HumanEval でパス率 91% 達成（GPT-4 ベース）。
Self-Refine: Iterative Refinement with Self-Feedback
Madaan et al. (CMU / Yann LeCun Group), arXiv 2023年3月
同一モデルが生成・評価・改善を繰り返す「自己改善ループ」。追加学習なしに品質向上が可能なことを示す。数学・コード・要約など 7 タスクで平均 +20% の品質向上。
Tree of Thoughts: Deliberate Problem Solving with LLMs
Yao et al. (Princeton), arXiv 2023年5月
Chain-of-Thought を「木」に拡張。複数の思考経路を並列探索し、バックトラックを可能にする。ループの分岐・探索概念の先駆け。Game of 24 で GPT-4 を 4% → 74% に向上。
AgentBench: Evaluating LLMs as Agents
Liu et al. (THU / UC Berkeley), arXiv 2023年8月
エージェントとしての LLM を 8 環境で評価する統一ベンチマーク。ループ実行能力（長期整合性・自己修正・探索）の差がモデル選択で重要になることを示す。
SWE-bench: Can LMs Resolve Real-World GitHub Issues?
Jimenez et al. (Princeton), arXiv 2023年10月〜（継続更新）
実際の GitHub Issue 解決を評価するベンチマーク。エージェントがコード読解 → 修正 → テスト実行のループを何度回せるかが性能に直結。GLM-5.2 が OW 首位（62.1%）を取得。

ループ設計の 5 パターン

エージェントループには用途に応じた複数の設計パターンがあります。

① 単純反復ループ（Until-Condition）

「条件を満たすまで繰り返す」最もシンプルな形。終了条件の設計が全て。

# Claude Code パターン
until [ "$(npm test)" = "PASS" ]; do
  # Claude が自律的に修正を試みる
  sleep 2
done

適用: バッチ処理・フォーマット変換・単純な修正タスク

② TDD ループ（テスト駆動エージェント）

テストを先に書き、テストが通るまで実装を繰り返す。品質担保と終了条件が一体化した優れた設計。

# 1. テストを書く（人間 or エージェント）
# 2. 実装する（エージェント）
# 3. テスト実行（ハーネス）
# 4. 失敗 → Reflect → 再実装
# 5. 全テスト GREEN → 完了

適用: 機能実装・バグ修正・リファクタリング

③ 評価ループ（Eval Loop / LLM-as-judge）

生成 → 評価 → 改善を繰り返す。評価者と生成者が同一モデルでも分離したモデルでも機能。

for i in range(max_rounds):
    output = generator.generate(task)
    score, feedback = judge.evaluate(output)
    if score >= threshold:
        break
    task = enrich_with_feedback(task, feedback)

適用: コンテンツ品質向上・翻訳精度向上・レポート生成

④ 並列ループ（Parallel Agent Swarm）

複数のエージェントが独立した作業を並列実行。オーケストレーターが結果を統合。

# オーケストレーター
tasks = decompose(goal)
results = await asyncio.gather(*[
    agent.run(task) for task in tasks
])
final = synthesize(results)

適用: 大規模コンテンツ生成・マルチリサーチ・コードベース全体修正

⑤ 階層ループ（Orchestrator-Worker）

高レベル計画エージェント（オーケストレーター）が低レベル実行エージェント（ワーカー）を管理する 2 層構造。

class Orchestrator:
    def run(self, goal):
        plan = self.plan(goal)
        for step in plan:
            worker = Worker(step.type)
            result = worker.execute(step)
            self.update_state(result)
            if self.goal_met(): break

適用: 複雑な長期タスク・Kanban エージェント・マルチモーダルパイプライン

// heartbeat.ts — 定期実行エージェント
async function heartbeat() {
  const pendingNotes = await vault.search("status: draft");
  for (const note of pendingNotes) {
    const enriched = await claude.enrich(note.content);
    await vault.update(note.path, enriched);
  }
}

// 毎朝 6:00 に実行
cron.schedule("0 6 * * *", heartbeat);

08 エンジニア Reflexion 実装 ── 言語フィードバックによる自己改善ループ

Reflexion パターンの最小実装：

def reflexion_loop(task, max_trials=5):
    memory = []  # エピソード記憶
    for trial in range(max_trials):
        # 過去の反省を注入してから実行
        context = "\n".join(memory) if memory else ""
        result = agent.run(task, context=context)

        # 外部評価（テスト / LLM-judge）
        success, feedback = evaluate(result, task)
        if success:
            return result

        # 失敗した場合、自然言語で反省文を生成
        reflection = llm.reflect(
            f"タスク: {task}\n試行結果: {result}\n失敗理由: {feedback}"
        )
        memory.append(reflection)  # 次のループに引き継ぐ

    return None  # max_trials 超過

記憶（memory）への反省文の蓄積がループを賢くします。trial を重ねるごとに「何をすべきでないか」の知識が増えます。

信頼できるループを作る 7 つのフィードバックゲート

「フィードバックのないループはエージェントが自分に同意しているだけ」── ゲートがループを機能させます。

① テストスイート（最強）

ユニットテスト・統合テストが通るかどうか。バイナリ（合格/不合格）でエージェントの主観を排除。TDD ループの要。

② 型チェッカー

TypeScript の tsc・Python の mypy など。エラーゼロを終了条件にすると収束が安定。

③ Linter / Formatter

ESLint・Prettier・Ruff など。コードスタイルの客観的評価。低コストで即座にフィードバックが得られる。

④ LLM-as-judge

別の LLM（または同一モデル）が出力を評価するゲート。主観的品質（文章の自然さ・論理性）の自動評価に有効。スコアに閾値を設定。

⑤ ビジュアル差分

スクリーンショット比較・ピクセル差分。UI 実装・デザイン生成ループで人間の目を代替。Percy / Chromatic などで自動化可能。

⑥ 人間レビューゲート

特定ステップで人間の承認を必須にする。コスト・安全性に関わる操作や「確信が持てない場合」に配置。Claude Code の permission system が実装例。

⑦ 上限カウンター（Safety）

最大反復回数・最大トークン使用量・最大実行時間のハードリミット。すべてのループに必須。無限ループ防止の最後の砦。

アンチパターン 5 選

① 無限ループ（Infinite Loop）

終了条件が未定義、または達成不可能な条件を設定してしまう。最も危険なアンチパターン。APIコスト・時間が無限に消費される。

✅ Fix: max_iterations・max_tokens・timeout を必ず設定。loop 開始前にログで可視化。

② 自己承認ループ（Echo Chamber Loop）

エージェントが自分で生成し、自分で評価し、自分で合格とする。外部フィードバックゲートがないため、品質が改善されない。

✅ Fix: 評価は必ず外部（テスト・別モデル・人間）が行う。自己評価のみに頼らない。

③ コンテキスト肥大化（Context Bloat in Loop）

ループを重ねるたびに会話履歴・ツール出力が蓄積し、コンテキストウィンドウを圧迫。後半のループで初期の判断を「忘れる」。

✅ Fix: N ループごとに状態を要約圧縮。重要な状態のみ Task State（層⑦）として明示的に管理。

④ 過剰ループ（Over-Engineering the Loop）

1 回で十分なタスクに複雑なループを設計する。オーバーヘッドが大きく、シンプルな実装より遅く高コスト。

✅ Fix: まず単純実装で試す。反復が本当に必要かを検証してからループを導入。

⑤ フィードバックラグ（Slow Feedback Gate）

フィードバックゲートの実行に時間がかかりすぎてループが遅い。E2E テスト全件実行をすべてのループで行う等。

✅ Fix: 高速ゲート（型チェック・単体テスト）を先に配置。遅いゲート（E2E）は最終ループのみに。
