週次ルーティン

Hub ヘルスチェック

毎週実施。全カテゴリの鮮度を確認し、ALERT/WARN ページを特定して次のアクションを作る。所要時間: 約 15〜20 分。

最終更新: 2026-05-30 | 実施頻度: 週1回（週末目安）

鮮度しきい値（カテゴリ別）

🔴 ALERT（45日超）

  • 全カテゴリ共通の警戒ライン
  • 発見次第 next-actions に追記
  • creator-system は 30 日でも要確認

🟡 WARN（30日超）

  • workbench・research は 30 日で WARN
  • 優先度に応じて次スプリントで対応

🟢 OK（30日以内）

  • 対応不要。記録のみ
  • foundations / logs は 14 日を目安に

実施手順

1

git 状態の確認

git fetch origin git status git log --oneline -10 # 直近コミット確認 git branch -r # 並走セッションのブランチ確認

未プッシュのコミットや他セッションのブランチがあれば先にマージ方針を判断する。

2

カテゴリ別ファイル鮮度の計算

Claude に以下を実行させる（Bash ツール）:

for dir in creator-system claw-stack workbench research foundations strategy logs; do count=$(find ./$dir -name "*.html" | wc -l) # 最終更新日時の平均を計算 avg_days=$(find ./$dir -name "*.html" -exec stat -c %Y {} \; | \ awk -v now=$(date +%s) '{sum += (now-$1)/86400} END {print int(sum/NR)}') echo "$dir: $count pages, avg ${avg_days}d old" done
3

ALERT ページの特定

45 日以上更新されていないページを列挙する:

find . -name "*.html" -mtime +45 | sort | \ grep -v ".git" | grep -v "node_modules"

リストを確認し、各ページが「意図的に放置（アーカイブ）」か「要更新」かを判断する。

4

hub-health.html の更新

計算した数値（総ページ数・平均鮮度・カテゴリ別ステータス）を logs/hub-health.html に反映する。ALERT/WARN の欄は必ず最新状態に保つ。

5

next-actions.html へのフィードバック

ALERT ページを logs/next-actions.html の「緊急」セクションに追記する。既に記載済みのものは優先度を確認して更新する。

6

コミット

git add logs/hub-health.html logs/next-actions.html git commit -m "Weekly hub health check — $(date +%Y-%m-%d) Categories: [OK/WARN/ALERT の概要] Alerts: [ALERT ページ名があれば]" git push

ALERT ページの対応判断フロー

状況対応
内容が現在も正確（技術情報が変わっていない）「最終確認: YYYY-MM-DD」を追記して日付を更新。実質 no-op コミット。
情報が古い（API 仕様・モデル名が変わった）次の Claude セッションで更新タスクとして実施。next-actions に追記。
アーカイブ済み（demos/ の過去資料など）ページ先頭に ARCHIVE バッジを追加して age 計算対象から除外。
削除対象（リンク切れ・重複内容）ADR に記録してから削除。ADR-005 のパターン（表示ラベルのみ変更）も検討。
原則: 削除より退避を優先。情報の鮮度より「次のインスタンスが理解できる状態」を目標とする（operating-principles.html #6）。
