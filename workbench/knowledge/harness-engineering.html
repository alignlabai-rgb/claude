ハーネスエンジニアリングとは何か

「The harness is everything that wraps an LLM except the model itself — tool execution, memory, state management, error handling, retry logic, validation gates. Most agent failures aren't model failures: they're harness failures.」
── Mitchell Hashimoto（HashiCorp / Terraform 創業者）、2026年2月

プロンプトエンジニアリングが「指示の書き方」、コンテキストエンジニアリングが「何を見せるか」であれば、ハーネスエンジニアリングは モデルの外側にある環境全体の設計 です。

最も重要な発見：

  • 「モデルを変えるより、ハーネスを改善する方が効果が大きいことがある」 ── 同じモデルでも、ハーネス設計次第で成果が劇的に変わる
  • エージェントの失敗の大半は「モデルが賢くない」ではなく「ツールが壊れた」「エラー処理がない」「状態管理が不適切」といったハーネスの問題
  • 本番環境でのエージェント信頼性は、モデルの能力よりもハーネスの堅牢性に依存する

ハーネスの 5 レイヤー構造

本番エージェントのハーネスは以下の 5 レイヤーから構成されます。

①
Tool Layer（ツール層）
エージェントが実際に使えるツールの定義・実行・サンドボックス化。ツールの I/O スキーマ、権限管理、タイムアウト、実行環境の分離が含まれる。
実装例: MCP ツール定義・OpenClaw defineToolPlugin・LangChain Tool・function calling スキーマ
②
Memory Layer（メモリ層）
短期記憶（セッション内）・長期記憶（クロスセッション）・エピソード記憶・セマンティック記憶の管理。ベクトルDB・KV ストア・グラフDB を組み合わせる。
実装例: Mem0・Letta・Zep・Pinecone・ClawMem・pgvector・Cloudflare KV
③
State Layer（状態層）
タスク進捗・チェックポイント・セッション継続性・エラーリカバリーの管理。エージェントが中断後に再開できるかどうかを決める。
実装例: Redis・SQLite チェックポイント・Claude Code の project 継続機能・OpenClaw Workboard
④
Validation Layer（検証層）
型チェック・テスト実行・LLM-as-judge・人間レビューゲート。エージェント出力の品質を保証する。ループエンジニアリングのフィードバックゲートと直結。
実装例: Zod/Pydantic バリデーション・pytest/Jest・RAGAS・Claude Code permissions
⑤
Orchestration Layer（オーケストレーション層）
複数エージェントの協調・並列/直列実行の制御・フォールバック・リトライロジック・コスト管理。マルチエージェントシステムの司令塔。
実装例: LangGraph・CrewAI・AutoGen・Hermes Kanban・OpenClaw マルチエージェント

01 クリエイター Claude Code の CLAUDE.md ── ハーネス設定ファイルとしての実装

Claude Code において CLAUDE.md はハーネスの設定ファイルとして機能します（System Instructions であると同時に、ハーネス動作を制御する）：

# CLAUDE.md の役割マッピング
[ツール層①]  → 使ってよいツール・禁止ツールの宣言
[メモリ層②]  → プロジェクト固有知識の永続化
[状態層③]   → 作業継続のための前提情報
[検証層④]   → Editing Policy・Definition of Done
[調整層⑤]   → 並走セッションのプロトコル

「新しい Claude インスタンスがこのファイルを読むだけで正しく動く」── これがハーネス設計の完成形です。

07 エンジニア MCP（Model Context Protocol）── ツール定義の業界標準化

Anthropic が主導する MCP はハーネスのツール層（①）を標準化するプロトコルです：

// MCP ツール定義（JSON Schema）
{
  "name": "search_web",
  "description": "Web を検索して結果を返す",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "検索クエリ" },
      "num_results": { "type": "integer", "default": 5 }
    },
    "required": ["query"]
  }
}

// → Claude・Gemini・OpenAI など複数モデルで同じ定義を再利用

MCP により「ツール定義は一度書けばどのモデルでも使える」が実現。ハーネスのポータビリティが飛躍的に向上。150+ のサービスが MCP サーバーを実装済み。

詳細: a2a-protocol.html 参照
08 エンジニア Claude Code Hooks ── ハーネスの検証層・自動化をコードで制御

Claude Code の hooks システムはハーネスの検証層（④）とオーケストレーション層（⑤）をコードで定義します：

// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "bash /path/to/security-check.sh"
        // 危険なコマンドを自動ブロック
      }]
    }],
    "PostToolUse": [{
      "matcher": "Write",
      "hooks": [{
        "type": "command",
        "command": "npx prettier --write $TOOL_OUTPUT_FILE"
        // ファイル書き込み後に自動フォーマット
      }]
    }],
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "git add -A && git commit -m 'auto checkpoint'"
        // 停止時に自動コミット
      }]
    }]
  }
}

「何かをするたびに自動的に別のアクションを実行する」── これがハーネスの検証・自動化層の実装です。

09 エンジニア CrewAI ── 役割ベースマルチエージェントのオーケストレーション実装

CrewAI のオーケストレーション層（⑤）の実装パターン：

from crewai import Agent, Task, Crew

# エージェント定義（役割・ゴール・バックストーリー）
researcher = Agent(
    role="AI リサーチャー",
    goal="最新の AI トレンドを調査する",
    backstory="5年の AI 研究経験を持つ専門家",
    tools=[web_search, arxiv_search]
)
writer = Agent(
    role="テックライター",
    goal="研究結果を読みやすい記事にする",
    tools=[draft_tool, edit_tool]
)

# タスク定義（依存関係を明示）
research_task = Task(description="AI の最新動向を調査", agent=researcher)
write_task    = Task(description="記事を執筆", agent=writer,
                     context=[research_task])  # ← 依存関係

# 実行
crew = Crew(agents=[researcher, writer], tasks=[research_task, write_task])
result = crew.kickoff()

11 エンジニア DSPy ── プロンプトをハーネスがパラメータとして最適化する逆転発想

Stanford の DSPy（Declarative Self-improving Python）は「プロンプトをハーネスが自動設計する」逆転の発想：

  • 従来: 人間がプロンプトを手動設計 → ハーネスが実行
  • DSPy: 人間が評価指標を定義 → ハーネスがプロンプトを自動最適化
  • 実装: 評価ループ（生成→評価→Few-shot 選択→再生成）をハーネスが自律実行
  • 効果: 手動プロンプトエンジニアリングと同等以上の精度を自動達成

「ハーネスがプロンプトエンジニアリングを代替する」── 4 つの規律が互いに影響し合う象徴的な例。

12 エンジニア A2A Protocol ── エージェント間通信を標準化するハーネス間インターフェース

Google 主導の A2A（Agent-to-Agent）Protocol は、異なるハーネスで動くエージェントが通信する標準を提供：

// A2A タスク送信（Agent A → Agent B）
const task = {
  "id": "task-001",
  "message": {
    "role": "user",
    "parts": [{ "type": "text", "text": "競合分析レポートを作成してください" }]
  }
};

// Agent B（異なるハーネス・異なるモデル）が受け取って実行
// 結果を Agent A に返送
const result = await agentB.sendTask(task);

LangChain 製エージェントと CrewAI 製エージェント、OpenClaw 製エージェントが同じプロトコルで通信できます。150 社が採用（2026年6月）。

詳細: a2a-protocol.html

本番ハーネス設計チェックリスト 20 項目

① ツール層

  • 全ツールに入出力スキーマを定義している
  • ツールのタイムアウトを設定している
  • ツール実行を分離された環境（サンドボックス）で行っている
  • 危険操作（削除・外部送信）に確認ゲートがある

② メモリ層

  • 重要な状態が永続化されている（セッション跨ぎ対応）
  • ベクトルDB のインデックスが最新に保たれている
  • 記憶の更新・削除ポリシーが定義されている
  • 個人情報・機密情報の除外ルールがある

③ 状態層

  • タスク進捗がチェックポイントに保存されている
  • 中断からの再開が可能（冪等性がある）
  • エラー発生時のロールバック手順がある

④ 検証層

  • 出力の型バリデーションがある
  • 最低 1 つの外部評価ゲートがある
  • 人間レビューが必要なステップが明確
  • コスト上限アラートが設定されている

⑤ オーケストレーション層

  • 最大反復回数・実行時間の上限がある
  • エージェント失敗時のフォールバックがある
  • 並列実行の競合（race condition）対策がある
  • コスト・トークン使用量をログ記録している

アンチパターン 5 選

① ハーネスなし直接呼び出し（Bare API）

LLM API を直接呼ぶだけで、ツール・メモリ・検証を実装しない。プロトタイプには可だが、本番運用では失敗が積み重なる。

✅ Fix: 最低限ツール層と検証層（型バリデーション + エラー処理）を実装してから本番投入。

② 過剰な抽象化（Framework Over-Engineering）

LangChain の全機能を使おうとして、シンプルなユースケースに過剰な複雑さを持ち込む。デバッグが困難になり、チームの学習コストが爆発する。

✅ Fix: まず必要な 2-3 レイヤーだけを実装。フレームワークは必要になってから選定。

③ 状態の漏洩（State Leakage）

複数のエージェントが同じ状態を無制御に読み書きし、互いの作業が干渉する。並列エージェントのアンチパターン。

✅ Fix: エージェントごとに名前空間分離された状態ストアを持たせる。書き込みには必ずロックを。

④ 検証レイヤー欠如（Validation Gap）

エージェントの出力をそのまま使い、型チェック・サニタイズ・評価ゲートがない。本番でデータ破損・セキュリティ問題が発生。

✅ Fix: すべてのツール出力・エージェント出力を Zod/Pydantic でバリデート。

⑤ モデル依存設計（Vendor Lock-in Harness）

特定モデルの固有機能に依存したツール定義をして、モデル交換ができない状態になる。モデルの API 変更で全体が壊れる。

✅ Fix: MCP / 共通インターフェースでツールを定義。モデル固有機能はアダプタ層で吸収。
