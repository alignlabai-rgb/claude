Control UI と運用観測：画面の状態を、完成の証拠へつなぐ

最終更新・公式情報確認：2026-10-13。確認日は発表日ではありません。本文の教材・評価案は筆者の提案であり、実行済み成果や導入保証ではありません。

このページの URL は旧記事から保持するが、Mission Control という名前だけで特定の公式製品や標準の mission 設定形式があるとは扱わない。ここでは公式の Control UI と状態確認を中心に、「運用者が依頼と結果を見渡す」機能を説明する。存在を確認していない dashboard API や mission.yaml は作らない。

Control UI は Gateway の画面

公式文書は、Control UI を Gateway が配信する単一ページのアプリで、同じ Gateway の WebSocket と通信すると説明する。OpenClaw Control UI 画面が開くことは接続確認の一つだが、全てのチャネルやツールが正しく動くことの証明ではない。表示している Gateway とプロファイルを意識し、別の状態を見ていないか確かめる。

筆者の観測案は、画面で確認する項目を「入口」「進行」「提出物」「配送」「未確認」に絞る。大量の緑のバッジを並べるより、最後の一件がどの段階まで進んだか読める方が有益である。ユーザーが見ていない画面の常時集計を成果の目的にしない。

受け付け済みは完成ではない

公式 architecture では、runId を伴う受け付けと、後に返る実行結果が分かれている。OpenClaw Gateway architecture ステータスが accepted と表示されても、下書きが保存されたとは限らない。会話の「了解」「調べます」といった途中の返答と、結果の提出を区別する。

教材例として、公開告知の差分表を一件頼んだ場合、完了には比較表、根拠へのリンク、未確認事項が必要になる。接続の緑色表示だけで採点しない。結果が空なら未完了、根拠が矛盾していれば保留、通知が不明なら配送不明、と明示する。

切断時は再送の前に観察する

公式 UI の説明は、再接続時に一部の保存表示を利用する一方、キャッシュされた表示が変更の権限を与えるわけではないと注意する。OpenClaw Control UI 古い表示が残っていても、現在の状態を確定したことにはならない。接続表示と実行 ID を確認し、同じ操作を新規に開始する前に元の結果を見る。

再接続で戻った画面を「最初から処理し直した」と解釈しない。仕事は画面の寿命と別の寿命を持つことがある。重複送信や再作成が心配な課題なら、作業の ID と通知の確認を保存し、後から照合できるようにする。

定期ジョブを観測する

現在の公式名は Automations。openclaw cron は同じコマンド群の alias と説明される。OpenClaw Automations このページでは新しいジョブを作成しない。運用者が設定を見る際は、予定があること、実行されたこと、結果があること、届けたことを別々に確認する。

一覧には数十行のニュースではなく、対象、前回結果、次回条件、停止条件を置く案がよい。変更がないときに静かに終わる監視と、毎回記事を生成する定期化は別である。通知が必要な差分だけ人へ返すと、画面の量ではなく判断の負担を減らせる。

観測そのものが公開境界を持つ

画面には会話、接続名、モデル、認証に関連する情報が出ることがある。スクリーンショットを共有する前に、誰が何を見られるか確認する。秘密を伏せたつもりでも、端末名や内部の案件名が残る可能性がある。公開教材は合成した依頼で作り、実際の運用画面を安易に証拠として転用しない。

長期に残す観測は、完成物への参照と失敗条件に限定する。全会話を dashboard のデータへ複製すると、新しい保存と削除の問題が生まれる。元の証拠へ戻るための最小の ID と状態を使う。

異常を見つけた後

画面が白い、結果が来ない、サービスが止まる、チャネルの配送が失敗する、といった症状は公式 runbook でも分かれている。OpenClaw Troubleshooting UI の不具合をモデル選定の問題へすり替えたり、配送の不具合をプロンプトで直そうとしない。次の検査で何を否定できるかを決め、変更前の状態を残す。

運用観測の価値は、仕事を増やすことより、進んでいない仕事を完成扱いにしないことにある。見える範囲と分からない範囲を並べ、完成の証拠に戻れる画面を目指す。
