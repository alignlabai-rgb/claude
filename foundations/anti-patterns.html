アンチパターン集

Claude / Codex 等のエージェントにこのハブの更新を任せた時に失敗した例と、救った例を蓄積する場所です。同じ失敗を繰り返さないための知識資産として運用します。

編集方針: 抽象的な「気をつけよう」ではなく、具体的な事例＋発生条件＋対処を残す。良い事例（recovery）も同じ重みで記録する。

導き出された原則

① エージェントは「実在しない情報を実在のように書く」

Web検索の前提条件・URLパターン・人物発言など、「ありそう」な情報を確信を持って書く傾向がある。必ずソースリンクを実 URL で残し、後から検証できる状態にする。

② エージェントは「フォルダ構造を勝手に変える」

「整理して」と頼むと、物理リネームをしてしまい既存リンクを破壊する。カテゴリラベルと物理パスは別物として扱う方針を明示しないと、リンク切れが大量発生する。

③ エージェントは「過去の更新を上書きしがち」

「最新の状態に」と頼むと、過去の決断やコンテキストを削除して書き直してしまう。「追記」「移動」「廃止に注記」を明示しないと履歴が消える。

失敗事例（Anti-patterns）

AP-001: 編集前にファイル全体を読まずに古い情報のまま追記

FAILURE claude-recent-updates 発生: 過去セッション

何が起きたか

claude-recent-updates.html に「最新の」更新を追記する際、既存の「最終更新: 2026-04-XX」表記を見落として、新セクションを足した上で古いまま放置してしまった。読者は「最新」と書いてあるのに古い日付が下に残っている混乱状態に。

発生条件

  • 大きなファイル（500行以上）への部分編集
  • ヒーロー部・footer の日付メタ情報を見ずに本文だけ編集

対処

  • 大きな更新の最初と最後に「last-update / 最終更新 / footer date」を grep して全て同期更新する
  • 本セッションでは grep -n "最終更新\|last-update" research/claude-recent-updates.html で全箇所を確認してから編集する手順を確立

AP-002: 推測 URL を実 URL のように書く

FAILURE research/* sources 発生: 2026-05-25

何が起きたか

claude-recent-updates.html のソースリストに anthropic.com/news/claude-for-legal のような「ありそう」な URLを実在確認せず記載してしまった。後でWebSearchで裏取りした際、実際の URL が異なるケースが10件以上見つかった。

発生条件

  • 「ソース」セクションを後付けで埋める作業
  • WebFetch / WebSearch を使わずに記憶ベースで URL を生成

対処

  • 外部 URL を書くときは必ず WebSearch / WebFetch で実在確認する
  • 確認できない URL は「Source: メディア名（日付）」のみのテキスト形式で書き、リンクは張らない
  • 本セッションでは10本の推測 URL を実 URL に差し替え修正済み

AP-003: 日付の混同（announcement vs rollout vs coverage）

FAILURE timeline entries 発生: 2026-05-25

何が起きたか

Karpathy 入社（実際は 5/19）を 5/20、KPMG 提携（実際は 5/19）を 5/22 と書いた。AI ニュース日次（5/20、5/22 の記事）に出てきた日付をそのままイベント日として扱ったため。

発生条件

  • 二次情報（ニュース記事）の掲載日と実際のイベント日を混同
  • 「Anthropic announces」「Bloomberg reports」「The Verge covered」の使い分けが曖昧

対処

  • イベント日と報道日を明示的に書く（「5/19 公開、5/22 報道」など）
  • WebSearch の結果から1次ソース（公式発表・本人 X 投稿）を探す
  • 本セッションでは Karpathy@X・KPMG プレスリリースで実日付を確認して修正

AP-004: 旧情報を完全置換してしまう（履歴喪失）

FAILURE claude-recent-updates hero 発生: 過去セッション

何が起きたか

ヒーロー部のサマリーを「最新の状態に」とお願いした際、以前のサマリー（4月時点の分析）を完全に置換してしまったケース。後で「4月の文脈はどうだったか」を読み返したくなった時、履歴が消えている。

発生条件

  • 「最新の状態にして」というオープンな指示
  • 既存テキストの意図を理解せずに上書き

対処

  • サマリーは追記方式にする（「4月の本質は...」「5月の本質は...」と段落を足す）
  • 履歴的価値のあるテキストは削除せず、必要なら「過去サマリー」セクションを別建てで持つ
  • 本セッションでは「4月後半の本質」段落を残したまま「5月の本質」を追記する形に修正

AP-005: 重複コンテンツを放置（同じものが2ヶ所に出る）

FAILURE index.html 発生: 2026-05-25

何が起きたか

LLM Updates Hub を新設した際、既存の Research カード内にあった「Claude 最新アップデート」を削除し忘れて、同じリンクが2ヶ所に表示される状態に。ユーザーから指摘されて初めて気づいた。

発生条件

  • 新コーナーを追加するときに、既存コーナーとの重複を確認しない
  • 「足す」ことに集中して「整理する」を忘れる

対処

  • 新カード・新リンク追加時は、同じ目的のリンクが他にあるかを grep で確認する
  • 「足したら同等のものを引く」を運用ルール化

AP-006: HTML コメントの取り残し（陳腐化したラベル）

FAILURE claude-recent-updates 発生: 2026-05-25

何が起きたか

セクションを「新→古」に並べ替えた後、各セクション直前にあった <!-- ===== 2月中旬〜4月中旬 補完追記 ===== --> のようなHTMLコメントだけが古い順のまま残り、直後のセクション内容と不一致になった。

発生条件

  • HTML 構造を機械的に並べ替える際、コメントを「内容の一部」とみなさない
  • Python 等の自動化スクリプトでセクション順を変えると、隣接コメントが取り残される

対処

  • 並べ替え後に grep "<!-- ====" でコメントの位置を確認する
  • 陳腐化したセクションコメントは一律削除する判断を運用に組み込む

救った事例（Recovery patterns）

RP-001: 並走作業のセッション間で git pull を必ず先に行う

RECOVERY git workflow 確立: 2026-05-26

何を救ったか

本セッションで Industry Trends のスタブを作った直後、別セッション（または別エージェント）が長文記事6本（trend-* 計3,021行）を並走で完成させていた。再開時に git pull しないと、自分の作業ブランチで stale な状態で書き続けて衝突マージ祭りになる。

運用パターン

  • セッション再開時は必ず git fetch origin && git status で差分を確認
  • 「behind ahead」表示を見て、push 前に必ず pull
  • 並走作業がある状態を前提とし、楽観的競合を避ける

RP-002: 大きな構造変更前にユーザー確認ステップを挟む

RECOVERY workflow 確立: 2026-05-25

何を救ったか

カテゴリ再編・Research 刷新・demos リネーム検討など、後から戻すコストが大きい変更を行う前に、選択肢を A/B/C で提示してユーザーが選ぶ形にした。結果、demos の物理リネームを「見送る」判断ができた（ADR-005）。即実行していたら大量のリンク切れになっていた。

運用パターン

  • カテゴリ構造変更・フォルダ移動・ファイル削除は、事前に選択肢を提示して確認
  • 「リンク切れ・既存ブランチへの影響」を見積もって伝える
  • 「決断を遅延させる選択肢」（リネームせず表記だけ変える等）を必ず含める

RP-003: 二段階の裏取り（既存資産 → 外部ソース）

RECOVERY research workflow 確立: 2026-05-25

何を救ったか

ChatGPT / Gemini ページを書く際、まず research/ai-news/ の20日分から既存抽出して下書きし、その後 WebSearch で主要マイルストーンを裏取りした。結果、ai-news に出ていなかった重要事象（GPT-5.5 リリース日・Atlas 公開日・Gemini 3 Pro / Flash 公開日など）も補完できた。

運用パターン

  • まず既存ハブ内のコンテンツを grep / Python 抽出で集める
  • 次に WebSearch で「日付」「定量数値」「URL」を補強
  • 二段階の出典で書くと一次/二次ソースが明示できる

RP-004: TaskCreate でステップ可視化

RECOVERY execution 確立: 2026-05-25

何を救ったか

「ChatGPT / Gemini ページ作成 + index 更新 + コーナー追加」の複合タスクで、TaskCreate / TaskUpdate を使って進捗を可視化した。ユーザーが途中でレビューしやすく、終わったタスクと残タスクが明示された。

運用パターン

  • 5ステップ以上ある作業は TaskCreate で全部出してから着手
  • 各タスクを in_progress → completed で逐次更新
  • 新規発見タスクは即座に TaskCreate で追加（後でまとめてやらない）
