GitとGitHub — 更新を安全に届ける

Gitは変更の履歴を管理する道具、GitHubはその履歴を共有しレビューや公開を行うサービスです。「ローカルに保存」「commit」「push」「mainへmerge」「サイトのdeploy」は別の出来事です。どこまで終わったかを区別できれば、AIが毎日書く記事と人間が直す解説を、互いの変更を消さずに運用できます。

最終更新: 2026-10-13 · 公式資料の確認日。手順例は未実行の教材です。

まず五つの状態を分ける

作業ツリーは編集中のファイル、ステージは次のcommitに入れる選択、commitは履歴上の保存点、remote branchは共有先の履歴、公開サイトは配信された結果です。commitだけではGitHubは変わりません。pushしたbranchがmainでなければmainも変わりません。PRは変更を相談する仕組みで、開いた時点ではmerge済みではありません。

公開までの経路はリポジトリの設定次第です。GitHub Pagesはbranchの特定フォルダからも、GitHub Actionsのworkflowからも公開できます。「mainにある」と「サイトで見える」を同義にしないでください。公式: Pages公開元

同期の前に読む、同期の後に比較する

fetchは共有先の履歴を取得する操作です。pullは取得した履歴を現在のbranchへ統合します。したがって、編集中の変更を把握しないままpullを繰り返すのは更新手順として不十分です。--ff-onlyは履歴が分岐している場合に更新を止めます。失敗は「強制上書きの合図」ではなく、両方の変更を確認する合図です。公式: git pull

# 教材例: 既存repoの場所で、まず読み取り確認
git status --short --branch
git remote -v
git branch -vv
git diff --stat
git diff
# remote履歴の取得はネットワーク操作
git fetch origin
git log --oneline --left-right HEAD...origin/main

remote URLの出力には埋め込み認証情報が含まれる場合があります。そのままチャットや公開記事へ貼らないでください。origin/mainも仮定であり、実際のremote名と公開branchを先に確認します。statusはステージ済み・未ステージ・未追跡の差を示します。公式: git status

AIと人間が同時に更新する小さな手順

  1. 変更の目的を一つ決め、未commitの変更のownerを確認する。別の人の差分を勝手にstageしない。
  2. 公開対象だけを作業branchで編集する。実行前にテスト方法と戻し方を決める。
  3. 必要なファイルだけをstageし、git diff --cachedで本文と削除を読む。
  4. commit、対象branchへのpush、PRの差分・checks・reviewを確認する。
  5. merge後、mainのcommitを確認し、公開workflowの結果と実際のURLを別に検査する。

これは筆者の運用提案です。直接main更新が許される小規模repoでも、確認する状態は同じです。自動ニュースがmainへ書くなら、最後のpush直前にも共有履歴を取得し、non-fast-forwardの拒否が出たら止めて統合します。force pushで自動ニュースを消す解決はしません。

秘密と履歴破壊は「後で直す」にしない

API key、環境ファイル、ブラウザprofile、個人ログ、未公開素材は公開commitへ入れません。ignore設定は未追跡ファイルの予防であり、既にcommitされた秘密を履歴から消す機能ではありません。秘密を公開した場合は、削除commitより先に責任者と失効・ローテーションを調整します。履歴の書き換えには他のclone、fork、PRへの影響があり、初心者の通常更新とは分けるべき作業です。公式: 機密情報の除去と副作用

reset --hard、clean -fd、保護解除、force pushは「同期ボタン」ではありません。conflictでは両側の意味を読み、AIによる一括採用の前に記事・リンク・設定の意図を照合します。戻す必要があれば共有済み履歴を消すより、取り消しcommitを検討します。

成功の評価と、まだ言えないこと

合格条件は「コマンドがexit 0」だけではありません。対象ファイルのみ変更、秘密なし、リンク検査通過、共有先の目的branchに同じcommit、公開job成功、公開URLの本文一致を確認します。古い画面ならcache、deploy失敗、別branch、別repoの四つを分けて調べます。

このページは特定repoの権限・認証・Pages設定を検査した報告ではありません。利用者の設定が不明なまま「pushすれば必ず公開される」とは断定しません。小さな変更で一巡を確かめてから、自動化を足してください。
