CHAPTER 00

Codexの本質と責任分界

成果物の品質は、モデル性能だけでなく制御系の設計で決まる。

CORE DOCTRINE

Codexは、与えられた環境の中で観測 → 判断 → 行動 → 検証を反復するコーディングエージェントです。人間の仕事は逐一コードを書くことから、目的・境界・評価基準・停止条件を設計することへ移ります。

1. Observeリポジトリ、指示、差分、失敗、外部情報を読む
2. Orient既存設計、制約、リスク、依存関係を解釈する
3. Act最小の変更を行い、必要なツールを実行する
4. Verifyテスト、表示、差分、要件との一致を証明する
5. Report変更、証拠、残余リスク、次の判断を返す
Codex owns

実行責任

  • 対象コードと周辺規約を読む
  • 変更前に影響範囲を把握する
  • 既存パターンに沿って編集する
  • 適切な検証を実行する
  • 不確実性と未実施事項を報告する
Operator owns

委任責任

  • 何を達成するかを決める
  • 許容できるリスクと権限を決める
  • ビジネス上の正しさを定義する
  • 外部への送信・公開を承認する
  • 最終的な採否を判断する

マスターと初心者を分ける5つの差

観点初心者マスター
依頼「これを作って」目的・文脈・制約・完了条件を渡す
権限止まるたびに広げる必要最小限をタスク前に設計する
並列化何でも複数エージェントに投げる所有ファイルと統合点を分離できる時だけ並列化する
検証最終回答を信じるテスト・画面・差分・ログの証拠を要求する
改善毎回同じ説明をする反復知識をAGENTS.md、Skill、Hookへ昇格する
最重要原則: Codexに自由を与えるほど、先に観測可能性と停止条件を強くする。権限だけを広げて検証を弱くしてはいけません。

CHAPTER 01

サーフェスを仕事で選ぶ

慣れた画面ではなく、実行場所・並列性・レビュー方法で決める。

サーフェス強み選ぶ仕事避ける誤用
CLI低摩擦、shell連携、正確な作業ディレクトリローカル実装、調査、修正、反復現在地やbranchを確認せず起動
IDE選択範囲と開いているfileが文脈になる局所編集、説明、editor中心の実装巨大変更を選択範囲だけで判断
Codex App複数thread、Worktree、diff review、Goal、Apps計画、長時間作業、並列委任、レビュー同じfileを複数threadで編集
Cloud隔離環境、非同期、複数試行、別端末独立task、PR準備、重い調査、best-of-N未pushのlocal状態が見えると仮定
Chatrepo非依存の思考とconnector作業調査、企画、接続済みserviceの操作local codeを読める前提で依頼

30秒選択ルール

  1. ローカル環境固有か。 YesならCLI / IDE / AppのLocal。
  2. 並列化または長時間化するか。 YesならAppのWorktreeまたはCloud。
  3. 実コードを変更しないか。 YesならChatまたはRead-only。
  4. 人が差分を細かく対話レビューするか。 YesならAppまたはIDE。
  5. 定型処理か。 YesならCLIのcodex exec、Automation、SDKを検討。
Local thread

現在の状態を使う

未commit差分や導入済みtoolを直接使う。hostへの影響をSandboxで制限します。

Worktree

同一repo内で隔離

別branch・別directoryに分け、長い作業や並列編集の衝突を減らします。

Cloud thread

hostから隔離

GitHubからcloneした環境で実行。setupとagent実行のnetwork条件を分けます。

長いpromptではなく、判断に必要な情報を欠けなく渡す。

CContext

Operational

状態使うモード指示
小さく明確直接実行対象と完了条件を渡し、そのまま実装
複雑だが目的は明確/plan調査・設計・検証計画を確認後に実装
目的自体が曖昧インタビュー重要な選択肢を質問させる
長く完了判定が明確/goal測定可能な目標と停止条件を持続
方針を比較したい/fork / Cloud attempts独立案を評価軸で比較
本流を止めず質問Side chat状態説明や論点確認を別会話で行う
Goal:
  設定画面の保存失敗を解消する。

Context:
  - 再現: 通知をOFFにして保存すると500
  - 関連: src/settings/, api/preferences.ts
  - ユーザーの未commit変更があるので保全する

Constraints:
  - API response形は変えない
  - 新規依存は追加しない
  - 関係のない整形をしない

Done when:
  - 原因を説明できる
  - 回帰testを追加して通る
  - 既存test、lint、diff reviewが完了する
  - 残余riskを報告する
コンテキスト過多: 全fileを貼るより、入口・症状・制約を渡してCodex自身に探索させる。長期作業ではcompact後も残す判断をGoalや文書へ外部化します。

CHAPTER 03

実行ループを制御する

速く書かせるより、誤った方向へ長く走らせない。

01

Orient

pwd、git status --short --branch、指示file、対象構造を確認。ユーザー変更と境界を把握します。

02

Investigate

検索、呼び出し関係、test、履歴、再現から原因仮説を作る。症状だけを書き換えません。

03

Plan

変更点、非変更点、検証、復旧方法を決める。単純作業は過剰に儀式化しません。

04

Execute

既存patternに沿った最小変更。前提が崩れたら惰性で続けず再調査します。

05

Verify

近いtestから広げ、静的検査、実行、表示、link、diffをriskに応じて確認します。

06

Review & Report

重大risk優先で自己review。変更・証拠・未実施・残余riskを報告します。

Continue

継続してよい信号

  • 仮説がcodeと再現で支持
  • 範囲が依頼と一致
  • 検証方法が存在
  • 失敗しても戻せる
Stop

停止すべき信号

  • 破壊的操作や外部送信
  • 製品判断が必要
  • 秘密・個人情報が絡む
  • ユーザー変更と分離不能
  • 同じ失敗を根拠なく反復
方向修正「実装を止め、今の仮説と反証を3点ずつ示して」
範囲縮小「UIは触らず、API層の原因特定だけ完了して」
証拠要求「成功を支えるcommand出力と画面状態を示して」
復旧優先「編集を増やさず、現状を保全して復旧案を作って」

CHAPTER 04

権限・Sandbox・外部作用

「できる範囲」と「確認する時点」は別の制御です。

Technical boundary

Sandbox mode

技術的に読み書き・実行できる境界。代表的にread-only、workspace-write、danger-full-accessがあります。

Decision boundary

Approval policy

境界外操作、network、外部作用を実行する前に、人へ確認する条件を決めます。

仕事推奨出発点理由
調査・review・設計Read-only誤操作の面積を最小化
通常のlocal実装Workspace-write + on-requestworkspace内を自律化し外側だけ確認
定型CI・非対話限定Workspace + never人待ちを避け環境側で制限
network必須Workspace-write + 宛先制限必要性と送信先を分離
Full Access隔離済み環境のみhost全体への影響を通常化しない
# 通常のlocal実装
codex --sandbox workspace-write --ask-for-approval on-request

# 読み取り専用で調査
codex --sandbox read-only --ask-for-approval on-request

# workspace-writeでcommand networkを許可
[sandbox_workspace_write]
network_access = true

Web search

Codexの検索tool。取得内容は不信な入力として扱います。

Command network

npm installやcurlの通信。Sandbox設定で別に許可します。

Connector action

GitHubやCalendar等の読み書き。副作用と明示的意図を確認します。

Full Accessの誤解: 確認が減ることは品質向上ではありません。信頼できないrepo、Web由来命令、秘密情報がある環境では攻撃面を広げます。

CHAPTER 06

並列化・Subagents・Worktree

速さはagent数ではなく、依存関係の切り方で決まる。

並列化できる条件独立した入力明確な所有範囲比較可能な出力一人の統合責任者
方式適する仕事主な危険
Subagents読み取り調査、test log分析、独立観点reviewtoken増、重複、編集競合
複数thread別機能、別文書、別候補案同じfileや前提の競合
Worktree長い実装、別branch、並列編集ignored依存、環境差、統合忘れ
Cloud attempts複数解法を比較する独立task評価軸がないと選べない
Good decomposition

観点で分ける

  • A: 変更箇所と依存関係
  • B: test不足と再現条件
  • C: securityと権限
  • Main: 重複排除、重大度、統合
Bad decomposition

同じ所有物を分ける

  • 同じcomponentを複数agentが編集
  • 共通型を別々に変更
  • 統合者がいない
  • 成功条件を各agentに任せる
この変更を3つの独立観点で調査してください。
- Architecture: 影響範囲と既存pattern。読み取りのみ。
- Tests: 再現条件と不足test。読み取りのみ。
- Security: 入力境界と権限risk。読み取りのみ。

各担当は根拠file、重大度、推奨対応を返すこと。
完了後、main担当が重複を統合し、実装計画を1つ作ること。
編集は計画承認後にmain担当だけが行う。
1. Inspectdirty treeと基準branch
2. Isolate目的別worktree
3. Prepare依存・環境を再現
4. Execute所有範囲内で編集
5. Integratediff・test・merge
並列化しない判断: 設計が未収束、編集対象が密結合、検証環境が一つなら、直列の方が総時間も品質も良くなります。

CHAPTER 07

検証・レビュー・証拠

「testが通った」は品質証明の一部でしかない。

Requirement依頼された振る舞い
Focused test変更箇所の失敗と成功
Regression周辺を壊していない
Static checks型、lint、format、build
Runtime / Visual実環境、画面、log
Diff review不要変更、秘密、互換性

検証順序

  1. 再現または失敗test
  2. 最も近い対象test
  3. 型・lint・format
  4. 関連test群
  5. build / integration
  6. 表示・操作・link
  7. 最終diff review

riskで広げる

  • 共有module: 利用側
  • 認証・決済: 境界値と失敗経路
  • DB: migrationとrollback
  • UI: desktop/mobileと操作
  • 文書: link、索引、検索
  • 依存更新: lockfile、license、build
/review対象狙い
Base branchとの差PR全体の回帰・契約・設計risk
未commit変更commit前の取りこぼし、不要変更
特定commit独立した変更単位の妥当性
Custom instructionaccessibility、性能、security等の重点監査
この差分をコードレビューしてください。
優先順位は、正しさ、データ損失、security、互換性、test不足です。
style上の好みは、実害がない限り指摘しないでください。
各所見に重大度、再現条件、file参照、最小修正案を付けてください。
所見がなければ、残るtest gapだけを報告してください。

完了報告の契約

Changed何を、なぜ
Verified検査と結果
Not verified未実施検査
Residual risk残る不確実性

CHAPTER 08

Git・競合・公開

編集の成功と、安全に共有できる状態は別です。

1. Statusbranch・dirty・他者変更
2. Syncfetch・upstream差
3. Scope意図したfileだけstage
4. Verifystaged diff・checks
5. Publishcommit・push・PR
git status --short --branch
git fetch origin --prune
git diff
git diff --cached
git add path/to/intended-file
git commit -m "Explain the completed change"
git push -u origin HEAD
Dirty tree

ユーザー変更を保全

無関係な差分は戻さない。同じfileなら内容を理解して共存させ、不可能な時だけ判断を求めます。

Remote conflict

事実を3層に分ける

local HEAD、origin HEAD、working treeを別々に確認。履歴意図に合う統合方法を決めます。

  1. 保全未commit差分とbranchを記録。
  2. 分類行の衝突と意味の衝突を分ける。
  3. 意図確認ours / theirsを内容と履歴で判断。
  4. 統合有効な変更を再構成。
  5. 検証marker、test、diff、履歴を確認。
  6. 共有push前にremote差を再確認。
禁止: 状況確認なしのreset --hard、ユーザー差分へのcheckout --、無差別なgit add .、意味を理解しないours/theirs一括採用。

CHAPTER 09

自動化・拡張・プログラム接続

会話で安定した仕事だけを、自動実行へ昇格する。

手段用途選択基準
codex exec非対話の単発・shell連携入力と完了条件が固定
Automation定期check、追跡、反復失敗時の通知と再実行が定義済み
Skill人が起動する再利用workflow複数案件で手順・資料を共有
Hooktool実行前後の検査・強制規則が決定的で機械判定可能
GitHub ActionCI / PR内でCodex実行repo eventと権限をGitHub管理
SDK / App Server独自app、control UI、統合会話外からthreadやeventを制御
MCP ServerCodexへ外部toolを提供標準化されたtool/resource接続

自動化前の4条件

  1. 入力形式が安定
  2. 成功・失敗を機械判定
  3. 権限が必要最小限
  4. 通知・再実行・停止がある

自動化しない仕事

  • 製品判断が毎回変わる
  • 秘密・個人情報の送信判断
  • 破壊対象が曖昧
  • 成功が主観だけ
  • 手順が頻繁に変わる
# 非対話実行
codex exec "Run repository checks, fix only deterministic lint errors, and report remaining failures"

# 機械可読event
codex exec --json "Review the current diff and return prioritized findings"

# Cloudへ複数試行
codex cloud exec --env ENV_ID --attempts 3 "Propose and verify a fix"
1Prompt手動で成功
2AGENTS前提を固定
3Skill手順を再利用
4Hook規則を強制
5Automation安定後に無人化

CHAPTER 10

診断・復旧ランブック

症状ではなく、状態・権限・文脈・環境・統合の層で診断する。

1. Statethread、goal、branch、dirty、cwd
2. ContextAGENTS、file、compact、指示競合
3. PermissionSandbox、approval、network
4. Environment依存、env、service、worktree
5. IntegrationMCP、plugin、auth、policy
承認待ちのまま進まない

/statusと/permissionsで権限を確認。何のために境界外操作が必要か限定し、一時承認で済むか判断。

同じ修正と失敗を繰り返す

実装を止め、失敗log、仮説、反証、変更履歴を要約。新しい証拠のない再試行を禁止し、最小再現へ縮小。

長い会話で前提を忘れた

Goal、決定log、diff、次の検証を外部化。/compact後に重要制約を再提示し、必要ならhandoff。

Worktreeだけ動かない

ignored依存、未追跡設定、env、port、DB、submoduleを比較。Git管理外の状態は自動複製されません。

MCP / Appが見えない

提供元、plugin install/enable、connector認証、MCP設定、workspace policy、再起動・新threadの順に確認。

CLIとAppで挙動が違う

version、cwd、profile、config layer、feature flag、認証、local/cloudを比較。

pushがrejectされた

working treeを保全し、fetch後にlocal・remote・merge-baseを確認。意味的に競合解消。

変更が大きくなりすぎた

必要差分と偶発変更を分類。無関係な整形・生成物・依存更新を切り離す。

全端末を止め、dirty treeを保全。remote基準で価値ある変更を意味的に統合し、単一端末からpush。

CASE C

明朝までの大規模移行

Goalへ測定可能な条件を設定。Worktree隔離、読み取り調査を並列化、段階commitと定期検証。

CASE D

毎日更新する情報hub

公式sourceと更新箇所をSkill化し、link検査をHookへ。安定後にAutomation化し、公開は明示承認。
