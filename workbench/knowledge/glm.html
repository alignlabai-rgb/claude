GLM実務ガイド — Thinking・Coding Plan・公開重みの境界

GLMという一語で、APIモデル、Coding Plan、Z.aiのアプリ、AutoClaw、公開重みを同一視しない。移行で壊れやすいparameterとquotaの単位を先に理解し、使える仕事だけを小さく検証します。

1. 現行の二つの系統

GLM-5.3公式docsはtext-only入力、常時reasoning、reasoning_effortのlow/high/max、thinking.type: disabled非対応を説明します。一方、GLM-5.3-Flashの公式公開cardは視覚を含むmodelです。同じ世代の名前でもmodalityとAPI契約は同じではありません。GLM-5.3仕様 / Flash card

text-onlyの対象に画像を送って失敗した場合、model全体の能力不足と判断するのではなく、surfaceの入力契約違反として切り分けます。アプリが画像を扱えても、裏で別modelやtoolを使っている可能性があるため、APIの能力へ移して記載しません。

2. 移行時にparameterを先に直す

旧実装がthinking無効を送っているなら、IDだけ変更しても新modelでは失敗します。公式はenabledとlow effortへの移行を案内しています。複雑なtaskでmaxが推奨されても、全仕事にmaxを付ける設計は待ち時間や消費量を増やすだけになり得ます。Feature Changes

本ハブの提案は、短い分類、仕様抽出、コード修正で別のprofileを用意することです。model固有parameterはadapterに閉じ込め、業務taskは「何を返すべきか」を定義します。errorを文章化して握り潰さず、invalid request、quota、timeout、tool拒否、出力不適合を区別します。

# 接続を行わない説明用設定
profile: text_extract
model: glm-5.3
thinking: {type: enabled}
reasoning_effort: low
tools: []
acceptance: 出典span付きの構造化抽出
stop_on: 契約違反／未確認source／試行上限

低いeffortで失敗した後にmaxで成功しても、それを初回成功として扱いません。どのtaskに追加の推論が必要だったかを記録すると、quotaを仕事の価値へ結びつける判断ができます。

3. Coding Planと通常APIを分ける

Coding Planの現行overviewはGLM-5.3と5.3-Flash対応、旧5.2/5.1から5.3、旧4.7からFlashへの自動routingを説明します。quotaは5時間と週のcreditsで、input、cached input、output、MCP toolに計算係数があります。「prompt回数」や「無制限tokens」に換算してはいけません。Coding Plan公式overview

provider側のkeyやendpointは契約に結びついています。通常APIとCoding Planを同じ課金bucketとしてまとめず、使用surfaceと計測単位を別々に扱います。契約歴によってprotocolの利用条件が変わる注意も公式docsにあり、実際のアカウントを読まずに全員の対応を断定できません。How to Use

評価は一つのtaskに必要なcreditsと人の修正時間を測ります。余ったquotaを埋めるための再生成は、導入効果には数えません。仕事の完了物がない大量の呼出より、検証できる差分一件の方が次の判断に使えます。

4. Flashのopen weightsをどう読むか

GLM-5.3-Flashの公式cardはMIT licenseを表示し、提供側のblogはSGLang、vLLM、TokenSpeed対応を案内しています。提供側の効率比較はその測定環境の主張で、手元のPCで同率に速くなる保証ではありません。公式card / 公式技術説明

Flashという名前を小さいダウンロードや単一GPU可動性に変換しません。weights全体、量子化、KV cache、batch、runtimeを調べます。local化で外部送信を減らせる場合でも、取得ツールや追加検索がnetworkを使うなら、その工程はofflineではありません。

5. Agentの誤りをmodelと環境に分解する

公開code fixtureで、既存testが一つ落ちるbugを用意します。修正範囲は小さくし、外部package追加、credential変更、公開を禁止します。modelがtool callを作り、harnessが実行し、testが返り、modelが差分を修正する一巡を記録します。

失敗は、仕様誤読、tool引数不正、環境不足、test未実行、結果の誤報、過剰変更に分けます。modelの回答が自然でも、testを実行せず「通った」と言えば不合格です。拒否されたtoolを別経路で実行する挙動も、task達成とは別の重大な失敗です。

改善時は一度に一条件だけ変えます。model、harness、memory、権限、入力を同時に変更すると、次回再利用できる方法が残りません。同じ失敗が続く場合は試行枠を勝手に増やさず、fixtureを小さくして原因を確認します。

6. 採用と観測を有限に閉じる

採用候補を「使うべき」で終えず、対象task、期待効果、評価入力、失敗条件、担当の判断範囲を一枚にまとめます。資料作成とrepository修正を同じ採用決定へ束ねず、用途ごとに別の受入を用意します。

結果の共有ではmodelの宣伝文より、原稿、patch、test結果、未解決条件を優先します。このガイドは公開一次資料から作った試験設計であり、実行済み評価、課金変更、組織の正式採用を意味しません。
