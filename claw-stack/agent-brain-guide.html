エージェントの
頭脳（LLM）の選び方

Hermes Agent・OpenClaw・PicoClaw などの「主脳」を、クラウド API にするかローカル LLM にするか。
自動でコンテンツを量産する運用を前提に、どこに何を置くかを判断するためのガイドです。

結論を見る Claw 比較表へ
結論

主脳はクラウド、量産の下流だけローカル

迷ったら、まずこの原則から逆算してください。

エージェントの主脳（オーケストレータ）は基本クラウド API にします。 賢さが一段上で運用の手間がほぼゼロだからです。 ローカル LLM は「賢さ」で選ぶものではなく、 経済性・制御・プライバシーのために使います。

量産の下流工程（下書き・分類・整形・タグ付け）だけをローカルに切り出すのが定石。 ここはトークン量が多く、品質要求が一定で、外に出したくないデータも混ざるため、ローカルの旨味が最も出ます。

※ 本ハブの多軸構成（kimi.html）とも整合する立て付けです。 「質の最終判断は Claude / GPT、長文の整合は Kimi、量産下流は Qwen / GLM」という役割分担をそのまま頭脳選定に写しています。

☁

クラウドを主脳にする理由

  • 賢さが一段上（複雑な判断・長期ワークフロー）
  • 運用負荷ゼロ（GPU・量子化・更新の管理が不要）
  • ツール使用・関数呼び出しの信頼性が高い
  • 立ち上げが速く、失敗の戻しが容易
▣

ローカルを使う理由

  • 経済性：高頻度・大量トークンを API 課金なしで回す
  • 制御：モデル固定・オフライン・レイテンシの安定
  • プライバシー：データを外部送信しない
  • 量産下流に限定すれば品質要求を満たしやすい
⚖

やってはいけない切り分け

  • 「賢さが欲しいから」ローカルを主脳にする
  • 運用体制がないのに全工程をローカル化する
  • 品質ゲート（最終判断）までローカルに任せる
  • 下流の最適化のために主脳を妥協する
判断マトリクス

Cloud vs Local — 4軸で比べる

「賢さ・運用負荷・コスト・向くタスク」の4軸で見ると、置き場所はほぼ自動的に決まります。

軸 クラウド API（主脳向き） ローカル LLM（下流向き）
賢さ 最上位。複雑な判断・長期計画・曖昧な指示の解釈に強い。 定型タスクなら十分。複雑な判断は不安定になりやすい。
運用負荷 ほぼゼロ。API キーだけ。更新はベンダー任せ。 GPU 確保・量子化・推論エンジン運用・モデル更新が自前。
コスト構造 従量課金。量が増えるほど効く。低頻度なら割安。 初期投資（GPU）後は電気代中心。高頻度・大量で逆転。
制御・プライバシー 外部送信あり。モデルはベンダー都合で更新される。 完全ローカル。モデル固定・オフライン・閉域に対応。
向くタスク 主脳のオーケストレーション・最終品質判断・難所の推論。 下書き・分類・整形・タグ付け・大量バッチ。
本ハブの位置づけ 主脳・品質ゲート 量産の土台

コストの分岐点は呼び出し頻度とトークン量で決まります。詳細な試算と推論エンジンの選び方は SLM ガイド を参照してください。

エージェント別の実践

エージェントごとに何を脳にするか

実行環境の前提が違うので、置けるモデルも変わります。

H

Hermes Agent

ローカル PC だけで閉じる発想より、VPS / GPU マシン / クラウド上に居続ける前提で設計された常駐エージェント。 canon 上は GPT-5.5 / GPT-5.5-pro（Codex OAuth 経由）・DeepSeek V4・Qwen 3.6-Plus に対応。

主脳は GPT-5.5 系などのクラウド。GPU を持つなら下流を Qwen 3.6-Plus / DeepSeek V4 でローカル化し、常駐の強みを活かす。
Hermes Agent 詳細 →
O

OpenClaw

フルスケール本番運用・AI パイプライン統合向け。Orchestrator + Worker のマルチエージェントをフル対応し、クラウド / On-premise で動く。

Orchestrator はクラウド主脳（Claude / GPT-5.5）、Worker 群の下流は Qwen / GLM をローカルに。役割で脳を分けるのが本領。
OpenClaw 連携設計へ →
P

PicoClaw

軽量・単一エージェントのローカル寄りスタック。HTTP / CLI のみで、ローカル SLM をバックエンドに据えやすい。PoC・個人開発・エッジノード向け。

ローカル SLM（Gemma 4 / 軽量 Qwen）を素直にバックエンドに。難所だけクラウドへルーティングするハイブリッドが効く。

量産パイプラインでの頭脳配置

量産の下流＝ローカル

2

3

最終品質判断＝クラウド

1本を丁寧に仕上げる品質ゲートを Claude Opus 4.8 / Sonnet 4.6 ・ GPT-5.5 で締める。

下流ほどローカル・低コスト、上流（判断）ほどクラウド・高品質。トークン量の多い工程を下に寄せるのがコスト設計の勘所です。

Kimi は「②の一貫性レイヤー」を一手に引き受ける専用エンジンで、速報や量産の主役ではない、という整理（canon: kimi.html）に揃えています。
