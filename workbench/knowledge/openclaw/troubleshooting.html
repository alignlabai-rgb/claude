OpenClaw トラブルシューティング：再インストールの前に層を分ける

最終更新・公式情報確認：2026-10-13。確認日は発表日ではありません。本文の教材・評価案は筆者の提案であり、実行済み成果や導入保証ではありません。

問題が出たら最初に全部を初期化する、という方法では原因も回復条件も学べない。OpenClaw は入口、Gateway、モデル、ツール、保存、配送から成る。症状をどの層の問題か切り分け、状態を読んでから一つの変更へ進む。本稿は診断の考え方であり、運用サービスの再起動や認証変更を実行する指示ではない。

最初の三つの問い

いつから起きたか、直前に何を変えたか、一件の依頼のどこまで証拠があるかを記録する。エージェントが「できない」と言ったことと、実際の tool が拒否したことは違う。依頼を受け付けた ID、エラー、保存物、通知の状態を分ける。秘密を含むログ全体を公開相談へ貼らない。

公式 runbook も更新、provider、UI、サービス、設定、チャネルとツールを別の症状群へ分けている。OpenClaw Troubleshooting 症状が違えば調べる場所も違う。接続失敗をモデルの頭脳の問題へ、権限拒否をプロンプトの不足へ読み替えない。

読み取りから始める

公式 runbook にある openclaw status と openclaw gateway status は、状況を知る入口になる。OpenClaw Troubleshooting 実行する場合も、表示には識別情報や接続の情報が含まれ得るので、共有前に内容を点検する。検査する CLI と実際のサービスが同じ版かも確認する。

doctor や channel probe は、名前から完全な無作用と決めない。修復の選択肢や外部接続を含む検査を、単なる状態の読み取りと区別する。設定を変える工程へ進む際は対象と効果を確認し、診断の一環だから全て許可されているとは扱わない。

画面はあるが返答が来ない

Gateway 接続、依頼の受け付け、モデルの応答、ツールの結果、保存、配送の順に、最後に確認できた証拠を探す。推論先のエラーなら、認証、利用条件、制限、障害のどれかを読み、同じ失敗を大量に再送しない。別の provider へ替えることは、入力の送信先と料金も変える可能性がある。

UI が古い状態を見せているだけなら、元の仕事を新しく始める前に ID を使って状態を確認する。結果が不明な送信を無条件に再実行しない。保存物があるなら処理全体ではなく配送を確認する。モデルの最終文より、実際の成果物と送信確認を優先する。

ツールが拒否された

Sandbox の公式説明には、openclaw sandbox explain で有効な mode、作業領域、mount、tool policy などを読む案内がある。OpenClaw Sandboxing 意図した制限なら拒否は正常な結果である。許可が必要な仕事なら、運用者が要件を再確認し、禁止効果を別経路で実行しない。

設定を変える前に「どの仕事に、どの対象への、どの操作が必要か」を書く。すべてを許可することで一件の拒否を消すと、他の仕事の境界も変わる。局所的な要件に対して、範囲を限定した許可を検討する。

更新の後に起動しない

現在の公式 Getting started の Node 要件は旧記事より新しい。OpenClaw Getting started ランタイム、CLI、サービスの実体、設定の解釈がそろっているかを確認する。旧い状態を新しい版で読んだ後、以前の版へ戻せば必ず起動すると決めつけない。戻す前に、移行と rollback の公式文書を確認する。

合成の同じ課題を更新前後で通せるよう、入力と採点を残しておく。チャネル接続だけ復旧しても、道具や記憶の読み込みが変わっている可能性は残る。起動成功と業務の回帰検査を分ける。

記憶の整理でエラーが出る

公式 memory provenance は、削除が全面消去ではなく、対象の追跡と保存場所に境界があることを説明する。OpenClaw Memory provenance and deletion エラーを消すために出自や保存の証拠を手動で削除しない。対象、影響、部分的な状態を読んで、必要な検査を先にする。本稿では削除を実行しない。

診断の完成条件は、直ったという一文ではなく、原因候補、否定した候補、行った変更、確認した結果、残る不確実性を示せることだ。解決した失敗を合成教材へ変えれば、次回の更新時にも同じ検査を使える。再現できない成功談より、再利用できる診断手順を残す。
