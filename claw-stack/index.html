Claw Stack：常設エージェントを選ぶための入口

最終更新・公式情報確認：2026-10-13。確認日は発表日ではありません。本文の教材・評価案は筆者の提案であり、実行済み成果や導入保証ではありません。

チャットから頼めば、資料を読み、手順を実行し、時間になれば結果を返す。常設エージェントの魅力はこの連続性にある。しかし選ぶべきものは「最も賢いボット」ではない。誰が入口を使い、どのデータが記憶に残り、実行の失敗を誰が回収するかを含む、小さな運用システムである。この棚は製品の機能数を競う入口ではなく、その運用を設計する入口として読む。

四つの名前を同じ製品の大小版と考えない

OpenClaw は Gateway を中心にチャネルと実行面を接続する。PicoClaw は Sipeed による独立した Go 実装で、OpenClaw のフォークではない。NanoClaw はホストの配送とセッションのコンテナを分ける。Hermes Agent は Nous Research のエージェントで、CLI・Gateway と、再利用するスキルや永続メモリを備える。それぞれの一次入口は OpenClaw 公式リポジトリ、PicoClaw 公式リポジトリ、NanoClaw 公式リポジトリ、Hermes Agent 公式リポジトリ。名前が似ていても設定互換、同じ安全境界、同じ更新方法は仮定しない。

最初に決めるのは成果物

筆者の設計提案として、初回課題を「架空の三つの告知文から、変更点を一枚の比較表へまとめる」に限定する。入力は公開または合成した文章、出力はローカルの下書き、送信や購読やアカウント変更は含めない。こうすると読み取り、根拠の保持、停止、再実行という能力を、秘密や実サービスの事故を伴わず比較できる。ニュースを何本書けたかより、誤読を根拠へ戻せるかを観察する。

成果の仕様には、主張・根拠の段落・確認日・不明点・次に人が決める事項を含める。判断に必要な情報が足りなければ「未確認」で終了できることも正解にする。空欄を埋めるために推測するエージェントは、長い記事を出してもこの課題には不適合である。

読む順序を用途で変える

  • 選定前なら 実行・記憶・隔離の比較 で要件を作る。
  • モデル変更が目的なら Agent Brain：モデル選定 でハーネスとの責任分担を確認する。
  • チャネル常設を考えるなら OpenClaw の適合条件 を読む。
  • 小型機器なら PicoClaw の検証設計 を読む。
  • コンテナと配送を分離したいなら NanoClaw の境界 を読む。
  • 手順の再利用を中心に見るなら Hermes のスキル・メモリ を読む。

試行から常設へ進む条件

一回の良い回答から常設へ飛ばない。合成入力での試行、許可した作業領域での限定実行、送信先を一つに絞った監督付き運用、定期化の順に検討する。各段階でデータの出入口、書ける範囲、止め方、更新後の再検証を一枚に残す。これは本棚の評価提案であり、どの製品についても実地検証済みの認定ではない。

再起動後に同じ通知を二度送る、他の会話の記憶を混ぜる、結果がないのに完了と表示する。こうした失敗を合格条件へ入れると、見栄えだけでは選べなくなる。逆に、失敗時に入力と結果を切り分け、処理済みか不明かを表示できるなら、対象業務を限定して価値を作りやすい。

導入しないという結論も有益

月に数回しか頼まない仕事には常設 Gateway より、保存した手順と手動起動の方が合う場合がある。機能を増やすと監視、更新、権限確認も増える。まず消したい待ち時間を一つ選び、その削減が運用の負担を上回るか評価する。星の数、デモ動画、低価格の宣伝は試す動機にはなるが、手元の業務を任せる証拠にはならない。

運用記録を記事へ変える

機能を試すたびに記事を増やすのではなく、同じ失敗を減らす知識を残す。たとえば「再起動後に通知が重複した」なら、開始時刻と対象 ID、処理済みの判断、送信確認を記録し、重複の再現条件を次回の教材へする。秘密を含むログをそのまま公開せず、合成した入力で現象を説明する。試行の記録と読者へ推奨する手順は別の成果物である。

日次のモデル更新はこの棚で毎回手順を書き換える理由にはならない。変わったのが推論先、実行基盤、認証、保存形式のどれかを分類し、影響する章だけ見直す。読み手が自分の構成に変更が必要か判断できる粒度を優先する。
