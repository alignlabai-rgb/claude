Mission Control

Programming the Agent: The Art of the Spec

自律型エージェントに対する指示は、「プロンプト」ではありません。
それは「Spec (仕様書)」であるべきです。
曖昧な Spec は、曖昧な成果物（または無限ループ）を生みます。

The Perfect Mission Spec

OpenClaw に仕事を投げるときは、必ず以下のフォーマットで記述した Markdown ファイル (MISSION.md) を渡してください。

Template: MISSION.md
# Mission 001: User Profile Refactoring ## 1. Objective (目的) 現在の `UserProfile` コンポーネントは巨大すぎる。 これを `Avatar`, `Bio`, `Stats` の3つのサブコンポーネントに分割し、可読性を向上させること。 ## 2. Constraints (制約条件) ← 最重要 - **No Logic Change**: ビジネスロジックは一切変更してはならない。 - **Library Lock**: 新しいライブラリ (`npm install`) は禁止。 - **UI Preservation**: DOM構造やCSSクラス名は変更しないこと（E2Eテストが壊れるため）。 ## 3. Definition of Done (完了の定義) ← エージェントはここを目指す - [ ] `src/components/profile/` 以下に3つの新ファイルが存在する。 - [ ] `npm run test` が全てPASSする。 - [ ] `npm run lint` がエラーゼロである。 ## 4. Resources - 参照すべきファイル: `src/components/UserProfile.tsx` - 参照してはいけないファイル: `src/legacy/*`
このファイルを保存し、$ openclaw run MISSION.md と実行します。

Why "Definition of Done"?

人間と違い、エージェントは「いい感じになったら終わり」という感覚を持ちません。
明確な終了条件（テストオールグリーン、ファイル存在確認など）を与えないと、彼は「もっと綺麗にできるはずだ」と無限にリファクタリングを続けてしまいます。

Intervention (介入)

Mission実行中、Operatorはログ監視画面（Mission Control）で状況を見守ります。

  • Pause & Redirect: 「方向性が違う」と思ったら即座に一時停止し、チャットで軌道修正を指示します。
  • Inject Knowledge: エージェントが迷っていたら、ヒントや追加資料を途中で差し入れます。

完全に放置するのではなく、「困っているときだけ助け船を出す」のが熟練Operatorの技です。

実戦 Mission サンプル集

以下の4つのサンプルは、現場でそのまま使えるテンプレートです。 Objective・Constraints・Definition of Done の3点セットを必ず揃えることが、成功率を高める鍵です。

Sample A: 機能実装 Mission

feature-search.md
# Mission: 検索機能の実装 ## 1. Objective ユーザーが商品名でアイテムを全文検索できる機能を実装する。 ## 2. Constraints - DB は既存の PostgreSQL を使う（新しい DB は追加しない） - フロントエンドは既存の React コンポーネントの設計パターンに従う - レスポンスタイム: 300ms 以内（ベンチマークテストで証明すること） - 絶対に変更してはいけないファイル: src/db/schema.ts ## 3. Definition of Done - [ ] POST /api/search エンドポイントが実装されている - [ ] フロントエンドの SearchBar コンポーネントが動作する - [ ] `npm test` が全 PASS - [ ] レスポンスタイムのベンチマーク結果が logs/benchmark.json に保存されている ## 4. Resources - 参照ファイル: src/db/schema.ts, src/api/routes.ts, src/components/ItemCard.tsx
新機能実装の場合は「制約」と「測定可能なDoD」が特に重要。ベンチマーク結果ファイルをDoDに含めることで検証可能にします。

Sample B: バグ修正 Mission

bugfix-234.md
# Mission: ログインループバグの修正 ## 1. Objective Issue #234: ログイン後に /dashboard にリダイレクトされず、 ログイン画面に戻るバグを修正する。 ## 2. Resources - 再現手順: src/docs/bug-234-reproduction.md - 関連ファイル: src/auth/callback.ts, src/middleware/auth.ts ## 3. Constraints - 認証ロジックのリファクタリングは禁止（スコープ外） - Cookie の設定は変更しない - 絶対に変更してはいけないファイル: src/auth/session.ts, src/tests/auth.test.ts ## 4. Definition of Done - [ ] bug-234-reproduction.md の手順でバグが再現しない - [ ] `npm test -- --testPathPattern=auth` が全 PASS - [ ] 修正内容のコメントを該当箇所に追記している
バグ修正では「再現手順ファイル」をResourcesに含め、DoDに「その手順でバグが再現しないこと」を入れるのが鉄則。

Sample C: リファクタリング Mission

refactor-auth.md
# Mission: 認証モジュールの分割 ## 1. Objective 600行ある src/auth.ts を責務単位に分割する。 ## 2. Target Structure src/auth/ ├── index.ts (re-export のみ) ├── login.ts (ログイン処理) ├── session.ts (セッション管理) ├── permissions.ts (権限チェック) └── utils.ts (共通ユーティリティ) ## 3. Constraints - 外部から見た API は一切変更しない（index.ts で全て re-export） - 既存のテストコードは変更しない - 絶対に変更してはいけないファイル: src/tests/auth.test.ts ## 4. Definition of Done - [ ] `npm run build` が成功する - [ ] `npm test` が全 PASS - [ ] 元の auth.ts が削除されている - [ ] src/auth/ 以下に5ファイルが存在する
リファクタリングでは「外部から見た API 変更禁止」という Constraints と、テストが PASS することを DoD にすることで安全性を担保します。

Sample D: ドキュメント生成 Mission

doc-api.md
# Mission: API ドキュメントの自動生成 ## 1. Objective src/api/ 以下のすべてのエンドポイントに JSDoc コメントを追加し、 OpenAPI 仕様書 (docs/api.yaml) を生成する。 ## 2. Constraints - コメントを追加するのみ。実装コードは変更しない - 生成ツールは既存の `swagger-jsdoc` を使用する（新パッケージ不可） - 英語でコメントを書く（既存コードの言語に統一） ## 3. Definition of Done - [ ] `npm run docs:generate` が成功する - [ ] docs/api.yaml が生成されている - [ ] src/api/ 以下の全ファイルに JSDoc コメントが存在する - [ ] `npm test` が引き続き全 PASS ## 4. Resources - 参照ファイル: src/api/routes.ts, package.json（既存スクリプト確認用） - 参照してはいけないファイル: src/legacy/*
「変更してよいもの／してはいけないもの」を明確に分離するだけで、エージェントのドリフトを大幅に防げます。

Mission の失敗パターンと対策

Mission が思い通りに動かないとき、ほとんどの原因は「Spec の書き方」にあります。 よくある失敗パターンを把握し、事前に手を打ちましょう。

パターン 症状 根本原因 対策
Constraints が曖昧 エージェントが勝手に判断して想定外の変更をする 「しないこと」が明記されていない NGワード（「絶対に〇〇してはいけない」）と「絶対に変更してはいけないファイル」セクションを追加
DoD が測定不能 「いい感じに」で終わりが来ない / 無限改善ループ 合否を判定できる基準がない コマンドで確認できる基準のみ（npm test PASS、ファイルの存在確認）を DoD にする
Resources が多すぎ コンテキスト溢れ / 混乱して誤ったファイルを編集 LLM のコンテキストウィンドウを超える情報量 参照するファイルは5個以内に絞る。巨大ファイルは関連セクションのみ抜粋して渡す
スコープが大きすぎ 途中でタイムアウト / 作業がドリフトして別の問題に取り組む 30分以内に完了できないサイズ Mission を「30分以内で終わるサイズ」に分割。大きなゴールは Orchestrator Mission でサブタスクに分ける
Objective が複数ある どちらかの目標が中途半端になる / 両立できず止まる 「これもやって、あれもやって」型の指示 1 Mission = 1 Objective の原則を守る。2つのゴールは2つの Mission に分割する
技術前提が不明 フレームワークやバージョンを誤って推測する コードベースの文脈情報が不足 Resources に package.json や README.md を含める。使用技術スタックを Objective に明記する
Mission 品質チェックリスト（実行前に確認）
  • Objective は1文で言い切れるか？（2つ以上あれば分割）
  • Constraints に「絶対に変更してはいけないファイル」が書かれているか？
  • DoD の各項目はコマンドや存在確認で検証できるか？（「いい感じ」は NG）
  • Resources のファイルは5個以内か？
  • 30分以内で完了できるサイズか？（不安なら分割）
