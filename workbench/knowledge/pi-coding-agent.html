Pi coding agent — 小さなharnessと大きな実行権限を理解する

Piはearendil-worksの最小・拡張可能なagent harnessです。独自LLMではなく、モデルへの接続、tool実行、会話と開発workflowを組み合わせる道具です。小さいcoreは理解や改造の入口になりますが、小さいこと自体は安全、低コスト、高性能の保証ではありません。

最終更新: 2026-10-13 · 公式資料の確認日。提案は実行・採用の報告ではありません。

Piが提供するものと提供しないもの

公式repoはPiをextensions、skills、prompt templates、themesで拡張し、packagesとして共有できるharnessと説明します。interactive利用、print/JSON mode、RPC、TypeScript SDKなどの入口があります。coreではsub-agentやplan modeを既定機能として抱え込まず、必要なworkflowを追加する方針です。公式: Pi

model選択とharness選択は別です。同じmodelでもtoolの仕様、context組み立て、履歴の扱い、retryの設計が違えば挙動は変わります。PiをinstallしてもモデルのsubscriptionやAPIが無料になるわけではありません。接続先がlocal endpointならそのendpointの能力、cloudならその契約が実行条件になります。

最重要: 組込みpermission systemはない

現行READMEは、filesystem、process、network、credential accessを制限する組込みpermission systemをPiが持たず、起動userとprocessの権限で動くと明記しています。強い境界が必要な場合はcontainerizationやsandboxのpatternを別に示しています。公式: Permissions & Containerization

「このfolderだけ触って」とpromptに書くことは有用なinstructionですが、OSによる強制境界ではありません。広いhost folder、credential、Docker socketを渡せば、containerという見た目でも強い権限が残ります。公開教材だけのprojectから始め、必要な入力と出力を明示するのが筆者の提案です。

現在の配布情報を固定する

公式のnpm packageは@earendil-works/pi-coding-agentで、現行資料はNode.js 22.19以降を要求し、通常installにはdependency lifecycle scriptsが不要と説明します。公式installerは依存関係をpinし、npm直接installはtransitive dependenciesをpinしないという違いもあります。公式: coding-agent README

install commandをそのまま実行する前に、配布元、release、依存lock、対象platformを確認します。古いpackage名やcommunity packageの手順を公式coreの仕様と混ぜないでください。この記事ではinstallやloginを実行していません。

教材例: 一件の修正を拡張なしで試す

公開してよい練習用repoを用意し、「parserが空入力で例外を出す」という一件を扱う想定です。最初からpackageを大量追加するより、coreの動きを観察する方が比較可能な記録になります。

  1. 変更前のtestと差分を保存し、対象functionと許可範囲を指定する。
  2. 空入力、通常入力、壊れた入力の期待をfixtureへ書く。
  3. agentに最小修正とtestを依頼する。networkや外部serviceは別許可にする。
  4. 変更されたファイル、tool実行、test出力を人間が確認する。
  5. 同じ課題を別modelで試すならharness設定と入力を固定する。

これは設計例であり、修正成功の実績ではありません。評価表には「完了したと言ったか」ではなく、既存testが壊れていないか、fixtureが期待通りか、余分な変更がないかを残します。

extensionsとsessionは新しい境界になる

extensionはharnessの挙動を変えるコードです。第三者packageを導入する時は、実行code、依存関係、network、取得するcontextを確認します。sub-agent packageを追加しても、そのreviewやsecret除外を自動で得られるわけではありません。公式siteもpackagesがcodeを実行しagent behaviorへ影響すると注意しています。公式directoryのpackage security note

sessionには入力資料、tool出力、source code、環境情報が入り得ます。共有機能があっても、privateな作業sessionをそのまま公開しないでください。公開OSSの改善用共有と、内部作業の保存は違う用途です。履歴を学習素材へ転用する場合も、権利と公開境界の確認が先です。

選択と検証

harnessを自分のworkflowに合わせたい、既存appへSDK/RPCで組み込みたい、挙動をsourceで追いたい時にPiは比較対象です。強い管理policyを一体で欲しい時は、OSやsandboxの設計を含めた総体で比較します。coreの短いpromptだけで消費量や品質の優位を一般化しないでください。

評価は差分品質、test通過、権限の説明可能性、model切替時の再現性、障害時の停止と復旧です。実機のtokens/sec、費用、tool成功率は未測定です。小さなharnessを「無制限に任せられるagent」と取り違えないことが、再利用できる制作環境への第一歩です。
