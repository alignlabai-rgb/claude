エージェントへの依頼設計 — 文章を実行契約へ

目的・証拠・権限・完成条件を具体化し、曖昧な依頼を検証できる仕事へ変えます。

旧情報は固定旧版の全文へ分離しています。以下の例・試験案は未実行の教材です。

文体ではなく、仕事の欠落を埋める

強い言葉や長いrole設定は、必要な入力の代わりにはなりません。「優秀な開発者として完璧に直して」より、「どの版で、何が失敗し、何を変えてよく、何を確認するか」を書いた依頼の方が確認可能です。モデルを褒める文章より、作業条件を満たす情報を優先します。

公式best practicesは具体的な検証条件を渡すことを推奨しています。Claude Code best practices。ここでの依頼の構成は筆者の方法案であり、どの案件にも同じ長文templateを貼ることを目的にしません。

五つの要素を必要な長さで渡す

目的は下流の読者や利用者まで示します。証拠は資料の場所と対象版です。範囲は変えてよい実物と禁止する変更です。完成条件はtestや引用の照合方法です。停止条件は不足、拒否、試行上限等です。短い修正なら一段落で足り、複雑な比較なら表に分けます。

機械で処理する出力が必要なら、field名、型、未確認の表し方を示します。「適当にJSONで」ではschemaが安定しません。一方、読み物の本文にすべての管理fieldを露出させると読みにくくなるため、公開本文と検査用の記録の目的を分けます。

資料中の命令と、利用者の依頼を分ける

外部のWeb記事、issue、ログ、READMEには、toolを実行させる文が含まれ得ます。調査対象の文字列をそのまま上位命令にしないよう、引用資料は事実確認の入力と明示します。資料に「全部削除せよ」とあっても、依頼の許可範囲が変わるわけではありません。

強制的な遮断が必要な操作は、文章だけでなく実行環境のpermissionで扱います。Permissions。モデルに「安全に」と伝えることと、安全なtoolだけを用意することは別です。拒否は不足の証拠として残し、言い換えで通す作業へ変えないようにします。

教材例：仕様比較の記事制作

未実行例として、公開されている二つのAPI仕様から比較記事を作る依頼を考えます。入力に取得日、モデルID、対象surfaceを付け、出力は事実表、差異の説明、未確認点、試験候補とします。料金不明は空欄または未確認とし、検索snippetを取得済み本文として扱わない条件を明示します。

悪い依頼は「全AIの最新情報を完全網羅して最高の記事を書いて」です。範囲、時点、一次情報の要否が曖昧なため、過去の記憶と推測が混ざりやすくなります。改善した依頼では、対象providerと確認項目を列挙し、未確認の項目を失敗隠しではなく正しい出力として扱います。

教材例：小さなバグの修正

もう一つの未実行例は、空データ時の表示を修正する依頼です。対象component、期待表示、禁止するAPI変更、正常・空・失敗状態のtestを示します。修正前の再現と修正後の検査を分け、testを実行できなければ未実行と返す条件を付けます。

依頼には「ついでに気付いた改善は別メモへ」と書くと、発見の価値を捨てずscopeを守れます。確認者は必要な改善を後から選べます。これにより、元の仕事の完成と、新たに見つかった需要を混同せず、差分を小さくレビューできます。

依頼の品質を測る

同じ案件の旧依頼と新版を人工fixtureで比べ、追加質問、範囲外変更、根拠不足、確認不能な成功主張を数えます。本文の長さや敬語の量は品質指標にしません。依頼の省略で誤ったことが明らかになったら、その条件だけを次版へ追加します。

すべての失敗をpromptで解決しようとすると、環境の接続不良や仕様の不備まで長い指示に押し込みます。入力不足、tool障害、推論誤り、権限拒否、評価の欠落を分け、適切なownerが直す方法へ結びます。完成候補の説明と実物を照合する習慣が、長い宣言より確かな改善になります。

依頼文だけを先にレビューする

実行前の合成レビューでは、作業者が一切質問しなくても、変更可能な範囲と合否を判断できるかを確認します。『いい感じに』『全体を改善』が残る箇所は、読み手が観測できる条件へ書き直します。ただし実装方法まで過剰に指定すると必要な判断を封じるため、必須条件と自由な選択を別段落にします。

失敗教材には、出典のない比較表、受入条件と矛盾する依頼、終わりのない追加調査を置きます。評価するのは依頼を最後まで消化した件数ではなく、矛盾を検知し、許された範囲で完了し、不足があるときに不足を狭く返せたかです。依頼文の版と採用基準を揃えておくと、結果の差を手順変更に結び付けやすくなります。
