Codexで、小さな変更から検証可能に開発する

新機能の年表ではなく、環境の選択・依頼・実装・検証・公開の区切り方を扱います。

最終更新・公式資料確認: 2026-10-13 / ここにある試験例は未実行の教材。実機の対応状況・利用枠は個別確認が必要です。

Codexは、モデル名ではなく開発の実行系

Codexはコードを理解し、編集し、道具を使って確認するためのcoding agentです。CLI、IDE、デスクトップ、クラウドなど入口があり、モデルはその中で推論を担います。現在の公式code generation guideは、Codexで多くの開発作業に最新の汎用モデルを使う方向を案内しています。公式の位置付け。「Codex専用モデルでなければ開発できない」という選択基準は適切ではありません。

一方、モデルが賢くなっても、依存関係、テストデータ、変更権限、公開先を自動で正しく決められるわけではありません。開発で効くのは、対象を再現できることと、変更後に反証できることです。モデル選択はその土台の上で比較します。

どこで動かすかを先に選ぶ

入口向いている使い方（筆者提案）確認したい境界
CLI既存repoの調査、小修正、手元のテスト実行cwd、読み書き範囲、コマンドとnetworkの許可
IDEコードを読みながら変更を選び、差分を見て進める選択contextとプロジェクト全体の関係
デスクトップ複数の仕事や成果を見ながら開発を進めるどのfolder・host・作業版を編集するか
Cloud environment設定済み環境で遠隔・非同期の開発を進めるrepo、依存関係、アクセス設定、結果の受取り
API組込み独自ツールで生成や評価を制御するtool loop、保存、再試行、請求を自分で設計する

CLIは手元のrepoと既存ツールを使う入口で、cloudは再利用する環境を作って選ぶ入口です。CLI公式ガイド / Cloud environmentの入口。手元で動くclientと、モデルを手元で推論することは同義ではありません。

最初の仕事は「一つの再現」から始める

新しいプロジェクトでは、いきなり全面改修を頼まず、構成、起動方法、既存の検証、直近の変更を確認します。既存の未commit変更を「余計なもの」として消さないことも重要です。説明を求める依頼と、変更する依頼を区別すると、調査の途中で意図しない編集が起きる余地を減らせます。

教材例：修正前の限定調査
このrepoの一覧画面で、検索後に項目が消える原因を調べてください。
まだ修正はしません。
入口・関連する状態更新・再現条件・確認に使えるテストを示し、
分かった事実と推測を分けてください。

原因が分かったら、変更する対象と対象外を固定します。仕様が曖昧なら、実装前に現在の動作と期待する動作を比べる小さい例を作ります。AIに仕様の決定まで暗黙に渡すと、テストが新しい思い込みに合わせて書き換えられる危険があります。

実装・検証・レビューを別の問いにする

実装は「何を変えるか」、検証は「期待する現象が起きるか」、レビューは「別の条件を壊していないか」です。同じ担当で進めても、問いは分けられます。影響が大きい変更では、書いていない担当が原依頼と同じ版から読む独立レビューが役立ちます。担当の人数やモデル系統の数だけでは独立性を証明できません。

教材用の完了条件
1. 修正前の版で症状を再現できる
2. 新しい版で症状が消える
3. 空入力と連続操作でも期待する動作を保つ
4. 関係のない画面・保存形式を変更しない
5. 実行した検証と、実行できなかった検証を報告する

テストを追加しただけでは、修正前に失敗した証拠になりません。コードがcompileしただけでは、ユーザーが望んだ動作の確認になりません。また、スクリーンショットを一枚作れても操作全体を検証したことにはなりません。何を反証できる検査なのかを短く説明できることが大切です。

モデル設定は、小さい比較で決める

GPT-6.1 SolはAPI仕様上、reasoning.effortにlow/medium/high/xhigh/maxを持ち、none/minimalは非対応です。tool callingを使うAPIの入口はResponsesです。モデル仕様。アプリの選択肢やアカウントで利用できる設定が、APIと同じとは限りません。

比較は既知の小修正、原因が複数ある不具合、仕様を読む必要がある変更という、異なる仕事で行います。期待動作を満たしたか、意図しない変更、レビュー修正量、総所要時間を残します。難しい一件でうまくいったモデルが、日々の短い作業にも最適とは限りません。高いeffortを常時使うことも、低いeffortで何度も手戻りすることも、測らずに推奨しません。

並列化は、共有資源の分離から

調査を分けるだけなら、各担当が読む対象と返す形式を固定できます。書込を並列化する場合は、ファイルや作業版をexclusiveに割り当て、統合担当だけが共有indexやGitを扱う方法が実務的です。同じファイルの別の節なら安全、という前提も危険です。formatterや全文再生成が他の節を変えることがあるからです。

統合後は個別の成功だけでなく、名前、リンク、型、期限、例の前提が揃うかを確認します。複数担当の同じ未確認情報が一致していても、それは一次根拠の代わりになりません。外部資料の確認日を合わせ、異なる対象の数字を混ぜないことが必要です。

権限を「便利さ」だけで広げない

CLIではpermissionsを選び、activeなsandboxやwrite範囲を確認する操作が案内されています。CLIの境界。プロンプトに「安全に」と書くだけで、技術的なアクセス制限が設置されるわけではありません。資料の読み取り、コード編集、network、外部サービスの作用を区別し、今の仕事に必要な範囲から始めます。

権限拒否は、別のshellやtransportに替えて同じ操作を通す合図ではありません。未実行の操作を明示し、許可された独立の仕事だけを続けます。認証情報は例文、ログ、成果物へ貼らず、公開資料と合成データで試験します。この記事で設定変更や実インストールは行っていません。

GitHubと公開サイトは、別々に読み戻す

localの編集、commit、topic branchのpush、PR、mainへのmerge、サイトへの配備はそれぞれ確認点が違います。「pushしたので公開済み」と省略すると、mainに未mergeなのか、配備が失敗しているのか分かりません。成果の報告にはPRまたはcommitと、閲覧先があるならその確認範囲を残します。

日次更新など別のwriterがいるrepoでは、反映直前にremoteの差分を取り込み、他の更新を残して統合します。force pushや無断resetで競合を消す方法は取らないでください。旧版を参照する読者には、固定commitへのリンクを使うと、main更新後も当時の根拠へ戻れます。
