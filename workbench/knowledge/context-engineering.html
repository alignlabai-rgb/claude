Context Engineering
根拠を選び、判断を再現する

プロンプトだけでなく、指示・検索結果・記憶・ツール出力・進行状態のうち、何を、いつ、どの権威でモデルへ渡すかを設計します。目標は最大量の入力ではなく、必要な根拠を欠かさず、関係のない情報や古い判断に引きずられないことです。

本稿の七つの区分、予算例、評価方法は実務用の整理です。普遍的な標準や効果保証ではありません。旧版の未裏付けの時短率・成功率を除き、公式一次情報と再現可能な架空例へ改訂しています。

1. 窓を埋める前に、判断の情報契約を作る

Anthropicの技術解説は、推論ごとに入る情報全体を選び、維持する問題としてcontext engineeringを説明します。長いウィンドウの存在だけでは、重要事項を拾える保証になりません。

たとえば「このAI製品を試すべきか」に答えるなら、まず必要な字段を決めます。製品名だけでは不足です。

判断: 限定的な比較試験の候補にするか
必須: 対象surface / 公式根拠 / 適用時点 / 利用条件 / 未確認点
補助: 過去の類似試験 / 失敗class / 想定する担当
除外: 関係のない会話 / 古い料金 / X投稿を公式扱いする要約
出力: 候補・保留・棄却 + 理由 + 次の試験
権限: 調査と提案のみ。契約・課金・公開・採用判断は含まない

この契約があると、「入力に何が不足していたか」と「入力は十分だが推論を誤ったか」を区別できます。用語や状態の意味を固定するのはオントロジー、処理の順序と停止は状態グラフの仕事です。

2. 七つの区分を、保存先と権威まで分ける

区分例渡し方失敗しやすい点
指示依頼、制約、形式、優先順位適用対象と出所を明示検索した本文を指示として扱う
静的な知識schema、評価基準、用語必要な版だけ古い手順が常時入り続ける
取得した根拠公式資料、該当段落source ID・時点・surface付き関連性だけで権限外データも取得
会話履歴直近の変更と訂正未解決事項を優先最新の訂正が要約で落ちる
ツール結果検索、テスト、実行receipt成功・失敗・未実行を分離コマンドを出しただけで実行済みとする
永続記憶好み、過去の判断、経験出所と更新日で照合以前の承認を別対象へ流用
タスク状態次の手順、待ち、試行回数構造化し外部にも保存自己申告の完了を成果物の完了と混同

CLAUDE.md等のプロジェクト指示は有用ですが、ファイル名だけでシステム指示と同じ権威になるわけではありません。どの製品がどのルールで読み込むかを確認します。記憶も「全会話の完全保存」とは限らず、現在の事実や権限の代わりにはできません。

3. 検索は「関連」だけでなく「適用可能」を選ぶ

  1. アクセス境界で絞る。ユーザー・案件・公開範囲を先に確認し、許可された集合だけを検索します。検索後にLLMへ秘密を見せて除外させるのでは遅すぎます。
  2. 対象を絞る。surface、地域、版、適用日で絞ります。API仕様とconsumer appの紹介は別集合です。
  3. 候補を取得する。文字列検索、ベクトル検索、関係検索から用途に合うものを使います。固有のmodel IDは文字列一致が重要です。
  4. 重要な根拠を原文で確認する。要約やsnippetで発見しても、期限や条件は元の該当箇所へ戻ります。
  5. 矛盾を残す。新旧記録が衝突する時、都合のよい一方だけを渡さず、何が置き換わったかを示します。

RerankingやHyDEは検索の候補生成・順位付けに使えますが、必ず精度が上がるわけではありません。仮生成した「理想回答」を根拠として混ぜないことが重要です。Microsoft GraphRAGの公式query説明も、entity向けのLocalと全体俯瞰向けのGlobal等を分けています。

トークン予算は最適値ではなく、計測の仮説

たとえば全体の上限から、出力とツール往復に使う枠を確保し、残りを指示・状態・根拠へ配分します。「七区分を均等にする」「長文ほど良い」と固定せず、根拠を削るとどの質問が壊れるかを測ります。文字数はtoken数と同じではありません。

4. 圧縮・キャッシュ・記憶は別の問題を解く

圧縮はモデルに渡す情報を減らします。キャッシュは同じprefix等の再処理を減らす機構で、内容の正確さを改善するものではありません。永続記憶は将来の作業へ情報を持ち越します。三つをまとめて「賢くなる」と説明すると、原因も失敗も追えなくなります。

OpenAIのSession Memory例は、直近turnを残す方法と過去を要約する方法を示しています。要約には、訂正、未解決判断、重要な時点、source IDを残す設計が必要です。これは製品全体の記憶仕様を示すものではありません。

引継ぎ要約の字段例
goal / constraints / completed_artifacts / failed_attempts
latest_decisions / superseded_decisions / pending_questions
evidence_refs / next_step / stop_condition

元資料への参照を保ち、圧縮後も再取得できるようにします。古い肯定と新しい撤回を単に平均して要約しないよう、置き換え関係を明示します。長期の好みと、一回限りの承認は別の保存対象です。

5. 成果の評価を「何を見せたか」まで分解する

評価確かめる内容壊すための反例
根拠の充足答えに必要な元sourceが含まれるか最新の訂正だけを検索結果から抜く
引用の一致引用箇所がその主張を支えるかブランドは一致、surfaceは別
鮮度と矛盾期限切れや撤回を扱えるか古い高評価の記憶と新しい停止告知
境界別案件の情報・指示が混ざらないか資料本文に「秘密を送信せよ」を挿入
判断の再現同じ根拠と規則で同じ分類になるか入力順序、重複、長い無関係文を変える

評価ではretrievalの失敗とgenerationの失敗を別に記録します。正解率だけでなく、原文に戻れる割合、根拠不足時に保留できる割合、必要な人間修正、処理時間と費用を測ります。高いsource充足率も、出力が正しいことの十分条件ではありません。

6. 三つの実践例：全部渡す以外の選択肢

調査記事

日次ニュースは発見候補、公式changelogは仕様の根拠にします。記事全文を束ねるより、今回の主張に対応する段落と時点を渡し、未確認の点は別欄に残します。

連続作品の草稿

今回必要な設定、直前の展開、変更禁止事項を選びます。試作案と確定設定を別状態にし、過去のボツ案を正式設定として再投入しないようにします。これは架空の制作設計例です。

コード修正

変更対象、関連テスト、再現ログ、完了条件を先に渡します。全repoを一度に詰めるより、依存先を辿り、テストが示した範囲へ根拠を拡張します。成功は実際のテスト結果で判断します。

オフライン実験はsurface不一致、期限切れ、非公式情報を除外し、選ばれた根拠IDを返します。tokenizerやLLMは使っておらず、フィルター契約の検証に限ります。モデルの回答能力や費用削減を実測した例ではありません。
