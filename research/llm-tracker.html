まず目的を選び、それからモデルを見る

文章を書く、コードを変える、資料を検索する、動画を作る、常設agentに監視を任せる。この五つは同じ“AI”でも必要条件が違います。Embedの新世代を文章生成の新世代として比べたり、画像入力を動画生成と読んだりすると、導入候補がずれます。以下の表は一社一位のランキングではありません。MetaのMuseとLlamaのように、同じ会社でも異なるfamily・提供面は別行です。

会話appの契約、開発harness、pay-as-you-go API、weightsのローカル配備は別に確認します。weights公開は手元の端末で快適に動く保証でも、APIの利用料金がゼロになる証拠でもありません。逆に、ローカルclientがあることはローカル推論を意味しません。

表の段階をどう読むか

  • CATALOG：公式の現行一覧で確認。特定アカウントでの実応答を保証しない。
  • MIXED：正式提供、preview、app、API、weightsなどが混在。行の注意と個別sourceで切り分ける。
  • PARTNER_ONLY：partnerのhosted catalogで確認。原厂のGA・weights・直接APIへ読み替えない。
  • HISTORICAL_REFERENCE / WEIGHTS_REFERENCE：取得できたreleaseやcardを示す。2026年最新familyを網羅したとの主張ではない。
  • FRESHNESS_GAP：公式面を確認しても現行modelを確定できなかった。空欄を旧名で埋めない。

“確認日が今日”と“modelが今日発表された”は違います。予定日の経過だけで停止済みとしません。英語のLive、GA、Previewも、API・weights・appで作用範囲が違う場合があります。

三つの読み方：速報から試験へ

1. 新しいモデル名を見たとき

ニュースやXの投稿を発見源として使い、まず名前・原厂・提供面を一致させます。たとえばKimi K2.8 Previewのpartner掲載から、Kimi原厂APIや公開weightsの利用可能性を決めません。まだ根拠が足りないなら候補に置くこと自体は有益です。確認済みに昇格しないことが重要です。

2. 導入を比較するとき

同じ公開・合成fixtureで、必要な入力、出力、tool protocol、保存条件、費用上限、棄却条件を固定します。モデル別の宣伝benchmarkを同一測定として横に並べません。一つの成功例を、複数ジャンルや本番品質の証明にしないでください。

3. 既存運用を守るとき

新しいものだけでなく、aliasの変更、旧endpointの停止、preview更新、cache料金や計算量上限を見ます。移行の期限は“この仕事がどこを使っているか”と照合して初めて意味を持ちます。使っていないAPIの停止を大騒ぎする必要も、使っている旧aliasの変更を見逃す理由もありません。

情報を成果へ変える最小packet

対象: 提供者 / model ID / surface
根拠: official URL / 公表日 / 確認日
影響: 既存のどの用途に、何が変わるか
未確認: account / region / license / runtime
限定試験: 合成入力と合格・棄却条件
提案: 対応するdomain担当に検討を依頼
作用: このpacket自体は契約・導入・公開を実行しない

組織への共有は記事の長さではなく、受け手が次の一件を判断できるかで評価します。routing、意味の判断、実行許可を別に扱う方法はニュースを組織の能力へ変える解説で詳しく扱います。
