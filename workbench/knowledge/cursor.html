Cursor — エージェントの速度をレビュー可能な変更へ変える

Cursorはモデル名ではなく、モデル・instruction・toolを統合してコードを変更する開発環境です。便利さの中心は編集から実行までのloopですが、同じloopが意図しない副作用も生みます。最新機能を全部有効にする前に、対象workspace、実行境界、reviewの出口を決めましょう。

最終更新: 2026-10-13 · 公式資料の確認日。提案は実行・採用の報告ではありません。

モデルとharnessは別の選択

公式説明はAgentをinstruction、tool、選択したmodelの三要素で説明しています。Agentはファイルの探索と編集、terminal実行、browserによる確認などを組み合わせます。モデルが同じでも渡すcontextやtoolが違えば結果は変わります。公式: Agent overview

選定では「何のモデルを使えるか」に加え、projectをどう読むか、失敗した時にどう止まるか、変更をどうreviewするかを見ます。ローカルのeditorとCloud Agentsも実行場所が違います。手元にUIがあることは、model inferenceやすべてのデータ処理が手元で完結することを意味しません。

2026年10月の見直し点: read boundary

現行Run Modes資料には、Cursor 3.23以降のRead Accessが記載されています。SystemとWorkspaceの選択があり、Workspaceは外側の読み取りに承認とallowlistを使います。ただしRun Everythingではこの制御は適用されません。古い「承認不要なら効率的」という案内だけで現在の境界を判断しないでください。公式: Read AccessとRun Modes

この設定を使っても、workspace内のsecretを自動で無害にするわけではありません。agentに必要な小さいprojectを開き、秘密、個人ログ、browser profileを作業対象から分けることが先です。自動判定やallowlistは万能なsecurity boundaryではなく、設定と実行場所の確認が必要です。

Rulesは作業の地図、実行権限は別

Project Rulesは.cursor/rulesで管理でき、単純なinstructionにはAGENTS.mdも使えます。現行資料はrootとsubdirectoryのAGENTS.mdを扱い、より具体的な範囲のinstructionを組み合わせます。公式: Rules

有益なruleは「丁寧に」より、変更してよいsurface、生成物の保存先、test command、禁止する外部effectを示すものです。rulesを増やし続けると矛盾や古い指示も増えます。実際のconfigと一致する短いruleから始め、文書の指示をOSやsandboxによる権限制限の代用にはしないでください。

# 教材用のproject instruction
目的: 公開HTMLの読みやすさを直す。
範囲: 指定HTMLと専用CSSだけ。
維持: source URLと事実の意味を変えない。
検証: diff、リンク、mobile表示。
停止: credential、公開deploy、課金操作が必要になった時。

一件の変更を最後まで見える形で進める

  1. 現状の画面・test・diffを確認し、成功条件を先に書く。
  2. Agentへ一件だけ依頼し、必要なsource fileを指定する。
  3. 実行前にcommandと対象を読む。設定変更や外部アクセスは意味を確認する。
  4. 保存された差分とtest出力を見る。Agentの「完了」をtest成功と同義にしない。
  5. 別の問いでreviewし、残る不具合と戻し方を整理する。

たとえば教材用のformで「空文字を拒否する」という依頼なら、正常入力、空文字、空白だけ、境界長をtestにします。見た目のscreen shotだけでは入力検証を確認できません。上記は設計例であり、Cursorで実行済みの結果ではありません。

起こりやすい失敗を境界から見る

公式security資料はprompt injectionやhallucinationの可能性、workspace変更の即時保存、auto-reloadによるreview前の実行に注意を示しています。外部READMEやWeb情報を読むagentは、その内容を正しい命令と取り違える可能性があります。資料は資料として扱い、作業の許可範囲を変えないことが重要です。公式: Agent Security

並列agentでは速さよりファイルownerが重要です。同じ設定を複数agentが直す、formatterと実装が競合する、local testがcloud環境と違う、という失敗を区別します。Cloud利用では実行場所、network、secret注入、artifact公開範囲を契約と設定で別途確認します。本ページでは保持期間や各planの値を未確認のまま断定していません。

効果を測り、更新を追う

評価するのは提案数ではなく、review後に採用できた変更、必要な人間修正、失敗の再現性です。同じ小さな課題を既存editorでの作業と比較し、速さだけでなく戻しやすさも記録します。価格、対応model、versionは変動するので、導入時は公式changelogと自分のplanを確認します。利用者の契約や実行環境はここでは検査していません。
