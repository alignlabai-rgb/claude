Claude Code実践 — 任せる範囲と検証を設計する

現在の用途から再構成した新版です。過去のニュースや旧仕様は混在させず、刷新前の全文（固定旧版）に保存しています。以下の教材例・評価案は未実行です。

対話でコードを書く道具から、開発作業を閉じる道具へ

Claude Codeは、ソースを読み、複数ファイルを編集し、コマンドを実行して開発ツールと連携するエージェント型の開発環境です。terminal、IDE、desktop、webという提供面があります。公式Overview。しかし、どの面で使っても「変更を作った」と「正しく動くことを確認した」と「本番へ反映した」は別の結果です。

価値を出す出発点は、巨大な依頼を丸投げすることではありません。入力の実物、変更可能な範囲、確認手順、停止する境界を一件にまとめ、実装と検証が結び付いた小さな完成単位を作ります。本記事は実際の設定変更・インストール・provider呼び出しを行った記録ではなく、公式仕様に基づく運用ガイドです。

モデルは仕事に応じて選びます。現在のCodeで何が選べるかは利用面、アカウント、管理設定に依存します。モデルの思考を深くするeffortと、コマンドを実行するpermission modeを混同しないでください。Opusであることはadministrator権限や外部送信の許可を意味しません。

まず五つの層を分ける

層役割使いどころできないこと
CLAUDE.md案件の事実・目的・作法を伝えるbuild/testの入口、避けたい設計書いた禁止事項だけでOS権限を遮断する
Skills再利用する手順や知識を必要時に読む繰り返すレビューや制作手順MCP接続や契約を自動的に与える
MCP外部ツール・データへ接続するissue、database、APIの情報や操作接続しただけで安全な操作を保証する
Hooks処理イベントに応じて動作する検査、通知、記録、機械的な制御任意のhookを安全と見なす
Subagents独立した文脈で限定作業を行う大量ログの調査、分野別レビュー人数だけで独立監査や正しさを保証する

機能の根拠: Memory、Skills、MCP、Hooks、Subagents。「使いどころ」と「できないこと」は筆者の設計整理です。

SkillsはSKILL.mdと補助資料・script等を含められ、必要に応じて呼び出す手順です。MCPは接続の仕組みなので、両者を同じものとして「Skills (MCP)」と呼びません。例えばレビューSkillが確認する順序を定義し、MCPがissue本文を読む、という組み合わせは可能ですが、読み取りと書き込みの権限は別に点検します。

Hooksにはshell command、HTTP、MCP、prompt等の種類があります。特にcommand hookは利用者の権限でファイルを変更・削除・取得できるため、便利な短い設定でも実行コードとしてレビューします。Hooksの種類とDisclaimer。秘密を含むログを自動送信するhookは、指示の改善とは別の外部作用です。

最初の一件：小さな表示バグを最後まで直す

以下は教材用の未実行手順です。既存Webアプリの「空の一覧で説明文が表示されない」不具合を想定します。追加機能やデザイン全面刷新は範囲外とし、既存の利用者変更を消さずに、再現・最小修正・テスト・差分説明までを閉じます。

  1. 開始状態を読む。Git状態、対象ファイル、README、既存テストと指示書を確認する。未commit変更があれば自分の変更と区別する。
  2. 不具合を再現条件へ変える。空配列の入力、期待表示、現在の表示を短く書く。画面で未確認なら、画面確認済みとは記録しない。
  3. 先に修正方針を限定する。関連componentとテストだけを対象にする。共有styleや依存更新が必要なら理由を明示する。
  4. 小さく実装する。関係のない整形や命名変更を混ぜない。修正対象が変わったら完了条件も照合する。
  5. 反例を入れて確認する。空、正常、読み込み中、取得失敗を別々に試す。変更前から失敗するテストと新しい失敗を分ける。
  6. 差分で引き渡す。変更した箇所、実行した検査、未確認、残る制約をまとめる。deployやpushは別の指示がある場合だけ行う。
教材用依頼例:
空の一覧で「まだ項目はありません」を表示してください。
対象は一覧componentと既存テストです。API仕様・依存関係は変えません。
まず既存仕様と再現方法を確認し、最小差分で修正してください。
テスト結果と未確認を区別し、公開・送信は行わないでください。

このような完了条件は、モデルの印象的な説明より検査しやすく、後から別の担当が続けられます。作業途中に「ついでに認証も改善」と広げるのは、意図した価値を増やすとは限りません。変更の相互作用が増え、reviewと復旧の負担を大きくするためです。

承認を減らすことと、権限を消すことは違う

公式permission modeにはManual、acceptEdits、Plan、auto、dontAsk、bypassPermissions等があります。autoはclassifierが行動を確認し、dontAskは通常ならpromptになる呼び出しを拒否します。bypassPermissionsは広くpromptを省略するため、公式は損害を起こせない隔離環境での使用を求めています。Permission modes

したがって「人に毎回尋ねない」という要望に対し、すべての権限を外す必要はありません。既に許可された低リスクな検査を限定的に通し、秘密、支出、外部送信、破壊的変更などを別の判断として残す設計が可能です。具体的な許可は利用環境の管理者が決めます。本文の例は読者の設定を上書きする推奨ではありません。

CLAUDE.mdはモデルへの行動指示であり、実行を強制的に遮断する層ではありません。permission、sandbox、OSや実際の接続権限を分けます。さらにBashのdeny patternは、同じprogramの異なる呼び出し表記をすべて遮断するsecurity boundaryではないと公式が注意しています。Permission rulesとBashの限界。拒否された操作を別表記や別ツールで再演するのは、安全な自律運用ではありません。

並列化は、仕事を分けてから行う

Subagentsは専用context、指示、tool access、permissionを持つ補助作業者です。大きなログや資料の探索を切り離す用途に向きます。公式Subagents。しかしPlanner=Opus、Worker=Sonnet、Reviewer=Haikuという固定組織が標準で存在するわけではありません。

未実行の分担例として、Aはログから失敗時刻を抽出、Bは関連テストの不足をread-onlyで調査、親は対象componentの変更を所有する、とします。同じファイルを三者が自由に書く分担ではなく、出力の範囲、返す証拠、編集ownerを先に決めます。review役には実装者の結論だけでなく、対象差分と反例を渡し、指摘の根拠を求めます。

人数を増やしても依存する作業は早くなりません。調査の返答が大量になるほど統合時間と文脈消費が増え、同じ思い込みを共有することもあります。並列化の評価では最終修正までの時間、重複調査、競合差分、漏れた反例、採用できた指摘を測ります。workerの稼働数は価値の指標にしません。

費用・継続・品質を別々に記録する

/usageは現在の利用状況を確認する入口です。APIのsession費用は推定表示で、正式請求はConsole側、subscription利用者のsession換算額はそのまま請求額を意味しません。公式Usageと費用の読み方。長いsession、過剰な資料、並列worker、繰り返す失敗はすべて使用量に影響します。

運用評価では「何トークン使ったか」に加え、完成した差分の有用性、人による訂正量、再現試験、未確認、再開可能な記録を残します。調査だけで終了した場合と修正済みの場合、testが通った場合と表示を見た場合を区別してください。モデルやCodeが更新されたときは、固定の小案件で挙動とpermissionを再確認し、昔のcommand一覧を無検証で現在仕様へ持ち越さないことが重要です。
