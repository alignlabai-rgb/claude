MCP運用設計 — 障害・更新・権限を閉じる

初回接続後の保守を、tool契約と結果照合を軸に設計します。

旧情報は固定旧版の全文へ分離しています。以下の例・試験案は未実行の教材です。

本番の課題はserver数ではない

外部systemへの接続が増えると、認証、tool schema、検索意味、network、利用枠、保存方針の依存が増えます。一つの接続が動いても、全部を同じ安全水準にできたとは言えません。運用では案件に必要なtoolだけを選び、接続を外した場合に何が止まるかを示します。

Claude CodeのMCP公式referenceはtransport、scope、tool search、managed configuration等を扱います。MCP reference。細部はインストール版と管理者の設定で確認し、旧記事の設定断片を全環境へ一括適用しないでください。

tool契約を読む

各toolについて、入力fieldの意味、未指定の既定値、返す対象ID、部分結果、pagination、error、副作用を点検します。同じsearchという名前でも、全件検索か最近の一部かで結論が変わります。表示titleだけで対象を決めず、repository・record ID・版等で同一性を確認します。

未実行例では、人工document十件に似た名前と異なる時点の資料を入れます。一頁しか返さない結果から全件を見たと主張しないか、空結果を確定不存在と扱わないかを試します。read-onlyで意味の検査を済ませてから、必要な書込toolの候補を別に評価します。

permissionとscopeの照合

project、local、user、managedの適用差は一つの設定だけでは説明できません。Settings／Permissions。機械の操作権限と、今回の仕事で与えられた許可を別に考えます。読み取り可能な資料でも公開してよいとは限りません。

組織で使う場合、接続を有効にする人、対象データのowner、出力を採用する人は一致しないことがあります。管理者がtoolを導入したことを、業務の採用や外部公開の許可と見なさず、実際の依頼のscopeで作用を限定します。接続先の権限を解決するためにcredentialやACLを勝手に変更しません。

結果不明は、再実行の前に照合する

timeout後に操作が実行されたか不明な場合があります。例えばlabel追加は重複を許せても、message送信は二重送信が問題になります。操作ID、対象ID、期待差分、receipt、結果照会を使い、安全なretryかを決めます。これは未実行の設計例であり、MCPが自動でexactly-onceを保証するという説明ではありません。

途中失敗ではどこまで完了したかを分け、全面再実行を既定にしません。認証失敗は認証owner、schema不整合は接続maintainer、意味的な不足は業務ownerへ返します。原因を分けると、同じ拒否を別経路へ繰り返す行動を避け、必要な修正だけを選べます。

更新と供給元のリスク

serverの追加や更新はソフトウェア依存の変更です。提供元、version、更新差分、必要permission、外部通信先をレビューします。コミュニティで人気のserverだからといって、秘密を渡す許可や業務の安全性は証明されません。pluginを通じた配布の場合も中身を点検します。

tool descriptionの変更は、modelがどのtoolを選ぶかへ影響します。機能追加だけでなく、削除、名前変更、入力の意味変更、出力の欠落を回帰試験へ入れます。小さい人工fixtureを維持すれば、更新によって以前の案件が壊れたかを評価できます。

保守の価値を測る

確認するのは呼出し件数ではなく、情報取得から利用までの正確さです。誤対象、抜けたpagination、出典漏れ、失敗の隠蔽、訂正時間を記録します。正常応答を返すtoolと、利用者の目的を達成するtoolは違うため、完成した実物と元資料を照合します。

導入後も使われない接続は、停止候補として扱います。保守の手間が価値を上回る場合、手動処理へ戻す判断も成功です。戻し方は接続解除、依存した手順の代替、未完了の照合を含め、保存データの削除やcredential変更と混同せずownerが選びます。

運用変更の差分を評価する

接続先の版が変わった教材では、成功応答だけでなく、空の一覧、途中のページ、権限不足、重複した識別子を再投入します。比較するのはJSONの見た目ではなく、欠落を欠落として残せるか、同じ資料を二重採用しないか、以前の出典へ戻れるかです。

一つの利用者だけが成功したから全利用者へ展開可能と判断しません。権限、資料の種類、最大件数など適用条件を記し、範囲外は未評価として残します。廃止時には依存する方法と参照先を先に把握し、代替がないまま接続名だけを消す事故を避けます。これは運用設計の提案です。
