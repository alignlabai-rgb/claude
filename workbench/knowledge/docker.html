Docker — 再現できる実行環境と境界を設計する

Dockerを使う価値は、AIが作ったコードを何でも安全に実行できることではありません。依存関係と実行条件を持ち運び、失敗を再現しやすくすることです。image・container・永続データ・公開portを分ければ、制作ツールの検証も壊しにくくなります。

最終更新: 2026-10-13 · 公式資料の確認日。手順例は未実行の教材です。

imageは設計された環境、containerは実行中のprocess

imageはアプリと依存ファイルを含む実行用の元データです。containerはそれから起動する隔離されたprocessで、通常のVMのように一台分のOS kernelを毎回持つものではありません。複数containerはkernelを共有します。Mac上でLinux containerを使う場合にはDesktop側のLinux環境が関わるため、MacのGPUやdeviceがそのまま同じ条件で見えると考えないでください。公式: containerとVM / Desktop FAQ

AIツールを隔離したい時も、hostの全フォルダ、Docker socket、認証情報を渡せば境界は弱くなります。container化と最小権限は別の設計です。初回は公開データ、作業用フォルダ、必要なnetworkだけで試すのが筆者の提案です。

何を残すかでstorageを選ぶ

置き場所用途失敗しやすい点
container内の書き込み層捨ててよい一時ファイルcontainer削除で失う
bind mounthost上の入力・成果物を共有hostファイルも変更される
named volumeDBなど継続するデータ場所が見えにくくbackupを忘れる

bind mountは既定で書き込み可能です。入力しか要らないならread-onlyを明示します。既存のcontainer内ディレクトリにmountすると元の内容が隠れるため、「imageにはファイルがあるのに見えない」症状も起きます。公式: bind mountの意味と制約

静的サイトの教材例: 公開範囲を小さくする

以下は実行済みの成功報告ではなく、公開してよいHTMLだけを含む./siteを用意した場合のCompose教材例です。imageのtagは更新で中身が変わり得るので、継続運用では検証済みdigestも記録します。

services:
  preview:
    image: nginx:stable-alpine
    ports:
      - "127.0.0.1:8080:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro

localhostへportを限定し、入力をread-onlyで渡します。docker compose configで解釈された設定を読む、起動後にdocker compose psとlogsを確認する、表示を検査する、停止する、という順です。設定出力に秘密が含まれる時は保存先にも注意します。Composeはservices・network・volumesを一つのYAMLで定義する道具です。公式: Docker Compose

この例は認証、TLS、本番の権限管理を含みません。ローカルpreviewの成功をそのままinternet公開の準備完了とは扱わないでください。hostとcontainerで同じ「localhost」が別の相手を指す問題にも注意します。Desktopからhost側serviceへ接続する時は公式のhost.docker.internalの説明を確認します。公式: hostへの接続

AI制作で起きる四つの失敗

  • 再現性: latestだけ記録し、後日別の依存関係になる。image digest、lockfile、architectureを残す。
  • データ損失: 「掃除」でvolumeまで消す。生成物とDBの保存場所、復元手順を先に決める。
  • 境界漏れ: home全体をmountし、agentが不要な秘密まで読める。許可する入出力を最小化する。
  • 性能誤認: native runtimeの速度とcontainer、CPUとGPU、ARMとx86を同一視する。実行条件を別に測る。

imageの出所と更新履歴も依存関係です。名前が有名でも、第三者imageにはその第三者のコードが含まれます。AIが提案したinstall scriptやDockerfileを、隔離されているという理由だけで未確認のまま実行しないでください。

導入するか、使わないか

複数service、複数人、CIと同じ環境が必要ならDockerが有力です。単一の小さなscript、Macのnative GPU機能が主目的、依存関係が少ない作業ならvenvやnative runtimeの方が単純な場合もあります。製品名ではなく、再現に必要な境界で選びます。

評価は新しい環境で同じ入力が動くか、host側の不要ファイルへ触れないか、停止後も成果物が残るか、backupから戻せるかを確認します。本ページではcontainerの起動、image取得、Desktop契約やGPU性能の実測を行っていません。
