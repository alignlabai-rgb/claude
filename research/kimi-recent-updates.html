Kimi現況 — K3・K2.7 Code・終了モデルの移行

2026-10-13に公式model list、K3 API guide、公開repositoryを照合しました。モデルの世代、用途、履歴契約、終了済みIDを整理し、Webアプリの機能をAPI能力と混同しない現況ページです。

1. 現行APIの選択

公式model listはkimi-k3、kimi-k2.7-code、kimi-k2.7-code-highspeed、kimi-k2.6を掲載しています。K3はflagship、K2.7 Codeはcoding向け、K2.6は視覚・テキストを扱う一般用途として説明されています。highspeedという名前だけで、全taskで最適と判断しません。公式model list

別surfaceとして、Tencent TokenHubの現行catalogにはkimi-k2.8-previewが掲載されています。これはTencent hosted previewの確認であり、Moonshot直営APIや公開weightsの提供を確定したものではありません。上記の直営model listと一枚に混ぜず、必要な接続先で確認します。TokenHub公式catalog

選択では新しさだけでなく、必要modality、履歴の長さ、tool call、許容待ち時間を見ます。たとえば公開文書の抽出では、長い推論よりsource位置を正しく返すことが重要です。コード修正では会話の自然さよりpatchとtest結果の整合が重要になります。

2. 終了IDを新しい本文から外す

公式listはKimi K2.5とmoonshot-v1系列を2026年8月31日、K2系列を5月25日に終了したと記載しています。旧modelへの手順は履歴へ分離し、現在の利用案に含めません。v1のautoやvision-previewも同じ終了案内の対象です。Deprecated Models

移行はIDの置換だけで終えません。過去の試験の入力形式、thinking設定、tool履歴、context処理を棚卸しします。古い比較表に良い数字があっても、終了したAPIを新規採用候補へ戻さないようにします。過去の記事は固定履歴で読むことができ、当時の判断の理由を失いません。

3. K3で変わる履歴の扱い

K3は常時thinkingで、effortはlow/high/max。multi-turnとtool利用ではassistant message全体を保持して次requestへ戻す契約があります。表示用contentだけへ削る実装を移行すると、reasoningやtool callsの対応が失われます。公式Model Usage

本ハブの設計提案は、API状態と読者向け答えを分けることです。前者は再開に必要な構造を保存し、後者は結論、source、未確認点を短く渡します。完全履歴を保持することと、機密を全員へ共有することは違うため、保持期限と閲覧者も別に設計します。

圧縮やmemory生成を使う場合、tool call ID、未完了task、採用済み条件を壊していないか確認します。長いcontextに入るから全ログを無選別に投げるのではなく、taskの境界と必要な原文を整理して渡します。

4. 視覚・構造化出力の接続条件

K3 quickstartは画像content配列、動画file参照、structured outputを説明します。最終JSONとしてparseするのはmessage.contentで、reasoning文字列ではありません。tool実行後には完全assistant messageと対応するtool resultを戻します。公式API guide

画面の検査を試すなら、観察した事実、推定した原因、提案する修正を別欄にします。ボタンが見えることはクリックが成功した証拠ではありません。視覚的な不具合と動作testを分離して、修正後の画像を同じ版へ紐付けます。

5. K3 weightsとアプリの境界

公式repositoryはfull weightsをKimi K3 Licenseで公開し、API・推論framework・Kimi Codeの入口を説明します。以前の別modelのlicenseを引き継がず、K3固有条件を確認します。Deployment・License

Web上でスライドや文書が完成することは、base modelだけの能力ではありません。検索、編集、ファイル変換、UI、agent loopを含む製品体験です。API評価とアプリ完成物評価は別に設計し、自前推論も第三の運用候補として扱います。

local可動性はweights、量子化、cache、runtime、分散構成に依存します。MoEのactive規模を必要memoryへ直接変換せず、対象artifactを固定して段階的に試験します。最大contextの宣伝を、手元での安定稼働や長時間task成功の保証に変えません。

6. 次の実務試験と未確認

筆者提案は、公開資料をもとに一つの短い解説と検証用表を作る試験です。最初にsourceを揃え、抽出、原稿、照合を区切り、途中成果と不足を残します。最後まで生成できたことではなく、途中で止まっても同じ仕事を二重実行せず再開できることを評価します。

料金、地域、account rate limit、Web全機能の利用可否はこの確認から全員共通の値として断定しません。K3がproviderの最高性能という説明は、自分のtaskで最高という独立証拠ではありません。本ページは資料照合と試験提案で、provider利用、契約、組織採用を行っていません。
