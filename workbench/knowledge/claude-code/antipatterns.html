Claude Codeの失敗パターン — 原因を修正へ結ぶ

見かけの成功と実物の不達を分け、同じ失敗を繰り返さない方法に変えます。

旧情報は固定旧版の全文へ分離しています。以下の例・試験案は未実行の教材です。

失敗をmodelの賢さ一つへ帰さない

入力がない、toolが使えない、permissionが拒否する、仕様が違う、推論が誤る、検査が抜ける、という異なる失敗を分けます。ひとつの「AIが悪い」にまとめると、入力や環境を改善できません。まず対象版、期待、実結果、根拠を残します。

公式best practicesも明確な検証条件や文脈管理を重視します。Best practices。ここでの分類は筆者の方法案であり、失敗を隠すためにlabelを変えるものではありません。実物を直すか、次の方法へ再利用するかをownerが決めます。

パターン1：成功の文章で閉じる

「全部確認しました」という返答があっても、実行logがない、testが途中で止まった、画面を見ていない可能性があります。完成条件はdiff、test、出典、表示等の対象を指定します。起動、正常終了、内容合格、採用を別に扱います。

未実行の反例では、空の入力で要約が生成される、test commandが存在しない、部分結果しか取得できない状況を作ります。正しい反応は未確認や不足を返すことです。無理に文章を埋めて成功を作る動作を、合格の条件から除外します。

パターン2：不足を推測で埋める

取得できない資料や存在しない設定を、過去の記憶で補うと古い情報が現在の結論へ混ざります。資料ID、取得日、対象面を添え、未取得は未確認とします。readerが必要な再確認を選べるように、どの項目が不足したかを具体化します。

データが足りないこととtaskが難しいことは違います。上位modelや高effortへ移す前に、欠けた資料や曖昧な単位を直します。人工fixtureで不足を検出できるなら、長いpromptを追加するより小さな入力検査が役立つ場合があります。

パターン3：scopeが膨らむ

小さなバグ修正で依存更新や全面整形を混ぜると、元の不具合の原因と差分が分からなくなります。改善案は別の候補へ残し、変更対象を限定します。高品質の追加作業であっても、依頼の許可範囲に入るとは限りません。

reviewで見るのは技術的に動くかに加え、必要な変更だけかです。元のtest、追加反例、共通消費者を照合し、機能が増えたことを完成として数えません。新しい仕事の需要があるなら、既存案件の安全な区切りから別に選びます。

パターン4：同じ作用を再実行する

network timeout後に結果不明なのにmessage送信や外部変更を再演すると重複します。開始のreceiptと完成のreceiptを分け、対象ID・操作ID・外部状態を照合します。permission拒否を別command表記へ迂回することも、正常なretryではありません。

Bash patternはprogramのすべての呼び方を遮断するsecurity boundaryではないと公式が注意しています。Permission rulesの限界。モデルが別経路を思いついたからと、拒否理由を消して実行範囲を広げないようにします。

パターン5：rewindをbackupと思う

checkpointは外部作用の復旧や全ファイルのbackupではありません。Bashの変更、他session、通常のsubagent編集等に制約があります。Checkpoint limitations。戻せる範囲と保存した原本を別に考え、唯一の資料を直接書き換えない方法にします。

未実行の試験では、編集toolの差分とshellによる生成fileを分け、復旧対象の違いを確認します。作業の再開もconversationの復元と結果の復旧を分けます。安全のための記録があることは、restoreが検証済みという意味ではありません。

パターン6：並列化が統合を壊す

複数workerが同じfileを編集し、shared portやDBへ作用する分担は競合を起こします。排他的な対象と出力契約を先に作り、依存する工程は順に進めます。worker数を増やす前に単独baselineで完成条件を確認します。

失敗から残すのは長い日誌ではなく、人工入力、該当版、反例、直した条件、適用限界です。次の案件で同じclassを検出できたら方法の価値が現れます。件数やtoken消費を成果へ換算せず、訂正が減り、利用者が使える完成物が増えたかを確認します。

失敗記録の最小単位

一件の失敗を残すなら、期待した結果、実際の証跡、最初にずれた判断、次の試験条件を一つずつ書きます。長い会話全文を貼ることより、他の人が同じ種類の失敗を試せる入力と判定条件が重要です。実データや秘密を再利用せず、問題の構造だけを合成ケースへ移します。

直した後は『今回はうまくいった』で閉じず、以前の失敗ケースを含む複数の入力で境界を確認します。改善が特定の入力にだけ効いた場合は適用範囲を狭く記し、万能なプロンプトへ一般化しません。反例を残すことが、成功談だけでは見えない方法の限界を引き継ぐ手段になります。
