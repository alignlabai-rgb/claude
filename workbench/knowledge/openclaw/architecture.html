The Recursive Architecture

Understanding the OODA Loop

OpenClaw は、単なる「チャットボット」ではありません。
それは、目標が達成されるまで無限に自己対話を繰り返す再帰的ループ・プログラムです。

The OODA Loop

軍事戦略で用いられる OODA (Observe-Orient-Decide-Act) ループが、そのまま実装されています。

┌─────────────────────────────────────────────────────────────┐ │ OBJECTIVE │ │ "このリポジトリの全テストを通るように修正せよ" │ └───────────────────────────┬─────────────────────────────────┘ │ ┌───────▼───────┐ ┌───────────────┤ 1. OBSERVE │ (環境認識) │ │ 「現在のエラーログを見る」 │ └───────┬───────┘ │ │ │ ┌───────▼───────┐ │ │ 2. ORIENT │ (状況判断) │ │ 「これは非同期処理のタイミング問題だ」 │ └───────┬───────┘ │ │ ┌──────┴───────┐ ┌───────▼───────┐ │ 4. ACT │◄──────┤ 3. DECIDE │ (意思決定) │ ツール実行 │ │ 「wait時間を増やしてリトライしよう」 └──────────────┘ └───────────────┘ │ ▼ (New State / New Logs) ──► Loop Back to OBSERVE

1. Observe (観測)

エージェントは盲目です。ls, cat, browser.screenshot などのツールを使わない限り、世界が見えません。
OpenClawは最初のステップで必ず「現状分析」のためのコマンドを乱射します。

2. Orient (方向付け/思考)

観測結果（ツール出力）を元に、内部で推論（Reasoning）を行います。
「ファイルAを修正したのにエラーが変わらない...ということは、原因はファイルBにあるのでは？」といった仮説構築フェーズです。

3. Decide (決定)

仮説に基づき、次に行うべき「たった一つの行動」を決定します。
「ファイルを全部書き換える」といった無謀な計画ではなく、検証可能な最小の一手を打ちます。

4. Act (行動)

実際にファイルシステムやブラウザに対し、副作用のある操作（Write/Click）を実行します。
この結果が、次のループの「観測」対象となります。

State Management

この無限ループを支えているのが "Scratchpad" (思考ノート) です。
エージェントは各ステップごとに、自分の思考過程を隠しファイル（またはメモリ上）に追記していきます。

Step 15: - 試したこと: src/utils.ts の修正 - 結果: 失敗 (Error: Timeout) - 次の仮説: タイムアウト設定が短すぎる - 次の行動: .env の TIMEOUT 値を確認する

これにより、Operator（あなた）は後から「彼がなぜその修正をしたのか」を完全に追跡（Audit）できるのです。

Tool System（ツールシステム）

OpenClaw がデフォルトで持つツール群は、エージェントが世界と相互作用する「手足」です。 各ツールは副作用の大きさによってリスクが異なるため、副作用の小さいツールを優先して使う設計になっています。

ツール 説明 副作用 代表的な使用例
read_file(path) ファイルを読み込む なし コードを理解する・構造を把握する
list_dir(path) ディレクトリ一覧を取得する なし プロジェクト構造を把握する
write_file(path, content) ファイルを書き換える（上書き） 書き込み 実装・修正・ドキュメント生成
bash(command) シェルコマンドを実行する 高リスク テスト実行・ビルド・パッケージ操作
browser_navigate(url) ブラウザで URL を開く 外部通信 Web 上の資料を確認する・API ドキュメントを読む
browser_screenshot() 現在の画面をキャプチャする なし UI の表示状態を確認する・レイアウトのデバッグ
mcp_call(server, tool, args) MCP サーバーのツールを呼び出す 外部通信 GitHub / Slack / DB など外部 API との連携
ツール選択の原則: 最小副作用

エージェントは read > write > bash の順で、より副作用の小さいツールを選ぶよう設計されています。 「まず読んで理解し、最小限だけ書き、どうしても必要なときだけシェルを叩く」というアプローチが 予測可能な動作と安全性を両立させます。

Mission の Constraints に --read-only を指定すると、分析フェーズで write ツールを完全に封じることができます。

カスタムツールの追加

OpenClaw は MCP（Model Context Protocol）経由でツールを拡張できます。 .claude/settings.json の mcpServers セクションにサーバーを追加すると、 そのサーバーが提供するツールが自動的にエージェントから利用可能になります。

# .claude/settings.json の例 { "mcpServers": { "github": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"], "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" } }, "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "/workspace"] } } }

Multi-Agent Coordination（マルチエージェント協調）

複雑なプロジェクトでは、単一エージェントに全作業を任せるより、 複数の OpenClaw インスタンスが役割分担する設計が効果的です。 以下の3パターンが代表的な協調アーキテクチャです。

Orchestrator / Worker

1つのメインエージェントが全体計画を立て、複数ワーカーに作業を分配する。ワーカーは独立したサブタスクを並列実行する。

Blackboard パターン

共有メモリファイル（.agent/shared-state.md）を黒板として、複数エージェントが読み書きして情報を交換する。

A2A Protocol 連携

他フレームワーク（MAF / LangGraph）のエージェントと A2A プロトコルでハンドオフし、異種エージェントを協調させる。

Orchestrator / Worker パターンの実装例

# Orchestrator に投入する Mission ファイル # Mission: フルスタック機能実装（オーケストレーション） ## 1. Objective 検索機能を並列開発する。フロントエンドとバックエンドを同時に実装し、 最後に統合テストで接続を確認する。 ## 2. Sub-tasks - [Worker A] フロントエンド実装: missions/frontend-search.md - [Worker B] バックエンド実装: missions/backend-search.md - [Integration] Worker A + B 完了後: missions/integration-test.md ## 3. Coordination - Worker A / B は .agent/shared-state.md に API 仕様を記録してから実装開始 - どちらかが API 仕様を変更する場合は shared-state.md を先に更新する ## 4. Definition of Done - [ ] フロントエンドとバックエンドの統合テストが PASS する - [ ] shared-state.md に最終 API 仕様が記録されている
# 実行コマンド（Orchestrator モード） $ openclaw run orchestration-mission.md --orchestrate \ --max-workers 2 \ --shared-state .agent/shared-state.md

Blackboard パターン（共有状態ファイル）

# .agent/shared-state.md の構造例 # Shared State ## API 仕様（Worker B が記録 → Worker A が参照） - POST /api/search - Request: { query: string, limit?: number } - Response: { items: Item[], total: number } ## 完了フラグ - [x] Worker B: バックエンド実装完了 - [ ] Worker A: フロントエンド実装完了

実行フロー詳細ダイアグラム

Mission 投入から DoD 達成までの完全なフローです。 エージェントの内部処理がどのように進むかを俯瞰することで、 どのフェーズで何が起きているかを理解できます。

[Operator] → MISSION.md 投入 ↓ [Parser] → Objective / Constraints / DoD を解析 「何を達成するか」「何を禁止されているか」「どうなれば終わりか」を抽出 ↓ [Planner] → タスクをサブステップに分解（内部計画） 「まずファイル構造を読む」→「テストを走らせる」→「修正する」の順を決める ↓ [Executor] ←→ OODA Loop × N 回 ┌─ Observe: ツール実行（read_file / bash / screenshot） ├─ Orient: 推論・仮説構築（Scratchpad に記録） ├─ Decide: 次の最小アクションを決定 └─ Act: 副作用ある操作を実行 → Loop back ↓ [Checker] → DoD チェックリストを1つずつ検証 未完了項目があれば Executor に戻る（最大 --max-steps 回まで） ↓ [Reporter] → 完了レポート生成（何をしたか・なぜしたか） ↓ [Operator] ← 通知: "Mission Complete" / "Mission Failed: 理由"

各フェーズの役割

Parser は MISSION.md を読み込み、構造化された内部表現に変換します。 Constraints を正確に解析できないと、後の全フェーズに影響するため、 MISSION.md の書き方の品質が直接エージェントの行動精度に影響します。

Planner は Objective を達成するための大まかな手順を立てます。 この計画は実行中に更新されますが、最初の計画が間違っていると 後の OODA ループで修正コストが増大します。

Checker は DoD の各項目を実際にコマンドや確認で検証します。 DoD が「テストが PASS すること」のように機械的に検証できる形式であれば、 Checker は確実に判定できます。「いい感じになること」では判定できません。

Reporter は Scratchpad に記録された推論ログを元に、 人間が読めるサマリーを生成します。なぜその変更をしたかの追跡が可能になります。

フローを理解するとデバッグが速くなる

エージェントが期待通りに動かないとき、「どのフェーズで問題が起きているか」を特定することが重要です。
Parser フェーズの問題なら MISSION.md の書き方を修正。
Executor フェーズの問題なら --max-steps を増やすか Mission を分割。
Checker フェーズの問題なら DoD をより具体的な検証コマンドに書き直す。
