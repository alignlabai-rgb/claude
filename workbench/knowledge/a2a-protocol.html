Protocol Ecosystem
A2A の立ち位置 — プロトコルエコシステム全体図

A2Aはゼロから生まれたのではなく、MCP（ツール統合）の"横"を埋める存在として設計された。

A2A
Agent ↔ Agent（エージェント間委任）
異なるベンダー・フレームワーク・クラウドで動くエージェント同士が、タスクの委任・進捗共有・成果物受け渡しを行う。「OpenClaw が Hermes に検索タスクを委任する」がA2A。
MCP
Agent ↔ Tool（エージェントとツール統合）
エージェントがデータベース・API・ファイルシステム等の外部ツールを呼び出す標準。AnthropicのMCPはすでに5,000+サーバーを持つ事実上の標準。A2AはMCPと競合しない。
ACP
Agent Client Protocol（IDE/ツール統合）
Grok Buildが採用するプロトコル。エージェントを外部IDE・ツールに組み込む際の通信仕様。A2A・MCPとは異なるレイヤー。
🔗 3プロトコルの使い分け図
ユーザー →（自然言語）→ メインエージェント（例：OpenClaw）
    ↓ A2A ↓ サブエージェントへタスク委任（例：Hermes に記憶検索）
    ↓ MCP ↓ ツール呼び出し（例：GitHub / DB / Web検索）
    ↓ ACP ↓ IDE統合（例：Cursor から起動）
Specification
技術仕様の全体像

A2Aは既存のWeb標準（HTTP・JSON・OAuth）を最大限に活用するシンプルな設計。新規技術は不要。

📡 転送層
HTTP + JSON-RPC 2.0
すべての通信はHTTPS上のJSON-RPC 2.0。新しいネットワークプロトコルは不要で、既存のAPIゲートウェイやロードバランサーがそのまま動く。
SSE（Server-Sent Events）
長時間タスクのストリーミング進捗報告に使用。エージェントが途中経過をリアルタイムにクライアントへ送信できる。WebSocketより軽量。
Push Notifications（Webhook）
非同期タスク完了時に指定URLへプッシュ。エージェントを「火付けて離席」する非同期ワークフローの基盤。
🔐 認証・セキュリティ
OAuth 2.0 / Bearer Token
Agent Card に認証スキームを宣言。Basic / Bearer / OAuth 2.0 から選択。エージェント間の認証はHTTPヘッダー経由で既存インフラと統合できる。
Agent Card による能力開示
https://<host>/.well-known/agent-card.json に自身の能力・エンドポイント・認証要件を公開。クライアントがGET一発で発見できる。
マルチモーダル対応
テキスト・画像・ファイル・構造化データを統一的に扱う。エージェント間でPDF・画像・コードファイルを渡すことが可能。

Practical Use Cases
OpenClaw / Hermes との組み合わせシナリオ

A2A が実装されると、このハブで扱う自律エージェントたちがどう協調するかの具体例。

🦀
OpenClaw → Hermes（記憶委任）
OpenClaw がタスクを受けた際、Hermes の過去記憶を検索したい場合に A2A でタスク委任。「先週の設計議論の結論を教えて」を Hermes に委任し、結果を受け取って回答に組み込む。
🔨
メインエージェント → Grok Build（コーディング委任）
汎用エージェントが「この仕様を実装してPRを作って」をコーディング特化エージェント（Grok Build / Claude Code）に A2A 経由で委任。PR成果物を受け取って確認するだけ。
🔍
Orchestrator → Research Agent（情報収集）
複数の調査タスクを複数の検索特化エージェントに並列委任。各エージェントの A2A Agent Card を読んで能力を確認し、最適なエージェントに自動ルーティング。
🏢
エンタープライズ：部門間エージェント連携
HR部門エージェント・Finance部門エージェント・IT部門エージェントが A2A で相互接続。ベンダーが異なっても（Salesforce / SAP / ServiceNow）統一プロトコルで協調動作。

Security
セキュリティ設計と注意点
🔑
OAuth 2.0 による認証
エージェント間の認証はHTTPヘッダーのBearerトークン。スコープを絞ってタスク委任できる権限を最小化することが推奨。
🔒
TLS 必須
すべての通信はTLS 1.2以上。平文通信は仕様上サポート外。プロダクション環境では証明書の自動更新（Let's Encrypt等）を設定する。
⚠️
Agent Card 改ざんリスク
悪意ある Agent Card への接続を防ぐため、ドメイン検証・証明書ピニングの実装を推奨。未知のエージェントからのタスク委任は審査を挟む設計に。
