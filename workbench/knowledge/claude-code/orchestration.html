Desktop Integration: "Claude Cowork"

ブラウザの中だけで完結する時代は終わりました。専用デスクトップ環境 Claude Cowork が、PC操作のすべてを掌握します。

  • Secure Sandbox: OSから隔離されたコンテナ内で動作するため、システム破壊のリスクなしにフル権限を与えられます。
  • Skill System: 「PPTX作成」「画像編集」「データ分析」などのスキルをモジュールとして追加可能。コードを書くだけでなく、ドキュメント作成やプレゼン資料まで一貫して任せられます。

Director's Mastery: "Effort Parameter"

最新のオーケストレーションにおいて、Director（あなた）が調整すべき唯一のパラメータは "Effort" (思考深度) です。

  • Low Effort: 「とりあえず動くプロトタイプを」 → Sonnet中心で爆速実装。
  • High Effort: 「堅牢な金融システムを」 → Opusが数分間沈黙して思考（Deep Reasoning）し、完璧な設計図を描いてからSwarmを展開します。

「どう書くか」ではなく「どれくらい深く考えるか」を指定する。これが2026年のマネジメントです。

Sub-agents パターン（2026年版）

Claude Code では1つの親エージェント（Orchestrator）が複数のサブエージェントを同時起動できます。これは単なる「モデルを切り替える」話ではなく、本物の並列作業を実現する仕組みです。

Task ツールによる起動メカニズム

親エージェントは Task ツールを呼び出すことでサブエージェントを起動します。各サブエージェントは以下の特性を持ちます。

  • 独立したコンテキスト: 親の会話履歴を引き継がない。サブエージェントは「新鮮な頭」で作業を開始する。
  • 独立したツール権限: 親が持つ権限セットをサブエージェントに継承させるか、制限するかを制御できる。
  • 非同期完了: 親エージェントは全サブエージェントの完了を待ち、結果を集約する。
  • 失敗の局所化: 1つのサブエージェントが失敗しても、他のサブエージェントの実行は継続される。

並列実行の実例

大規模リファクタリングを3つの並列タスクに分割する典型パターン。

大規模リファクタリングを以下の並列タスクに分割して実行してください: 1. src/components/ のTypeScript型エラーを全修正（Sonnetを使用） - strict モードのエラーをすべて解消 - any 型を適切な型に置き換える 2. src/utils/ の単体テストを新規作成（Sonnetを使用） - 現在テストが存在しない関数にVitestで網羅的なテストを追加 - カバレッジ目標: 80%以上 3. docs/ のREADMEを最新仕様に更新（Haikuを使用） - package.json の依存関係と照合して古い記述を修正 - インストール手順を最新化 各タスクは独立して実行できます。並列で処理してください。

コスト比較: Opus 1個 vs Sonnet 3個並列

オーケストレーション設計において最重要の判断がここです。

構成 スループット コスト目安 適合タスク
Opus 1個（直列） 低（順番に処理） $0.03〜$0.15 高度な設計・判断が必要なタスク
Sonnet 3個（並列） 高（同時に処理） $0.003〜$0.03 独立した実装・修正・テスト作成
Haiku 5個（並列） 最高 $0.0005〜$0.005 ログ解析・フォーマット変換・単純チェック
設計の鉄則: 「タスクを分割できるか」を最初に問う。分割できる場合は並列 Sonnet が Opus 単体より速くて安い。分割できない（前の結果が次に必要）場合のみ直列を選ぶ。

Parallel Agents 実装パターン

実務で繰り返し使えるパターンを体系化しました。並列エージェントの設計は「どこで結果を集約するか」を最初に決めることが重要です。

パターン1: Fan-out / Fan-in（分散→集約）

最も基本的なパターン。1つの親が複数のサブエージェントに作業を分散させ、全結果を集約して最終アウトプットを生成します。

# Fan-out / Fan-in パターンの指示例 以下を並列で実行し、最後に結果を統合してください: [サブエージェント1] auth モジュールのコードレビューを行い、 セキュリティ問題の一覧を JSON で返してください。 [サブエージェント2] payment モジュールのコードレビューを行い、 セキュリティ問題の一覧を JSON で返してください。 [サブエージェント3] profile モジュールのコードレビューを行い、 セキュリティ問題の一覧を JSON で返してください。 全サブエージェントの結果が集まったら、重大度順にソートして SECURITY_REPORT.md として出力してください。

パターン2: Pipeline（直列チェーン）

各エージェントの出力が次のエージェントへの入力になる直列パターン。コンパイル → テスト → デプロイなど、順序が重要な作業に使います。

# Pipeline パターンの指示例 以下を順番に実行してください（前のステップが成功した場合のみ次へ）: Step 1 [Sonnet]: TypeScript のビルドエラーを全修正。 エラーが 0 になったことを確認してから次へ進む。 Step 2 [Sonnet]: 全テストを実行。 失敗しているテストを修正。パス率 100% を確認してから次へ。 Step 3 [Haiku]: CHANGELOG.md を今回の変更内容で更新。 git commit メッセージのドラフトを提案。

パターン3: Speculative Execution（投機的実行）

複数の「アプローチ案」を並列で実装させ、後から最良のものを選ぶ。設計の正解が不明な時に有効です。

# Speculative Execution パターンの指示例 認証トークンの保存方法について、以下の3案を並列で実装してください: [案 A / Sonnet]: HttpOnly Cookie + CSRF トークン方式 [案 B / Sonnet]: localStorage + リフレッシュトークン方式 [案 C / Sonnet]: SessionStorage + 短命トークン方式 各案の実装後、セキュリティ・UX・実装コストの観点から 比較レポートを作成してください。採用案はユーザーが決定します。
並列エージェント設計のチェックリスト タスクAとタスクBに「依存関係」はないか？（あれば直列にする）
各サブエージェントの作業範囲は「明確に分離」されているか？
集約ロジック（結果をどう統合するか）を親エージェントの指示に含めたか？
失敗した場合のフォールバック（再試行 or スキップ）を定義したか？

Orchestration コスト管理

エージェントを「賢く使う」最大のポイントはコスト管理です。モデル選択の誤りは、品質を下げることなくコストを10〜100倍にしてしまいます。

モデル選択の判断基準

タスク難度 推奨モデル 目安コスト/タスク 具体例
複雑な設計・デバッグ Opus $0.01〜$0.05 システム設計、難解なバグ特定、アーキテクチャレビュー
通常実装・修正 Sonnet $0.001〜$0.01 機能実装、コードリファクタリング、テスト作成
ログ解析・単純変換 Haiku $0.0001〜$0.001 ファイル名変換、ログフィルタ、型チェック
定型フォーマット処理 Haiku（複数並列） $0.00005〜$0.0005 CSV変換、マークダウン整形、コメント生成

--effort パラメータとモデル選択の関係

--effort パラメータはモデルの「思考深度」を制御します。モデル選択と組み合わせることでコストを精密に制御できます。

# 低コスト優先: 実装タスクに Sonnet + low effort claude --model claude-sonnet-4-6 --effort low "src/utils/ の関数に JSDoc コメントを追加" # バランス重視: 標準開発に Sonnet + medium effort（デフォルト） claude --model claude-sonnet-4-6 "認証モジュールを実装" # 品質優先: 設計タスクに Opus + high effort claude --model claude-opus-4-6 --effort high "マイクロサービスのAPIゲートウェイ設計を提案"

claude_config.json でデフォルトモデルを設定

プロジェクトや用途に応じてデフォルトモデルを固定しておくと、コスト超過を防げます。

{ "model": "claude-sonnet-4-6", "defaultEffort": "medium", "subAgentModel": "claude-haiku-4-6", "orchestratorModel": "claude-opus-4-6" }
コスト削減の実践テクニック:
1. まず Haiku で「可能か」を確認 → 本番は Sonnet で実行
2. 定型タスク（フォーマット変換、コメント追加）は常に Haiku
3. Opus は「設計・診断・レビュー」だけに限定する
4. 1タスクあたりのコストを定期的に計測し、モデル選択を見直す

Human-in-the-Loop（HITL）設計

エージェントに自律性を持たせるほど、「人間がどこで介入するか」を設計することが重要になります。HITL（Human-in-the-Loop）は、エージェントの暴走を防ぎながら自動化の恩恵を最大化する設計思想です。

Permission Mode の3段階

最も安全
--permission-mode plan
全アクション実行前に確認プロンプトを表示。「次にこれをやろうとしています。承認しますか？」とエージェントが都度確認する。初めてのプロジェクトや、重要なコードベースでの初回作業に推奨。
標準
--permission-mode ask
通常操作は自動承認。ファイル削除・外部API呼び出し・git commit など、副作用の大きい操作だけ確認プロンプトを表示。日常的な開発作業のバランス設定。
CI/CD向け
--permission-mode auto
確認なしで全操作を自動実行。バックグラウンド実行・夜間バッチ・完全自動化パイプラインに使用。権限を明示的に allow/deny リストで制限することが必須。

Hooks で特定ツール使用前に承認を挿入

Permission Mode よりも細粒度の制御が必要な場合は、Hooks を使います。特定のツール呼び出しの直前に任意のシェルコマンドを実行できるため、独自の承認ロジックを差し込めます。

# .claude/hooks.json の例 { "beforeToolUse": [ { "match": { "tool": "Bash", "pattern": ".*rm.*" }, "command": "echo '削除操作を検出: ${TOOL_INPUT}' && read -p '続行しますか？ [y/N] ' yn && [[ $yn == y ]]" }, { "match": { "tool": "Bash", "pattern": ".*kubectl.*deploy.*" }, "command": "echo '本番デプロイを検出。Slack に通知中...' && curl -X POST $SLACK_WEBHOOK -d '{\"text\":\"デプロイが開始されました\"}'" } ], "afterToolUse": [ { "match": { "tool": "Write" }, "command": "npm run lint --silent || true" } ] }

本番デプロイ前の人間レビュー設計パターン

完全自動化が危険な領域では、エージェントに「ここで止まれ」を教えておきます。

# エージェントへの指示に「承認ゲート」を明示する 以下の手順でリリース準備を行ってください: Phase 1（自動）: テストを全実行し、パス率100%を確認。 Phase 2（自動）: CHANGELOG.md を更新し、バージョンを bump。 Phase 3（自動）: ステージング環境にデプロイし、スモークテストを実行。 ★ ここで停止してください ★ 「ステージング確認が完了しました。本番デプロイを承認しますか？」 と質問し、ユーザーの明示的な OK を待ってから Phase 4 に進む。 Phase 4（ユーザー承認後のみ）: 本番環境にデプロイ。
HITL 設計の 4 原則 1. 「元に戻せない操作」の前には必ず人間を介在させる
2. 承認待ちポイントを事前に指示文に明記する（エージェントに推測させない）
3. `auto` モードでは必ず `deny` リストを設定して安全網を張る
4. 承認ログを残す（誰が・いつ・何を承認したか）

Background Agents（非同期実行）

Background Agents は、ユーザーの目の前ではなくクラウド VM 上で非同期に実行されるエージェントです。長時間かかるタスクを「外出中に任せる」ために設計されています。

長時間タスクをバックグラウンドで実行

通常の Claude Code セッションはターミナルを開いている間のみ動作します。Background Agents はセッションを切断してもクラウド上で実行継続します。

# バックグラウンド実行の起動例 claude --background "全 3,000 ファイルのレガシーコードを TypeScript strict モードに移行してください。 完了後に Slack に通知してください。" # 進捗確認（IDを使って後から確認） claude status --job-id abc123 # 結果の取得 claude result --job-id abc123

claude.ai/code からモバイルで進捗確認

バックグラウンド実行中のエージェントは claude.ai/code のダッシュボードから進捗を確認できます。スマートフォンからでも以下が確認できます。

  • 現在実行中のステップと進捗率
  • これまでに変更されたファイルの一覧
  • エラーや警告のリアルタイムログ
  • Checkpoint（中間セーブポイント）の状態

Slack 通知との連携（完了時に通知）

長時間タスクは「完了したらすぐ知りたい」ニーズがあります。Hooks の afterSession イベントを使って Slack 通知を自動化できます。

# .claude/hooks.json に完了通知フックを追加 { "afterSession": [ { "command": "curl -X POST $SLACK_WEBHOOK_URL \\ -H 'Content-Type: application/json' \\ -d '{\"text\": \"Claude タスク完了: ${SESSION_SUMMARY}\", \"channel\": \"#dev-alerts\"}'" } ], "onError": [ { "command": "curl -X POST $SLACK_WEBHOOK_URL \\ -H 'Content-Type: application/json' \\ -d '{\"text\": \"Claude タスク失敗: ${ERROR_MESSAGE}\", \"channel\": \"#dev-alerts\"}'" } ] }

複数の非同期タスクを並走させる実践

複数の Background Agent を同時に起動することで、チームのように並走させることができます。

# 朝出社前に複数タスクをキューに積む例 # Job 1: ドキュメント更新（低優先・Haiku） claude --background --model haiku --job-name "doc-update" \ "docs/ 以下のすべての README を最新の API 仕様に同期してください" # Job 2: テスト追加（中優先・Sonnet） claude --background --model sonnet --job-name "test-coverage" \ "カバレッジが 60% 未満のモジュールにテストを追加。目標 80%" # Job 3: パフォーマンス調査（高優先・Opus） claude --background --model opus --job-name "perf-audit" \ "Lighthouse スコアが 60 未満のページを調査し、改善案をレポートしてください" # 全ジョブの状態一覧 claude jobs list
Background Agents を使うべきタスクの条件:
実行時間が10分以上かかる見込みのタスク
ターミナルを閉じても継続してほしい作業
外出中・就寝中に完了させたい作業
CI/CD パイプラインで定期実行したい処理
