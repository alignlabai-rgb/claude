Power Automate：失敗から復旧できる自動処理

成功経路を増やすより、重複・timeout・認証拒否・容量切れをどう扱うか。反復処理を小さく設計し、結果不明を無確認で再送しない実践ガイド。

最終更新：2026-10-13 / 公式一次資料確認。実環境の機能・契約検査は未実施。

flowは「動いた」より「再び動かせる」が重要

Power Automateのcloud flowにはイベント起点、手動起点、予定起点がある。cloud flowの種類。どの種類でも業務の成功条件は同じとは限らない。たとえば「実行成功」はメールが相手に理解された証拠ではなく、「保存成功」は内容の正しさの証拠ではない。本文では未実行の教材例を通して、入力、検証、作用、記録を分ける。

開始条件を自然言語で作れたとしても、誰の接続で動くか、同じイベントが再び来た時どうなるか、処理の途中で止めた時何が残るかは設計者が決める。AIにflow案を作らせることと、そのflowを本番で実行する許可は別だ。

教材例：新しい資料を確認キューへ整理する

架空の入力は、document_id、版、取得日時、題名、本文、公開可能フラグを持つ。最初は外部通知をせず、キューへ候補を一つ作るだけにする。重複キーはdocument_idと版の組合せにし、同じ本文の再取得と、改訂された資料を区別する。本文が変わって同じ版を名乗る時は、自動上書きせず競合として確認する。

AI要約を使う場合、原文参照を候補に保存し、要約の失敗で原文まで失わないようにする。日付なし、内容なし、扱えない形式、公開境界が不明な入力は、例外キューへ送る。例外に担当と再開条件がなければ、エラーを可視化しただけで仕事を閉じてはいない。

入力受領 → schema検査 → 重複/競合検査
  → 許可範囲確認 → 候補作成 → 記録
不明/拒否/不適合 → 確認キュー（外部送信なし）

Try/Catchと結果不明を分ける

公式のエラー処理ガイドはRun after、Scope、retry、Terminate等を説明する。これらは処理の分岐を組む道具であり、業務作用を一度だけ実行する保証ではない。network timeoutの後に相手側で保存されていることはあり得るので、失敗表示を見たらすぐ全工程を再実行する設計は危険だ。

状態筆者の処理案避けること
一時的な読取エラー上限付きで間隔を広げてretry無制限の短周期再試行
入力不適合原因と必要な入力を返す値をAIで創作して続行
認証・policy拒否該当ownerへ条件確認別接続や別アカウントへ迂回
書込結果が不明宛先で業務キーを照合二重作成・二重送信
容量不足未処理を保持、再開条件を示す従量課金を無断で有効化

作用前にintentを記録し、結果にreceiptを付ける設計は役立つが、記録と外部書込みの間にも失敗は起きる。相手APIの重複制御や結果照会の有無を調べ、保証できる範囲を明示する。「冪等キーを付けた」だけで全工程をexactly-onceと呼ばない。

AI Builder・agent flowと費用を混ぜない

Power Automate cloud flowとCopilot Studio agent flowは似た画面でも別の課金対象だ。公式standard harnessのbillingは、Power Automate cloud flowsはPower Automate licensingを使いCopilot Creditsのenforcement対象ではないと区別する。さらにAI Builderを呼べばAI容量が別に関わる。AI Builder容量。

flow一回の費用を見積もる時は、入力件数、loop、AI呼出し、処理ページ数、retry、失敗した出力の人手修正を分ける。テスト中にbillingされるかも、使っているharnessや機能の公式条件で確認する。見積りの式は残し、単価は購入や変更時に読み直す。

受入試験と引継ぎ

正常な一件だけでなく、同時に二件、再送、訂正版、対象外の利用者、接続失効、作用後timeoutを教材に含める。期待するのは、候補の重複がない、未処理が消えない、外部作用の結果が照合できる、失敗を一人の担当へまとめて届けるという状態だ。

通知を一工程ごとに連発すると、重要な失敗が埋もれる。検知と人への通知を分け、同じ原因を集約する。最後にflow版、接続owner、再開条件、失敗した案件の入口を引き継ぐ。生成したflowを読む人が、成功経路だけでなく止まり方も理解できれば、automationは再利用可能な方法になる。
