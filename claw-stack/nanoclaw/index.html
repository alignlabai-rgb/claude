NanoClaw：コンテナ、配送、共有単位を切り分ける

最終更新・公式情報確認：2026-10-13。確認日は発表日ではありません。本文の教材・評価案は筆者の提案であり、実行済み成果や導入保証ではありません。

NanoClaw を理解する入口は「小さい OpenClaw」という呼び方ではなく、ホストの配送とエージェントの実行を切り分ける設計にある。現在の公式リポジトリは nanocoai/nanoclaw。旧 namespace のリンクは現行へリダイレクトすることを確認した。NanoClaw 公式リポジトリ コンテナがあるだけで安全認定をするのではなく、何を共有し、何を外へ出せるかを読む。

メッセージと実行の間にあるもの

公式 architecture は、Node.js のホストがチャネルと配送を持ち、実行中の各セッションに Docker コンテナを用意する構造を示す。ホストからの入力とコンテナからの出力は SQLite の対のファイルで受け渡す。NanoClaw Architecture 入口へ届いたこと、エージェントが処理したこと、外へ配送できたことは別の事象になる。

この分離を使った筆者の観測案では、各段階へ合成の依頼 ID を付ける。入力行があるのに結果がないなら実行側、結果があるのに受信者へ届かないなら配送側を調べる。エージェントの「送った」という返答だけで配送を完了扱いにしない。再試行で同じ入力を増やしてしまう構成なら、先に重複の検査を用意する。

秘密の分離は group の設計

公式 isolation guide では、同一 agent group のセッションは会話を分けてもファイルとメモリを共有し、group 内の履歴へアクセスできる。別の信頼領域を分けるには、セッション名ではなく group を分ける設計が必要だ。NanoClaw Isolation levels「顧客ごとにスレッドを作った」は、その顧客同士の秘密分離を証明しない。

たとえば公開ニュースを読むエージェントと内部契約を読むエージェントを同じ group へ置くかは、話題の近さでは決められない。利用者とデータの境界が違うなら、共有による便利さより、情報が混ざったときの影響を優先する。ここでの例は構成検討の教材であり、実際の運用や導入実績を示さない。

コンテナが守る範囲を読む

security 文書は、プロンプト注入が起きる前提で影響範囲を縮める設計を説明する。同じ group の共有領域は残るため、セッションのコンテナが分かれていることだけから、ファイルの完全隔離は言えない。NanoClaw Security model さらに既定の外向き通信は開いている。通信制限は hardening の別設定として確認する。NanoClaw Hardening

検討表には、コンテナから見える mount、書ける領域、使える資格情報、ネットワーク、ホスト側の配送権限を別々に書く。生の秘密をコンテナへ渡さない設計であっても、許可された外部操作を悪用する可能性は別に残る。「キーを盗めない」と「キーで悪い操作をできない」は同じ性質ではない。

最小の試行で壊す場所を決める

筆者の試行案は、合成した公開 FAQ の整理を一つの group で行い、利用者 A と B の会話を別セッションへ置く。次に A で保存した合成ファイルが B へ見える条件を確認し、共有の意図を説明できるかを見る。秘密を使わずに、共有境界の理解違いを見つけるための試行である。

その後、コンテナ終了、配送先の不在、入力の重複を順番に試す。一度に三つ壊すと原因を分けられない。処理済み、未処理、不明の状態を区別し、復旧時に元の ID を使えるよう記録する。コンテナを作り直せば全て直る、といった回復説明はしない。永続する group の状態は別の対象になる。

カスタマイズの小ささと責任

README は読みやすいコードを利用者が自分の fork へ適応する姿勢を打ち出している。NanoClaw 公式リポジトリ それは変更が安全に自動検証されるという意味ではない。チャネルや provider を追加すれば、新しい通信と保存の経路が生まれる。コード量ではなく、変更した境界と回帰検査を残す。

採用候補に残す条件は、group の責任者が共有を理解し、ホストとコンテナを別々に診断でき、更新後も禁止した効果を確認できることだ。必要な仕事が単発の文章生成なら、この構造を常設する利益がない場合もある。安全設計の思想と、手元で要件を満たした証拠は分けて判断する。
