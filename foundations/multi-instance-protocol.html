並走プロトコル — マルチインスタンス運用

このハブは複数の Claude / Codex セッションが非同期で同時稼働することを前提に運用されています。 本ページは、並走を検出した時の振る舞い・ブランチ命名規約・コンフリクト解消手順・コミュニケーション方法を定めます。

並走が現実であることは ADR-008（Trend 記事6本の並走立ち上げ）と RP-001（pull 漏れによるコンフリクトの回避パターン）で実証済み。

なぜこのプロトコルが必要か

並走を放置すると以下のような問題が起きる:

  • 同じファイルを別々に編集 → push 時にコンフリクト、最悪片方の作業が失われる
  • 同じトピックを別々に書く → 重複コンテンツがハブ内に存在することになる（AP-005 の重複問題と同根）
  • 古い前提で意思決定 → 別セッションがすでに ADR を書いた構造を踏み潰してしまう
  • 並走ブランチを発見できない → 自分の作業が無効化されていることに気付かない

これらは「一人で書いている前提」を捨てるだけで、ほぼ防げる。

1. 並走の検出

セッション開始時に必ず実行

git fetch origin
git status
git branch -r | grep -E "claude/|codex/"
  • "behind N commits" 表示があれば、即 git pull。差分を取り込んでから作業
  • claude/laughing-cannon-* 等の自動命名ブランチがリモートに複数あれば並走の証拠
  • 直近のコミット（git log --oneline -10）で誰が何をしているか把握

→ 並走作業の取り込みなしに編集を始めると、コンフリクトが確定する。事前に必ず確認。

大きな編集の前にも再 fetch

git fetch origin
git log HEAD..origin/main --oneline

セッション開始から30分以上経った場合、編集前にもう一度 fetch して別セッションの新着コミットを確認する。長時間作業中に並走作業が降ってくることがある。

2. ブランチ命名規約

パターン用途例
main 公開状態。直接コミット可（小さな修正・即時反映） —
claude/<auto> Claude 自動命名のフィーチャーブランチ（並走作業用） claude/laughing-cannon-bKOHI
codex/<auto> Codex 自動命名のフィーチャーブランチ codex/feature-xxx
feat/<slug> 人手でつける明示的なフィーチャーブランチ feat/sitemap
fix/<slug> 小さな修正系 fix/broken-link
experiment/<slug> 戻すことを前提とした実験 experiment/new-css

原則: 自動命名ブランチ（claude/* / codex/*）は消さない。手動 push したブランチも、リモートに残っていれば「別セッションが使用中の可能性」を疑う。

3. 並走に遭遇した時の振る舞い

CASE A

リモートに「behind」が出た（自分が古い）

  1. git pull で差分を取り込む
  2. 取り込まれたコミットの内容を git log -p HEAD@{1}..HEAD で確認
  3. 自分が編集しようとしていたファイルが含まれていないか確認
  4. 含まれていれば、自分のタスクをやり直しか、既に解決済みかを判定
CASE B

同じファイルを別セッションが編集中

  1. 自分の編集を新規ブランチ（fix/... 等）に隔離
  2. 相手の作業が main に着地するのを待つ（短時間なら）
  3. 長引くなら、相手の編集箇所と衝突しない部分だけ先にコミット
  4. 同じ行を編集する必要があるなら、ユーザーに判断を仰ぐ
CASE C

並走作業が完了して main に取り込まれた（自分の作業が無効化）

  1. 慌てず差分を確認（自分の作業が完全に置き換わったか、部分的か）
  2. 並走側の出力の方が品質が高ければ、自分の作業は捨てる
  3. 並走側に欠けている観点があれば、追記する形で再開
  4. ADR にこの経緯を残す（ADR-008 のように「並走で立ち上がった」記録は資産）
CASE D

同じトピックを別々に書いていた

  1. 両方の成果物を比較（行数・取材深さ・ソース）
  2. 片方を「正本」とし、もう片方の独自情報を吸収
  3. 「ベンダー横断は Industry Trends、個別は LLM トラッカー」のような役割分担を ADR で定める

4. やってはいけないこと（Don'ts）

DON'T 並走ブランチを勝手に削除

claude/* / codex/* のリモートブランチを git push --delete しない。他セッションがまだ使っている可能性。削除はユーザーが明示的に指示した時のみ。

DON'T force push を main へ

git push --force / --force-with-lease を main ブランチに対して行わない。他セッションの作業を消す。フィーチャーブランチでも、相手が pull していたら force は事故の元。

DON'T 別セッションのコミットを revert

「自分のと違う」と感じても、即座に revert しない。意図が分からないならdecisions.html の最近の ADR を確認、または next-actions に「TODO: 〇〇 のコミット意図確認」として残す。

DON'T long-lived branch を放置

自分のフィーチャーブランチが 1週間以上 unmerged のまま放置されたら、消すか main にマージするか決める。放置すると他セッションが「これは何？」と混乱する。

5. やるべきこと（Do's）

DO 小さく頻繁にコミット

1ページ完成 = 1コミットくらいの粒度で。大きな塊を抱え続けるとコンフリクトリスクが上がる。

DO コミットメッセージで「何のタスクか」を明示

「update」「fix」だけのメッセージは禁止。「foundations/multi-instance-protocol を新規作成（Phase 1）」のように、後で別セッションが見て分かるレベルで書く。

DO 並走を予告する

長時間ロックする作業（同じファイルを30分以上編集する等）の場合、事前にコミットして状態を明示。または logs/next-actions.html に「作業中: foundations/* を再構成中（claude-XXX セッション）」と書いておく。

DO 並走で発生した事象を ADR に残す

ADR-008（Trend 記事の並走立ち上げ）のように、並走で起きたことは ADR で記録。後でパターンとして再利用できる。

6. コンフリクト解消の標準手順

  1. まず落ち着く — コンフリクトは「両方の作業が残るチャンス」。慌ててどちらかを捨てない。
  2. コンフリクト箇所を全部リストアップ 
    git status                  # コンフリクト発生ファイル
git diff --name-only --diff-filter=U
  3. 各コンフリクトを意味的に解消
    • テキストの追加同士なら、両方残すのが原則
    • 同じ箇所の置換同士は、ユーザーに判断を仰ぐか、両方の意図を読んで統合
    • 機械的な解消（行マージ）はしない
  4. 解消後に検証 
    git diff --check            # コンフリクトマーカー残存チェック
grep -rn "<<<<<<\|>>>>>>" .  # 念のため二重チェック
  5. コミットメッセージにコンフリクトを記録 
    Merge: foundations/ への並走編集を統合
- claude/laughing-cannon-XXX の用語集追加
- 自分の glossary レイアウト調整
- 両方の意図を保持
  6. 解消パターンを記録 — 大きなコンフリクトだったら ADR か anti-patterns に追加。

7. 「明示的コミュニケーション」のしくみ

並走セッションは互いに直接話せない。代わりに以下のファイルがメッセージボードとして機能する:

媒体用途レイテンシ
logs/next-actions.html 「これから何をやる」「作業中」の宣言 編集と同時に反映
foundations/decisions.html (ADR) 「こう決めた」の記録。覆す時は新 ADR で 編集と同時
logs/sessions/YYYY-MM-DD.html 「何をやったか」の時系列ログ（Phase 4 で運用復活予定） セッション終了時
コミットメッセージ 細かい変更の意図 コミット時
foundations/anti-patterns.html 「これは失敗パターン」の警告 編集と同時

原則: 並走相手に伝えたいことは、すべてテキストとしてリポにコミットする。記憶や思考の中に留めない。

8. クイックリファレンス（コマンド集）

# 開始時のチェック
git fetch origin
git status
git branch -r | grep -E "claude/|codex/"
git log --oneline -10

# 別セッションの最近の作業を確認
git log HEAD..origin/main --oneline

# 自分の作業中のブランチを整理
git branch --merged main      # 削除可能なローカルブランチ
git branch -d <branch>        # マージ済みブランチを削除

# コンフリクト発生時
git status
git diff --name-only --diff-filter=U
grep -rn "<<<<<<" .

# push 前の最終確認
git fetch origin
git status                    # behind になっていないか
git log origin/main..HEAD     # これから push するコミット一覧
