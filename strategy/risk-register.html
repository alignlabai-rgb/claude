CRITICAL リスク（最優先対応）

R-01: Creator System の長期未更新

CRITICAL コンテンツ鮮度 確率: 高（顕在化済み）/ 影響: 大

説明

2026-05-25 に「主軸領域」と宣言し spotlight 表示まで実装したが、配下7ファイルは大半が 45日以上未更新（4/10 前後で停止）。表示と実態の乖離が拡大している。

現在の対策

  • Hub Health Dashboard で ALERT として可視化
  • Q2 レビュー の Q3 next action 最優先項目に明記

予定の対策

  • Q3（7-9月）に Creator System の本格深化（動画/漫画パイプラインの実装反映、KPI ダッシュボード新設）
  • 月次で creator-system/* の最終更新を Hub Health で監視

R-06: 機密情報・取引先固有情報の混入

CRITICAL セキュリティ 確率: 低 / 影響: 大（信用毀損）

説明

本ハブは公開リポジトリ。エージェントが書き込む情報に取引先名・固有金額・個人情報等が混入すると、信用毀損につながる。特に Codex / Claude による自動編集で意図せず混入するパターンが怖い。

現在の対策

  • CLAUDE.md に「公開リポなので機密情報は混入させない」と明記
  • 取引先固有情報を扱う作業は ALIGN_Lab 本体（非公開・ローカル）側に分離

予定の対策

  • セッション終了前チェックに「機密情報スキャン」を加える（grep ベースの簡易チェック）
  • 大きな commit 前に git diff で目視確認する習慣化
  • 機密情報パターン（メアド・電話番号・社名+金額）の自動検出スクリプト検討

HIGH リスク

R-02: LLM トラッカー3社の更新滞り

HIGH コンテンツ鮮度 確率: 中 / 影響: 大（ハブの中核機能の劣化）

説明

Claude / ChatGPT / Gemini の3トラッカーは同じ粒度で並走更新することがハブの差別化軸。1社だけ古い、3社とも止まる、等が起きると LLM Updates Hub の意義が消失する。

現在の対策

  • 3社のページに last-update を明記、Hub Health で鮮度を一覧化

予定の対策

  • 更新運用ルール: 週1回以上、主要マイルストーンがあれば即日
  • 3社並走で書く際の「素材→裏取り→投稿」標準フロー化
  • 更新滞り検知（一定日数経過で Hub Health に ALERT 自動表示）

R-03: 外部 URL の腐敗

HIGH リンク健全性 確率: 高 / 影響: 中

説明

外部メディア URL（TechCrunch・Bloomberg・OpenAI ブログ等）は記事削除・移動・有料化で1年以内に 5-15% が腐敗するのが業界相場。LLM トラッカー・Industry Trends の信頼性低下リスク。

現在の対策

  • 外部 URL は実 URL でリンク（AP-002 で確立）

予定の対策

  • 四半期に1回、リンクチェッカー（wget --spider 等）で全外部 URL を検証
  • 腐敗した URL は archive.org へのリンクに置換するルール
  • 主要メディアは出典として記事タイトル + 日付を必ず併記（リンク死亡時の再探索用）

R-04: 内部リンクの腐敗

HIGH リンク健全性 確率: 中 / 影響: 大

説明

ハブ内のページをリネーム・移動・削除した時、参照していた他ページが壊れる。AP-005（重複削除漏れ）と同根の問題で、158ページ間の相互参照は把握が困難。

現在の対策

  • 物理リネームせず表示ラベルだけ変える方針（ADR-005）
  • 削除より移動、移動より追記を優先

予定の対策

  • 四半期に1回、内部リンクチェッカー（相対パス全探索）
  • 大きな構造変更時は事前に grep で被参照箇所を洗い出す運用
  • Site Map（site-map.html）と Hub Health の二段構えでナビゲーション補強

R-05: 並走セッションのコンフリクト

HIGH 並走運用 確率: 高（顕在化中） / 影響: 中

説明

Claude / Codex の並走セッションが同じファイルを編集して衝突するリスク。RP-001（pull 漏れ防止）で部分的に対処済みだが、人間が複数 PC で並走する場合は別系統のリスク。

現在の対策

  • 並走プロトコル（Phase 1 で整備）
  • セッション開始時の git fetch 義務化

予定の対策

  • セッションログ運用復活（Phase 4）で他セッションの作業中状況を可視化
  • 長時間ロック作業は事前に next-actions.html で予告する慣習化

R-07: MCP / Anthropic API の値上げ・仕様変更

HIGH 外部依存 確率: 中 / 影響: 大

説明

Anthropic は2026-06-15 から Agent SDK の月次クレジット制に移行予定。Claude Code SDK・GitHub Actions・OpenClaw 等のプログラム的利用が分離課金される。同様の仕様変更が今後も発生する可能性。

現在の対策

  • LLM トラッカーで仕様変更を逐次追跡
  • OpenClaw / Hermes のサブスクリプション利用禁止 → 撤回（5/24）のような事象も Industry Trends で記録

予定の対策

  • 本ハブで使う API・SaaS の依存リストを作成（次回 Phase 4 候補）
  • 料金変動の四半期チェックを定例化

MEDIUM リスク

R-08: ページ数増加によるナビ崩壊

MEDIUM スケール 確率: 高 / 影響: 中

説明

現在158ページ。半年で200を超える可能性。トップカードからの導線だけでは辿り切れず、Site Map に依存する状況になる。検索機能の不在も足枷。

現在の対策

  • Site Map（Phase 2）でカテゴリ別＋用途別の2軸ナビ整備

予定の対策

  • クライアント側 JS で title 検索を実装（軽量）
  • ページにタグ属性を埋め込み、タグ別索引を生成（dashboard / reference / long-form 等）

R-09: 業界変化への追従コスト

MEDIUM キャッチアップ 確率: 高 / 影響: 中

説明

AI 業界は新モデル・新製品が月次ペース。LLM トラッカー3本＋ Industry Trends 6本＋ Workbench 32 vendor ページの全鮮度を維持するコストが累積する。

現在の対策

  • AI News 日次運用で「素材プール」を毎日蓄積
  • Industry Trends を「ベンダー横断でしか書けない題材」に絞り、書く対象を絞る

予定の対策

  • 「追跡対象の優先度」を四半期ごとに見直す（trend-* の何を継続、何を凍結するか）
  • Workbench の vendor ページは四半期に1回の小棚卸しでメンテ頻度を抑える

R-10: ALIGN_Lab 本体との同期ずれ

MEDIUM 外部依存 確率: 中 / 影響: 中

説明

ALIGN_Lab 本体（非公開・ローカル運用）の戦略・ロードマップが進化した時、本ハブの foundations/align-lab-context.html や strategy/* が陳腐化する。

現在の対策

  • align-lab-context.html を本ハブ内に保持（オフライン参照可）

予定の対策

  • 四半期に1回、ALIGN_Lab がローカルにある PC で align-lab-context.html を refresh
  • 同期作業を Q3 next action として明記済み

R-11: 古いブランチ・実験ブランチの残骸

MEDIUM 並走運用 確率: 中 / 影響: 低

説明

claude/laughing-cannon-* 系の自動命名ブランチが累積し、何が active か不明になる。残骸ブランチが他セッションの誤解を招く。

現在の対策

  • 並走プロトコルで「削除はユーザー明示指示時のみ」を規定

予定の対策

  • 四半期に1回、ユーザー判断でブランチ棚卸し（merged / 30日以上 stale なものを削除）

LOW リスク（監視のみ）

R-12: Hub Health 等ダッシュボードの陳腐化

LOW コンテンツ鮮度 確率: 中 / 影響: 低

ダッシュボード自体が古い数値のままだと意味が薄れる。Phase 4 で半自動化を予定。

R-13: SEO / 公開 URL のインデックス安定性

LOW 外部公開 確率: 低 / 影響: 低

GitHub Pages の URL 安定性は基本問題ない。スマホからもアクセスする運用なので、レスポンシブ崩れだけ注意。

R-14: バックアップ消失（ローカル PC 故障）

LOW インフラ 確率: 低 / 影響: 中

GitHub remote が事実上のバックアップ。OneDrive 上で運用されているのも冗長性に寄与。push されていない作業中ファイルだけが消失リスク。セッション終了時の push 習慣化で十分対処可能。

リスク管理の運用

  • 四半期ごとに棚卸し: 各リスクの確率・影響度を再評価。新規リスクを追加、解消したリスクは「過去のリスク」セクションに移動
  • 顕在化したリスクは アンチパターン へ移行: 「これから起きそう」だったものが「起きた」になったら、ここから除去して anti-patterns に AP-xxx として記録
  • 新規リスクの追加基準: 「明日起きても驚かない」「起きたら作業が止まる」のどちらかを満たす場合のみ
  • スコア更新: 大きな構造変更があった四半期は再評価必須
