MiniMax現況 — M3.1 Preview・M3・H3とローカル制作

MiniMaxのLLMと動画を一括しない。現在の公式catalog、subscription、公開weightsを整理し、local制作とlocal推論の違いを明確にします。

1. LLM・動画・音声・アプリを分ける

MiniMaxは一つのモデル名ではありません。M系列はLLM、H系列は動画系、Speechは音声、MiniMax Codeは作業アプリ、M Planは利用契約です。同じ会社の名称でも、入力、出力、課金、公開weights、提供段階は別です。この記事では2026-10-13に取得した公式docsを優先し、古い製品catalogを本文へ混在させません。

2. M3とM3.1 Previewの違いを保つ

M3公式repositoryはnative multimodal、長context、thinkingのenabled/adaptive/disabled、local deployment資料を案内します。一方、M3.1 Flash Previewの提供範囲は現在のAPI catalogに限定条件があります。M3の公開weightsを見つけたことを、M3.1 Previewの公開weightsや通常APIの一般提供へ拡張しません。M3公式repository

アプリ内でmodelを選べても、自作toolが同じendpoint・parameter・権限で使えるとは限りません。評価記録にはrequested model、surface、plan、入力modalityを残します。Previewを本番必須の唯一の接続先にするなら、終了や変更時の代替経路を技術的に準備する必要があります。

M3のmodel cardはlicenseをminimax-communityと表示します。昔の別M系列やrepository codeの条件からMITと推測せず、対象weightsのLICENSE本文を確認します。公開weightsと商用APIは利用条件が別です。M3公式card

3. H3動画は非同期の制作工程

API overviewはH3とH3-Maxを掲載し、task作成、status照会、結果URL取得、取消やrecord削除を分けます。H3とH3-Maxは解像度やtask種別の対応が同一ではありません。成功responseが返るのは受理段階の場合があり、動画完成の証拠ではありません。公式動画API workflow

# 架空の制作状態。APIは呼び出さない
DRAFT_INPUT → SUBMITTED(task_id) → RUNNING
            → SUCCEEDED(output_url) → LOCAL_FILE_VERIFIED → REVIEWED
            → FAILED(reason) / CANCELLED
生成受理 ≠ 完成 ≠ ダウンロード検証 ≠ 内容受入

制作記録はpromptだけでなく、referenceの権利と版、model、task ID、output、採用理由を結びます。動画が生成されても、時間的一貫性、文字、人物、音との対応が用途に合わなければ採用しません。再生成の前には、すでに処理中のtaskかを確認し、結果不明のまま二重送信をしない設計が必要です。

H3の発表は7月31日で、公式はtext・image・video・audioを統合する生成modelとして説明します。提供側の商用制作への適性の主張は、こちらの作品における品質や権利受入を代行しません。H3公式発表

4. 「ローカルで動画を作る」の三つの意味

一つ目はlocal PCでpromptやreferenceを作り、remote APIで動画を生成すること。二つ目はremote生成物をlocalに保存・編集すること。三つ目は生成modelのweightsをlocal runtimeで推論することです。前二つは有用なlocal制作ですが、動画生成の計算がlocalで行われたとは限りません。

M3は視覚入力を持つLLMで、そのweights公開はHailuoやH3の動画weightsと同一ではありません。H3発表がopen modelという言葉を使っていても、対象weights・license・runtimeの取得と可動性を確認する工程は別です。この調査ではH3/Hailuoの自前推論を実行検証していません。

RAMを増やしたことはlocal workflowの余裕を増やしますが、特定の動画modelが動く証明ではありません。weights、量子化、runtime、GPU/CPU、解像度、尺、並列数で必要資源が変わります。model名だけで48GBなら動く、といった保証はしません。

5. M PlanとAPI keyの分離

M Plan overviewは個人向けsubscriptionとMiniMax Codeや他toolでの利用を案内します。公式API overviewはSubscription Keyを通常の従量API keyと区別しています。契約bucketを一つにまとめると、どの利用がどこから消費されるか見失います。M Plan利用範囲 / key区分

quotaはcontextやtaskの複雑さ、mediaによって変わるため、呼出件数を固定の利用量へ換算しません。特に動画とテキストを同じ単位として扱わず、完成物と修正回数を別に記録します。本調査は新規契約、plan変更、key入力を行っていません。

6. 音声・音楽は同じ利用範囲ではない

公式API overviewには音楽APIについて、8月20日から有料APIが新規ユーザー向け提供を終了し、既存有料ユーザーの継続と無料API終了を説明する注意があります。Audioアプリや公開Music modelは別の入口です。古い「音楽APIが誰でも使える」手順を現況へ残しません。Music Generation注意

声のcloneを使うなら、音声生成能力だけでなく本人の同意、利用範囲、入力音声の権利が必要です。voice IDの存在を永続的な利用保証にせず、サービスの保持条件を確認します。音楽制作も生成成功と公開可能性を分け、権利や最終採用をmodelへ任せません。

7. 次に行う価値のある試験

筆者提案は、公開・権利確認済みのreferenceで短い動画を一つ作り、camera、動作、文字、音、再生成の各条件を評価することです。LLMは制作仕様の整理、動画modelは生成、local editorは編集と品質確認に役割を分けます。

この試験はまだ実行していません。採用には完成動画、入力仕様、失敗例、修正条件をセットで残します。速報の新名称を追うことから、次回の制作で再利用できる方法へ情報を変えるのが、この現況ページの用途です。
