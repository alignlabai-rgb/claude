診断の専門ガイド：終了コードと業務の成功を分ける

最終更新・公式情報確認：2026-10-13。news という旧 URL は維持し、本文は用途別の現行ガイドへ刷新しました。確認日は発表日ではありません。

例と評価案は筆者の設計提案で、未実行です。性能測定・本番導入・安全認定・正式採用の実績を示すものではありません。

コマンドが 0 を返した、画面が緑になった、モデルが大丈夫と言った。どれも単独では業務の完成を証明しない。この章は基本の障害切り分けから一段進み、診断の結果を読み、修復へ進む前に何が確認できたかを明確にする。運用サービスの変更や provider の呼び出しはこの説明では実行しない。

終了コードの契約を読む

公式 Doctor lint 文書は、裸の openclaw doctor --json が読み取り専用・非対話で、report が出れば exit 0 になり、健康状態は payload の ok と findings を見ると説明する。明示の lint はしきい値に従う別の終了コード契約を持つ。Doctor lint and post-upgrade modes0 だけで「問題なし」と報告しない。

筆者の診断表は、検査を実行できたか、何を検査したか、所見があるか、今回の業務を阻害するか、何を未確認にしたかを分ける。検査の実行成功と、対象が健康なことと、仕事が完成したことは三つの判断である。

静かな出力の意味

公式 lint は severity のしきい値に応じて出力と終了条件が変わる。Doctor lint and post-upgrade modeswarning を表示しない設定なら、空の画面から warning がないとは言えない。report の対象としきい値を記録し、他の report と比較するときにも合わせる。

合成例として、低い重大度の所見一件と高い重大度の所見一件を用意し、表示のしきい値を変えた結果を読み分ける。見えなくなった所見を解決済みへ分類したら失敗である。修復を行わなくても、診断の意味の誤読を防げる教材になる。

検査と修復の境界

読むための mode と修復を行う mode は別である。公式 update の工程も、状態や移行を扱うため、単なる package の入れ替えとしては説明されない。Updating診断中に提案されたコマンドを、そのまま承認済みの修復としない。

変更へ進む前に対象、影響、保全する原本、戻せる条件を列挙する。拒否や権限不足があるなら、別名のコマンドで回避しない。要件に合う許可が必要なら、運用者が判断する。

症状へ戻る

公式 troubleshooting は provider、更新、UI、サービス、設定、配送と tool の症状を分ける。OpenClaw Troubleshooting広い診断に一つの所見があることから、目の前の症状の原因と決めつけない。症状の発生時刻と変更の前後を照合する。

例として、回答が届かないのに model catalog の警告だけを直しても、配送の問題は残る場合がある。最後に確定した受付、結果、保存、配送を探し、次の検査で何が否定できるかを決める。検査を増やすことを進捗にしない。

報告できる最小の資料

報告候補には、版、症状、再現する合成入力、期待、実際、関係する所見だけを入れる。公式 CONTRIBUTING も再現と影響を求める。公式 CONTRIBUTING実際の token、端末の内部名、顧客の文章を full log として添付しない。

切り詰めた stderr の最後の行だけで原因を断定しない。読み取り専用 report の範囲を示し、部分的な結果と全面検査を分ける。検査が中断したなら、所見なしではなく未検査とする。

回復した後の確認

同じ合成入力を再度使い、受付と結果と配送を確認する。診断コマンドが成功しただけで、実際の仕事も復旧したと書かない。元の問題が見えなくなった理由が不明なら、不明と残す。再現できる負の入力を評価集合へ入れると、次の更新でも同じ失敗を見つけられる。
