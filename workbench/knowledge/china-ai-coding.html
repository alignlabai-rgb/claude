中国系AIコーディングを選ぶ — ブランド比較から運用設計へ

安い、速い、長いcontextだけでは導入判断になりません。DeepSeek、Qwen、Kimi、GLM、MiniMaxを、完成物・権限・再現性・回復コストから選ぶための実践設計です。

1. 「どこが最強か」より四つの層を分ける

modelは推論器、APIは利用契約、harnessはtoolを実行する基盤、アプリは完成した利用体験です。同じmodelでもharnessが違えばpatchや停止挙動が変わり、同じアプリでもmodelやroutingが更新されれば再現性が変わります。中国系という一括分類では、この差が消えてしまいます。

対象今回の公式確認実務で先に見る条件
DeepSeekV4.1 Flashへ旧Flash名をrouting、Pro継続実際のAPI名・modality・adapter
QwenQwen Codeはmulti-provider harnessmodelとツール版を別々に固定
KimiK3 API・full weights・固有license完全message履歴と再開契約
GLMCoding Planはcredits制と旧ID自動routing契約surface・effort・消費単位
MiniMaxM3とPlan限定M3.1 Flash Preview、H3動画APIは別LLM／動画／音声を別の試験にする

この表は優劣ランキングではありません。APIを利用する試験とlocal weightsを比較する試験を混ぜず、まず自分が管理できる層を明確にします。価格の安さ、parameter規模、benchmarkを一つの「コスパ」に圧縮しないことが重要です。

2. 選択の順番を反転する

よくある失敗は新modelを見つけ、導入し、使い道を後から探すことです。代わりに、困っている仕事を一つ選びます。「日本語の仕様からtestを書く」「公開資料から比較表を抽出」「既存画面のアクセシビリティを直す」など、完成物と受入条件が具体的なtaskです。

  1. 原入力と完成物を決める。差分、test、原稿のどれを渡すか明示する。
  2. 送信してよい入力と、絶対に実行させない操作を区別する。
  3. 必要modality、context、tool contractを候補に照合する。
  4. 同じfixture・harness・予算で小さく試す。
  5. 修正時間と未解決点を含めて採否を決める。

この順なら、既存subscriptionに適したmodelがあれば使い、新契約が必要なら採用提案として分離できます。良さそうな候補を見つけたことは、新しい課金、credential変更、外部公開の権限になりません。

3. 互換APIの落とし穴

共通SDKで送信できても、thinking、reasoning effort、画像のblock形式、tool choice、streaming、response schemaはproviderごとに異なります。共通部分だけを業務コードに置き、固有部分をadapterへ閉じ込めます。「互換」の範囲は実際のdocsとfixtureで確認します。

Kimiの完全assistant履歴、GLMのthinking無効非対応、DeepSeekのalias変更は、IDだけ置換する移行の危険を示す具体例です。エラーが出なかった時にも、違うmodelへ転送された可能性を記録します。successful HTTP responseは、期待したmodel・内容・taskの成功を証明しません。

# 架空の比較taskカード
task_id: csv-border-case-r1
input: public synthetic fixture
success: 空行・quoted comma・欠損列をtestで扱う
allowed_tools: read/edit fixture, run tests
forbidden: publish, credential edits, original deletion
record: requested_model, surface, harness_version,
        first_result, retries, patch, test_receipt, human_repair
stop: same_failure_at_limit

4. 並列化は独立な差分から

多くのagentを同じファイルへ向けると衝突と重複が増えます。調査、test設計、UI検査、source監査など独立な成果物へ分割し、書込対象と返却形式を固定します。親の統合者は矛盾、名前、引用、重複を解消して一つの完成物へ戻します。

単純taskは並列化の利益が小さい場合があります。総待ち時間だけでなく、統合時間と読解量も測ります。十個の回答を人が全て読む設計なら、modelの出力速度は組織の作業速度になりません。結論を押し付けるのではなく、判断に必要な根拠の密度を高めます。

5. 価格・quota・local costを別に記録する

APIのinput/output/cache課金、subscriptionのcredits、チャット回数、localの占有時間は異なる単位です。古い料金表を本文に積み重ねるより、現行pricingへの直接リンクと確認日を維持します。期間限定割引を恒久価格として試算せず、regionとsurfaceを揃えます。

local化を比較する場合、RAM/VRAMだけでなくsetup、依存更新、障害対応、電力、他仕事との競合を考えます。MoEのactive規模を使って小さいmemoryで必ず動くと断定しません。同じ結果を得るのに人が何度も直すなら、安い呼出でも全体の費用は高くなります。

6. 三つの受入例

抽出：答えではなく根拠

公開表から5項目を取り、各値へsource位置を付ける。存在しない値はnullにする。自然な補完は誤答。

修正：patchとtest

小さいbugのfixtureを使い、既存testの前後を記録する。testを実行せず成功と言う、無関係なrefactorは失敗。

制作：体験と仕様を別々に

動く短い画面を作り、入力、keyboard、errorのtestと、人の見やすさ確認を分ける。画像だけで機能成功にしない。

すべて説明用の試験案です。実行後は、採用できる条件と採用できない条件を両方残します。一件の成功から「このproviderは全仕事に最適」と一般化せず、入力、版、環境、権限を結びつけて再利用します。
