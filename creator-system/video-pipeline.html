システム内での役割

パイプラインの
コアエンジン

動画制作モジュールはAI Creator Hubのメイン収益エンジンです。 ネタ生成AIからテキストを受け取り、完成動画ファイルを評価システムへ渡す 中核パイプラインとして機能します。全ステップはOpenClawが自律制御します。

  • 入力元: ネタ生成LLM（テキスト・JSON）
  • 出力先: 評価システム（動画ファイル + メタデータ）
  • 処理時間: ショート動画 約8〜15分 / 長尺動画 約45〜90分
  • 並列処理: 最大4本同時生成（GPU依存）
  • 失敗時: OpenClawが自動リトライ、3回失敗で人間へアラート

モジュール入出力定義

# OpenClaw スキル定義 (SKILL.md 抜粋) name: video-pipeline version: "2.2.0" input: topic_text: string # ネタ文章 genre: string # shorts|long|podcast target_sec: int # 目標尺（秒） style_preset: string output: video_path: string # 完成動画パス thumbnail_paths: list metadata: object # タイトル/説明/タグ cost_usd: float # API使用コスト
制作フロー

7ステップで完成動画へ

1

ネタ文章の受け取り & 前処理

別ラインから生成されたテキストを受け取り、ジャンル・ターゲット・トーンを自動分析。不適切コンテンツフィルタリングも同時実行。

入力: テキスト GPT-5.5 / Claude Sonnet 4.6 / Gemini 3.1 Pro
2

動画スクリプト生成

ネタ文章をYouTube/ショート動画向けのスクリプトに変換。フック（冒頭掴み）・本編構成・CTA（行動喚起）を自動設計。字幕テキストも同時生成。

// スクリプト生成プロンプト例 const script = await llm.generate({ system: "あなたはYouTube動画脚本家です", prompt: `以下のネタを元に動画スクリプトを作成: - フック: 最初の3秒で視聴者を掴む - 本編: ${targetDuration}秒の構成 - CTA: チャンネル登録・いいね誘導 ネタ: ${sourceText}` });
3

ビジュアル素材生成

スクリプトの各シーンに対応する画像・映像をAIで生成。スタイルの一貫性を保ちながら、シーンごとに最適な構図・色調を自動選択。 Sora撤退（2026-04-26）以降、動画生成AIはRunway Gen-4.5（品質）/ Kling 3.0（コスパ）/ Google Veo 3.1（エコシステム）の3極構造に収束しており、本パイプラインもこの3系統を並列評価する設計にしている。

Nano Banana 2 系（画像） RunwayML Gen-4.5 Kling AI 3.0 Google Veo 3.1 Grok Imagine Video 1.5

⚠️ Google Imagen 4 は2026-08-17廃止予定。新規シーンは後継の Nano Banana 2 Lite / Pro（Gemini API 経由）へ切り替え中。詳細は下の「動画生成AIランドスケープ」参照。

4

音声合成（ナレーション）

スクリプトをリアルな日本語音声に変換。複数の声質から自動選択し、感情・速度・イントネーションを最適化。BGM選択も自動。

ElevenLabs VOICEVOX CoeFont Suno AI (BGM)
5

字幕・テロップ生成

音声に同期した字幕を自動生成。強調ワードのハイライト・エフェクト・フォントスタイルも動画の雰囲気に合わせて自動調整。

Whisper (文字起こし) FFmpeg (字幕埋め込み)
6

動画編集・結合

映像・音声・字幕をFFmpegで自動合成。トランジション・カット編集・テロップアニメーションをルールベースで適用し、完成動画を生成。

# FFmpegによる自動合成例 ffmpeg -i video_scenes.mp4 \ -i narration.mp3 \ -i bgm.mp3 \ -filter_complex "[1:a]volume=1.0[v1]; [2:a]volume=0.15[v2]; [v1][v2]amix=inputs=2[aout]" \ -map 0:v -map "[aout]" \ -vf "subtitles=subs.srt" \ output_final.mp4
7

サムネイル生成

動画の内容から最も視聴クリックされやすいサムネイルを複数パターン生成。A/Bテスト用に3〜5パターンを自動作成し評価システムへ送付。

トラブルシューティング

よくある失敗パターンと対処法

動画生成AIは高品質だが、まだ完全ではない。パイプラインを自動運転させる上で頻発する失敗モードと、現時点で有効とされる対処法を記録する。 いずれも「絶対に直る」保証はなく、モデル世代が進むごとに改善される前提の暫定対処。

🧑
キャラクターの一貫性が崩れる（シーンごとに顔・服装が変わる）
複数ショットで同一キャラクターを描く際に最も頻発する問題。対処法：①Veo系はIngredients機能でImagen/Nano Banana生成のキャラクター画像を事前登録し参照させる、②Runway/Klingでは参照画像（First Frame / reference_image）を毎ショット同一のものに固定する、③プロンプトのキャラクター描写文をテンプレート化して使い回す（服装・髪色・体型の記述を毎回一言一句揃える）。それでも数十カット規模になると崩れは避けにくく、評価システム側で「顔が変わったカット」を検出し再生成する運用にしている。
✋
モーションアーティファクト（手・液体・布・複雑な動作の破綻）
手指の変形、髪や液体の不自然な挙動は動画生成AI共通の弱点。Kling 3.0は複雑な動作（髪・液体・布）に強いとされ、こうしたカットはKling系へルーティングするのが現実的。 それ以外の対処：①1クリップあたりの尺を4〜6秒に短く区切りExtendで繋ぐ（長尺一発生成より破綻しにくい）、②プロンプトで複雑な手の動作を明示的に避ける（例：「軽くジェスチャーする」程度に留める）、③破綻カットは評価システムで自動検出し、同一プロンプトで再生成（temperature/seedを変えて）する運用にしている。
🗣
口パク・音声のズレ（リップシンク不一致）
Veo 3.1は"セリフ" [感情]構文での台詞指定で口パク精度±120ms程度とされる（ベンダー公表値の目安）。Kling 3.0・Grok Imagine Video 1.5もネイティブ音声同期を搭載しており、台詞ありカットはこれらのモデルを優先する。 ElevenLabsで別途ナレーションを当てる構成（本パイプラインの主フロー）では、そもそも映像側の口パクを目立たせない画角（後ろ姿・引きの画）を選ぶことでズレを回避する設計判断もしている。
🔎
解像度不足・仕上げ（アップスケーリング）
Veo 3.1 Quality（1080p〜4Kプレビュー）以外の多くのモデルは720p〜1080p出力が中心。ショート動画では実用上問題ないことが多いが、長尺・広告用途では不足する場合がある。 外部アップスケーラー（Topaz Video AI等）との連携は本パイプラインではまだ正式統合しておらず検証段階——導入する場合はFFmpeg合成の後段に追加ステップとして挟む設計になる見込み。現状は「最初から高解像度ティアのモデルを選ぶ」運用で代替している。
💡 いずれの対処法も「モデルが今どれだけ得意か」で最適解が変わる。並列生成＋評価システムでの自動選別（本ページ「設計意図」参照）が、個別の弱点をパッチする以上に効くというのがこのパイプラインの基本思想。
設計意図

なぜこのツール構成なのか

ツール比較表は「何を使うか」を示しますが、「なぜそれを選んだか」は別の問いです。 将来のセッションがこのページを読んだとき、選定の意図が分かるように記録します。

🎤
ElevenLabs を音声合成の主軸にした理由
日本語のイントネーション・抑揚の自然さが Azure / Google TTS より一段上で、視聴継続率に影響する冒頭30秒の「語り口」で差が出やすかった。 API の安定性と日本語マルチボイス対応がパイプライン自動化の前提条件を満たす実質唯一の選択肢だった。 フォールバックとして VOICEVOX をローカルに保持している理由も同じ——クレジット超過時に音声品質が突然落ちるリスクを許容できないため。
🎬
RunwayML Gen-4.5 / Kling 3.0 / Google Veo 3.1 を「どれか1本」にしなかった理由
いずれも「API 経由で自動制御できる高品質」という条件を満たすが、強みの軸が異なる。 Runway Gen-4.5 はプロンプト一貫性・カメラ制御（複数シーンでスタイルが崩れにくい）、 Kling 3.0 はコスト効率と量産適性（$0.07〜0.10/秒目安）、 Veo 3.1 は Google エコシステム統合とネイティブ音声品質に強みがある。 並列で生成して評価エンジンが高スコアを選ぶ設計にすることで、半年単位のモデル更新にも自動で追従できる。 この判断の正しさは 2026年4月の Sora 撤退で裏付けられた——1本に絞っていたクリエイターは、そのモデルがサービス終了した瞬間に制作基盤ごと失うリスクを負う。 必要に応じて Grok Imagine Video 1.5 のような新興モデルも同じ評価ループに追加できる設計にしている。
⚙️
最終合成を FFmpeg で行う理由
映像・音声・字幕の合成はローカルで完結できる唯一の工程であり、ここだけがクラウド API コストのかからない要素。 フレームレート・ビットレート・コーデック（H.264 / H.265）の細かい制御が YouTube 最適化に必要で、クラウドレンダリングでは自由度が足りない。 FFmpeg はオープンソースで永続性が保証されており、プラットフォーム依存リスクがない。これも選定基準の一つ。
🔢
7ステップに分割した理由（一括処理でないのはなぜか）
各ステップが独立した API 呼び出しになることで、途中失敗時の再開コストが最小化できる。 ステップ4（映像生成）が失敗してもステップ1〜3の成果物（スクリプト・ナレーション・サムネ素材）を再利用できる。 並列化可能なステップ（映像生成 + 音声合成 + サムネ生成）を3並列で回すためにも、ステップ分割が有効になっている。
💡 将来のセッションへ: ツール名が変わってもこの設計思想は変わらない。「API制御可能・最高品質・フォールバック先あり・ローカル合成」という4軸で代替を探すこと。
Google エコシステム連携（2026年版）

Flow / Antigravity 2.0 との
統合オプション
