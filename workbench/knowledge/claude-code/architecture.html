Agent-First Architecture

Designing Systems for the AI Mind

「2週間で動くシステムを作る」ためには、人間にとっての読みやすさよりも、AI（Opus 4.8）にとっての理解しやすさを優先したディレクトリ構造が必要です。

1. The "Context-Friendly" Directory Structure

エージェントが迷子にならないための推奨構成です。「どこに何を置くか」の判断を迷わせないために、トップレベルは極めてシンプルにします。

/ (Project Root) ├── .ai/ # エージェント専用の記憶領域 │ ├── CONTEXT.md # [重要] プロジェクトの全貌・目的・制約条件 │ ├── RULES.md # [重要] コーディング規約 (例: "TSはstrictモードで") │ └── MEMORY.md # エージェントが自分で更新する「作業ログ・決定事項」 │ ├── modules/ # マイクロサービス的な機能区分 │ ├── auth/ # 認証機能 (独立したContextを持つ) │ │ ├── api/ │ │ ├── ui/ │ │ └── services/ │ ├── billing/ # 課金機能 │ └── core/ # 基盤ロジック │ ├── shared/ # 共通コンポーネント │ ├── ui-kit/ │ └── utils/ │ ├── tests/ # E2Eテスト └── README.md
Key Strategy: "Colocation" (関連性の凝集)
従来のMVC（Model/View/Controllerフォルダに分ける）はAIにとって最悪です。機能 A を修正するために3つの離れたフォルダを行き来させる必要があるからです。
AIには「機能単位（modules/xxx）」ですべての関連ファイルが1箇所にまとまっている構造が最強です。

2. Format of CONTEXT.md

エージェントへの「最初の神の啓示」となるファイルのテンプレートです。

# Project Phoenix Context ## 1. Goal このプロジェクトは「SaaSに依存しない自社製Core Work System」を構築することである。 最終的には社内ユーザー50名が使用する日報・承認システムとなる。 ## 2. Tech Stack - Frontend: React 19 (No Next.js), TailwindCSS - Backend: Supabase (Edge Functions) - Language: TypeScript (Strict) ## 3. Core Principles 1. **Agent-First**: コードは常にAIによる修正を前提とする。複雑な抽象化よりも、冗長でも分かりやすいコードを好む。 2. **Speed over Beauty**: UIは `shadcn/ui` をそのまま使うこと。デザインに時間をかけない。 3. **No Hidden Logic**: ビジネスロジックは全て `modules/*/services` に集約すること。UIにロジックを書かない。 ## 4. Current Phase 現在は「Authモジュール」の実装中。ユーザー登録フローを完了させることが最優先。

3. Agent-Driven Development Flow

このアーキテクチャを使って開発を進める具体的なフロー。

Phase 1: Definition

まず .ai/CONTEXT.md を人間が書きます。コードは書きません。

Phase 2: Skeleton

Claudeにコマンドを投げます。
$ claude "Read .ai/CONTEXT.md and generate the directory structure and empty files for the Auth module."

Phase 3: Logic & Test

中身を埋めさせます。
$ claude "Implement the Auth service based on best practices. Create tests first."

4. CLAUDE.md の書き方（決定版）

CLAUDE.md はプロジェクトルートに置く「AIへの憲法」です。Claude がプロジェクトを開始する際に最初に自動的に読み込まれるファイルであり、エージェントの行動規範となります。

ポイントは「コードの説明」ではなく、「AI が間違いを犯しやすい判断」を事前に明文化することです。

推奨テンプレート構造

# Project: [プロジェクト名] ## 技術スタック - Frontend: React 19, TypeScript 5.4 (strict) - Backend: FastAPI 0.111, PostgreSQL 16 - Test: Pytest, Vitest - CI/CD: GitHub Actions ## コーディング規約 - 型はすべて明示（any 禁止） - コメントは「なぜ」だけ書く（「何を」はコードで表現） - 1関数1責任。1ファイル 300 行を超えたら分割を検討 - CSS は Tailwind のみ。インラインスタイル禁止 ## 作業前に必ず読むファイル - docs/API_SPEC.md（REST API の仕様・認証方式） - .env.example（環境変数の一覧と説明） - ARCHITECTURE.md（モジュール依存関係） ## やってはいけないこと - node_modules/ を直接編集しない - master/main ブランチに直接コミットしない - 外部 API キーをコードにハードコードしない - データベースのマイグレーションを直接 DROP TABLE で戻さない - package.json のバージョンを理由なく変えない ## よく使うコマンド - `npm run dev` — 開発サーバー起動（ポート 3000） - `npm test` — Vitest でテスト実行 - `npm run lint` — ESLint + Prettier チェック - `npm run build` — 本番ビルド ## 現在の作業フォーカス [担当者が毎回更新] 現在は認証モジュールのリファクタリング中。 JWT → セッション Cookie への移行が完了していない。 auth/services/token.ts を見ると現状が分かる。

CLAUDE.md の書き方のコツ

  • 「禁止事項」を必ず書く: AIが悪意なくやりがちなミス（`any` 型の多用、直接 commit 等）を明示する。
  • 「現在のフォーカス」を毎回更新する: これがないと Claude は全体を把握しようとして不要なファイルを大量に読む。
  • 「よく使うコマンド」を書く: Claude がコマンドを推測で実行するミスを防げる。
  • 「関連ファイルへのポインタ」を書く: 「この文脈を理解するにはこのファイルを読め」と案内する。
  • 200行以内に収める: 長すぎる CLAUDE.md は最後まで読まれない。
CLAUDE.md と CONTEXT.md の使い分け CLAUDE.md はプロジェクトルートに置き、Claude が自動的に読む（人間向け規約も兼ねる）。
CONTEXT.md は .ai/ や modules/xxx/ に置き、特定スコープの詳細文脈を格納する（AI 専用）。
両方あるプロジェクトでは、CLAUDE.md が概要・方針、CONTEXT.md が詳細情報を持つ構造が理想的。

5. 設定ファイル体系（3層構造）

Claude Code の設定は3つの層で構成されており、内側ほど優先度が高くなります。この構造を理解することで、「チーム共有」と「個人設定」を安全に分離できます。

~/.claude/CLAUDE.md ローカルのみ

全プロジェクト共通の個人設定。「自分はこういうコーディングスタイルが好き」「コミットメッセージは日本語で書いてほしい」といった個人の癖・好みを書く。git には入れない。

.claude/settings.json git 管理

プロジェクト固有の設定。チームメンバーが共有するべき設定（許可ツール・デフォルトモデル・MCP サーバー等）を書く。git にコミットしてチームで共有する。

.claude/settings.local.json gitignore 必須

ローカル専用の上書き設定。API キー、個人の MCP サーバー設定、デバッグフラグ等。.gitignore に追加してリポジトリに入れない。

.claude/settings.json の完全例

{ "model": "claude-sonnet-4-6", "defaultEffort": "medium", "permissions": { "allow": [ "Bash(npm:*)", "Bash(git add:*)", "Bash(git commit:*)", "Bash(git diff:*)", "Bash(git status)", "Bash(git log:*)", "Edit", "Write", "Read" ], "deny": [ "Bash(rm -rf*)", "Bash(git push --force*)", "Bash(git reset --hard*)", "Bash(DROP TABLE*)" ] }, "mcpServers": { "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/project"] }, "github": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"], "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}" } } }, "hooks": { "afterToolUse": [ { "match": { "tool": "Write" }, "command": "npm run lint --silent || true" } ] } }

設定の優先順位（高→低）

同じキーが複数の層に存在する場合、以下の順で上書きされます。

  1. コマンドライン引数（--model, --effort 等）
  2. .claude/settings.local.json（ローカル上書き）
  3. .claude/settings.json（プロジェクト共有）
  4. ~/.claude/settings.json（ユーザーグローバル）
設定ファイルのセキュリティチェックリスト:
.claude/settings.local.json が .gitignore に追加されているか確認する
settings.json に API キーや認証情報が混入していないか確認する
deny リストに破壊的コマンドを登録する（rm -rf, --force 等）
CI/CD 環境では --permission-mode auto と組み合わせて使う

6. Checkpoint & Shadow Workspace

長時間エージェント実行における「安全網」となる2つの機能です。どちらも「試してから確認する」設計思想に基づいています。

Checkpoint（チェックポイント）

長時間タスクの実行中に自動的に取得される中間スナップショットです。タスクが途中で失敗・エラーになっても、直前のチェックポイントまで巻き戻すことができます。

  • 自動取得のタイミング: 一定のファイル変更数ごと、または重要なステップ完了時
  • 手動トリガー: エージェントへの指示に「チェックポイントを取ってから次へ」と書くと確実に取得させられる
  • 巻き戻し: claude checkpoint restore --id cp_abc123 で任意の時点に戻せる
  • 比較: claude checkpoint diff --id cp_abc123 でチェックポイント以降の変更を確認できる
# チェックポイントを明示的に指示する書き方 大規模リファクタリングを以下の手順で実行してください: Step 1: src/auth/ の移行を完了する。 ★ Step 1 完了後、チェックポイントを取得してください ★ Step 2: src/payment/ の移行を完了する。 ★ Step 2 完了後、チェックポイントを取得してください ★ Step 3: src/dashboard/ の移行を完了する。 各ステップは前のステップが成功した場合のみ進んでください。

Shadow Workspace（シャドウワークスペース）

エージェントがユーザーの実ファイルを変更する前に、コピー上で作業を試す仕組みです。ユーザーが承認したときのみ実ファイルへの変更が適用されます。

項目 Shadow Workspace 直接編集（デフォルト）
変更の即時反映 なし（承認後のみ） あり（即時）
安全性 高（承認前は git に影響なし） 中（git で戻せるが履歴が汚れる）
適合ケース 大規模リファクタリング・初めての変更 小規模な修正・テスト追加
# Shadow Workspace を使った大規模リファクタリングのフロー # 1. Shadow Workspace モードで起動 claude --shadow-workspace "全コンポーネントを React 18 → React 19 の新 API に移行" # 2. エージェントがコピー上で作業（実ファイルは未変更） # claude.ai/code のダッシュボードで変更プレビューを確認 # 3. 変更が問題なければ承認して実ファイルへ適用 claude shadow apply --job-id shadow_xyz789 # 4. 問題があれば破棄（実ファイルに影響なし） claude shadow discard --job-id shadow_xyz789
Checkpoint vs Shadow Workspace の使い分け:
Checkpoint → 実行中の「セーフポイント」。失敗時の巻き戻し用。長時間タスクに自動設定。
Shadow Workspace → 実行前の「プレビュー」。ユーザーが変更内容を確認・承認してから適用する。

7. Memory ファイルの活用

Claude Code には3つのレベルの「記憶」があります。適切に使い分けることで、毎回同じ説明を繰り返す無駄をなくせます。

種類 保存場所 自動読み込み 用途
プロジェクト記憶 CLAUDE.md（プロジェクトルート） 毎回自動 プロジェクトの規約・技術スタック・禁止事項
ユーザー記憶 ~/.claude/CLAUDE.md 毎回自動 個人の好み・コーディングスタイル・よく使うパターン
手動メモ ~/.claude/memory/ 明示的に指定時のみ プロジェクト横断のメモ・過去の決定事項・参照資料

~/.claude/memory/ の使い方

永続メモリファイルを置く場所。/memory スラッシュコマンドで管理します。

# メモリファイルの追加 /memory add "project-a-notes.md" # メモリファイルの一覧表示 /memory list # 特定のメモリファイルを今のセッションで読み込む /memory load project-a-notes.md

推奨メモリファイル構成

~/.claude/memory/ ├── my-preferences.md # コーディング好み・よく使うパターン ├── my-shortcuts.md # よく使うコマンド・エイリアス集 ├── project-a-notes.md # プロジェクトAの重要決定事項 ├── project-b-notes.md # プロジェクトBの重要決定事項 └── lessons-learned.md # 過去の失敗から学んだこと（エージェントへの戒め）

my-preferences.md の書き方例

# 私のコーディング好み ## 全般 - コメントは日本語で書く - 変数名・関数名は英語 - インデントは 2 スペース - セミコロンあり ## TypeScript - as any は絶対に使わない。unknown + 型ガードで対応する - interface より type alias を好む - enum より const assertion を好む ## コミットメッセージ - プレフィックス必須: feat / fix / docs / refactor / test / chore - 日本語で書く - 例: "feat: ユーザー認証モジュールを追加" ## 指示への応答スタイル - 短く簡潔に答える（長文不要） - コードを変更した後は変更点の要約を 3 行以内で報告する - 不明点があれば作業前に確認する（推測で進まない）

CLAUDE.md との違い（自動読み込み vs 手動）

CLAUDE.md はセッション開始時に常に自動で読み込まれます。そのため、すべての会話で必要な情報だけを書くべきです。
一方、~/.claude/memory/ のファイルは明示的に指定したときのみ読み込まれます。「プロジェクトAについて話すときだけ読み込む」という使い方に向いています。

Memory 管理のベストプラクティス CLAUDE.md は200行以内に抑える（長すぎると最後まで読まれない）
頻繁に参照するが全プロジェクト共通でない情報は memory/ に分離する
メモリファイルには「最終更新日」を必ず書く（古い情報を信じるミスを防ぐ）
重要な決定（「この設計を採用した理由」等）は lessons-learned.md に記録しておく
