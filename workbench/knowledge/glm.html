Zhipu AI（現 Z.ai / 智谱AI）の GLM シリーズは、清華大学の研究成果をベースにしたアカデミックな出自を持ちながら、極めて実用的な「ツール使用（Function Calling）」能力に焦点を当てて進化してきました。GLM-5.2 は現行のオープンウェイトモデル中、長期コーディングベンチ（SWE-Marathon・PostTrainBench・FrontierSWE）で首位を獲得しています。

"All Tools" & Agentic Workflow

GLM-5.1の最大の特徴は、単一のプロンプトから自律的に複数のツールを使い分ける能力です。

  • Autonomous Selection: ユーザーが「昨日の〇〇社の株価を調べてグラフにして」と言うだけで、自動的に「Web検索」→「データ取得」→「Pythonで描画」→「画像生成」というパイプラインを構築・実行します。
  • GLM-5.2（2026-06-16 MIT 公開・現行フラッグシップ）: 753B MoE（40B active）、1M コンテキスト（最大出力 131K トークン）。IndexShare アーキテクチャにより 1M コンテキスト時の推論 FLOPs を 2.9 倍削減。SWE-Bench Pro 62.1%・Terminal-Bench 2.1 で 81.0%。MIT ライセンスで HuggingFace / ModelScope に公開済み。API は $1.40 / $4.40（入力/出力 per MTok）。
  • GLM-5.1 Highspeed API（2026-05 追加）: 400 tokens/s の高速 API バリアント。主要 LLM プロバイダー中で最速クラスのスループット。リアルタイム性が要る用途向け。
  • GLM-5.1: 200K context / 128K max output。長時間の自律実行、thinking mode、function calling、MCP、context caching、structured output に対応。Coding Plan でも継続利用可能。
  • GLM-5（2026-02 リリース）: 744B MoE（40B active）・Huawei Ascend チップで学習（28.5T トークン）。現行は 5.2 が上位互換。

Mobile & Edge

GLMシリーズのもう一つの強みは、スマートフォンやPC上で動作する軽量版（GLM-Edge / Air）の性能の高さです。

On-Device AI

インターネット接続がない環境でも、高度な日本語・中国語の処理が可能。プライバシーを重視するローカルRAG（検索拡張生成）システムの基盤として最適です。

Flash Speed

MoEアーキテクチャを採用したGLM-4.5 Airなどは、驚異的なトークン生成速度を誇り、リアルタイム翻訳などの遅延が許されないタスクで重宝します。

Why use for Vibe Coding?

GLMは**「便利な道具箱（Swiss Army Knife）」**です。

  • API連携のテスト: 「このAPIを叩いて結果を整形して」といったタスクにおいて、JSONの構造理解やパラメータの正確な挿入が得意です。
  • Web検索統合: 独自ブラウザツールとの兼ね合いが良い為、最新ドキュメントを見ながらのコーディング支援において、幻覚（ハルシネーション）が比較的少ない傾向にあります。

Comparison

  • vs ChatGPT: Function Callingの安定性において、GLM-5.1はGPT系列に匹敵する性能を見せることがあります。特にアジア圏のローカル情報を含むタスクでは有利です。
  • vs Yi / Qwen: Qwenが「理数系特化」なら、GLMは「ツール連携特化」。外部システムを動かすオートメーションの接着剤（Connector）として機能します。

Role: 自動化/コーディングの「作業馬」

GLM-5.1 を本ハブの制作・OpenClaw 志向の中でどう位置づけるか。答えは明快で、「自動コンテンツ工場を安く回す作業馬（workhorse）」です。

  • 安く・止めずに回す: 低コストAPIと Coding Plan のモデル選択肢（GLM-5.1 / 5-Turbo / 4.7 / 4.5-Air）があるため、量産パイプラインで大量リクエストを単価で殴れます。最高品質を1回より「十分な品質を大量に」が効く工程の下層を担います。
  • "All Tools" で自走する: 「調べて→整形して→描画して」を1プロンプトで完結できるため、定型の制作タスク（素材収集・整形・下書き生成）を人間の逐次指示なしに回せます。
  • 役割分担の下層: 「設計・相談・品質判断 = フロンティア（Claude / GPT / Gemini）」「量産・接着 = GLM」という二層構造で組むのが正しい使い方。最高知能を狙う層ではなく、パイプラインを安価に支える The Connector（連結者） として設計に組み込みます。

Deep Dive ①: なぜ「コーディング/エージェント」が主戦場なのか

GLM を「マスターする」上で最初に押さえるべきは、GLM の土俵がコーディングとエージェント実行だという点です。汎用チャットの総合力で他社フラッグシップを上回るのではなく、「ツールを使って自律的にタスクを完遂する」能力で評価される系列です。

指標（canon）数値意味

推論コスト$1.40 / MTok（入力）GPT-5.5（$7.50）の約 1/5、Claude Fable 5（$10）の 1/7。同水準の OW 性能を大幅安価に。

含意: 「最高知能を1回」ではなく「十分な知能を安く大量に」が効く工程 — つまりコード生成・ツール連携・自動化の量産下層 — が GLM の主戦場です。

Deep Dive ②: "All Tools" モジュール — 1プロンプトで自走する

GLM-5.1 の中核機能が "All Tools" です。Web 検索・コード実行・画像生成といった複数ツールを、モデル自身が選んで・順番に呼び出してタスクを完遂します。人間が逐次「次はこれをやって」と指示しなくても回るのが価値です。

自律的なツール選択

「昨日の◯◯を調べてグラフにして」の一言で、Web 検索 → データ取得 → Python 描画 → 画像生成のパイプラインを自分で組んで実行する。Function Calling の安定性が土台。

接着剤（Connector）として

外部 API・ブラウザ・コード実行を「つなぐ」のが得意な The Connector。最新ドキュメントを見ながらのコーディング支援でハルシネーションが比較的少ない傾向。

使いどころ: 定型の制作タスク（素材収集・整形・下書き生成・データ加工）を人間の介在なしに回す自走レーン。質の最終判断はフロンティア（Claude / GPT-5.5 / Gemini）に通す二層構造が正解です。

Deep Dive ③: 自動コンテンツ工場の「作業馬」としての使い方

本ハブの制作・OpenClaw 志向の中での GLM の役割は明快で、「自動コンテンツ工場を安く回す作業馬（workhorse）」です。最高知能を狙う層ではなく、パイプラインを安価に支える層を受け持ちます。

  • OpenClaw スキルを安く回す: スキル化された定型工程（収集・整形・下書き）を、低コスト・高スループットの GLM で大量に叩く。「十分な品質を大量に」が効く工程の本命。
  • ツール連携で自走する: "All Tools" により、スキルの中で複数ツールを自分で呼び分けて完遂。人間の逐次指示を減らし、工場を止めずに回す。
  • Connector 的な接着: 外部システム・API を動かすオートメーションの接着剤。設計・相談・品質判断を担うフロンティア層と、量産・接着を担う GLM 層の二層構造で組む。

役割整理: GLM-5.2 =「自動化エンジン本体・量産と接着の作業馬」。質の最終判断は Claude Fable 5 / GPT-5.5、構成・長尺は Gemini、安く回す土台はローカル Qwen が担う多軸構成の中で、GLM は"自走する接着レーン"を受け持つ。GLM-5.2 は OW モデル中の長期コーディング首位（SWE-Bench Pro 62.1%）でありながら、Claude Fable 5 の 1/7 のコストで回せる点が本ハブ的な最大の価値。

Deep Dive ④: コスト設計 — API vs ローカルの損益分岐

GLM はオープンウェイトなので「クラウド API で呼ぶ」か「ローカルで回す」かを選べます。判断はコストの形で捉えると速い（qwen の Deep Dive に倣った考え方）。

API（従量）

トークン量 × 単価で使うほど比例増。GLM-5.1 の参考価格は入力 $1.40 / 出力 $4.40（per 1M）。初期投資ゼロ・即起動・最新版にすぐ乗れる。低〜中頻度・試作・即応向き。

ローカル（オープンウェイト）

重みが公開されているため自前 GPU でも動かせる。GPU 初期投資＋電気代で事実上使い放題。ただし 754B MoE は規模が大きく、量子化・複数 GPU 前提。大量反復・機密・オフライン向き。

損益分岐の考え方: 「月にどれだけ叩くか」が閾値。大量反復の量産工程はローカル（またはホスト型の安価 API）が効き、一発勝負の最終品質はフロンティア API に通す。GLM 自体がOpus 系の 1/3 以下のコスト（canon）なので、まずは安価 API で回し、量が読めてからローカル化を検討するのが現実解です。

注意: ローカルは「無料」ではない。電気代・GPU 減価・運用保守も“コスト”。754B 級は VRAM 要件が重いため、低頻度なら API のほうが総コストが安いことも多い。完全自前に振り切るより「量が読める工程だけローカル」から始めるのが安全。
