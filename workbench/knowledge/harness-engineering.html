ハーネスエンジニアリングとは何か

「The harness is everything that wraps an LLM except the model itself — tool execution, memory, state management, error handling, retry logic, validation gates. Most agent failures aren't model failures: they're harness failures.」
── Mitchell Hashimoto（HashiCorp / Terraform 創業者）、2026年2月

プロンプトエンジニアリングが「指示の書き方」、コンテキストエンジニアリングが「何を見せるか」であれば、ハーネスエンジニアリングは モデルの外側にある環境全体の設計 です。

最も重要な発見：

  • 「モデルを変えるより、ハーネスを改善する方が効果が大きいことがある」 ── 同じモデルでも、ハーネス設計次第で成果が劇的に変わる
  • エージェントの失敗の大半は「モデルが賢くない」ではなく「ツールが壊れた」「エラー処理がない」「状態管理が不適切」といったハーネスの問題
  • 本番環境でのエージェント信頼性は、モデルの能力よりもハーネスの堅牢性に依存する

ハーネスの 5 レイヤー構造

本番エージェントのハーネスは以下の 5 レイヤーから構成されます。

①
Tool Layer（ツール層）
エージェントが実際に使えるツールの定義・実行・サンドボックス化。ツールの I/O スキーマ、権限管理、タイムアウト、実行環境の分離が含まれる。
実装例: MCP ツール定義・OpenClaw defineToolPlugin・LangChain Tool・function calling スキーマ
②
Memory Layer（メモリ層）
短期記憶（セッション内）・長期記憶（クロスセッション）・エピソード記憶・セマンティック記憶の管理。ベクトルDB・KV ストア・グラフDB を組み合わせる。
実装例: Mem0・Letta・Zep・Pinecone・ClawMem・pgvector・Cloudflare KV
③
State Layer（状態層）
タスク進捗・チェックポイント・セッション継続性・エラーリカバリーの管理。エージェントが中断後に再開できるかどうかを決める。
実装例: Redis・SQLite チェックポイント・Claude Code の project 継続機能・OpenClaw Workboard
④
Validation Layer（検証層）
型チェック・テスト実行・LLM-as-judge・人間レビューゲート。エージェント出力の品質を保証する。ループエンジニアリングのフィードバックゲートと直結。
実装例: Zod/Pydantic バリデーション・pytest/Jest・RAGAS・Claude Code permissions
⑤
Orchestration Layer（オーケストレーション層）
複数エージェントの協調・並列/直列実行の制御・フォールバック・リトライロジック・コスト管理。マルチエージェントシステムの司令塔。
実装例: LangGraph・CrewAI・AutoGen・Hermes Kanban・OpenClaw マルチエージェント

01 クリエイター Claude Code の CLAUDE.md ── ハーネス設定ファイルとしての実装

Claude Code において CLAUDE.md はハーネスの設定ファイルとして機能します（System Instructions であると同時に、ハーネス動作を制御する）：

# CLAUDE.md の役割マッピング
[ツール層①]  → 使ってよいツール・禁止ツールの宣言
[メモリ層②]  → プロジェクト固有知識の永続化
[状態層③]   → 作業継続のための前提情報
[検証層④]   → Editing Policy・Definition of Done
[調整層⑤]   → 並走セッションのプロトコル

「新しい Claude インスタンスがこのファイルを読むだけで正しく動く」── これがハーネス設計の完成形です。

07 エンジニア MCP（Model Context Protocol）── ツール定義の業界標準化

Anthropic が主導する MCP はハーネスのツール層（①）を標準化するプロトコルです：

// MCP ツール定義（JSON Schema）
{
  "name": "search_web",
  "description": "Web を検索して結果を返す",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "検索クエリ" },
      "num_results": { "type": "integer", "default": 5 }
    },
    "required": ["query"]
  }
}

// → Claude・Gemini・OpenAI など複数モデルで同じ定義を再利用

MCP により「ツール定義は一度書けばどのモデルでも使える」が実現。ハーネスのポータビリティが飛躍的に向上。150+ のサービスが MCP サーバーを実装済み。

詳細: a2a-protocol.html 参照
08 エンジニア Claude Code Hooks ── ハーネスの検証層・自動化をコードで制御

Claude Code の hooks システムはハーネスの検証層（④）とオーケストレーション層（⑤）をコードで定義します：

// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "bash /path/to/security-check.sh"
        // 危険なコマンドを自動ブロック
      }]
    }],
    "PostToolUse": [{
      "matcher": "Write",
      "hooks": [{
        "type": "command",
        "command": "npx prettier --write $TOOL_OUTPUT_FILE"
        // ファイル書き込み後に自動フォーマット
      }]
    }],
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "git add -A && git commit -m 'auto checkpoint'"
        // 停止時に自動コミット
      }]
    }]
  }
}

「何かをするたびに自動的に別のアクションを実行する」── これがハーネスの検証・自動化層の実装です。

09 エンジニア CrewAI ── 役割ベースマルチエージェントのオーケストレーション実装

CrewAI のオーケストレーション層（⑤）の実装パターン：

from crewai import Agent, Task, Crew

# エージェント定義（役割・ゴール・バックストーリー）
researcher = Agent(
    role="AI リサーチャー",
    goal="最新の AI トレンドを調査する",
    backstory="5年の AI 研究経験を持つ専門家",
    tools=[web_search, arxiv_search]
)
writer = Agent(
    role="テックライター",
    goal="研究結果を読みやすい記事にする",
    tools=[draft_tool, edit_tool]
)

# タスク定義（依存関係を明示）
research_task = Task(description="AI の最新動向を調査", agent=researcher)
write_task    = Task(description="記事を執筆", agent=writer,
                     context=[research_task])  # ← 依存関係

# 実行
crew = Crew(agents=[researcher, writer], tasks=[research_task, write_task])
result = crew.kickoff()

11 エンジニア DSPy ── プロンプトをハーネスがパラメータとして最適化する逆転発想

Stanford の DSPy（Declarative Self-improving Python）は「プロンプトをハーネスが自動設計する」逆転の発想：

  • 従来: 人間がプロンプトを手動設計 → ハーネスが実行

12 エンジニア A2A Protocol ── エージェント間通信を標準化するハーネス間インターフェース

Google 主導の A2A（Agent-to-Agent）Protocol は、異なるハーネスで動くエージェントが通信する標準を提供：

// A2A タスク送信（Agent A → Agent B）
const task = {
  "id": "task-001",
  "message": {
    "role": "user",
    "parts": [{ "type": "text", "text": "競合分析レポートを作成してください" }]
  }
};

// Agent B（異なるハーネス・異なるモデル）が受け取って実行
// 結果を Agent A に返送
const result = await agentB.sendTask(task);

LangChain 製エージェントと CrewAI 製エージェント、OpenClaw 製エージェントが同じプロトコルで通信できます。150 社が採用（2026年6月）。

詳細: a2a-protocol.html

本番ハーネス設計チェックリスト 20 項目

① ツール層

  • 全ツールに入出力スキーマを定義している
  • ツールのタイムアウトを設定している
  • ツール実行を分離された環境（サンドボックス）で行っている
  • 危険操作（削除・外部送信）に確認ゲートがある

② メモリ層

  • 重要な状態が永続化されている（セッション跨ぎ対応）
  • ベクトルDB のインデックスが最新に保たれている
  • 記憶の更新・削除ポリシーが定義されている
  • 個人情報・機密情報の除外ルールがある

③ 状態層

  • タスク進捗がチェックポイントに保存されている
  • 中断からの再開が可能（冪等性がある）
  • エラー発生時のロールバック手順がある

④ 検証層

  • 出力の型バリデーションがある
  • 最低 1 つの外部評価ゲートがある
  • 人間レビューが必要なステップが明確
  • コスト上限アラートが設定されている

⑤ オーケストレーション層

  • 最大反復回数・実行時間の上限がある
  • エージェント失敗時のフォールバックがある
  • 並列実行の競合（race condition）対策がある
  • コスト・トークン使用量をログ記録している

ハーネスの可観測性（Observability）

従来ソフトウェアと異なり、AI ハーネスは 確率的・非決定論的 に動作します。「なぜ失敗したか」を後から再現することが難しいため、観測設計はハーネス設計と同時に行う必要があります。

「You can't optimize what you can't observe. For AI harnesses, observability isn't optional — it's the foundation of reliability.」
── LangSmith ドキュメント、2026年

なぜ AI ハーネスの観測は特別か

  • 非決定論: 同じ入力でも出力が変わるため、「平均的な動作」を追跡する必要がある
  • 長いチェーン: ツール呼び出しが 10 段以上連なることがあり、どのステップで品質が落ちたかを特定しにくい
  • コスト直結: トークン消費 = 費用なので、異常なコスト増を即時検知する必要がある
  • プロンプト変更の影響追跡: プロンプトを 1 行変えるだけで品質が劇的に変わるため、変更前後の比較が必須

何をログに残すか ── 最低ロギング仕様

入力ログ

  • システムプロンプト（バージョンタグ付き）
  • ユーザー入力（個人情報はマスク）
  • 使用モデル名 + パラメータ（temperature 等）
  • リクエスト ID・タイムスタンプ・セッション ID

ツール呼び出しログ

  • ツール名・引数（サイズ制限付き）
  • 実行時間・成功 / 失敗
  • エラーメッセージ（スタックトレース）
  • リトライ回数

中間状態ログ

  • エージェントの思考ステップ（reasoning）
  • 各ステップのトークン消費
  • チェックポイント保存のタイミング
  • サブエージェントへの委譲イベント

出力ログ

  • 最終出力（サイズ上限付き）
  • 合計トークン数・合計コスト
  • バリデーション結果（Pass / Fail）
  • LLM-as-Judge スコア（実装済みの場合）

Langfuse 統合コード例（Python）

Langfuse を既存 Claude API 呼び出しに最小コストで統合する例：

from langfuse import Langfuse
from anthropic import Anthropic

langfuse = Langfuse(
    public_key="lf-pk-...",
    secret_key="lf-sk-...",
    host="https://cloud.langfuse.com"   # セルフホストも可
)
client = Anthropic()

def run_agent_task(user_input: str, session_id: str) -> str:
    # トレース開始
    trace = langfuse.trace(
        name="agent-task",
        session_id=session_id,
        input=user_input,
        metadata={"model": "claude-opus-4-5", "harness_version": "2.1.0"}
    )

    # LLM 呼び出しのスパン
    span = trace.span(name="llm-call")
    generation = span.generation(
        name="claude-call",
        model="claude-opus-4-5",
        input=user_input
    )

    response = client.messages.create(
        model="claude-opus-4-5",
        max_tokens=2048,
        messages=[{"role": "user", "content": user_input}]
    )
    output = response.content[0].text

    # メトリクス記録
    generation.end(
        output=output,
        usage={
            "input": response.usage.input_tokens,
            "output": response.usage.output_tokens
        }
    )
    span.end()

    # ツール呼び出しを別スパンで記録
    tool_span = trace.span(name="tool-execution", input={"tool": "file_write"})
    # ... ツール実行 ...
    tool_span.end(output={"status": "success"}, level="DEFAULT")

    trace.update(output=output)
    return output

# スコア（品質評価）を後から追加
def score_output(trace_id: str, score: float):
    langfuse.score(
        trace_id=trace_id,
        name="quality",
        value=score,   # 0.0 〜 1.0
        comment="LLM-as-Judge による自動評価"
    )

アラート条件の設計

コストスパイク（Cost Spike）

単一タスクのトークン使用量が 30 分移動平均の 3 倍を超えた場合、または日次累計コストが予算の 80% に達した場合に即時アラート。無限ループや誤った再帰呼び出しの早期検知に必須。

監視ポイント: タスク開始時にコスト上限を設定し、超過時はタスクを強制終了して人間にエスカレーション。

レイテンシ劣化（Latency Degradation）

P99 レスポンスタイムが通常比 3 倍超え、または特定ツールのタイムアウト率が 10% を超えた場合。外部 API の障害・モデル過負荷の早期検知に活用。

監視ポイント: ツールごとに別々に計測。LLM 呼び出しとツール実行を分けてログを取ることで原因特定が容易になる。

エラー率上昇（Error Rate Increase）

5 分間ウィンドウのエラー率が 5% を超えた場合、または特定ツールの失敗が連続 3 回以上続いた場合に Slack / PagerDuty に通知。デプロイ後の品質劣化を即時検知。

監視ポイント: バリデーション失敗・ツールタイムアウト・LLM API エラーを別々にカウントする。原因が違えば対応も異なる。

セキュリティとハーネス設計

ツールを実行するハーネスは、従来の Web アプリと同じ攻撃面を持ちながら、LLM 固有の攻撃ベクターが加わります。設計段階からセキュリティを組み込む「Security by Design」が必須です。

プロンプトインジェクション攻撃

外部コンテンツ（Web ページ・PDF・ユーザー入力）にエージェントの指示を書き換える命令を埋め込む攻撃です。

ツール呼び出しセキュリティ ── コマンドインジェクション

# 危険な実装（ユーザー入力をそのままシェルコマンドに渡す）
def run_bash_tool(command: str):
    import subprocess
    return subprocess.run(command, shell=True, capture_output=True)

# ユーザーが以下を入力:
# "ls -la; rm -rf /important/data; echo done"
# → セミコロンで複数コマンドが実行される

# 安全な実装
def run_bash_tool_safe(command: str):
    import subprocess, shlex
    # 1. 許可リスト方式でコマンドを制限
    allowed_commands = ["ls", "cat", "grep", "echo"]
    parts = shlex.split(command)
    if parts[0] not in allowed_commands:
        raise PermissionError(f"Command '{parts[0]}' is not allowed")
    # 2. リスト渡し（shell=False）でインジェクション防止
    return subprocess.run(parts, shell=False, capture_output=True,
                          timeout=30)  # 3. タイムアウト必須

シークレット管理の原則

絶対にやってはいけないこと

API キー・パスワード・トークンをプロンプト・CLAUDE.md・ハーネスのコード本体に直書きしない。LLM はコンテキストウィンドウの内容をログ・トレースに記録することがあり、秘密情報が漏洩する。

✅ Fix: 環境変数（os.environ）・シークレットマネージャー（AWS Secrets Manager / HashiCorp Vault）経由で取得。ツール定義にシークレットを含めない。
# NG: プロンプトにシークレットを埋め込む
system_prompt = f"Use API key: {API_KEY} to call the service."

# OK: 環境変数経由でツール内部で取得
import os

def call_external_api(query: str) -> str:
    api_key = os.environ["EXTERNAL_API_KEY"]  # ← ツール内部で取得
    # プロンプト・ログには API キーが現れない
    response = requests.get(endpoint, headers={"Authorization": f"Bearer {api_key}"},
                            params={"q": query})
    return response.json()

出力サニタイズ（Output Sanitization）

エージェントの出力をユーザーに表示する前に、以下を必ず除去・エスケープします：

  • XSS: HTML タグ・JavaScript を HTML エスケープ（<script> → &lt;script&gt;）
  • 機密情報の漏洩: 出力にシークレットパターン（sk-... / Bearer ...）が含まれていないか regex でチェック
  • 過剰な内部状態の露出: エラーメッセージにスタックトレース・DB スキーマ・ファイルパスを含めない
  • Markdown インジェクション: ユーザー表示前に Markdown を適切にレンダリング（未レンダリングのまま表示すると攻撃ベクターになりうる）

Claude Code の権限システム ── 実装参考例

Claude Code の .claude/settings.json はハーネスの権限バウンダリ設計の実例です：

// .claude/settings.json
{
  "permissions": {
    "allow": [
      "Bash(git:*)",          // git コマンドのみ許可
      "Bash(npm run *)",       // npm スクリプトのみ許可
      "Read(**)",              // 全ファイル読み取り許可
      "Write(src/**)"          // src/ 以下への書き込みのみ許可
    ],
    "deny": [
      "Bash(rm -rf *)",        // 危険な削除を明示的に禁止
      "Bash(curl * | bash *)", // パイプ実行を禁止
      "Write(.env*)"           // .env ファイルへの書き込み禁止
    ]
  }
}
// → モデルが「許可されていない操作」を試みると
//    ハーネスレベルで自動ブロック（モデルに判断させない）

コスト最適化戦略

本番ハーネスではコストの最適化はアーキテクチャの問題です。後から「削減しよう」とすると大幅なリファクタリングが必要になるため、設計段階から組み込む必要があります。

モデルルーティング ── クエリ難易度に応じてモデルを自動選択

全てのクエリに最高性能モデルを使うのは最もコストが高い設計です。難易度を推定してモデルを振り分けることで 60〜80% のコスト削減 が可能なケースがあります。

from anthropic import Anthropic

client = Anthropic()

def classify_query_complexity(query: str) -> str:
    """クエリ難易度を安価なモデルで分類する"""
    resp = client.messages.create(
        model="claude-haiku-4-5",   # 分類自体は安価なモデルで
        max_tokens=20,
        messages=[{
            "role": "user",
            "content": f"""以下のクエリの難易度を答えてください:
            simple: 事実確認・翻訳・要約・フォーマット変換
            complex: 推論・コード生成・複数ステップ問題・分析
            クエリ: {query}
            答え（simple/complex のみ）:"""
        }]
    )
    return resp.content[0].text.strip().lower()

def smart_route(query: str) -> str:
    complexity = classify_query_complexity(query)
    if complexity == "simple":
        model = "claude-haiku-4-5"          # 入力 $0.80/MTok
    else:
        model = "claude-sonnet-4-5"         # 入力 $3/MTok
    # 最上位モデルは明示的に指定した時のみ使用

    resp = client.messages.create(
        model=model,
        max_tokens=2048,
        messages=[{"role": "user", "content": query}]
    )
    return resp.content[0].text

キャッシュ戦略

手法 仕組み 効果 注意点
完全一致キャッシュ クエリ文字列のハッシュをキーにレスポンスを Redis にキャッシュ 同一クエリを 100% カット テキストが 1 文字違うとミス
セマンティックキャッシュ クエリを Embedding 化し、コサイン類似度が閾値（例: 0.95）以上なら同じレスポンスを返す 類似クエリも再利用可能 類似度閾値の調整が必要
Prompt Caching（API） Anthropic の Prompt Caching 機能。長いシステムプロンプトをサーバー側でキャッシュ キャッシュヒット時に入力トークンコスト 90% オフ 1,024 トークン以上のブロックが対象
結果キャッシュ（TTL 付き） ニュース要約・レポート生成など、一定時間で陳腐化するタスクに TTL を設定 同じ作業の重複実行を防止 TTL の設定ミスで古い情報を返す

プロンプト圧縮（Prompt Compression）

長いコンテキストを必要とするタスクでは、入力トークンの削減が最大の節約ポイントです：

  • LLMLingua / LLMLingua-2: Microsoft Research 製。LLM を使ってプロンプトを最大 20× に圧縮しながら精度を維持
  • 選択的要約: 会話履歴が長くなったら古い部分を自動要約してコンテキストを圧縮（rolling summary）
  • チャンク戦略: 大きなドキュメントを全文渡さず、RAG で関連チャンクのみを渡す
  • 構造的削除: コードの場合、関数シグネチャとコメントのみを渡し、実装本体は必要な時だけ取得する

タスク実行前のコスト推定

import anthropic

# 価格テーブル（2026年6月時点）
PRICING = {
    "claude-haiku-4-5":   {"input": 0.80,  "output": 4.00},   # USD/MTok
    "claude-sonnet-4-5":  {"input": 3.00,  "output": 15.00},
    "claude-opus-4-5":    {"input": 15.00, "output": 75.00},
}

def estimate_cost(model: str, input_tokens: int, output_tokens: int) -> float:
    price = PRICING[model]
    return (input_tokens * price["input"] + output_tokens * price["output"]) / 1_000_000

def count_tokens(text: str) -> int:
    """tiktoken 相当の近似カウント（実際は API の count_tokens を使用）"""
    client = anthropic.Anthropic()
    result = client.messages.count_tokens(
        model="claude-haiku-4-5",
        messages=[{"role": "user", "content": text}]
    )
    return result.input_tokens

# タスク実行前に予算チェック
def guarded_run(prompt: str, budget_usd: float = 0.10) -> str:
    tokens = count_tokens(prompt)
    estimated = estimate_cost("claude-sonnet-4-5", tokens, tokens * 3)
    if estimated > budget_usd:
        raise ValueError(
            f"推定コスト ${estimated:.4f} が予算 ${budget_usd} を超えています。"
            f"入力 {tokens:,} トークン → claude-haiku-4-5 に切り替えることを推奨"
        )
    # 予算内なら実行
    client = anthropic.Anthropic()
    resp = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=tokens * 3,
        messages=[{"role": "user", "content": prompt}]
    )
    return resp.content[0].text

    # LLM に制約を渡して最適化版を生成
    return llm.generate(f"{core_content} を {constraints} に合わせて最適化")

16 エンジニア Multi-model Routing ハーネス ── クエリ難易度でモデルを自動選択

コスト最適化とパフォーマンス確保の両立を実現するルーティングハーネスの完全実装。分類・実行・観測の 3 フェーズを一つのハーネスに統合します：

from anthropic import Anthropic
from langfuse import Langfuse
import time

client = Anthropic()
langfuse = Langfuse()

# モデルルーティング設定
ROUTING_CONFIG = {
    "simple": {
        "model": "claude-haiku-4-5",
        "description": "翻訳・要約・フォーマット・事実確認"
    },
    "moderate": {
        "model": "claude-sonnet-4-5",
        "description": "コード生成・分析・複数ステップ推論"
    },
    "complex": {
        "model": "claude-opus-4-5",
        "description": "高度な推論・創造的タスク・長文生成"
    }
}

def route_and_execute(query: str, session_id: str) -> dict:
    trace = langfuse.trace(name="routed-query", session_id=session_id)

    # Step 1: 最安価モデルで難易度分類
    classify_span = trace.span(name="classify")
    classifier_resp = client.messages.create(
        model="claude-haiku-4-5",
        max_tokens=10,
        system="クエリ難易度を simple/moderate/complex の1単語のみで答えよ",
        messages=[{"role": "user", "content": query}]
    )
    tier = classifier_resp.content[0].text.strip().lower()
    if tier not in ROUTING_CONFIG:
        tier = "moderate"  # フォールバック
    classify_span.end(output={"tier": tier})

    # Step 2: 選択されたモデルで実行
    config = ROUTING_CONFIG[tier]
    exec_span = trace.span(name="execute", metadata={"model": config["model"]})
    start = time.time()
    response = client.messages.create(
        model=config["model"],
        max_tokens=2048,
        messages=[{"role": "user", "content": query}]
    )
    latency = time.time() - start
    exec_span.end(output=response.content[0].text,
                  metadata={"latency_s": latency, "tier": tier})

    trace.update(output={"tier": tier, "model": config["model"]})
    return {
        "output": response.content[0].text,
        "tier": tier,
        "model": config["model"],
        "tokens_used": response.usage.input_tokens + response.usage.output_tokens
    }

アンチパターン 5 選

① ハーネスなし直接呼び出し（Bare API）

LLM API を直接呼ぶだけで、ツール・メモリ・検証を実装しない。プロトタイプには可だが、本番運用では失敗が積み重なる。

✅ Fix: 最低限ツール層と検証層（型バリデーション + エラー処理）を実装してから本番投入。

② 過剰な抽象化（Framework Over-Engineering）

LangChain の全機能を使おうとして、シンプルなユースケースに過剰な複雑さを持ち込む。デバッグが困難になり、チームの学習コストが爆発する。

✅ Fix: まず必要な 2-3 レイヤーだけを実装。フレームワークは必要になってから選定。

③ 状態の漏洩（State Leakage）

複数のエージェントが同じ状態を無制御に読み書きし、互いの作業が干渉する。並列エージェントのアンチパターン。

✅ Fix: エージェントごとに名前空間分離された状態ストアを持たせる。書き込みには必ずロックを。

④ 検証レイヤー欠如（Validation Gap）

エージェントの出力をそのまま使い、型チェック・サニタイズ・評価ゲートがない。本番でデータ破損・セキュリティ問題が発生。

✅ Fix: すべてのツール出力・エージェント出力を Zod/Pydantic でバリデート。

⑤ モデル依存設計（Vendor Lock-in Harness）

特定モデルの固有機能に依存したツール定義をして、モデル交換ができない状態になる。モデルの API 変更で全体が壊れる。

✅ Fix: MCP / 共通インターフェースでツールを定義。モデル固有機能はアダプタ層で吸収。
