ClawHub の選び方：人気順位ではなく権限と版を読む

最終更新・公式情報確認：2026-10-13。news という旧 URL は維持し、本文は用途別の現行ガイドへ刷新しました。確認日は発表日ではありません。

例と評価案は筆者の設計提案で、未実行です。性能測定・本番導入・安全認定・正式採用の実績を示すものではありません。

スキルや plugin を探せる場所があっても、人気の上位を入れれば仕事が安全に自動化されるわけではない。旧記事のランキング、収益化、審査保証は、現行の根拠として引き継がない。ここでは ClawHub の配布単位と監査表示を読み、どの権限を渡す前に何を確認するかを具体化する。

二つの配布単位

公式 ClawHub は OpenClaw の skills と plugins の公開 registry と説明する。スキルは文書と補助ファイルの版付き bundle、code plugin は互換性の情報を持つ package として区別される。ClawHub 説明文を読むこと、手順を入れること、コードを動かすことは同じ作用ではない。

筆者の導入検討表は、提供者、source、版、変更点、必要なツール、通信先、秘密、出力、戻し方を持つ。保存するときは latest という名前だけでなく評価した版を記す。後の更新が同じ権限と通信を維持するとは仮定しない。

監査表示の二軸

公式 Security Audits は、audit status と risk level を別の問いとして説明する。Pass は無危険の保証ではなく、Review、Pending、Error なども別の状態である。ClawHub Security Audits「低リスクに見える」と「確認が完了した」を混ぜない。Pending を問題なしへ置き換えない。

たとえば記事を公開できるスキルは、目的に沿っていても外部アカウントへ意味のある権限を持つ。監査表示だけで許可するのではなく、今回の仕事にその公開効果が必要かを判断する。読み取りの仕事へ公開権限を配る必要はない。

導入前に文書を読む

スキルは読み込む指示として動くため、文章の中に何を実行するかが書かれている。OpenClaw Skills「便利なカレンダー」という名前より、読み取り、作成、変更、削除のどれを要求するかを読む。補助スクリプトや依存の取得も、本文の文言だけで見落とさない。

合成の予定表を使い、予定の一覧だけを返す、矛盾した日付で止まる、編集が必要なら許可を求める、という試験を作る。実アカウントの秘密や会議情報を初回の評価に入れない。スキルの文書が正しくても、実際のツール設定が過剰なら別の問題として扱う。

更新の差分を評価する

一度採用したスキルの更新は、新規導入より軽く見られがちだ。しかし新しい通信先や補助コードが加わるなら境界が変わる。変更の行を読み、以前の負の入力を再利用する。レビュー済みというラベルを、未来の全版へ延長しない。

相対パスが変わる、依存が増える、出力先が変わる、承認の扱いが変わる、といった差分を記録する。自然な日本語の説明が増えただけか、実行の意味が変わったかを分ける。分からない差分は更新保留の理由になる。

公開する工程は別

公式文書は検索や導入の native flow と、認証を伴う公開や削除の registry flow を分ける。ClawHubこのページは公開や login を実行しない。自作の手順を保存することと、registry へ公開することを別段階にする。

公開候補にするなら、実際の秘密、内部の識別名、個人情報、専用の権限前提を外した合成の例へ変える。出典、対象版、失敗条件も添える。ダウンロード数より、読者が自分の境界で使えることを目標にする。
