PUBLIC HUB EDITING METHOD

完成基準：書いた・確かめた・届いたを分ける

長い本文や検査の緑表示だけで完成を宣言しないための、公開知識ページの引き渡し基準です。制作、事実確認、独立レビュー、公開反映を別々に扱います。

最終更新: 2026-10-13

完成は一つのラベルではない

原稿完成は、読者の問いへ答える本文が揃った状態です。著者検査済みは、著者が構造、参照、根拠と差分を確認した状態です。独立レビュー済みは、別の視点で主張と証拠を突き合わせた状態です。公開反映済みは、対象ブランチと実際の公開ページで反映を観測した状態です。前の段階が次の段階を自動的に保証することはありません。

このページは本リポジトリの編集基準であって、外部製品の品質認証ではありません。最新の配置と編集方針はREADMEと編集入口で確認します。自分で書いた記事に「独立監査合格」と付けないことが、引き渡しの信頼性を守ります。

本文の完成条件

  1. 冒頭で対象読者、解きたい問題、扱わない範囲が分かる。
  2. 仕組みの説明だけで終わらず、選ぶ条件、具体的な手順または入力例、失敗しやすい点、確かめ方がある。
  3. 現行仕様と過去の出来事が混ざらず、製品名、モデル名、APIの識別子、提供面を分けている。
  4. 主要な外部事実は、実際に本文を確認した一次情報へ近接リンクがある。公式の性能主張は、独立した実測と区別されている。
  5. 不明点が具体的である。「調査不足」ではなく「このプランでの利用可否はログイン後の画面を確認していない」と書く。
  6. 秘密、個人情報、非公開作品、内部実行環境を読者向け例に転用していない。

一つの公式資料しかないテーマに、出典数のノルマを満たすため無関係なリンクを足す必要はありません。反対に、料金、ライセンス、提供終了のように用途の判断を左右する主張を、一般的なトップページ一つで済ませてはいけません。

構造と読みやすさの完成条件

本ハブの新しい深掘りページは、識別できるtitle、主題を示す一つのh1、順序立ったh2/h3、更新日、親へのナビゲーション、関連ページと固定旧版を備えます。一つのh1はこのハブの統一規約です。見出しによる論理的な構造と本文領域の識別は、W3Cのページ構造解説も参照できます。

表は比較や対応関係が文章より分かりやすいときだけ使います。見出しセルとデータセルの関係を明示し、レイアウトのために表を使いません。これはW3Cの表の解説で確認した考え方です。色だけに意味を依存せず、長いコードやURLは狭い画面でも読めるか確かめます。

検査結果を過大に読まない

ローカル検査スクリプトは参照先の存在確認に役立ちます。ただし厳密な見出し・タグ・アンカー検査は対象が限定されているため、実行しただけで全記事の構造が保証されたとは言えません。追加したページは個別に検査し、本文も読み直します。外部URLを列挙できても、現在アクセスできることや主張の正しさの証明ではありません。

例として、架空の動画APIの記事なら、タスク作成の説明、完了待ち、結果取得、失敗時の扱いを一続きで説明できれば原稿の条件を満たします。しかし、未実行なら「動作確認済み」とは書けません。APIの存在を公式で確認したことと、そのアカウントで動画を生成できたことは別の証拠です。

引き渡しに残す最小情報

対象: 更新したページの一覧
内容: 読者のどの判断が変わるか
確認: 実行した検査と対象範囲
未確認: 追加の証拠が必要な点
反映: ローカル / commit / push / merge / 公開観測
レビュー: 著者検査か、独立レビューか

不足がある場合は、どの条件が未達かを示して引き渡します。本文が揃っていて独立レビュー待ちなら、そのまま候補として読めます。公開の権限や実行条件が不明なら、検査を理由に公開まで進めません。小さな修正でも対象と証拠の範囲を残せば、次の編集者が再確認の入口を失いません。
