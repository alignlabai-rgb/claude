OpenClaw リファレンス：設定名より先に、責任の場所を探す

最終更新・公式情報確認：2026-10-13。確認日は発表日ではありません。本文の教材・評価案は筆者の提案であり、実行済み成果や導入保証ではありません。

このリファレンスは全設定を複製する辞書ではない。OpenClaw は文書も実装も速く変わるため、古い JSON を長く配布するより、何を変えたいときにどの公式文書へ戻るかを示す。確認していない mission 設定や独自の API を標準機能として掲載しない。

各文書の先には用途別の詳細がある。親ページの短い説明だけを読んで、すべての backend と実行面へ同じ挙動を当てはめない。

Model、provider、channel

Model は使う推論対象、provider はその接続と認証に関係する対象、channel はメッセージの入口である。公式 provider 文書はチャットの channel とモデル provider を分けている。OpenClaw Model providers 同じブランドの Web サービスと API とローカル配布を、同じ利用権限や課金として扱わない。

設定の読み取り表には、対象 ID、接続方式、入力の区分、代替先、確認日を書けばよい。値の見た目が同じでも、実際の接続先と認証方式が違う場合がある。カタログに名前があることは、その利用者が契約上使えることや、その版で対象の機能が動くことの証明ではない。

Skill、tool、plugin

公式 Skills は、SKILL.md を持つ指示の文書を、環境や設定に従って読み込むものとして説明する。OpenClaw Skills 手順の文書を追加することと、実行可能な道具を追加することは同じではない。手順が「送信しろ」と書いても、その送信の許可を自動的に獲得するわけではない。

筆者の読解方法は、スキルの前提、呼ぶツール、入力、出力、禁止効果、失敗時の停止を抜き出すことだ。曖昧な「いい感じに全部処理する」を、実行できる契約へ変える。外部から入れたスキルは通常の資料より実行へ近い位置にあるため、提供元と変更内容を確認する。

Session、workspace、memory

会話の単位、作業の場所、次回へ残る情報は別々に読む。会話を新しくしても、作業領域のファイルや記憶がなくなったとは限らない。逆に作業ファイルを整理しても、元の会話や外部サービスに結果が残る場合がある。削除の相談では「何を消すか」をこの三つへ分解する。

公開資料の整理では、原本へ戻れる URL、確認した日、結論の有効条件を記憶へ添える設計が有益だ。大量の履歴を毎回読み込むより、今の課題へ必要な証拠を選び直す。記憶の数を増やすことを目的にしない。

Automation、実行、配送

現行の公式説明では openclaw automations が定期処理の入口で、openclaw cron は alias である。OpenClaw Automations 旧名が使えることと、旧文書の全設定が現行で同じ意味を持つことは別だ。導入版のヘルプと公式の詳細を確認する。

ジョブの定義がある、開始された、結果が保存された、届けられた、という状態を同じ成功へ畳まない。手動で動かす試行から定期化へ進む際は、時間と配送の条件が新しく増える。失敗時の重複や未確定結果を扱えるか再評価する。

設定変更を検討する順序

対象の仕事を一つ選び、変更したい責任をこの表へ当て、現在の有効設定を読み、効果と回復方法を列挙する。新しい値を書く前に、旧版の何を置き換えるかを説明する。似たキーへ名前だけ置換する移行はしない。

このリファレンスの例は検討の方法であって、秘密登録、公開待受、権限拡大の承認ではない。必要な値は公式文書と実際の環境で確認し、未確認は空欄のまま残す方が、架空の設定例を埋めるより安全である。
