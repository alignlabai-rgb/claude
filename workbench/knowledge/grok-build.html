Grok Build — 再現・最小diff・検証で開発を閉じる

coding agentをコード生成機ではなく、仕様から証拠までつなぐ実装担当として使います。権限とsandboxの違い、macOSの制約、並列作業の分担までを具体化します。

公式資料で確認した仕様、提供側の評価、本稿の設計提案を区別しています。実アカウント・APIでの性能試験や契約は実施していません。旧本文は刷新前の固定版で参照できます。

1. Buildは「コードを読む」から「変更を検証する」道具

公式のGrok Buildはcoding agentです。対話型TUI、headlessなscript実行、他アプリ向けACPを提供します。Botの共有cloud computerや、Grokの一般チャットとは別の実行面です。Build overview

実務での主な価値は、repoを理解し、対象を限定したdiffを作り、テストで説明を裏付けることです。「修正しました」という返事だけでは完成を確認できません。変更前の失敗を再現し、変更後に同じ失敗が消え、無関係な挙動が変わっていないことを証拠にします。

Web検索が上手なモデルでも、ローカルの未保存ファイル、依存版、実行権限は自動では理解しません。開始rootと対象版を明示し、他人の未commit変更を保護します。読むだけの調査、草稿変更、実テスト、Git公開を別工程にすると終了点が曖昧になりません。

2. PermissionとSandboxは別の防御

Permissionsはtool callを実行してよいかを決めます。Ask、classifierによるAuto、Always-approveがあり、deny ruleとhookは残ります。一方Sandboxは承認済み処理が触れる範囲を制限し、公式docsでは既定offです。

とくに重要な限界は、read-only／strict profileの子process network制限がmacOSではno-opとされること、in-processのmodel APIやweb toolは子network設定で止まらないことです。profile名だけで「外部送信なし」と判断できません。資格情報pathもbuilt-inだけで恒久保護されるとは限りません。Sandboxの制約

したがって、未知repoの依存installやtest scriptを動かす前には、そのscript自身が通信・削除・秘密の読取りをしないか確認する設計が必要です。プロンプトの「安全に」はOS境界を代替しません。逆にsandboxがあるだけで、公開を承認したことにもなりません。

3. 教材例：一件の不具合を閉じる

以下は未実行のworkflow案です。たとえば日付の比較がtimezone境界で一日ずれる不具合では、先に入力と期待値を固定します。「日時処理を全部改善」ではなく、UTCの同一瞬間を日本時間へ表示した場合の一ケースから始めます。

依頼:
対象: date formatting moduleと対応testのみ
再現: UTC日付末尾 → Asia/Tokyoでは翌日になる入力
期待: timezone指定で正しい表示、元入力を破壊しない
返却: 変更diff / 再現test / 実行結果 / 残る制約
禁止: 認証変更、依存全更新、本番deploy、Git push
  1. 最初は読むだけで入口、test runner、関連関数を説明させる。
  2. 変更前testを追加し、狙った理由で落ちることを確認する。
  3. 最小diffで直し、同じtestと周辺testを実行する。
  4. 未実行のtest、環境依存、残る問題を列挙する。
  5. producerとは別の読み手が仕様とdiffを確認する。

テストが通らない時は「環境だから大丈夫」とまとめず、依存不足、実装失敗、再現ケースの誤りを分けます。既存testがゼロなら、緑のexit codeだけを品質証拠にはしません。テスト対象が実際の修正関数を呼んでいるかも確認します。

4. 並列化は共有変更の交通整理から

複数workerには、調査・test設計・別module編集など重ならない対象を渡します。同じpackage fileやindexへ同時に書けば、速く作るより競合を解く時間が増えます。worktreeの採用を含む方法は、使用中の版の公式機能と実際のGit構造を確認して選びます。

共通interface変更は一人がまとめ、workerは依存条件を明示します。別workerの結論をコピーしたreviewは独立検証ではありません。reviewerに原依頼、変更箇所、実test出力を渡し、producerの「合格」を前提にしない構造が有効です。

比較評価では、test成功率だけでなく、不要diff数、秘密への接触要求、拒否後の挙動、再試行の重複、修正に要した人間時間を見ます。小さな実入力での試験に合格してから対象を広げる方が、最初から全面自動化するより失敗の理由を学べます。本稿はBuildを実行しておらず、以上は導入提案です。
