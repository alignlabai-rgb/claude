Llama — Open-weightを自分の運用へ持ち込む設計

weightを取得できる価値は、推論環境と更新時期を選べることです。MoE、メモリ、量子化、license、検索品質を分解し、ローカル採用を判断するための具体的な評価方法を示します。

公式資料で確認した仕様、提供側の評価、本稿の設計提案を区別しています。実アカウント・APIでの性能試験や契約は実施していません。旧本文は刷新前の固定版で参照できます。

1. LlamaとMuseを同じモデル名にしない

LlamaはMetaが公開してきたモデルweightの系統で、手元または自分で選ぶ推論基盤に配置する判断が中心です。一方Museは個人agent、Spark／Wonderはmodel系統、Codeは開発agent、Glimmerは別のopen-weightモデルです。Metaという提供者が同じでも、利用面、license、地域は同一ではありません。Llama 4発表とMeta Connect開発者資料が対象を分けています。

このページは「Metaの最新モデルは全部Llama」と扱わず、Llamaを選ぶ理由から説明します。自分でweightとruntimeを保持し、通信の有無、更新時期、量子化、推論parameterを管理したい場合が候補です。代わりに、model配布物の保管、推論runtimeの更新、hardware容量、運用監視まで自分で持ちます。

2. MoEのactive parameterは必要メモリではない

公式Llama 4記事はScoutとMaverickをnative multimodalなMoEとして説明します。双方のactive parameterは17Bですが、expert構成は異なります。Scoutのsingle H100説明にはInt4量子化条件があります。構成と条件

active parameterは一tokenの計算に使う部分であって、必要なweight保管量ではありません。MoEの総weight、KV cache、vision encoder、runtime workspaceを加えて容量を見積もります。PCのRAMを増やしただけで、GPU memoryや転送帯域まで同じように増えるわけではありません。Apple unified memoryでもOSと他アプリの占有を引く必要があります。

量子化は容量を抑える選択ですが、実装互換、画像入力、日本語、tool callingの品質が同じままとは限りません。モデルを起動できるか、必要なcontextで動くか、要求品質で続けられるかを三段階で確認します。最大contextをそのまま常用すると、速度とcache容量が運用制約になります。

3. Open-weightと利用条件を分ける

Llama 4はCommunity Licenseで配布され、再配布時のlicense添付や表示、Acceptable Use Policyなどの条件があります。単にweightを取得できることからApache 2.0相当とみなしません。公式license本文

本稿は法的適合を判定するものではありません。実際の利用では、配布物の版と付属license、対象地域、作成物の提供形態を担当者が確認します。第三者の量子化配布でも元の条件が消えるとは限りません。最新版のgeneric READMEだけではなく、使用するartifactに対応したlicenseを保管します。

ローカル推論を選ぶ場合でも、installer、model downloader、telemetry、外部embedding、web searchが通信する可能性は別に残ります。「ローカルmodel」という名前ではなく、入力がどのprocessへ渡り、どの通信があるかを検査する設計が必要です。

4. 教材例：私有資料検索を小さく評価する

未実施の設計例として、まず架空の規程10文書で検索と回答を試します。質問には、答えが一箇所にある、二版が矛盾する、文書に答えがない、画像captionが必要、という四種類を入れます。正解表はmodelとは別に準備します。

実験票:
artifact: weightの版、量子化方式、runtime版
入力: 文書集合版、質問ID、context長
測定: 根拠箇所、誤断定、未回答、初回遅延、速度、peak memory
停止: memory不足、外部送信、根拠のない回答、license不明
成果: 正常例だけでなく失敗入力と訂正を残す

RAGを入れるなら、モデル回答の前にretrievalが正しい箇所を拾ったかを別採点します。見つからない失敗を推論modelの問題として誤診しないためです。要約に過去版を混ぜてしまう場合は、modelサイズを上げる前に文書versionと検索filterを見直します。

5. 選択を固定する基準

採用候補にするのは、自分の入力で必要品質を再現し、運用できるruntimeとlicenseが分かり、失敗時の停止と復旧が定義できた場合です。provider benchmarkや公開communityの速度は、同じmachine・量子化・context条件とは限りません。

APIの大モデル、ローカルの小モデル、embedding専用modelの組合せも候補です。ただし秘密をローカルへ置きながら最終回答だけ外部APIへ渡す構成では、その渡す内容を新たな境界として扱います。良い設計はブランドを一つに揃えることではなく、各工程の必要品質と情報境界を満たすことです。

現行Llama全catalogの取り切りは本稿では保証しません。今回取得できた一次資料でScout／Maverickの構成とlicenseを確認し、Muse系統の新発表はMeta更新ガイドへ分離しています。未取得のmodelを「未発売」とは断定しません。
