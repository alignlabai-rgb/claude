1. Azure AI Foundry とは

Microsoft Foundry（旧称: Azure AI Studio + Azure Machine Learning + Azure OpenAI の統合）は、企業が生成 AI アプリケーションを設計・構築・デプロイ・運用するための統合 PaaS プラットフォームです。Google Cloud の「Vertex AI」に相当する Microsoft のエンタープライズ AI 基盤として 2024 年に統合され、2026 年現在は Foundry Agent Service GA・1,900+ モデルカタログ・A2A プロトコル対応を達成しています。

Microsoft Foundry = Azure OpenAI Service + AI Studio + Azure ML + Semantic Kernel + Agent Service の統合プラットフォーム。各サービスが個別に存在していた時代は終わり、単一のポータル・SDK・RBAC で一元管理できる。

コアコンセプト

ハブ（Hub）

組織レベルの管理単位。ネットワーク設定・コンプライアンス・共有リソース（Azure AI Search・Storage・Key Vault）をまとめて管理する。1つのハブに複数のプロジェクトを紐付け可能。

コアコンセプト

プロジェクト（Project）

チーム・用途別の作業空間。モデルデプロイ・ファインチューニング・評価・エージェント構築はプロジェクト内で実施。接続リソース・API キー・データアセットを分離管理。

コアコンセプト

デプロイメント（Deployment）

モデルを API エンドポイントとして公開する単位。従量課金（Pay-as-you-go）またはプロビジョンドスループット（PTU）で課金される。リージョン・バージョン・コンテンツフィルターを個別設定。

コアコンセプト

Foundry Control Plane

2026 年追加。サブスクリプション横断でエージェントを発見・管理するガバナンス層。エージェント監視ダッシュボード・パフォーマンス指標・評価結果を一元可視化。

4. Azure AI Agent Service — マネージドエージェント実行環境

Foundry Agent Service（2025年後半 GA）は、エージェントのインフラ管理を不要にするフルマネージドな実行環境です。Google の Agent Engine に相当する概念で、コードインタープリター・ファイル検索・関数呼び出しを1つの API で提供します。

コードインタープリター

Python コードをエージェント内の分離サンドボックスで実行。データ分析・グラフ生成・計算処理を自律的に実施。セッションは1時間有効（アイドル30分でタイムアウト）。

ファイル検索（File Search）

ベクターストアを自動管理し、エージェントが PDF・Excel・Markdown 等のドキュメントを検索・参照できる RAG 機能。独自ベクターDB 管理が不要。

関数呼び出し（Function Calling）

外部 API・社内システムをツールとして登録。エージェントが状況に応じてツールを選択・実行・結果をフィードバックするループを自律的に制御。

Agent-to-Agent (A2A)

2026 年追加。Foundry エージェントが A2A プロトコルで他エージェントを呼び出し可能。明示的な認証付きマルチエージェントオーケストレーションを実現。

Foundry MCP Server

クラウドホスト型 MCP（Model Context Protocol）を mcp.ai.azure.com で提供（Preview）。VS Code・Visual Studio・Foundry ポータルから Entra 認証で接続。

Long-term Memory（Preview）

エージェントセッション間で記憶を継続する長期メモリストア。自動抽出・統合・検索によりユーザー設定・過去の会話コンテキストを維持。

Python コード例 — Foundry Agent Service で RAG エージェントを構築

# pip install azure-ai-projects azure-identity
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import FileSearchTool, CodeInterpreterTool, AgentsApiToolChoiceOptionMode
from azure.identity import DefaultAzureCredential

# プロジェクトクライアント初期化
client = AIProjectClient(
    endpoint="https://<your-hub>.services.ai.azure.com",
    credential=DefaultAzureCredential(),
)

# ファイル検索ツールを作成（社内 PDF を登録）
file_search_tool = FileSearchTool()
with open("company_policy.pdf", "rb") as f:
    uploaded_file = client.agents.upload_file_and_poll(file=f, purpose="assistants")

vector_store = client.agents.create_vector_store_and_poll(
    file_ids=[uploaded_file.id],
    name="company-docs",
)
file_search_tool.resources.vector_store_ids = [vector_store.id]

# エージェント作成（複数ツールを統合）
agent = client.agents.create_agent(
    model="gpt-4o",
    name="社内 QA エージェント",
    instructions="あなたは社内規程の専門家です。提供された文書を参照して正確に回答してください。",
    tools=file_search_tool.definitions + CodeInterpreterTool().definitions,
)

# スレッドでチャット
thread = client.agents.create_thread()
client.agents.create_message(
    thread_id=thread.id,
    role="user",
    content="就業規則において残業時間の上限は何時間ですか？グラフで示してください。",
)

run = client.agents.create_and_process_run(
    thread_id=thread.id,
    agent_id=agent.id,
)

messages = client.agents.list_messages(thread_id=thread.id)
print(messages.last_text_message_by_role("assistant").text.value)

5. Semantic Kernel — エージェントオーケストレーションフレームワーク

Semantic Kernel（SK）は Microsoft が開発したオープンソースのエージェントオーケストレーションフレームワーク。2026 年 4 月に Microsoft Agent Framework（MAF）1.0 GA としてリリースされ、Semantic Kernel と AutoGen の後継として統合・刷新されました。Python / C# / Java の3言語を公式サポートし、他の主要エージェントフレームワークが Python 専用な中で C# エコシステムとの親和性が特徴です。

Plugins（プラグイン）

エージェントの能力拡張ユニット。ネイティブコード関数・プロンプトテンプレート・OpenAPI スペック・MCP プロトコルをプラグインとして登録。モデルが状況に応じてプラグインを選択・実行。

Agent Framework

チャットエージェント・アシスタントエージェントをモジュール型で構築。ツール・メモリ・計画能力を持つエージェントの生成・統合が可能。GPT-4o / o3 などの推論モデルが計画を内部で処理。

Memory & Context

短期メモリ（会話コンテキスト）・長期メモリ（ベクターストア）・セマンティックメモリ（エンティティ抽出）を管理。Azure AI Search・Redis・Qdrant など複数のバックエンドを選択可能。

マルチエージェント

専門エージェント群を協調させるオーケストレーションパターン。Agent Group Chat・A2A プロトコル・イベント駆動型ワークフローに対応。AutoGen の後継として複雑なマルチエージェント設計を吸収。

モデルプロバイダー

Azure OpenAI / OpenAI / Anthropic Claude / Amazon Bedrock / Google Gemini / Ollama の6プロバイダーに対応。プロバイダー切り替えはコード1行で完了するポータビリティが強み。

LangChain / LlamaIndex 比較

SK の優位点: C# ネイティブ・エンタープライズ統合（M365/Teams）・マルチ言語。LangChain の優位点: Python エコシステムの広さ・OSS コミュニティ。LlamaIndex: RAG 特化で細粒度なインデックス制御。用途で使い分けが基本。

Python コード例 — Semantic Kernel で RAG パイプラインを構築

# pip install semantic-kernel azure-search-documents
import asyncio
from semantic_kernel import Kernel
from semantic_kernel.connectors.ai.open_ai import AzureChatCompletion, AzureTextEmbedding
from semantic_kernel.connectors.memory.azure_ai_search import AzureAISearchCollection
from semantic_kernel.core_plugins.text_memory_plugin import TextMemoryPlugin
from semantic_kernel.memory.semantic_text_memory import SemanticTextMemory

kernel = Kernel()

# Azure OpenAI を AI サービスとして登録
kernel.add_service(AzureChatCompletion(
    deployment_name="gpt-4o",
    endpoint="https://<your-resource>.openai.azure.com/",
    api_key="<your-key>",
))

embedding_service = AzureTextEmbedding(
    deployment_name="text-embedding-3-large",
    endpoint="https://<your-resource>.openai.azure.com/",
    api_key="<your-key>",
)

# Azure AI Search をベクターストアとして接続
collection = AzureAISearchCollection(
    collection_name="company-docs",
    search_endpoint="https://<your-search>.search.windows.net",
    api_key="<search-key>",
    embedding_generator=embedding_service,
)

memory = SemanticTextMemory(storage=collection, embeddings_generator=embedding_service)
kernel.add_plugin(TextMemoryPlugin(memory), plugin_name="memory")

# RAG プロンプト関数を定義
rag_prompt = kernel.add_function(
    plugin_name="rag",
    function_name="answer",
    prompt="""
関連コンテキスト:
{{memory.recall input=$query collection='company-docs' limit=5}}

質問: {{$query}}

上記のコンテキストのみを参照して、正確かつ簡潔に回答してください。
情報がコンテキストにない場合は「情報が見つかりませんでした」と答えてください。
""",
)

async def main():
    result = await kernel.invoke(
        rag_prompt,
        query="Azure AI Foundry の Private Endpoint を設定する手順を教えてください",
    )
    print(result)

asyncio.run(main())

6. RAG パターン — Azure AI Search + Azure OpenAI

RAG（Retrieval-Augmented Generation）は、LLM の回答をコーパスデータでグラウンドするアーキテクチャ。Azure では Azure AI Search + Azure OpenAI + Azure AI Document Intelligence の組み合わせが標準スタックとして確立しています。

標準 Azure RAG スタック: Azure Data Factory（取込）→ Document Intelligence（解析・チャンク化）→ Azure AI Search（インデックス・検索）→ Azure OpenAI（生成）→ Azure Container Apps（配信）

Azure AI Document Intelligence

PDF・Word・Excel・画像からテキスト・表・レイアウトを抽出。Layout モデルでセクション・ページ・段落を構造的に認識してセマンティックチャンキングを実施。スキャン帳票・手書き文書にも対応。

Azure AI Search

ベクター検索（近似近傍）・全文検索・ハイブリッド検索（RRF: Reciprocal Rank Fusion）を統合。Semantic Ranker による意味的な再ランキング。Agentic Retrieval で推論型クエリ分解に対応（2026）。

チャンキング戦略

  • 固定サイズ: チャンクサイズ 512〜1,024 トークン・オーバーラップ 10〜20%
  • セマンティック: 段落・セクション単位で意味を保持
  • 階層: 親チャンク（要約）+ 子チャンク（詳細）の2層構造

ハイブリッド検索

ベクター検索（意味的類似性）と BM25 全文検索を RRF でスコア統合。どちらか一方では取りこぼす文書も発見できる。Azure AI Search では設定1行で有効化可能。

On Your Data（ノーコード RAG）

Azure OpenAI の「On Your Data」機能で、コードを書かずに AI Search をグラウンディングソースとして接続。プロトタイプ・デモ用途に最適。本番では SDK 経由が推奨。

Agentic Retrieval（2026）

複雑な質問を AI Search が自動でサブクエリに分解し、複数ステップで情報を取得。「先月の売上と前年比を製品カテゴリ別に教えて」のような複合クエリに対応。

RAG アーキテクチャ 実装フロー

インデックス構築フロー（オフライン）
1. データ取込: Azure Data Factory / Blob Storage
↓
2. 文書解析: Document Intelligence (Layout model)
↓
3. チャンキング: セマンティック / 固定サイズ分割
↓
4. 埋め込み生成: text-embedding-3-large
↓
5. インデックス: Azure AI Search (Vector + BM25)
クエリ処理フロー（オンライン）
1. ユーザークエリ受信
↓
2. クエリ埋め込み生成 (text-embedding-3-large)
↓
3. ハイブリッド検索 → Semantic Ranker
↓
4. Top-K 文書をコンテキストに注入
↓
5. GPT-4o で回答生成（引用付き）

7. Fine-tuning — カスタムモデル構築

Azure OpenAI のファインチューニングは、独自データでモデルの文体・専門用語・出力フォーマット・応答スタイルを特定タスクに特化させる手法。プロンプトエンジニアリングで解決できない反復的なパターンの学習に有効。

注意: ファインチューニングは万能ではない。「知識を追加する」用途（最新情報など）には不向きで、RAG の方が適切。ファインチューニングが有効なのは「出力形式の一貫化」「特定ドメインの文体習得」「Few-shot 例を大量に必要とするタスクの削減」。

ファインチューニングが有効な場面

  • 特定の出力フォーマット（JSON スキーマ厳守）
  • ブランド固有のトーン・文体の学習
  • 業界専門用語の精度向上
  • Few-shot プロンプトの長さを削減
  • 反復的なタスクのレイテンシ改善

ファインチューニング vs RAG

  • 最新知識の追加 → RAG
  • ハルシネーション防止 → RAG
  • 文体・形式の一貫化 → Fine-tuning
  • 応答速度改善（Few-shot 削減） → Fine-tuning
  • 両方必要な場合 → Fine-tuned model + RAG を組み合わせ

8. エンタープライズ機能 — セキュリティ・コンプライアンス

Azure AI Foundry は Microsoft のエンタープライズクラウドインフラを活用したゼロトラスト・閉域ネットワーク・規制業界向けコンプライアンスを標準提供します。

ネットワーク

Private Endpoint（閉域接続）

Azure Virtual Network 内に Private Endpoint を設定することで、インターネットを経由しないフルプライベート通信を実現。Azure OpenAI・AI Search・Storage へのアクセスをすべて VNet 内に閉じ込める。

  • パブリックアクセス完全無効化が可能
  • ExpressRoute / VPN Gateway との統合
  • MCP サーバー・Azure AI Search を含む全接続に対応（2026）
アイデンティティ

Microsoft Entra ID（旧 Azure AD）を使った細粒度なアクセス制御。APIキー認証よりも Entra 認証が推奨（Microsoft 公式方針）。

  • Azure AI Developer / Contributor / Reader ロール
  • マネージド ID でシークレットレス認証

PTU（プロビジョンドスループット）の考え方

PTU（Provisioned Throughput Units）とは、一定のスループット（トークン処理能力）を月単位で予約する課金モデル。従量課金がトークン単価で課金されるのに対し、PTU は「処理能力を借りる」イメージ。

  • いつ PTU を選ぶか: 月間トークン消費が安定して 1.5〜2 億トークンを超えるようになったとき。それ以下なら従量課金の方が安い。
  • 節約効果: 従量課金比 最大 70% コスト削減（GPT-4o の大規模利用時）
  • リスク: 使わなくても月額固定費が発生。使用率の予測が必要。
