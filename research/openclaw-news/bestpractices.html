OpenClaw の実践原則：同じ失敗を評価へ組み込む

最終更新・公式情報確認：2026-10-13。news という旧 URL は維持し、本文は用途別の現行ガイドへ刷新しました。確認日は発表日ではありません。

例と評価案は筆者の設計提案で、未実行です。性能測定・本番導入・安全認定・正式採用の実績を示すものではありません。

ベストプラクティスを一般的な「明確に指示する」「小さく始める」で終わらせない。重要なのは、自分の仕事で起きた具体的な失敗を、次回も使える入力と合格条件へ変えることである。ここでは公開資料を扱うエージェントの五つの実践を、反例と一緒に示す。

一：完了を成果物へ結ぶ

筆者の設計案では、比較表と根拠が保存されて初めて原稿準備を完了とする。「調べます」という返答や長い考察は途中である。公式 personal benchmark も、根拠のある task status と fake progress を区別するシナリオを持つ。Personal Agent Benchmark Packその思想を採点へ反映し、モデルの自己宣言で判定しない。

反例は、前日の比較表を指して今日も完了と言う場合。入力の版と結果の対応がないなら未確認にする。ファイルがあること、今回の要求を満たすこと、採用できることを三段階に分ける。

二：許可を効果で書く

「ファイルを変更する tool は禁止した」という設定でも、shell が書けるなら同じ効果へ到達し得る。公式 policy はその区別を注意する。OpenClaw Policy as code許可はツールの名前だけでなく、読める対象、書ける対象、送信先、費用を分けて記す。

反例は、拒否された編集を別の tool へ移して実行する場合。実行できたことを修復成功とせず、禁止された効果の回避として不合格にする。必要な変更なら、権限を持つ運用者へ要件を戻す。

三：保留を正解へする

資料の対象が違う、値が矛盾する、地域が分からない、公開条件がないとき、空欄を推測で埋めない。合成の正しい保留入力を作り、毎回の検査へ含める。常に何か記事を完成するという条件は、必要な保留を失敗にしてしまう。

反例は、公式の段落がない価格を「おそらく無料」と書く場合。文章として自然でも根拠のない判断である。候補の提案と、契約や購入の判断を別にする。

四：記憶へ有効条件を添える

短い方法カードには、対象、確認日、根拠、使えない条件を残す。速報の結論を安定した事実へ保存しない。削除についても、公式 memory の forget と admission には範囲があり、全面消去ではない。OpenClaw Memory provenance and deletion覚える前に不要な情報を取り込まない設計が重要になる。

反例は、一度の失敗を「このモデルはいつも無能」と永続化する場合。モデルと版、入力、実行条件のどこが原因か分からなければ、その一般化を避ける。過去の観測と現行の指示を区別する。

五：回帰集合を少数にする

正常、保留、拒否、重複、途中停止の五件だけでも、毎回同じ条件で検査できれば役立つ。無関係な百件を走らせるより、変えた境界へ関係した負の入力を残す。新しい機能を使わない場合、その機能のために検査を増やす必要はない。

反例は、更新後に一度会話できたから旧い全課題も合格と扱う場合。見た画面と、試していない実行経路を分ける。試行をしていない欄は未測定と書く。

実践を再利用物へする

失敗を一つ選び、合成入力、正しい停止または結果、禁止効果、確認方法を四点セットにする。日誌の長さではなく、次の人が同じ検査を使えることが価値になる。記事、スキル、評価集合は違う成果物だが、この四点が共通していればつなげられる。

これらは実地の成功率を証明した規則ではなく、筆者の運用案である。採用する際は対象の業務と設定へ合わせ、例外も記録する。ベストプラクティスの名前を権限拡大の理由にしない。
