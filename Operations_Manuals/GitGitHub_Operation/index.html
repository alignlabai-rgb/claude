GitとGitHub操作ガイド：保存・同期・公開を分ける

作業木、commit、リモート、main、配信を別の状態として確認する手順です。

旧本文は固定旧版へ分離しました。本稿の教材・依頼例・試験案は合成データによる未実行例です。実案件の実績を再認定するものではありません。

五つの状態を混ぜない

作業木は現在のファイル、stagingは次のcommitへ入れる変更、commitはローカル履歴です。GitHubへpushするのはリモートの参照と履歴を更新する操作で、すべてのローカルファイルを無条件で同期するものではありません。status・commit・push。

ブランチへpushした、mainへ取り込まれた、Webサイトが配信されたという状態は別です。公開サイトを持つ場合、配信元とdeployの仕組みを確認します。mainへの更新で公開する設定もありますが、すべてのリポジトリが同じではありません。GitHub公式配信チュートリアル。

作業開始は状態の確認から

未実行の確認例はgit status --short --branchとgit diffです。変更されたファイルと未追跡の対象、現在のブランチを確認します。既存の変更は自分のものと決めつけず、誰の作業か分からない差分をまとめて消したりcommitへ混ぜたりしません。状態確認・差分。

複数の端末や自動ニュース生成が同じリポジトリへ書くなら、前回見たorigin/mainを最新と扱わないことが重要です。対象のリモートとブランチを確認し、取得して差分を把握してから統合します。『自分以外は触っていないはず』という認識では、自動処理の更新を見落とします。

pullはダウンロードだけではない

pullはfetchした内容を現在のブランチへ統合する操作です。単にGitHub側を読むだけとは違います。未実行例のgit pull --ff-only origin mainは、現在のブランチが意図したmainであり、作業状態を確認した場合に使う例です。分岐があれば失敗するため、そこで統合方法を判断します。公式pull。

分岐や競合がある状態で、何度もpullを繰り返して解決しようとしません。相手の変更、こちらの変更、現在進行中のmergeまたはrebaseを確認します。別のfeature branchで作業している場合に、上のmainの例をそのままコピーすることも避けます。コマンドの成功より、どの履歴をどこへ統合したかが要点です。

変更を小さく確定する

合成のarticle.htmlを直す教材なら、まず本文とローカル参照を検査します。許された対象だけをstagingへ入れ、git diff --cachedで次のcommitへ入る差分を読みます。関係ない変更、内部パス、秘密値、未公開素材が紛れていないかも確認します。staged差分。

commitの説明には目的と確認できた範囲を残します。『全面更新』だけでは次の人が採用理由を追えません。ローカルcommitができたことをGitHub更新として報告しないようにします。公開が別承認の仕事なら、ここで止めることも正しい区切りです。

pushとPull Request

pushする時は対象のリモートとブランチを確認します。明示したgit push origin mainはローカルmainからリモートmainへの更新例ですが、ブランチ保護や運用次第で直接pushできない場合があります。目的の履歴がどこへ届いたかを実際の結果で確認します。拒否されたからforceへ進む手順は標準にしません。公式push。

Pull Requestは変更を提案し、レビューし、取り込むための区切りです。PRを開いただけではmainが更新されたことになりません。差分、checks、必要な承認、取り込み先を確認します。公式PR。同じ人の作業でも、受入条件を見える形に残せる利点があります。

競合で守るもの

競合が出たら双方の意図を読み、どちらかの全ファイルを採用して終わらせないようにします。合成教材では、片方が説明を更新し、もう片方が出典リンクを直したケースを考えます。解消後は両方の期待条件が残っているかを検査し、競合マーカーが消えたことだけを合格にしません。

mergeやrebaseを中断する入口は公式pull文書にありますが、既存の未確定変更がある場合は正確な対象と状態を先に確認します。全体reset、履歴の強制上書き、credentialの変更は通常の競合解消とは別です。復旧できることを確認せずに広い破壊操作を使わないでください。統合と中断。

同期したのにWebが古い場合

GitHub上で意図したファイルとcommitがmainへ入ったかをまず確認し、次に配信の対象ブランチ、ディレクトリ、build、deploy結果を調べます。GitHubのファイル更新と配信完了が別なら、pushの再実行では原因が変わらない場合があります。ブラウザの古い表示も、履歴の欠落と同じに扱いません。

未実行の教材では、feature branchだけを更新した状態、mainには入ったがdeployが失敗した状態、配信済みだが表示が古い状態を分けます。それぞれで調べる証拠を変え、未確認の状態を『更新済み』と報告しないことを評価します。公開経路の成功は配信結果で確認します。

終了時に返す短い状態

終了報告は『ローカル編集』『commit』『リモートの対象ブランチ』『mainへの取り込み』『Web公開』の各状態と、未確認を並べます。必要に応じて対象commitやPRを付けます。長い操作ログを共有するより、どこまで確定したかが分かる報告を重視します。

安全な運用はGitを自動同期の魔法として扱わないことです。新規ファイルやignoredファイルは別に存在でき、自動更新との競合も起こります。差分と対象を確認し、履歴を小さく残し、公開の区切りを見失わない方法を、合成の正常例と競合例で練習してください。
