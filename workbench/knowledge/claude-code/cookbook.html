The Cookbook

Practical Recipes for Daily Engineering
Recipe 01: The "Strangler Fig" Refactoring LEGACY CODE

動いている巨大レガシーシステムを止めずに、少しずつ新システムへ移行させる高等テクニック（ストラングラー・フィグ・パターン）の実践。

Step 1: Interface Extraction

まず、既存の複雑な関数をラップするインターフェースを作らせます。

$ claude "src/legacy/OldBilling.js の `calculateTax` メソッドと同じ入出力を持つTypeScriptインターフェース `ITaxCalculator` を定義して。実装はまだしなくていい。"
Step 2: Dual Implementation

新旧両方のロジックを並行稼働させる準備をします。

$ claude "ありがとう。次に `BillingProxy` クラスを作成して。このクラスは `ITaxCalculator` を実装し、内部に `OldBilling` と `NewBilling` (まだ空でいい) の両方を持つ。 featureFlag が true なら New を、false なら Old を呼ぶようにして。"
Step 3: Test & Switch

新しいロジックを実装し、テストを通します。

$ claude "完璧だ。では `NewBilling` に最新の税率計算ロジックを実装して。その上で、Old と New が同じ入力を受けた時に、同じ結果を返すかを検証するテスト `parity.spec.ts` を書いて。"
Recipe 02: "Read-Only" Analyst Mode RESEARCH

コードを書き換えずに、プロジェクトの構造や潜在的なバグだけを調査させる、安全な分析モード。

The Prompt (Copy & Paste)
$ claude --print "このプロジェクトを Security Analyst として監査して。 以下の3点に絞ってレポートを出力せよ（ファイル修正は禁止）。 1. **SQL Injection**: 生のSQL文字列結合を行っている箇所はあるか？ 2. **Sensitive Data**: APIキーやパスワードがハードコードされていないか？ 3. **Dependency**: 脆弱性が既知の古いライブラリ (`package.json`) はあるか？ 出力はMarkdown形式のレポート `AUDIT_REPORT.md` として標準出力すること。" > AUDIT_REPORT.md
Recipe 03: The "TDD" Loop BEST PRACTICE

最も堅実な開発スタイル。テストファーストをAIに強制する。

Phase 1: Generative Testing
$ claude "機能: ユーザーがCSVをアップロードし、一括登録するAPI 要件: - 1回の上限は1000件 - メールアドレスの形式チェック必須 - 重複ユーザーはスキップ 上記仕様を満たす `import-users.spec.ts` を作成して。 実装クラス `ImportService` はまだ存在しないので、インポートエラーになっても構わない。 まずは『あるべき仕様』をテストコードとして定義して。"
Phase 2: Implementation to Green
$ claude "テストありがとう。 では、このテスト `import-users.spec.ts` がコンパイルエラーなく実行でき、かつ全てのテストケースが PASS するように `ImportService.ts` を実装して。 必要なライブラリがあれば `npm install` していい。"
Recipe 04: "API First" Generation API DESIGN

OpenAPI スペックを起点に、型定義・サーバー実装・クライアント SDK・テストをすべて自動生成するパターン。仕様を「単一の真実の源泉」として、実装とテストの乖離をゼロにする。

Step 1: スペック作成

ビジネス要件を Claude に渡し、OpenAPI 3.1 の YAML を生成させます。

$ claude "以下のビジネス要件を満たす OpenAPI 3.1 スペックを YAML で作成して。 - エンドポイント: POST /users, GET /users/{id}, PATCH /users/{id} - 認証: Bearer JWT - レスポンス: JSON、エラーは RFC 7807 準拠 ファイル名: openapi.yaml"
Step 2: クライアント / サーバー生成

生成したスペックから、型定義・ルーター・SDK を一括で出力させます。

$ claude "openapi.yaml を読んで、以下を生成して: 1. TypeScript の型定義 (types/api.ts) 2. FastAPI のルーター実装 (routers/users.py) 3. axios を使ったフロントエンド SDK (sdk/users.ts)"
Step 3: テスト生成

スペックに基づき、正常系・異常系を網羅したテストを自動生成します。

$ claude "openapi.yaml の各エンドポイントに対して pytest テストを生成して。 正常系・異常系（400, 401, 404, 422）を網羅すること。"
ポイント: スペック変更時は Step 1 だけを更新し、Step 2・3 を再実行する。「スペックが変われば実装とテストも自動で追随する」サイクルを作ることが目的。
Recipe 05: "Database Migration" Safety DATABASE

本番データに影響するスキーマ変更を安全に行うパターン。まず読み取り専用で影響分析を行い、人間が確認してから実行計画を作成する二段構えが鉄則。

Phase 1: 影響範囲分析（Read-Only）

migration ファイルを読み取り専用で分析し、リスクと rollback 手順をまとめます。

$ claude --print "migrations/ 以下の新しい migration ファイルを読んで: 1. 影響を受けるテーブルと列を列挙 2. データ消失リスクがある操作を赤字で特定 3. ロールバック手順を3ステップで説明 ファイルは修正しないこと。" > migration_analysis.md
Phase 2: ダウンタイムなし移行計画の作成

分析結果をもとに Blue-Green デプロイで無停止移行を実現する手順書を生成します。各ステップには必ずロールバック可否を明記させます。

$ claude "migration_analysis.md を読んで、 Blue-Green デプロイで無停止 migration を実現する手順書を作って。 各ステップに 'SAFE TO ROLLBACK: YES/NO' を明記すること。"
原則: migration は「実行→確認→次ステップ」の小刻みなサイクルで進める。1 回の migration で複数テーブルを変更しない。
Recipe 06: "Documentation Sync" DOCS

実装とドキュメントを常に一致させる自動化パターン。コードを正とし、ドキュメントの抜けを自動検出・補完する。

The Prompt (Copy & Paste)
$ claude "以下をすべて実行して: 1. src/ 以下の全 TypeScript ファイルを読む 2. 公開API（export された関数・クラス）の一覧を抽出 3. docs/API_REFERENCE.md と比較して、ドキュメントに抜けている関数を特定 4. 抜けている関数の JSDoc コメントを src/ に追記 5. docs/API_REFERENCE.md を自動更新"
応用: CI/CD に組み込むと、PR マージのたびにドキュメントが自動更新される。「ドキュメントが古くなる問題」を仕組みで解決するのが狙い。
Recipe 07: "Incident Response" Assistant DEBUGGING

本番障害時の高速トリアージパターン。エラーログをパイプで渡し、上級 SRE ペルソナで根本原因・緩和策・次の調査コマンドを 5 分以内に返させる。

Incident 発生時のコマンド（コピペで即使用）
$ cat /var/log/app/error.log | tail -n 200 | \ claude -p "あなたは上級 SRE です。 このエラーログを分析して以下を5分以内に回答してください: 1. 根本原因 (Root Cause) の仮説 TOP3 とその確率 2. 即時の緩和策 (Mitigation) — サービス影響を最小化するための操作 3. 調査すべき次の3コマンド 現在の時刻: $(date). 影響範囲を最小化することを最優先にしてください。"
ポストモーテム作成への応用
$ claude "incident_log.md を読んで、以下の形式でポストモーテムを作成して: - タイムライン（時系列の出来事） - 根本原因（技術的原因と組織的原因） - 影響範囲（対象ユーザー数・ダウンタイム） - 再発防止策（Action Item と担当者・期限）"
ポイント: ログの末尾 200 行だけをパイプすることでコンテキストを節約しつつ、最新の異常シグナルを確実に渡せる。ログが多い場合は grep ERROR で絞り込んでからパイプする。
Recipe 08: "Codebase Onboarding" KNOWLEDGE

新規参加者・新セッションのための高速キャッチアップパターン。Claude にリポジトリを探索させ、次のエージェントや人間が 30 分で戦力になれる ONBOARDING.md を自動生成する。

ONBOARDING.md 自動生成
$ claude --print "このリポジトリの新しい担当者向けに以下を作成してください: 1. 30行以内のアーキテクチャ概要（図なし・テキストのみ） 2. 開発環境の立ち上げ手順（コマンドつき） 3. 'はじめての修正' として適切な 3 Issues の提案（難易度: easy） 4. 地雷（このコードには手を出してはいけない）ファイル・関数の警告一覧 ONBOARDING.md として出力。" > ONBOARDING.md
新セッション開始時の高速リロード

ONBOARDING.md を作成したら、以降のセッションでは冒頭に読み込ませるだけで済みます。

$ claude "ONBOARDING.md と CLAUDE.md を読んで、現在の作業コンテキストを把握してください。 把握できたら「準備完了」と一言だけ返してください。"
応用: ONBOARDING.md は CI で定期自動更新すると鮮度を保てる。
CLAUDE.md との違い: CLAUDE.md はエージェントへの「命令書」、ONBOARDING.md は人間とエージェント双方への「地図」として使い分ける。
