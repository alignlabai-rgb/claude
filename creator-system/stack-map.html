このページの狙い

「比較」でも「フロー」でもなく
スタックと工程の対応

ハブには既に2種類の地図があります。 生成ツール比較は「どのツールが優れているか」の選定軸、 全体フローは「工程の順番」を示します。 しかし「ネタ生成にはどのモデルの頭脳が要り、評価には何が動き、深掘りはどのページを読めばいいのか」を 一望できる対応表がありませんでした。このページはその欠けていた背骨を埋めます。

  • 工程ごとに「担うモデル・ツール」を明示
  • 各ツールの深掘りページ（workbench/knowledge）へ直結
  • 代替・フォールバック先を併記して移行に強く
  • モデル世代交代に追従する仕組みへ接続

4つのレイヤーと担当ツール

🧠

L1 — 頭脳（LLM）

ネタ発想・ストーリー構造化・脚本・コマ割り設計・評価の自然言語判断を担う中枢。

担当: Claude Opus 4.8 / Sonnet 4.6・Gemini 3.1 Pro・GPT-5.5
深掘り: Claude / Gemini / ChatGPT
🎬

L2 — 生成エンジン

テキスト/画像を動画・キービジュアル・音声・音楽へ変換する生成モデル群。

担当: Veo 3・Runway・Kling（動画）/ SDXL・Imagen 4 Ultra（画像）/ ElevenLabs（音声）/ Suno（音楽）
深掘り: Veo / Imagen / Lyria / 生成ツール比較
🎛

L3 — 制御・評価

生成の一貫性を制御し、出力品質を機械採点して公開可否を判定する層。

担当: ComfyUI・ControlNet・IP-Adapter・LoRA（制御）/ CLIP・Gemini 3.1 Pro Vision（評価）
深掘り: ComfyUI 完全ガイド / 評価システム
🚀

L4 — 配信・運用

完成物をプラットフォームへ投稿し、全工程を自動オーケストレーションする層。

担当: YouTube / note / Kindle API・NotebookLM（派生）/ OpenClaw・PicoClaw・Signal
深掘り: NotebookLM / Claw Stack / OpenClaw 連携

接続方式のアップデート（2026年中頃）

「API直叩き」から
MCPコネクター経由へ

2026年4月28日、Anthropic は Blender・Adobe Creative Cloud・Ableton を含むクリエイティブ系 MCP コネクター9本を一斉公開しました。 Blender コネクターは Blender 開発チーム自身がメンテナンスする MCP サーバーとして提供され、Claude 以外の LLM からも呼び出せるオープンな設計になっています。 Adobe コネクターは 50 以上のツールにアクセスでき、画像/動画のアニメーション化や生成・改変を自然言語で扱えます。

これは L2/L3 レイヤーの接続方法における選択肢の追加であり、既存の REST API 直叩き構成（本ハブの現行構成）を置き換える必須要件ではありません。 「認証・ツール呼び出しの形式を MCP に標準化できる場面が増えた」という事実として記録します。

  • ComfyUI/LoRA中心の漫画生成は現状維持（MCP移行の優先度は低い）
  • ポスプロ微調整（色調整・テロップ位置修正等）は Adobe コネクター経由の HITL 修正が候補
  • 3Dアセットや複雑な画角指定が要る回では Blender コネクターが選択肢に
  • BGM/SEの精密編集は Suno（生成）+ Ableton コネクター（編集・確認）の二段構成も検討可

直叩きAPI vs MCPコネクター

# 従来: REST APIを個別に直叩き POST https://api.runwayml.com/v1/generate Authorization: Bearer RUNWAYML_API_KEY # → サービスごとに認証・スキーマ・エラー処理を個別実装 # MCP経由: ツール呼び出しを標準化 mcp_client.call_tool( server="adobe-creative-cloud", tool="animate_image", args={"asset_id": "scene_04.psd"} ) # → 認証・ディスカバリはMCPサーバー側が担い、 # 呼び出し側は「どのツールを叩くか」だけに集中できる
⚠️ ここで挙げたクリエイティブ用途への当てはめ（Blender/Ableton連携案等）は本ハブ側の仮説的な拡張案であり、実運用で検証済みの構成ではありません。導入前に各コネクターの権限スコープ・料金体系を必ず確認してください。
工程間データフローの具体例

構造化データが
各工程でどう変形するか

「②構造化・脚本」で生成される topic_data.structured が、動画パイプラインと漫画パイプラインでそれぞれどんな中間データ形式に変換されるかを具体例で示します。 型は 仕様書の型定義（TopicMeta / ContentArtifact）と整合させています。

動画: 脚本 → 絵コンテ → 生成リクエスト

// Step1: 構造化された脚本（L1出力） { "scenes": [ { "id": 1, "desc": "雨の商店街、主人公が傘を忘れる", "narration": "人生、忘れ物との闘い。", "duration_sec": 4 } ] } // Step2: 絵コンテ化（カメラ・尺を確定） { "scene_id": 1, "camera": "slow_pan_right", "style_preset": "news_modern", "ref_image": "gs://.../scene1_ref.png" } // Step3: 生成モデルへのリクエスト（L2） POST /v1/video/generate // Veo系API想定 { "prompt": "雨の商店街、傘を忘れる主人公、slow pan right", "reference_image": "gs://.../scene1_ref.png", "duration_sec": 4, "aspect_ratio": "9:16" }

漫画: 脚本 → コマ割り → 生成リクエスト

// Step1: 構造化された脚本（動画と共通のtopic_data由来） { "beats": [ { "id": 1, "desc": "雨の商店街、主人公が傘を忘れる", "dialogue": "…あ、傘。" } ] } // Step2: コマ割り設計（ページ/コマ/構図/セリフ位置） { "page": 1, "panel": 2, "composition": "low_angle_wide", "char_ref": "lora://characters/heroine_v3", "dialogue_bbox": [120,40,260,90] } // Step3: ComfyUI ワークフローAPIへのリクエスト（L2/L3） POST /prompt // ComfyUI標準API { "workflow": "manga_panel_v2.json", "inputs": { "lora": "heroine_v3.safetensors", "controlnet_pose": "low_angle_wide.png", "prompt": "雨の商店街、傘を探す仕草" } }
💡 Step3のAPI形状は各ベンダーの実仕様に厳密対応するものではなく、「何を渡す必要があるか」の設計イメージです。実装時は各サービスの最新APIドキュメントを一次情報として確認してください。
オーケストレーション層の選択肢

OpenClaw と汎用ツール群の
位置づけの違い

本ハブの L4 はOpenClaw/PicoClawを正本としていますが、汎用オーケストレーションツール（n8n・Zapier・Make）も2026年に入りAIネイティブ機能を大きく強化しています。 比較軸として記録し、将来「OpenClawで足りない部分を汎用ツールで補うか」を判断する材料にします。

ツールAIネイティブ度ホスティング得意領域このハブでの位置づけ
OpenClaw / PicoClaw Skill単位でLLM呼び出し・HITL・コスト管理を一体設計 セルフホスト（自前運用） Signal連携・独自ワークフロー・本ハブ固有の型定義との統合 正本（L4の主力）
n8n（2.0系） AI Agent Tool Node・LangChain連携・70+ AIノードとエージェント指向が強い（2026年初頭に強化） セルフホスト可（OSS） 汎用LLMパイプライン、ベクタDB連携、大量ノード実行のコスト最適化 参考枠。OpenClaw未実装の汎用連携を補う候補
Zapier / Make Zapier Agents・Make Maia等でエージェント機能を追加中だがAI呼び出しは「連携の一種」の扱いに留まる傾向 SaaS（マネージド） 数千規模の既製アプリ連携、非エンジニアでも組みやすいUI 本ハブでは非採用。配信系SaaSとの簡易連携が要る場合の候補に留める
⚠️ 表中の特性は各社のブログ・比較記事で一般的に報告されている傾向であり、機能の実測値ではありません。実運用で乗り換えを検討する際は必ず一次情報（公式ドキュメント）で再確認してください。

工程間連携で
よくある失敗パターン

仕様書のエラーコード表が単一APIのエラーを扱うのに対し、ここでは「工程Aから工程Bへの連携」で起きがちな症状を扱います。

症状想定原因対処の方向性
callback_url へのWebhookが401で弾かれる 署名検証用シークレットのローテーション漏れ、または時刻ズレ（HMAC/JWTのexp不整合） secret更新を送信側・受信側の両方に反映したか確認。サーバー間のNTP同期を確認
ジョブが queued のまま進捗しない Redisキューのワーカー枯渇、または MAX_PARALLEL_JOBS 上限に張り付いている /api/v1/system/status でqueue_depthを確認。上限緩和かワーカー追加を検討
動画・漫画で同じネタなのに構造化結果の解釈がズレる 共通前処理（②構造化）のスキーマがバージョン更新され、片方のconsumerだけ追従できていない topic_data にschemaバージョンを持たせ、両パイプラインの許容範囲を揃える
MCPコネクター経由の呼び出しが403で失敗 OAuthスコープ不足、コネクター側の権限失効・再認可待ち コネクターの認可状態を確認し再認可。必要スコープを最小権限で洗い出す
フォールバック先に切り替えても同じくタイムアウトする フォールバック候補が1系統しかなく、同時障害・共通基盤障害に弱い フォールバック先を2段以上用意する。最終段はHITL（人間判断）に必ず落とす
月次コストアラートは来るが、どの工程が原因か分からない コスト集計がSkill単位までで、Skill内のステップ単位のタグ付けがされていない ステップ単位でcost_so_far_usdを積算するようログを構造化する（モニタリング仕様参照）

モデルが世代交代しても
マップを腐らせない

このマップの弱点は「半年でモデル名が古くなる」こと。 そこで具体モデル名は 📚 LLMナレッジ 側のトラッカーを正本とし、 このページは「どの層の何を担うか」という構造の記述に徹します。 最新の型番・価格・性能はトラッカーで確認し、マップは工程対応の地図として長く使う——という役割分担です。

  • 型番・価格の最新値 → LLM トラッカー6本を正本に
  • 新モデルの台頭 → intelligence-matrix で時系列把握
  • このマップ → 工程対応の構造を維持（更新頻度低）

設計意図

なぜ3枚目の地図が要るのか

地図が3枚（比較・フロー・接続）あると重複に見えるかもしれません。それぞれ問いが違います。 将来のセッションが「統合すべきか」を検討するときの判断軸として記録します。

🧭
3枚の地図が答える問いの違い
生成ツール比較＝「どれが優れているか」（選定の問い）。 全体フロー＝「どの順番で流れるか」（手順の問い）。 接続マップ＝「どの工程で何が動き、深掘りはどこを読むか」（参照の問い）。 読み手の入口が違うため、統合せず3枚を保つ。
🔗
📚ナレッジと🎬主軸を繋ぐ背骨にした理由
workbench/knowledge の深掘りページ（Gemini・Veo・ComfyUI 等）は単体では「制作のどこで使うのか」が見えにくい。 主軸パイプライン側からも「この工程の技術を深く知りたい」導線が弱かった。 このマップが両者の双方向リンクを一手に引き受けることで、カテゴリをまたぐ回遊を成立させる （ロードマップ Phase 3「制作システムとの接続強化」の実装）。
💡 将来のセッションへ: モデル名が古くなったらこのページではなく LLM トラッカー側を更新する。このマップは「工程×レイヤー」の構造だけを保ち、更新頻度を低く保つのが設計上の意図。
