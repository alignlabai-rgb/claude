承認フロー設計の要点

シングル承認

「承認の開始と待機」アクション一発。タイムアウト（デフォルト30日）設定、リマインダーは別フローで。承認結果は outcome で判定。

逐次承認（多段階）

承認アクションをループで順番に実行。各承認者の結果を配列に蓄積し、全承認 OR 一人でも否決で分岐。

並列承認（最初の応答）

「最初の応答を待つ」モードで複数承認者に同時送信。誰か一人が応答した時点でフロー再開。

委任・エスカレーション

承認者不在時の委任は Approvals アプリで設定。期限超過は「タイムアウト後」分岐でマネージャーへ自動エスカレーション。

Desktop Flow（RPA）実践ポイント

無人実行（Unattended）には別ライセンス（RPA add-on $40/bot/月）が必要。 有人実行はPower Automate Premium ライセンスで可能。マシンをクラウドに登録してからフロー内で「デスクトップフローの実行」アクションを呼び出す。

レコーダーのコツ

「スマートレコーダー」はUI要素をセレクターで記録。ウィンドウタイトル・クラス名・テキストの複合セレクターで耐障害性を上げる。画面解像度が変わるとズレるため セレクターベースを優先。

Excel / Web の操作

Excel は UI 操作ではなく「Excelワークシートを読み取る」アクション（COM経由）を使うほうが安定。Web は「ウェブページからデータを抽出」でテーブル丸ごと取得可能。

パフォーマンス設計の鉄則

Power Apps の遅延原因の9割は「委任できないフィルター」。 SharePoint / Dataverse では Filter() に使える列と演算子が制限されている。委任警告（黄色い三角）が出たらクエリを見直す。500件上限に引っかかるとバグの原因になる。

委任対応設計

Dataverse 側でビュー（View）を作り、アプリは Filter(entity, viewName) で呼ぶ。複雑な条件はサーバー側クエリに任せる。

OnStart の最小化

App.OnStart はすべて完了するまで画面が表示されない。Concurrent() で並列化し、不要な ClearCollect を各画面の OnVisible に分散させる。

Gallery のキャッシュ

Gallery の Items に直接 SharePoint を指定せず、ClearCollect でコレクションにキャッシュしてから参照する。ページング対応に LoadData を活用。

オフライン対応

SaveData(collection, "local_cache") でローカルストレージに保存。LoadData() で復元。Connection.Connected で接続状態を監視しオンライン復帰時に同期。

Power BI 完全攻略

データモデリング — スタースキーマの原則

Power BI の性能と DAX の書きやすさはモデル設計で9割決まる。 フラットテーブルやスノーフレークは避け、ファクトテーブル（数値・トランザクション）+ ディメンションテーブル（マスター）のスタースキーマに変換することを最初に行う。
原則説明
1対多リレーションディメンション（1）→ ファクト（多）の方向で結合。双方向フィルターは原則 OFF（RLS と競合しやすい）
サロゲートキー自然キー（文字列ID）より整数のサロゲートキーで結合するとメモリ効率が大幅改善
日付テーブルを必ず作るカレンダーテーブルを独自に用意（M クエリ or DAX で生成）し、すべての日付列と結合。タイムインテリジェンス関数の動作に必須
計算列 vs メジャー計算列はモデル読込時に評価されメモリを消費。メジャーはクエリ時評価。集計はメジャーに書く
列の削減Power Query で不要列を削除してからロード。列を削るだけでファイルサイズが劇的に改善

DAX 基礎から実践まで

// 基本メジャー 総売上 = SUM(Sales[Amount]) 平均単価 = AVERAGE(Sales[UnitPrice]) 件数 = COUNTROWS(Sales) // 条件付き集計 アクティブ売上 = CALCULATE( SUM(Sales[Amount]), Sales[Status] = "Active" ) // タイムインテリジェンス（日付テーブルが必須） 前年同期売上 = CALCULATE([総売上], SAMEPERIODLASTYEAR('Date'[Date])) YTD売上 = TOTALYTD([総売上], 'Date'[Date]) 前月比率 = DIVIDE([総売上], CALCULATE([総売上], PREVIOUSMONTH('Date'[Date])) - 1) // RANKX — ランキング 売上ランク = RANKX(ALL(Products[Name]), [総売上], , DESC, Dense) // VAR で可読性向上 粗利率 = VAR revenue = [総売上] VAR cost = SUM(Sales[Cost]) RETURN DIVIDE(revenue - cost, revenue)

Dataverse 設計指針

テーブルの種類と使い分け

種類特徴向いている用途
標準テーブルDataverse ストレージに保存。フル機能（BPF/RLS/監査）業務の中核データ（顧客・案件・申請など）
仮想テーブル外部データを Dataverse テーブルとして見せる。データは外部に残るSAP・外部 DB・SharePoint をリアルタイム参照したいが移行できない場合
Elastic テーブル大量データ（数十億行）向け NoSQL ベース。削除/パーティション最適化IoT ログ・センサーデータ・高頻度イベント
Activity テーブルメール・タスク・電話などアクティビティ専用。タイムライン表示に連携CRM の活動履歴

リレーションシップ設計

1:N（最多用途）

親テーブルから子テーブルへの参照。子に親の主キーを外部キーとして持つ。Cascade Delete / Restrict / Remove Link を必ず設定する。

N:N（交差テーブル）

自動生成される中間テーブル経由。Dataverse が管理するため直接アクセス不可。Power Fx の Relate() / Unrelate() で操作。

自己参照（階層）

同テーブルの行を親として参照。組織図・商品カテゴリ・BOM に使用。Dataverse の階層ビジュアライザーで確認可能。

多形ルックアップ（Regarding）

複数のテーブルのどれかを参照できる汎用ルックアップ。Activity テーブルの Regarding フィールドが典型。型安全性が下がるため多用しない。

セキュリティモデルの設計

Dataverse セキュリティは「セキュリティロール × 事業部門（Business Unit）× チーム」の組み合わせ。 設計前にアクセス要件を表にまとめ、ロール数を最小化する。ロール増加は管理コスト増大の元凶。
アクセス範囲設定典型ユースケース
自分のレコードのみスコープ: ユーザー個人タスク管理
チームのレコードスコープ: 部署 + チームに所属部門内共有データ
事業部門全体スコープ: 事業部門地域別・部署別分離
組織全体スコープ: 組織マスターデータ・参照テーブル

Power Platform × Azure の統合レイヤー

Azure Logic Apps

Power Automate との使い分け

Power Automate がプロ/市民開発者向けなら Logic Apps はエンジニア向け。VNet 統合・カスタムコネクタの共有・SLA 保証が必要な場合は Logic Apps を選ぶ。

Azure Functions

カスタムロジックの実行

Power Automate から HTTP コネクタや Azure Functions コネクタで呼び出す。複雑な計算・外部ライブラリ使用・高頻度実行に。

Azure Service Bus

非同期メッセージング

Power Automate の「Service Bus メッセージの送信」でキューに投入し、大量処理を非同期化。バーストトラフィックの吸収に使用。

Azure AI Foundry

高度な AI モデル呼出

AI Builder では対応できないカスタム AI が必要な場合、Azure OpenAI / Foundry の REST API を Power Automate HTTP アクションで直接呼び出す。

環境を分けることが Power Platform ガバナンスの土台。 開発者が本番データを直接触れる環境は事故の元。小規模でも最低 Dev + Prod の2環境を用意する。
環境種別Dataverse用途アクセス
Defaultデフォルト有り（自動）個人プロトタイプのみ。業務フローを置かない全ユーザー
Devサンドボックス有り開発・テスト。本番データなし開発者のみ
Test / UATサンドボックス有り（匿名化データ）受入テスト・QA開発者 + テスター
Prod本番有り本番稼働。直接編集禁止運用チームのみ

ソリューション（Solution）管理

マネージド vs アンマネージド

種別特徴
アンマネージド開発環境用。編集自由だが誤って本番に持ち込むと危険
マネージド本番・Test 環境用。インポート後の直接編集不可。削除制御も可能

パイプライン（Power Platform Pipelines）

2023年 GA。Dev → Test → Prod の昇格を GUI で管理。承認ゲートを設けることでリリースを制御。Azure DevOps / GitHub Actions との連携も可能（pac CLI を使用）。

CoE Starter Kit — 管理者の必携ツール

Center of Excellence (CoE) Starter Kit は Microsoft が無償提供するガバナンスアプリ群。 Power Platform 環境の棚卸し・利用状況モニタリング・コンプライアンス管理に不可欠。大規模展開前に必ず導入を検討する。

Inventory（インベントリ）

全環境のアプリ・フロー・コネクタ・作成者を自動収集。利用状況ダッシュボードで孤立リソースを発見。

Compliance（コンプライアンス）

利用申告フォームで各アプリのビジネスオーナーと目的を記録。未申告アプリを作成者にメールで督促。

Nurture（啓発）

市民開発者向けトレーニング管理・「ヒーロー紹介」などコミュニティ育成コンポーネント。

Cleanup（整理）

一定期間使われていないアプリ・フローを検出し、作成者に確認メール。返答なければアーカイブ提案。

DLP（データ損失防止）ポリシー設計

DLP はコネクタを「ビジネスデータ / 非ビジネスデータ / ブロック」の3グループに分類する。 異なるグループのコネクタを同じフロー・アプリで使うと実行が禁止される。設計ミスが多いため、導入前に「コネクタ分類表」を作成して関係者とレビューする。
グループコネクタ例説明
ビジネスデータSharePoint, Teams, Outlook, Dataverse, Azure, Approvals業務データとの接続を許可
非ビジネスデータTwitter/X, Dropbox, 個人用 OneDrive（別テナント）ビジネスデータと混在禁止
ブロック汎用 HTTP, 未評価コネクタ（状況による）使用自体を禁止
