エージェント・エコシステム：系統図より責任の地図を作る

最終更新・公式情報確認：2026-10-13。news という旧 URL は維持し、本文は用途別の現行ガイドへ刷新しました。確認日は発表日ではありません。

例と評価案は筆者の設計提案で、未実行です。性能測定・本番導入・安全認定・正式採用の実績を示すものではありません。

名前を枝へ並べる系統図は分かりやすく見えるが、独立した実装を派生と呼んだり、ワークフローと常設 assistant を同一視したりすると選定を誤る。ここでは関連基盤の責任を、入口、推論、実行、状態、拡張へ分ける。あらゆる agent 製品の網羅的な最新ランキングではない。

似た名前から血縁を作らない

PicoClaw は独立した Go 実装と明示され、NanoClaw はホストとコンテナを分ける構造、Hermes は AIAgent と tool backend を持つ。PicoClaw 公式リポジトリ、NanoClaw Architecture、Hermes Architecture OpenClaw の大小版という一つの線へ並べない。共有する規格や名前と、実装の継承は違う。

筆者の比較図は、各基盤が何を常設し、どの状態を持ち、何を外へ送るかを書いた五列の表にする。言語の違いやコード量より、現在の業務とつながる境界を読む。

ワークフローと自由な依頼

決まった入力を決まった手順へ流す処理と、自然言語から都度ツールを選ぶ agent は別の設計問題である。決定的な変換で足りる仕事へ自由なモデル判断を増やすと、検査や再現が難しくなる場合がある。逆に調査の途中で未知の情報を読む仕事には、柔軟な分岐が役立つことがある。

教材では毎回同じ CSV を集計する処理と、仕様書の矛盾を調べる処理を分ける。前者は正しい計算と入力の検査、後者は根拠の選択と保留が主要な評価になる。同じ「自動化」の語でも、必要な証拠は違う。

拡張を入口へ戻して読む

ClawHub は skills と plugins を配布する registry として説明される。ClawHub plugin を加えると、新しい通信、保存、資格情報が生まれる可能性がある。便利な機能名だけを比較表へ追加せず、どの境界を変えるか書く。

スキルの形式が似ていても、同じ道具名や権限があるとは限らない。別基盤から移す際は、文書、補助コード、通信、出力を分け、合成入力で再評価する。互換は一つの yes/no ではなく、再利用できる部分の一覧になる。

推論先の独立性

OpenClaw の README は利用者側の状態と、選んだ model provider や chat service への通信を分けて説明する。OpenClaw 公式リポジトリ 常設する場所と推論の場所を混ぜない。手元の推論を使っても通知や検索は外へ出る可能性が残る。

候補表には本文、添付、推論入力、結果、診断の行先を記す。秘密の入力がある仕事なら、その区分に合う経路だけを残す。ローカルという広告語や cloud という一語から、全体の公開境界を推測しない。

置き換えの単位を小さくする

現在の構成を全部新しい基盤へ替える前に、差分の抽出、根拠の点検、下書きの提出など一つの仕事を選ぶ。入口と状態を変えずモデルだけ試すのか、配送だけ変えるのかを決める。全部を同時に変えると、何が効果を作ったか分からない。

成功時も失敗時も、入力、設定、提出物、禁止効果の検査を残す。候補を採用しなかった記録は、似た宣伝を次に見たときの比較材料になる。名前の数を増やすことではなく、選び直せる責任の地図を作ることが、このエコシステム記事の目的である。
