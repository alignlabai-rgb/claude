専門レシピ：候補を判断へつなぐ小さな成果物

最終更新・公式情報確認：2026-10-13。news という旧 URL は維持し、本文は用途別の現行ガイドへ刷新しました。確認日は発表日ではありません。

例と評価案は筆者の設計提案で、未実行です。性能測定・本番導入・安全認定・正式採用の実績を示すものではありません。

基本クックブックの依頼文から進み、この章では出力を次の人が判断できる小さな成果物へ変える。公開資料の情報が増えても、読む人が行動へつなげられなければ使われない。三つの例は筆者の設計提案であり、実行済みの成功事例や OpenClaw の標準 schema ではない。

一：技術差分カード

入力は合成した機能の旧仕様と新仕様。出力を「対象」「変化」「公式根拠」「影響する仕事」「未確認」「次の評価」の六欄へする。最新ニュースの全文を書くのではなく、いま読む人が再点検する条件を示す。対象が同じか分からなければ、その違いを保留へ入れる。

反例は、API の変更を Web アプリの全機能へ広げる場合、試験提供を全面提供へ変える場合、価格のない仕様から安価と結論する場合である。根拠の段落と一つずつ照合し、提案と事実を同じ文へ混ぜない。完成は六欄が埋まることではなく、埋まらない理由が読めることも含む。

二：業務適合の仮説カード

入力は技術差分カードと、架空の業務「公開 FAQ の根拠不足を減らす」。出力は、減らす負担、使う能力、入力区分、許す効果、失敗条件、評価の最小集合にする。特定担当の候補は提案にとどめ、正式な配送や仕事の受け入れを生成しない。

反例は、便利そうだから全社導入を提案する、権限不足を人に聞かず別の経路で実行する、契約済みと書く場合。採用判断にはまだ何が足りないかを示す。実際の購読や秘密登録は教材へ含めない。

三：再利用する失敗カード

入力は合成した失敗記録「地域限定を落とした」。出力は発生条件、誤った判断、正しい停止または出力、負の入力、回帰の確認を持つ。人格やモデルの名前に帰責して終わらせず、次回も検査できる条件へ変える。

反例は、一つの観測から「この provider は使えない」と恒久的に決める場合。版、入力、道具、条件のどこが原因かを分ける。公式 memory の長期情報と日付の記録を分ける考え方を踏まえ、試行の仮説を安定した事実へしない。OpenClaw Memory overview

カードをスキルへ変える条件

同じ仕事で再利用するなら、入力と停止条件と採点を手順の文書へまとめる。公式 Skills はそのような知識文書を読み込む仕組みを説明する。OpenClaw Skillsただし書いたスキルは候補である。正常入力と負の入力を通し、変更の前後で何が変わったか確認してから使う。

カードの内容をそのまま実行プログラムへ変換しない。候補を読む人、実行を判断する人、権限を維持する人の責任は別になる。素材の受け渡しに成功したことと、仕事が正式に受け入れられたことを分ける。

定期化するときの追加欄

カードを定期的に出すなら、対象 ID、有効期限、変更なしの扱い、重複、配送確認を足す。公式 automation lifecycle は実行と結果保持を別に説明する。OpenClaw Automation lifecycleタイマーがあることから、候補の品質や採用の価値は生まれない。

変化がないときは静かに終える設計を試す。毎日一枚を必ず作る条件にすると、前回の話題を新しい差分として出す誘因になる。必要な変化だけを人へ返し、生成件数を価値へ置き換えない。

完成したレシピの保存

公開または合成の入力、空欄を許す形式、反例、採点を一組で残す。秘密を含む実際の log をコピーする必要はない。次の人が同じ課題を試し、同じ境界を点検できることが、ボリュームのある原稿と実用的なレシピを分ける。
