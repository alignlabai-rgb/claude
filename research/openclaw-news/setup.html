セットアップの専門編：誰が package と常駐状態を所有するか

最終更新・公式情報確認：2026-10-13。news という旧 URL は維持し、本文は用途別の現行ガイドへ刷新しました。確認日は発表日ではありません。

例と評価案は筆者の設計提案で、未実行です。性能測定・本番導入・安全認定・正式採用の実績を示すものではありません。

基本の導入手順は セットアップ入門 にある。この章は、すでに入っているように見える環境で、CLI、app、package、runtime、サービスの所有者を確認する方法を扱う。二重の導入や更新が、同じ機械で違う状態を起動する失敗を避けるためである。

版は一つではない

筆者の記録案では、表示している app、起動する CLI、Gateway の package、Node runtime、plugin、保存形式を分ける。同じ名称のショートカットでも実体が違う場合がある。ターミナルで見えた版だけを、稼働サービスの版と決めない。

現行の Getting started は Node 24.16+ または 26.1+ を要件にし、Node 26 を推奨している。OpenClaw Getting started旧い PATH が優先される場合、必要な runtime を入れても期待どおり起動しないことがある。最初に所在を読む検査をし、名前が同じものを片端から削除しない。

更新の所有者を確認する

公式 Updating は、app-owned package が更新所有者を持つ場合、app の更新経路で bundled Gateway と runtime を扱うことを説明する。Updating同じ機械へ別の package manager を入れて更新すれば、app の実体も更新されるという推測はしない。

教材では「app 内の A」「shell からの B」「サービスが起動する C」の三つの候補を表へし、何を見たら同一と確認できるか考える。実際に二重導入を作る必要はない。更新する対象が不明なら、インストールを重ねる前に調査で止める。

前景と常駐の寿命

基本手順では前景の試行と OS のサービス登録が分かれる。OpenClaw Getting started前景で動いているときに、同じ仕事を常駐側も処理していないか確かめる。二つの process が同じ状態へ同時に書ける構成は、単純な「速くなる」並列化ではない。

起動と停止の責任を一つへする。誰がメンテナンス中の依頼を止め、終わったら再開するかを決める。自分の実行中の process が自分を落とす手順を、安易な日常回復として薦めない。

チャネルと release の意味

Release policy は stable、beta、extended-stable、dev の違いを説明する。Release policy「latest」という一語から、すべての配布面へ同じ更新が来ているとしない。検証の目的と、利用する提供面を合わせる。

実験なら beta を試す理由があっても、本番の仕事まで黙って切り替える理由にはならない。候補版と現行版を同じ表へ置き、合成入力での差と、変更する場合の影響を整理する。調査したことを更新承認と混同しない。

読み取り report を残す

公式 Doctor は読み取り専用の JSON または lint の姿勢を用意する。Doctor lint and post-upgrade modes利用する版の契約を確認したうえで、修復と診断を分ける。report の出力には識別情報が含まれ得るので、共有用には必要な所見だけにする。

検査が成功しても、資料整理、外部通知、記憶の取り込みが動くとは限らない。それらの業務へ合成の回帰入力を使い、適用した構成を確認する。setup 完了を、すべての機能の合格へ広げない。

この章の完成物

自分の環境の所有者表、起動する実体、更新経路、保持する原本、検査した版を一枚へする。公開教材には内部 path や秘密を入れない。分からなかった所有者は未確認として残し、それを埋めるためだけにサービスや package を変更しない。

導入の失敗を全初期化で消すより、所在と所有者を説明できる方が、次の更新にも役立つ。速く動かし始めることと、長く保守できる構成を持つことを分けて考える。
