コンテキストエンジニアリングとは何か

「The art of filling the context window with just the right information at the right time.」
── Tobi Lütke（Shopify CEO）、2025年6月
「The context window is the most valuable real estate in AI. What you put in it – and what you leave out – determines everything.」
── Andrej Karpathy（元 Tesla AI / OpenAI 共同創業者）、2025年

プロンプトエンジニアリングとの決定的な違いは「粒度」と「主語」にあります。

観点Prompt EngineeringContext Engineering
問いどう頼むか（How to ask）何を見せるか（What to provide）
主な技術Few-shot, CoT, XML tags, RoleRAG, Memory, Compression, Caching
関与者主にプロンプト作成者システム設計者・データエンジニア
上位/下位コンテキストの一部（System Prompt）プロンプトを包含する上位概念
競争優位の源低い（コモディティ化）高い（設計の巧拙が直接成果に直結）

Gartner は 2025年6月の公式レポートで「Context engineering is in, prompt engineering is out」と明言。プロンプトの書き方は素養として全職種に浸透した結果、次の差別化軸はコンテキスト設計に移行しています。

コンテキストの 7 層モデル

モデルのコンテキストウィンドウに入れる情報を 7 つのレイヤーで整理します。品質の高いエージェントやアプリは、この 7 層を意図的に設計・管理しています。

①
System Instructions（システム指示）
役割・人格・制約・禁止事項・出力フォーマット。常に存在し、最も権威のある層。CLAUDE.md や Cursor Rules がここに相当。
②
Static Knowledge（静的知識）
仕様書・マニュアル・製品ドキュメント・FAQ。クエリに関係なく常に注入する参照資料。Context Caching との相性が良い。
③
Retrieved Context（検索取得コンテキスト）
RAG によりクエリに応じて動的取得される情報。Semantic Chunking・HyDE・Reranking でリレバンスを最大化。
④
Conversation History（会話履歴）
直近の会話ターン。要約・スライディングウィンドウ・選択的圧縮でトークンを節約しながら文脈を維持。
⑤
Tool Outputs（ツール実行結果）
コード実行・Web 検索・API 呼び出し・ファイル操作の結果。エージェントループの「観測」フェーズで生成される動的情報。
⑥
Memory（記憶）
短期（セッション内）・長期（クロスセッション）・エピソード（特定イベント）記憶。Mem0・Letta・ClawMem 等で実装。
⑦
Task State（タスク状態）
現在のタスク進捗・変数・中間結果・未解決の判断。エージェントが「どこまでやったか」を把握するための実行文脈。

コンテキストエンジニアリングの実践とは、この 7 層をリソース（トークン・コスト・レイテンシ）の制約の中で最適に配置する設計行為です。

コア技術 8 選

① RAG（検索拡張生成）

クエリに応じてベクトルDBや検索エンジンから関連情報を取得し、コンテキストに注入。LlamaIndex・LangChain・pgvector 等で実装。精度は Recall@k で計測。

② HyDE（仮説文書埋め込み）

クエリから「理想的な答え」を LLM に仮生成させ、その埋め込みで検索。実クエリ埋め込みより検索精度が大幅向上（特に専門ドメイン）。

③ Semantic Chunking

固定文字数ではなく意味のまとまりで文書を分割。文の埋め込み類似度が急変する点を境界として検出する手法。LlamaIndex に実装済み。

④ Context Compression / 要約

長い会話履歴を逐次要約して圧縮。LangChain の ConversationSummaryMemory が代表例。重要情報を保持しながらトークン消費を抑制。

⑤ Context Caching（Anthropic）

変化しない静的コンテキスト（仕様書・マニュアル）をサーバー側でキャッシュ。API コストを最大 90% 削減。cache_control: {"type": "ephemeral"} で有効化。

⑥ Memory Systems

Mem0（ユーザー記憶 SaaS）・Letta（OSS エージェントメモリ）・ClawMem（OpenClaw 向け）・Cloudflare KV など。クロスセッションでユーザー情報・好みを保持。

⑦ Hierarchical Retrieval

文書全体の要約を先に検索し、命中した文書内の詳細チャンクを取得する 2 段階アプローチ。精度と網羅性を両立。大規模ドキュメント群に有効。

⑧ Reranking

ベクトル検索で上位 k 件を取得後、Cross-Encoder（Cohere Rerank・BGE-Reranker）でスコアリングし直す 2 段階精度向上。Recall と Precision を同時改善。

コンテンツ制作・AI 運用の現場でコンテキスト設計がどう機能しているか。

01 クリエイター NotebookLM ── 複数ソースを「Notebook」としてコンテキスト化

Google NotebookLM は PDF・YouTube 動画・音声・Web サイトを「ソース」として Notebook（= コンテキスト）に登録し、モデルはそのソース内の情報のみで回答します。これはコンテキストエンジニアリングの教科書的実装：

  • 静的知識層（②）: 登録したソースが常時コンテキストに入る
  • 検索取得層（③）: 質問に関連するソース部分を優先表示
  • 活用例: 参考文献 10 冊を登録 → 引用付きで記事下書きを生成、2 時間の作業が 20 分に短縮
効果: 調査&執筆時間 約 85% 削減（事例報告）
02 クリエイター Obsidian × MCPVault ── Vault 全体をエージェントのコンテキストに

Obsidian の Vault（数千のノート）を MCP サーバーとして公開することで、Claude Code・OpenClaw・Hermes Agent など複数のエージェントが同じ知識ベースを参照・書き込みできます。

# mcpServers 設定（.claude/settings.json）
{
  "mcpServers": {
    "obsidian": {
      "command": "npx",
      "args": ["-y", "mcp-obsidian", "/path/to/vault"]
    }
  }
}

エージェントは read_note・search_notes・create_note ツールで Vault を操作。毎日の AI News 記事を自動的に Vault に保存し、次のエージェントがそれを参照して週次まとめを生成、というコンテキスト連鎖が実現します。

03 クリエイター このハブの CLAUDE.md ── 新 AI インスタンス向けコンテキスト設計

本ハブ最上位の CLAUDE.md は「コンテキストエンジニアリングの実物」です。新しい Claude セッションが開始するたびに自動注入される静的知識層（②）として設計されています：

  • Purpose セクション: エージェントの役割・目的（System Instructions 相当）
  • Folder Rules: どのファイルがどこにあるかの地図（Static Knowledge）

「新しい Claude に読ませて、なるべく少ない追加説明で作業を始めさせる」── これ自体がコンテキストエンジニアリングの実践です。

04 クリエイター Cursor IDE ── @ symbol でコードベースをコンテキストに動的注入

Cursor はコンテキストエンジニアリングの UI を直接ユーザーに提供しています：

  • @file: 特定ファイルをコンテキストに追加
  • @folder: フォルダ全体を追加
  • @codebase: プロジェクト全体を Semantic Search 経由で RAG 参照
  • @docs: 公式ドキュメントを直接参照（Next.js, React 等）
  • @web: リアルタイム Web 検索結果を注入

Cursor Rules v2（.cursor/rules/*.mdc）はプロジェクト固有の System Instructions として機能。コードスタイル・命名規約・禁止パターンをファイル種別ごとに定義できます。

Rules v2: ファイル glob 単位で適用ルールを切り替え可能

06 クリエイター Midjourney v7 / Flux ── スタイル参照画像のコンテキスト注入

画像生成 AI でのコンテキストエンジニアリングは「何を見せるか」が文字通りの意味で重要：

13 クリエイター YouTube 動画スクリプト ── 前回動画の内容を記憶してシリーズ一貫性を維持

連続シリーズ動画のスクリプト生成では、前回・前々回の動画情報をコンテキスト層⑥（Memory）として注入することで、視聴者への重複説明を避けつつシリーズとしての連続性を保てます：

[System Instructions層]
あなたは YouTube チャンネル「AI実践塾」のスクリプトライター。
口語調・15分尺・初心者向け。

[Static Knowledge層]
チャンネルスタイルガイド: （略）
固定オープニング: 「どうも、実践塾のタケシです！」

[Memory層（前回エピソード要約）]
- EP.12: RAG の基礎を解説。ベクトルDB として Chroma を紹介済み。
- EP.13: HyDE の概念を解説。「仮説文書」という用語で定着。
- 視聴者アンケート: 「実装例をもっと見たい」という要望多数。

[Task State層]
今回: EP.14「Reranking で精度を上げる」
前回言及: 「次回はさらに精度を上げる技術を紹介」と予告済み。

この設計により「前回お話しした仮説文書の概念と組み合わせると…」といった自然な文脈参照が自動的に生成されます。シリーズが 20 本を超えても各エピソードの要約を Memory 層に保持することでトークンを節約しながら一貫性を担保できます。

効果: スクリプト修正回数 約 60% 削減（シリーズ間の矛盾・重複が激減）
14 クリエイター ゲーム世界観設定書をコンテキスト化 ── キャラクター台詞の整合性チェック

大規模なゲーム・小説・漫画プロジェクトでは、世界観設定書（ロアブック）を Static Knowledge 層（②）としてコンテキストに持つことで、個々の台詞・描写の整合性を自動チェックできます：

# 設定書の Context Caching（変更頻度が低いため適用）
settings_doc = open("worldbuilding/lore-bible.txt").read()
# → キャラクター一覧・種族設定・魔法体系・地理・歴史年表 (約 80,000 字)

response = client.messages.create(
    model="claude-fable-5",
    system=[
        {
            "type": "text",
            "text": settings_doc,
            "cache_control": {"type": "ephemeral"}  # キャッシュ適用
        },
        {
            "type": "text",
            "text": "以下の台詞がロアブックと矛盾していないか確認し、問題箇所を指摘してください。"
        }
    ],
    messages=[{
        "role": "user",
        "content": "「エルフのアリアは炎魔法で敵を一掃した」── この台詞を確認してください。"
    }]
)
# → 「エルフ族は設定書 P.23 で"水・風魔法のみ使用可"と定義されています。炎魔法は矛盾します。」

設定書が 100,000 字を超えてもキャッシュにより初回以降のAPI コストは 90% 削減。複数ライターが並走するプロジェクトでも設定の統一性を機械的に担保できます。

適用: ゲームシナリオ・TRPGリプレイ・連載漫画の設定管理
15 クリエイター SNS 過去投稿のコンテキスト化 ── ブランドボイスとスタイルの自動継承

X（Twitter）・Instagram・Threads の過去投稿データを RAG コンテキストとして活用することで、アカウント固有の「ブランドボイス」を学習・継承した新規投稿を自動生成できます：

# 過去投稿をベクトルDB に格納（初回のみ）
from llama_index.core import VectorStoreIndex, Document

past_posts = load_csv("past_tweets.csv")  # 過去1000件の投稿
docs = [Document(text=p["text"], metadata={"likes": p["likes"], "date": p["date"]})
        for p in past_posts]
index = VectorStoreIndex.from_documents(docs)

# 新規投稿生成時: 類似トーンの過去投稿を参照
def generate_post(topic: str) -> str:
    # 同トピック or 高エンゲージメント投稿を取得
    similar = index.as_retriever(similarity_top_k=5).retrieve(topic)
    style_examples = "\n---\n".join([s.text for s in similar])

    return llm.complete(f"""
以下は過去の高反応投稿例です。同じトーン・文体で新規投稿を作成してください。

【参考投稿】
{style_examples}

【今回のトピック】
{topic}
""")

# → 「語尾に『ですよね？』を使う」「3点リーダーを多用する」等の
#    個人スタイルが自然に継承される

さらに「いいね数上位20%の投稿のみ参照」とフィルタリングすることで、エンゲージメントが高かったスタイルを選択的に模倣します。

効果: 投稿スタイルの一貫性スコア（人間評価）が 素生成比 +40%

08 エンジニア HyDE（仮説文書埋め込み）── RAG 精度向上の実装パターン

Gao et al. (2022, "Precise Zero-Shot Dense Retrieval without Relevance Labels") が提案した手法の実装：

# Step 1: クエリから「理想的な答え」を生成
hypothetical_doc = llm.generate(
    f"以下の質問に対する理想的な回答を書いてください: {query}"
)

# Step 2: 仮説文書の埋め込みで検索
query_embedding = embed(hypothetical_doc)  # 実クエリではなく仮説文書

# Step 3: ベクトルDB検索
results = vector_db.search(query_embedding, top_k=5)

# Step 4: 実際の検索結果をコンテキストに注入
context = "\n\n".join([r.text for r in results])

検索精度: 素のベクトル検索比で NDCG@10 が平均 +15〜25% 向上（ドメインによって差異あり）。

09 エンジニア Mem0 ── クロスセッション記憶のコンテキスト注入

Mem0（mem0.ai）は「AIのための永続記憶レイヤー」として、ユーザーごとの記憶を自動抽出・保存・取得します：

from mem0 import Memory
m = Memory()

# 会話から記憶を自動抽出・保存
m.add("ユーザーは Python を好み、TypeScript が苦手と言った", user_id="user_123")

# 次回セッションで関連記憶を取得してコンテキスト注入
memories = m.search("どの言語を使うか", user_id="user_123")
# → [{"memory": "Python を好む", "score": 0.92}, ...]

# 層⑥（Memory）として system prompt に追加
system_prompt += f"\nユーザーについて覚えていること: {memories}"

これにより「初めて会ったのに前回の会話を覚えている」エクスペリエンスが実現。チャーン率改善・ユーザー満足度向上に直結。

18 エンジニア Context Window 使用率モニタリング ── 動的圧縮による自律管理

長期稼働するエージェントやチャットボットでは、コンテキストウィンドウの使用率が徐々に増加し、上限に達すると突然エラーになります。使用率をリアルタイムにモニタリングし、閾値を超えたら自動圧縮する設計が本番環境では必須です：

import anthropic
from dataclasses import dataclass

@dataclass
class ContextManager:
    model: str = "claude-fable-5"
    max_tokens: int = 200_000   # モデルの最大 context window
    compress_threshold: float = 0.75   # 75% を超えたら圧縮
    target_after_compress: float = 0.40  # 圧縮後の目標使用率

    def count_tokens(self, messages: list) -> int:
        """現在の messages のトークン数を推定"""
        client = anthropic.Anthropic()
        result = client.messages.count_tokens(
            model=self.model,
            messages=messages
        )
        return result.input_tokens

    def usage_ratio(self, messages: list) -> float:
        return self.count_tokens(messages) / self.max_tokens

    def maybe_compress(self, messages: list, system: str) -> list:
        ratio = self.usage_ratio(messages)

        # Prometheus / Datadog にメトリクス送信
        metrics.gauge("context.usage_ratio", ratio)

        if ratio < self.compress_threshold:
            return messages  # 圧縮不要

        # 閾値超過: 古い会話履歴を要約して圧縮
        target_tokens = int(self.max_tokens * self.target_after_compress)
        keep_recent = messages[-6:]   # 直近 3 往復は必ず保持

        summary_prompt = f"""
以下の会話履歴を、重要な情報・決定事項・未解決タスクを保持しつつ
{target_tokens} tokens 以内に圧縮してください。

{messages[:-6]}
"""
        summary = llm_summarize(summary_prompt)

        compressed = [
            {"role": "system", "content": f"[圧縮された会話履歴]\n{summary}"}
        ] + keep_recent

        metrics.increment("context.compression_triggered")
        return compressed

# 使用例
cm = ContextManager()
messages = conversation_history

while True:
    messages = cm.maybe_compress(messages, system_prompt)
    response = client.messages.create(
        model=cm.model, system=system_prompt, messages=messages
    )
    messages.append({"role": "assistant", "content": response.content[0].text})

このパターンを導入することで、エージェントが数時間・数日稼働してもコンテキストエラーが発生せず、かつ重要情報は失われません。

推奨アラート: usage_ratio > 0.85 で PagerDuty / Slack 通知

GraphRAG / 知識グラフ RAG

Microsoft が 2024 年に発表した GraphRAG は、テキストをただベクトル化する Naive RAG の限界を超え、エンティティ間の関係性をグラフ構造として保持することで複雑な多段推論クエリに対応します。

Naive RAG vs GraphRAG

観点Naive RAGGraphRAG
データ構造テキストチャンク + ベクトルエンティティ・関係・コミュニティのグラフ
得意なクエリ単一事実の検索多段推論・エンティティ関係・全体把握
例クエリ「Aの定義は？」「AとBとCの関係を説明して」
グローバル理解弱い（チャンク単位）強い（Community Summary でデータセット全体を把握）
構築コスト低い高い（グラフ構築に LLM 呼び出しが必要）
クエリコスト低いグローバル検索は高い（Local 検索は同等）

Community Detection + Summarization アプローチ

GraphRAG の中核は「コミュニティ検出 → 階層的要約」のパイプラインです：

  1. エンティティ抽出: LLM でテキストからエンティティ（人物・組織・概念）と関係（has / uses / conflicts_with 等）を抽出
  2. グラフ構築: 抽出した関係を有向グラフとして格納（Neo4j / NetworkX）
  3. コミュニティ検出: Leiden Algorithm でグラフをクラスタリング（密に繋がったノード群 = コミュニティ）
  4. 階層的要約: 各コミュニティの要約を LLM で生成 → これが「Global Search」のコンテキストになる
  5. クエリ時: Local Search（特定エンティティ周辺のグラフ探索）か Global Search（コミュニティ要約を横断）かを自動選択

使いどきの判断基準

GraphRAG を選ぶ場合

複数エンティティにまたがる多段推論（「A が B に与えた影響と C との関係」）／ 大量文書のテーマ・構造の全体把握 ／ 関係性の可視化・探索が目的

Naive RAG で十分な場合

単一事実の検索（「〇〇の定義は？」「〇〇はいつ発表？」）／ 構築コストを抑えたい ／ リアルタイム更新が必要なナレッジベース

クリエイター適用例

キャラクター関係図の知識グラフ化と物語整合性チェック
漫画・ゲームシナリオのキャラクター設定（登場人物・所属組織・関係性・過去イベント）を GraphRAG でグラフ化することで、「AとBは第3章で和解したが、第7章でなぜまた対立しているのか」という多段推論クエリが可能になります。Community Summary によりアーク全体の構造も把握でき、新しいライターがオンボーディングする際の参照資料としても機能します。

エンジニア適用例

コードベースの依存関係グラフを RAG で参照
大規模モノレポ（数万ファイル）では、モジュール間の import / call / extend 関係をグラフとして構築し GraphRAG で検索することで、「このAPIを変更すると影響を受けるモジュールをすべて列挙して」という多段影響調査が可能になります。従来の grep ベースの調査に比べ、間接依存（A → B → C → D というチェーン）まで自動的に追跡できます。

Agentic RAG

従来の RAG は「クエリが来たら固定手順で検索する」受動的なパイプラインでした。Agentic RAG ではエージェントが自律的に「何を・いつ・どのように検索するか」を決定し、必要なら複数回の検索を繰り返します。

「Traditional RAG retrieves once and generates. Agentic RAG thinks about what it doesn't know, retrieves to fill that gap, then decides if it needs to retrieve again.」
── LlamaIndex Blog、2024年

主要パターン

Query Routing（クエリルーティング）

クエリの種類に応じて参照先を自動選択。「製品仕様 → 仕様書 DB」「最新情報 → Web 検索」「コード → コードベース検索」を LLM が判断して振り分ける。

Query Expansion（クエリ拡張）

1 つのクエリを複数の視点から言い換えて並列検索し、結果をマージ。HyDE の発展形。「2次元検索」「サブクエリ分解」とも呼ばれる。

Iterative Retrieval（反復検索）

検索結果を見て「情報が不十分」と判断したら再検索する。ReAct ループ内で Retrieve → Reason → Retrieve を繰り返す。複雑な多段質問に有効。

Self-RAG（自己評価 RAG）

検索した情報が本当に質問に関連しているかをモデル自身が評価（Relevance Token）し、不十分なら再検索。精度は高いが実装コストが高い。

実装例（Query Routing + Iterative Retrieval）

from anthropic import Anthropic
import json

client = Anthropic()

TOOLS = [
    {
        "name": "search_docs",
        "description": "製品ドキュメント・仕様書をセマンティック検索する",
        "input_schema": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "検索クエリ"},
                "top_k": {"type": "integer", "default": 5}
            },
            "required": ["query"]
        }
    },
    {
        "name": "search_web",
        "description": "最新情報・ニュースをWeb検索する（公式ドキュメントにない情報）",
        "input_schema": {
            "type": "object",
            "properties": {"query": {"type": "string"}},
            "required": ["query"]
        }
    },
    {
        "name": "search_codebase",
        "description": "コードベースをセマンティック検索する",
        "input_schema": {
            "type": "object",
            "properties": {"query": {"type": "string"}},
            "required": ["query"]
        }
    }
]

def agentic_rag(user_query: str) -> str:
    """
    エージェントが自律的にツールを選択・反復実行して回答を構築。
    Claude がどのツールをいつ使うかを自分で決定する。
    """
    messages = [{"role": "user", "content": user_query}]

    while True:
        response = client.messages.create(
            model="claude-fable-5",
            max_tokens=4096,
            tools=TOOLS,
            system="""あなたはリサーチアシスタントです。
質問に答えるために必要なツールを自律的に選択・実行してください。
情報が不十分な場合は追加検索を行い、十分な情報が揃ったら最終回答を出力します。""",
            messages=messages
        )

        # tool_use がなければ最終回答
        if response.stop_reason == "end_turn":
            return response.content[0].text

        # ツール呼び出しを実行
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = execute_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": result
                })

        # 結果を messages に追加して次のターンへ
        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": tool_results})

Claude Code での Agentic Retrieval

Claude Code 自体が Agentic RAG の実装例です：

  • @codebase: プロジェクト全体を Semantic Search で検索（どのファイルを見るかをモデルが自律判断）
  • @docs: 公式ドキュメントをリアルタイム検索（React / Next.js / Anthropic API 等を自動参照）
  • Glob / Grep ツール: 必要に応じてファイル構造探索・パターン検索を繰り返し実行
  • 反復読み取り: 最初の Read 結果から関連ファイルを発見 → 追加 Read を自律的に連鎖

ユーザーが明示的に指定しなくても、Claude Code は「この質問に答えるには何を読むべきか」を自律判断して検索戦略を立てます。これが Agentic RAG の本質です。

アンチパターン 6 選

コンテキスト設計の失敗パターン。これを避けるだけで品質が大幅に改善します。

① Lost in the Middle

長文コンテキストの中央部の情報をモデルが軽視する現象。重要情報を先頭か末尾に配置することが重要。

✅ Fix: 最重要情報は冒頭 or 末尾に。中央に置かない。

② Token Stuffing

「とにかく情報を詰め込む」アプローチ。関係ない情報がノイズとなりモデルの集中を分散させる。コスト爆発も起きる。

✅ Fix: 取得情報は Reranking でフィルタリング後に注入。

③ Stale Context

更新されていない古い情報がコンテキストに残り、モデルが誤った前提で回答する。製品仕様・API 仕様の変更が特に危険。

✅ Fix: 静的知識に更新日を明記し、定期棚卸しを運用化。

④ Context Pollution

無関係なツール出力・エラーメッセージ・冗長な会話履歴が蓄積し、有効情報の比率が下がる。エージェントの長期実行で発生しやすい。

✅ Fix: ツール出力は要約してから層⑤に追加。

⑤ Single-Source Bias

1 つのデータソースのみに依存した RAG 設計。そのソースに誤りや偏りがあるとモデル全体が偏る。

✅ Fix: 複数ソースから取得し、矛盾があれば明示的に提示。

⑥ Memory Leakage

会話履歴や記憶が際限なく増加し続け、コンテキストウィンドウを圧迫。長期チャットボットで数ヶ月後に急速に劣化。

✅ Fix: N ターンごとに要約圧縮。重要度スコアで古い記憶を間引く。
