Definition of Done — ページ完成基準

このハブで作る・更新するページが「完成した」とみなされる条件を定義します。複数セッション・複数エージェントが書いても、最低限の品質が揃うようにするための判定基準です。

項目には MUST（必須） SHOULD（推奨） NICE（あれば良い）の3レベルがあります。MUST が満たされなければ「完成」とみなしません。

1. 必須の構造要件 MUST

HTML としての最低限の構造。これを満たさないと公開できない。

  • <title> が「ページ名 | カテゴリ名」形式 <title>Onboarding Checklist | Foundations</title> → なぜ：ブラウザタブ・履歴・検索結果で識別できる必要がある。
  • breadcrumb が冒頭にある（親カテゴリ index と Hub Top へのリンク） <a href="index.html">← Foundations</a> / <a href="../index.html">Hub Top</a> → なぜ：迷子になっても上に戻れる経路を保証する。
  • <h1> が 1 回だけ存在 → なぜ：見出し階層が崩れると、後で目次自動生成・検索が壊れる。
  • 最終更新日が YYYY-MM-DD 形式で記載 <p class="last-update">最終更新: 2026-05-26</p> → なぜ：鮮度判定のため。Hub Health の自動計測対象。
  • 「関連」セクションが末尾にある（最低でも親カテゴリ・Hub Top へのリンク） → なぜ：ページを読んだ後の動線を保証する。孤立したページは情報の墓場になる。
  • HTML が壊れていない（タグの閉じ忘れなし、エスケープ漏れなし） → なぜ：開いた瞬間にレイアウト崩壊する事態を防ぐ。

2. 内容品質 MUST

  • ページの目的が冒頭1-2段落で明示されている → なぜ：読み手が「自分が読むべきか」を3秒で判断できる必要がある。
  • 外部リンク（出典）は実 URL に張られている → なぜ：AP-002（推測 URL を書く失敗）の再発防止。WebSearch / WebFetch で実在確認してから書く。
  • 事実は断定、推測・未確定は明示 OK: 「2026-05-23 時点で複数メディアが報じている」 / NG: 「Anthropic の評価額は $900B です」 → なぜ：将来の読者を誤誘導しないため。情報の時点修飾は必須。
  • 機密情報・個人情報・取引先固有情報が混入していない → なぜ：このハブは公開リポ。R-06 リスクへの直接対処。

3. 動線・ナビゲーション MUST

  • 親カテゴリの index.html からリンクが張られている → なぜ：誰かが「foundations/ 配下に何があるか」を見た時、辿り着ける必要がある。
  • 必要なら top index.html のカードからもリンク → なぜ：重要なページはトップから1クリックで到達できるべき。ただし全ページではない（カードが溢れる）。基準は「新セッションが知っておくべきか」。
  • Site Map に追記されている → なぜ：158ページの全件索引は Site Map のみ。新規追加時は必ずここに登録。
  • 関連ページ（最低 2-3 ページ）への横リンクがある → なぜ：単独のページは孤立して死ぬ。意味的に近いページに相互リンクを張ることで生態系を作る。

4. スタイル準拠 SHOULD

  • カラーパレットを逸脱していない（スタイルガイド §3） → なぜ：別系統の色を持ち込むと、ハブ全体の視覚的統一感が崩れる。
  • テンプレート（Light / Rich）どちらかに準拠 Light = foundations/strategy/logs / Rich = research/ の長文 → なぜ：独自 CSS を毎回書くと差分が増え、後の一括変更が困難になる。
  • 見出し階層を飛ばしていない（h2 → h4 のような飛び級なし） → なぜ：目次の自動生成・スクリーンリーダーの読み上げが壊れる。
  • バッジ運用ルールに沿っている（スタイルガイド §4） 必読 / NEW / LIVE / アーカイブ / PROPOSED → なぜ：恣意的バッジは読み手の認知負荷を上げる。
  • 日付書式が YYYY-MM-DD で統一 → なぜ：ソート・grep・自動処理の標準化。

5. カテゴリ別の追加要件

LLM トラッカー（claude-recent-updates / chatgpt-recent-updates / gemini-recent-updates） MUST

  • 3社で同じ粒度・構造を保つ（hero / stats / 重要タイムライン / diary / sources） → なぜ：LLM Updates Hub の差別化軸が「横並列比較」。1社だけ厚い/薄いとハブ全体の意義が薄れる。
  • last-update が3社で同期している（同じカバー範囲）
  • 4タイル stats が現状の主要指標を反映している

Industry Trends（trend-*） MUST

  • テーマがベンダー横断である（単一ベンダーで完結する話は LLM トラッカー側に書く） → なぜ：ADR-003 で定めた棲み分け。重複コンテンツを防ぐ。
  • 4本以上の独立した1次/2次ソースを引いている
  • 「次の更新タイミング」が末尾に明記されている（例: 10月 IPO 実施後）

foundations/* の参照ドキュメント MUST

  • 運用判断の根拠が明記されている（「なぜ」までセットで書く）
  • 陳腐化条件が明記されている（いつ・何で古くなるか）

logs/* のダッシュボード MUST

  • 計測時点が明記されている
  • 再計測手順が記載されている（スクリプトや手順）

ADR（decisions.html 内のエントリ） MUST

  • Context / Decision / Consequences の3要素が揃っている
  • ステータス（ACCEPTED / SUPERSEDED / PROPOSED）が明記されている
  • 連番（ADR-NNN）がユニーク

6. 検証手順

ページを「完成」と判定する前のチェック手順。

# 1. 構造チェック
grep -c "<h1>" your-page.html             # 1 であることを確認
grep "最終更新\|last-update" your-page.html  # 最終更新日があるか

# 2. リンクチェック（外部 URL）
# WebSearch / WebFetch で各 URL を実在確認
# 確認できないものはテキスト出典に置換

# 3. 内部リンクチェック
# 相対パスで張ったリンク先が存在するか
grep -oE 'href="[^"]+\.html"' your-page.html

# 4. 親 index からの導線確認
grep "your-page.html" parent/index.html

# 5. Site Map への登録確認
grep "your-page" foundations/site-map.html

7. 「完成」と「公開」の違い

このハブでは Pull Request レビューや承認フローを使わず、main 直接 commit が中心です。そのため「完成」 = 「公開」に近い。だからこそ Definition of Done の遵守が重要。

状態条件記録先
WIP（作業中）MUST 要件未達git ステージ前 / フィーチャーブランチ
完成MUST 全件クリアmain へ commit & push
洗練済みMUST + SHOULD クリア同上 + Hub Health で OK 判定
陳腐化last-update から一定日数経過Hub Health で WARN / ALERT 表示

9. このページ自体の Done

Definition of Done は常に最新の運用に合わせてアップデートする必要があります。以下のタイミングでこのページを更新:

  • 新しいカテゴリ別要件が必要になった時
  • 失敗事例（anti-patterns）から学んだ要件を反映する時
  • 四半期に1回、棚卸し
  • カラーパレット・命名規約等のスタイル変更があった時
