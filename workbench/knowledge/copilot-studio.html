Copilot Studio：agent・workflow・harnessを選ぶ

旧チャットボットの説明から刷新。会話を作る機能と業務を実行する基盤を分け、現在のharness、知識、ツール、課金の関係を理解する。

最終更新：2026-10-13 / 公式一次資料確認。実環境の機能・契約検査は未実施。

会話の生成だけでなく、何を実行するかを作る

Copilot Studioはagentsとworkflowsを作り管理するlow-code studioだ。公式の現行説明はknowledge、tools、channels、評価と管理を扱い、app作成や自然言語による構築にはpreviewの表示がある。現行overview。一部の機能の発表を、すべてのtenantで使える完成サービスの説明へ広げない。

選択の出発点は会話の数ではなく、仕事の性質だ。情報を引用して回答するだけなら知識の接続と検索が主になる。記録の作成やメール送信を伴うなら、実行の身元、確認点、復旧、費用が主になる。会話が自然でも業務処理が正しいとは限らない。

2026年秋：harnessの差を理解する

harnessはモデルとagentの間で、呼出し、context、結果の解釈、ツール実行を制御するruntimeだ。現行公式harness比較はGitHub Copilot harness、standard harness、Copilot chat harnessを分けている。前者は長い推論・多段階処理、standardは定義した会話やagent flow、chatはCopilotの組織知識拡張という違いがある。

重要な注意として、StudioのGitHub Copilot harnessはGitHub Copilotサービスそのものではない。公式はStudio実行時に顧客データをGitHub Copilotサービスへ送信・処理しないと説明する。共通の技術名をサービスの契約や課金へ置き換えてはならない。同じStudioの中でもharnessを変えると機能と費用が変わる。

知識・指示・toolは同じ権限ではない

knowledgeは回答を支える資料、instructionsは役割や行動の条件、toolsは実際に操作できる対象である。教材では「公開FAQから答える」という知識agentと、「受付レコードを作る」というtoolを分ける。参照資料に書かれた手順が、ツール実行の許可へ自動昇格しないようにする。

自由記述から意図を推論する工程でも、宛先ID、数値、必須項目、許可された操作は通常の検証を通す。質問が曖昧なら確認を返し、知らない情報は回答しない。曖昧さを自信のある文章で覆うより、何が足りないかを短く返せる方が運用の価値が高い。

課金は「会話一件」で一律ではない

GitHub Copilot harnessは構築、preview、test、評価生成からCopilot Creditsを消費すると公式に説明される。現行usage-based billing。standard harnessの機能別表をそのまま当てはめない。standard側にも回答、action、grounding等の区分があり、ライセンス付き利用者の包含条件にはidentityやtriggerなどの条件がある。standard billing。

筆者の見積り案は、正常な一往復、資料不足、tool失敗、長い再計画という四経路を測ることだ。最短のdemoだけでは平均費用や上振れが分からない。クレジット、Power Automateライセンス、別モデルendpoint、外部サービスの費用を異なる欄にする。「M365で使うからすべて追加費用なし」という一般化を避ける。

採用前の質問

誰がagentを管理し、誰の接続でtoolを実行し、どの資料の版を正本とし、失敗を誰に返すか。答えがないまま公開channelを広げない。公式governanceが管理・policy・usage visibility等を提供していても、利用組織の責任者を自動的に決めるわけではない。

試験は閲覧だけのknowledgeから始め、次に候補の作成、最後に条件付きの確定処理へ広げる。性能の良いモデルへ切り替えるだけで、toolの境界や復旧が完成することはない。具体的な一件の作り方は実践ガイドで扱う。
