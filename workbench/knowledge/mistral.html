Mistral — Large 4、OCR、音声を工程から選ぶ

モデル競争の順位ではなく、文書・音声・検索を正確に扱うpipelineを設計します。新しいLarge 4のPreview条件と、OCR 4.1の根拠へ戻れる構造を軸に、実務導入を判断します。

公式資料で確認した仕様、提供側の評価、本稿の設計提案を区別しています。実アカウント・APIでの性能試験や契約は実施していません。旧本文は刷新前の固定版で参照できます。

1. 汎用LLMだけでなく、文書・音声・検索を組む

Mistralの現行catalogには、generalist、OCR、audio、code、embedding、moderationの異なるmodel群があります。10月13日確認ではLarge 4、Small 4、OCR 4.1、Voxtral系統などが掲載されています。第三者のZ.ai modelを提供する欄もあるため、catalog掲載をMistral自身の開発と取り違えません。Models overview

選択は「最強のmodel一つ」からではなく、資料を読取る、構造を抽出する、検索する、回答する、違反を検出するという工程から始めます。OCRに適したserviceへPDFを渡し、汎用LLMへ検証可能な構造を渡す方が、画像を何でも一つのchatに入れるより原因を切り分けやすくなります。

APIサービスとopen-weightのself-hostは運用責任が違います。APIではmodelの提供段階、region、費用、廃止方針を見ます。self-hostではweightのlicense、hardware、runtime、更新、監視を持ちます。Chatサービスの購読がAPI利用料を含むとは推論しません。

2. Large 4の新しさと、Previewの制約

Large 4のmodel cardは10月6日付のPublic Preview、open-weight、MoE、1M contextを記しています。active52Bと総1.05Tのparameter表記は異なる指標です。Large 4 card本稿はそのまま小型PCで動くという結論には使いません。

公式lifecycleではLabsとPublic Previewにsilent updateがあり、GAとは条件が違います。aliasは挙動や価格変更の影響を受け得るため、再現性が必要ならmajor.minorを固定するよう説明されています。Lifecycle policy

公開Previewは誰でも確認できる新候補ですが、「本番品質が自組織で検証済み」という意味ではありません。PoCには向いていても、同じinputを定期処理する仕事では提供側の変更が結果へ混ざります。実行日・model ID・入力版を保存し、変更通知の有無だけでなく少数の回帰testも持つ案が有効です。

3. OCR 4.1を文書pipelineの入口にする

OCR 4.1のGA cardは、paragraph-level bounding box、structural block label、block confidenceを説明しています。OCR 4.1座標とconfidenceが得られることは、完全に正しい転記の保証ではなく、人間の確認箇所を絞る材料です。

未実施の例として、縦書き説明、二段組、脚注、表、画像captionを含む公開PDFを教材にします。全文textだけでなくpage番号とblockを保存し、要約文の主張から元のblockへ戻れるようにします。表の罫線が正しくても、行や単位の対応が崩れる場合があるため、数値と単位は別の検査対象です。

文書処理の設計例:
PDF原本版 → OCR blocks → 構造検査 → 検索index → 回答
block: page / box / label / text / confidence
検査: 読順、表の行列、数値の単位、脚注、欠落
回答: 根拠blockを示す。原本にない結論は提案欄へ。

confidenceの低い箇所だけを確認すれば十分とも限りません。high confidenceの誤りを見逃さないため、抜取りの正解照合も併用します。低品質scanを拡大する、回転を正す、別OCRへ比較するという修正は、抽出後のLLMに意味を補わせる処理とは区別します。

4. 音声とlicenseの混同を防ぐ

catalogはtranscribe、realtime、TTSを別に列挙し、licenseもmodelによって異なります。たとえばVoxtral TTSの表示はCC BY-NC 4.0で、Apache 2.0と同じ扱いにはできません。Audioとlicense一覧

制作で音声を使う場合、文字起こしの品質、発話者識別、合成音声の権利、収録者の同意を分けます。modelが声を複製できることと、任意の人物の声を作品へ使えることは別です。commercial可否をcatalogの「Open」だけで決めず、利用artifactのlegal条件を確認します。

評価例には日本語固有名詞、BGM重なり、沈黙、短い相づちを入れます。単語誤りだけでなく、重要な否定が消えて意味が逆になる失敗を優先して記録します。realtimeでは字幕の訂正回数と遅延、batchでは後編集時間を別単位で測ります。

5. 採用までの小さな比較

  1. OCR、音声、検索など一工程と、その失敗条件を決める。
  2. 公開または架空の入力で正解表を用意する。
  3. 既存工程と新候補を同じ入力・同じ採点で比較する。
  4. 誤りの種類、後編集、費用、保管・通信条件を残す。
  5. model IDを固定し、Previewやalias変更時の再評価条件を定める。

汎用modelを大きくしても、PDF読順の破損や認識した単位の取り違えは直らないことがあります。どの工程が失敗したかを残すことが重要です。本稿はAPIやweightを実行していないため、速度向上・正答率・費用削減の実績は主張しません。取り入れる価値は、実作業の一工程をより検証しやすくするかで判断します。
