OpenClaw アーキテクチャ：Gateway と実行の流れを追う

最終更新・公式情報確認：2026-10-13。確認日は発表日ではありません。本文の教材・評価案は筆者の提案であり、実行済み成果や導入保証ではありません。

アーキテクチャを理解する目的は、構成図を暗記することではない。依頼が来たのに結果がない、結果はあるのに通知されない、同じ依頼が二度走る、といった現象をどの段階の問題か切り分けるためである。OpenClaw の主な登場人物を、実行の順序と権限の境界で読む。

Gateway、クライアント、ノード

公式の Gateway architecture では、Gateway が長く動いてチャネルを保持し、CLI・アプリ・Web 管理などのクライアントが制御 API へ接続する。ノードは role: node と提供する機能を宣言する別の接続主体だ。OpenClaw Gateway architecture アプリの画面がある機械と、ツールを動かす機械を自動的に同じと考えない。

筆者の説明用の流れは「入力→ルーティング→文脈→推論→ツール要求→検証→実行→保存→配送」とする。これは全てが一つの直列処理という実装上の断定ではなく、どの責任を確認するかの観察モデルである。並列や再開があっても、各効果をどの依頼へ帰属させるかは残る。

受け付けと完成を分ける

公式プロトコルの説明には、runId 付きの受け付け応答と、後のイベントや最終結果がある。副作用のある要求には idempotency key も必要とされる。OpenClaw Gateway architecture 受け付けの応答を仕事の完成へ読み替えない。再送は新しい仕事なのか、前の仕事の再確認なのかを明確にする。

教材例として、資料の比較を開始し、途中でクライアントの接続が切れた場面を考える。画面が見えないだけなら、仕事をもう一度開始する前に元の ID の状態を確認する。結果が不明な操作を新しい ID でやり直すと、通知やファイルの重複につながる可能性がある。実際の重複抑制の期間や条件は利用する版で確認する。

ツールの所在は別の地図

Sandbox を有効にしても Gateway プロセスはホストに残り、対象となるツール実行だけが sandbox backend へ移る。OpenClaw Sandboxing そのため「Gateway を Docker で動かす」「エージェントのツールを隔離する」「ノードの機能を呼ぶ」は分けて図にする。

この地図には、作業領域、読み取り専用の資料、書き込み可能な結果、外部通信、秘密の経路を書く。コンテナ名の箱を描くより、箱を横切る線が何かを記す方が重要である。ツールが拒否されたときは、どの境界の拒否かを調べ、別の場所で実行して回避しない。

定期ジョブの時計はモデルではない

公式 automation lifecycle は、スケジューラが Gateway 内で動き、Gateway が起きている必要があること、定義や実行状態が永続することを説明する。OpenClaw Automation lifecycle モデルが覚えているから時間通りに動く、という設計ではない。予定、実行、結果、配送を独立した状態として観測する。

筆者の設計案では、日付と対象資料 ID を使った仕事のキーを決める。再起動で期限を逃した場合に、遡って全件処理するのか、次回へまとめるのか、保留にするのかを先に選ぶ。タイマーが鳴ったという記録だけで、完成した記事があるとは言えない。

記録を三層へ分ける

会話は利用者が何を頼んだかを示す。実行記録は何が要求され実際に行われたかを示す。成果物は何が完成したかを示す。三つを同じ長文ログへ混ぜると、モデルの説明と実際の効果を区別しにくい。観察に必要な範囲だけ保持し、秘密や個人情報を診断資料へ複写しない。

更新後の回帰検査では、同じ入力と同じ禁止効果を再利用する。以前の構成が持っていた役割を新しい設定がどこで担うか対応表にし、空欄があれば移行未完了と扱う。名前が変わった設定を似た名前へ置き換えるだけでは、意味の移行を確認したことにならない。

構造の理解を使う場所

資料整理なら根拠と提出物、通知なら配送確認、端末操作なら対象機器と権限が重要になる。最も詳しい図を作るのではなく、その仕事で失敗すると困る線を一つ選んで観測する。構成の理解は、機能を増やすためだけでなく、必要のない機能を接続しない判断にも役立つ。
