OpenClaw マルチエージェント：分業の価値と共有の危険を分ける

最終更新・公式情報確認：2026-10-13。news という旧 URL は維持し、本文は用途別の現行ガイドへ刷新しました。確認日は発表日ではありません。

例と評価案は筆者の設計提案で、未実行です。性能測定・本番導入・安全認定・正式採用の実績を示すものではありません。

複数エージェントは、人数を増やした組織そのものではない。同じ誤った資料を読めば同じ結論を繰り返し、責任が曖昧なら完成したと誰も確定できない。この章では分業の対象、成果物の契約、共有する状態を具体化する。名前の違う人格を作るだけで、多角的な判断が得られるとは言わない。

agent と session の粒度

公式 multi-agent は、agent ごとに workspace、状態、session store を持ち、bindings で入口を振り分ける。workspace は既定の作業場所であって、それだけでは hard sandbox ではない。Multi-agent routing 別の agentDir と別の名前を用意したことを、ホストの能力の分離と混同しない。

話題を分けたいだけなら session の分離で足りる場合がある。一方、異なる秘密や道具を使うなら、権限と保存の範囲を確認する必要がある。どちらの問題を解きたいか決めてから構成を増やす。

三役の成果物契約

筆者の教材は公開仕様の比較である。調査役は根拠の表、執筆役は候補原稿、確認役は主張と出典の対応を提出する。確認役へ調査の結論だけ渡すと独立性が弱くなるため、原本も渡す。各役が使える入力と書ける出力を限定し、任意の役を作って仕事を増やさない。

全体の完成条件は、三役が応答したことではなく、原稿と根拠表と指摘が対応し、未確認の主張が分かることである。確認役が褒めたという文章だけを合格としない。人が採用する判断は最後に残す。

共有を表へする

公式文書は、plugin の保存が agent を増やせば全て自動で分割されるとはしない。Multi-agent routing 作業ファイル、履歴、記憶、秘密、外部サービスの接続を別々に確認する。推論モデルが同じか違うかより、この共有表の方が情報の漏れを説明しやすい。

教材では A のみに与える合成の識別語を使い、B の出力へ混ざる経路を探す。出なかった一回は安全の証明ではない。意図した共通知識と、分ける必要のある情報を一覧化し、外へ出せる結果も区別する。

委任は命令の増幅ではない

一つの依頼を何度も分解すると、確認すべき成果物も増える。役を増やす際は、どの専門性または独立した検査が増えるのかを説明する。単に同じ質問を三回言い換えるなら、並列化より一つの評価集合を作った方が有益な場合がある。

中間結果を返す役と、外部へ公開する役は分ける。担当候補の提案は正式な配送や作業命令ではない。全員へ同じ強い道具を配らず、必要な入力と出力へ限定する。拒否を別の役へ渡して回避しない。

待ち合わせの失敗を試す

調査が遅れ、執筆だけ終わった場合、確認が矛盾を見つけた場合、一役が止まった場合を合成して試す。全体の coordinator は、未完成、保留、完成を区別し、足りない役の成果を捏造しない。再試行する対象を一つに限定する。

公式 Team setup も、一つの Gateway 内の共同作業は信頼領域の内側の guardrail として説明する。Team setup 共同作業に便利な画面があることと、独立した審査者の判断があることを分けて扱う。

分業を残す条件

一人の処理より根拠の不足を見つけやすい、作業時間が短い、失敗箇所が分かる、という観測が揃えば分業を続ける候補になる。逆に待ち合わせと重複が増えたなら、役を減らすことも改善である。エージェント数を組織の成熟度として扱わず、責任と成果物の対応で判断する。
