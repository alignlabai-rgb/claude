Claude Codeの内部動作を、運用の判断に使う

文脈・tool往復・圧縮・キャッシュを理解し、長い作業の失敗箇所を見分けます。

旧情報は固定旧版の全文へ分離しています。以下の例・試験案は未実行の教材です。

モデルだけでは作業は進まない

公式はClaude Codeを、文脈を集め、行動し、結果を確認するagentic loopとして説明しています。How Claude Code works。モデルは次の行動を提案しますが、ファイルやコマンドへ実際に作用するのはツールと実行環境です。この区別があると、推論の誤りと接続失敗を分けられます。

教材の修正作業では、対象を探す、ファイルを読む、仮説を作る、編集する、テストする、結果を読み直す、という往復が発生します。途中のテストが失敗したとき、その出力を文脈へ戻さず「修正完了」とまとめると、loopの確認工程が失われます。実行ログをただ保存するのでなく、結果が次の判断に使われたかを確認します。

文脈は保管庫ではなく現在の作業机

文脈には会話、指示、tool定義、読み込んだファイル、実行結果が積み重なります。残しておきたい原資料と、今ターンで必要な情報は一致しません。すべてを毎回コピーするより、目的、制約、正本、現在の仮説、未解決を短い入口として保つ方が、関連の薄い情報に判断を奪われにくくなります。

要約した内容だけを証拠にすると、数値の単位や例外条件が消えます。長い調査では、要約の文に対象版と元の箇所を紐付け、訂正が必要なら原文へ戻れるようにします。資料が入ったから理解できたという期待ではなく、離れた二つの条件を実際に突き合わせる反例で確かめます。

キャッシュは記憶や成果の再利用ではない

Codeはprompt cachingを自動管理します。modelの変更や入力の変化でキャッシュの利用が変わるため、長い会話なら毎回安いとは限りません。Codeのprompt caching。キャッシュを当てにした費用設計では、入力、cache write、cache readを分けます。

再利用された入力は、今回の結論が正しいという意味ではありません。仕様が更新されたのに古い本文を送れば、効率よく古い判断を繰り返すこともあります。文脈の効率と知識の鮮度を別に検査し、長い安定prefixを保つ工夫が現在の制約の反映を妨げていないか確認します。

圧縮後の再開を試す

未実行例として、三段階の小型修正を一つの会話で進め、途中に文脈整理を挟む試験を作ります。圧縮前に「変更してはいけないAPI」「既存失敗」「次の対象」を明文化し、再開後のdiffとtestで保持を確認します。全文を覚えているかという曖昧な質問より、対象が変わらないかを観察する方が有効です。

CLAUDE.mdは指示の入口として使えますが、会話でだけ述べた重要条件は失われやすくなります。Memoryと指示の継続。条件を保存する場合も、秘密や一時的な手続きまで共有指示へ移さず、適用範囲と寿命を示します。

遅さの原因を分解する

遅延は深いthinking、長い入力、network待ち、巨大なログ、同じ失敗の繰り返し、workerの統合待ちなどで起こります。全部をmodelの性能へ帰すと、改善箇所が見えません。壁時計時間とAPIの処理時間、tool待ち、確認作業を別に記録し、どの工程が支配しているかを探します。

たとえばtest全件の出力が長い場合は、成功行を丸ごと会話へ載せるより、実行command・終了状態・失敗箇所を残し、必要な原ログへ戻れるようにします。これは未実行の方法案です。評価では結果を省いたことによる取り逃しがないか、少量の正常・異常fixtureで比べ、短くなっただけで品質が上がったとしません。

文脈事故を再現する教材

架空の仕様書を二つ用意し、一方には『金額は税込』、もう一方には『集計は税抜』と記します。両方を同時に渡す試験と、二段階で渡す試験を分け、回答が矛盾を指摘するか、どちらかを無言で選ぶかを比較します。これは文脈に入った情報をどう扱うかの評価で、特定モデルの性能実績ではありません。

再開の教材では、途中までの結論だけを渡す場合と、出典・未解決事項・次の一手を含む短い引継ぎを渡す場合を分けます。合否は同じ文章が再生成されることではなく、根拠を欠いた断定が増えず、残った課題から再開できることです。トークンが多い方を良い文脈とせず、必要な矛盾と境界が見えているかを評価します。
