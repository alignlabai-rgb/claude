Archive Policy — 古いコンテンツの処理ルール

このハブで古くなった・終了した・役割を終えたコンテンツをどう扱うかを定めます。「削除すれば綺麗になる」は最も避けたい判断で、過去の情報も将来の判断材料になるという前提でアーカイブ運用を設計しています。

大原則

① 削除より移動、移動より追記

情報を消すと「あったこと自体」が失われる。可能な限り、追記や注記で「過去のもの」と明示する方を選ぶ。

② リンク切れを作らない

外部からそのページを参照していたリンクが死ぬ。物理的に移動する場合もリダイレクトページを残すか、内部参照を全て更新してから移動。

③ 「アーカイブ」と「公開停止」は別物

アーカイブは「現役ではないが残しておく」。公開停止は「外部からアクセスさせない」。本ハブは公開リポなので、後者をやるなら別リポへ移動する必要がある。

④ git 履歴は最終バックアップ

うっかり削除しても git log から復元できる。だからこそ「意図的な削除」と「事故」を区別できるよう、ADR か session log にコンテキストを残すこと。

4 段階のアーカイブレベル

コンテンツの状態を 4 段階で扱います。状態が下がるほど目立たない位置に移し、最終的には物理削除も視野に入れる。

L1: Active 現役 — 通常運用

常時更新される、または更新される可能性が高いコンテンツ。トップカードからリンクされ、Hub Health でも監視対象。

  • 例: LLM トラッカー 3 本 / AI News 日次 / Industry Trends 6 本 / Creator System
  • 処理: 通常運用。Hub Health で鮮度を監視

L2: Stable Reference 安定参照 — 更新は稀

過去に確定した情報の記録。情報自体に変化はないが、参照価値が継続するもの。バッジに「参照」「年表」等が付くことが多い。

  • 例: claude-timeline.html / 過去の ADR / capability-map.html / glossary.html
  • 処理: トップカード上は active と同じ場所。鮮度判定は「内容が現状と乖離していないか」を基準にする（更新頻度ではなく）
  • 四半期に 1 回、内容の妥当性を確認

L3: Archived アーカイブ — 役割終了、参照価値あり

役割を終えたが、過去の経緯として参照価値があるもの。トップカードからの直接導線は外し、専用のアーカイブセクション経由でアクセスさせる。

  • 例: demos/ma-demo-2026.html（4/17 MA デモ）/ 過去の四半期レビュー / SUPERSEDED な ADR
  • 処理: 「アーカイブ」バッジを表示。親 index に「アーカイブセクション」を設けてそこから辿らせる。物理ファイルはそのまま、URL も変えない
  • ファイル冒頭に「これは過去のコンテンツです（YYYY-MM-DD 時点でアーカイブ）」のような注記を追加することも検討

L4: Retired 退役 — 物理削除候補

もう参照価値が無く、検索結果に出るとむしろ混乱を招くもの。物理削除を検討するが、必ず ADR で経緯を残してから実施する。

  • 例: 機密混入してしまったページ（ローテーションで作り直す）/ 完全にスタブのままだった実験ページ / 重大な誤りを含むまま放置されたページ
  • 処理: 必ず ADR を書く → 削除を実施 → セッションログにも記録 → 内部から張られていたリンクを全て掃除
  • 削除前に git log -- <file> で履歴の完全性を確認

レベル判定フロー

「これ古いかも？」と思ったページについて:

  Q1. 今後も参照される可能性はあるか？
       Yes → Q2 へ
       No  → Q3 へ

  Q2. 情報が現状と乖離していないか？
       乖離なし → L2: Stable Reference のまま
       乖離あり → 更新できるなら L1 として更新
                  更新できないなら L3: Archived（注記付き）

  Q3. 残しておくと混乱を招くか？
       No  → L3: Archived（静かに残す）
       Yes → L4: Retired（ADR を書いて物理削除）

カテゴリ別の運用

カテゴリ典型的なアーカイブ対象処理
research/ai-news/ 古い日次ニュース（3 ヶ月以上前） L2 のまま保持。日付付きの自然なアーカイブ。Site Map の AI News セクションは「直近 30 日」「過去」で分けると見やすい
research/claude-recent-updates 等 過去四半期分のタイムライン 同一ページ内で「新→古」順に保持。古い四半期は折りたたみ UI を検討
research/trend-* 記事化したテーマで状況が大きく変わったもの 原則 L1（更新可能）。更新コストが高すぎる場合は L3 にして「YYYY-MM 時点の分析」と注記
demos/ 過去のイベント専用資料 L3 が標準。demos/index.html 内の「アーカイブ」セクションで分離表示
workbench/knowledge/<vendor>.html ディスコンになったプロダクトのページ L3。ファイルは残し、冒頭に「YYYY-MM にサポート終了」の注記。後継があれば後継ページへのリンクを追加
foundations/decisions.html 覆された ADR 削除せず、ステータスを superseded に変更。新 ADR で「ADR-NNN を置き換える」と明示
logs/sessions/ 古いセッションログ L2 のまま全件保持。歴史資料として価値が高い
logs/2026-q2-review.html 等 過去の四半期レビュー L2 のまま全件保持。チェンジログとセットで運用

「アーカイブセクション」の作り方

カテゴリ index に L3 のページを置く時は、本体とは分離した「アーカイブセクション」を設ける。実例: demos/index.html の「イベント終了済み（アーカイブ）」セクション。

  <h2>役割終了済み（アーカイブ）</h2>
  <p class="small">下記は当時の文脈での資料です。物理ファイルは保持していますが、
  トップからの直接導線は外しています。</p>

物理削除のチェックリスト（L4 移行時）

削除は慎重に・手順通りに。「整理」のつもりが事故になる典型例（AP-005 と同根のリスク）。

  1. 削除理由を明記した ADR を書く（decisions.html）
  2. 内部の参照箇所を grep で全件洗い出し： 
    grep -rln "削除予定のファイル名" .
  3. 参照を全て更新（リダイレクト先 or 削除）
  4. 外部の参照可能性を検討（SNS で言及・他リポからリンク等）
  5. git rm でファイル削除 → commit メッセージに ADR 番号を明記 
    git rm path/to/file.html
git commit -m "Retire path/to/file.html (ADR-NNN)"
  6. セッションログとサイトチェンジログに経緯を記録
  7. Site Map から該当エントリを削除

「いつアーカイブを検討するか」のシグナル

  • Hub Health で 60 日以上 ALERT: 単に古いだけなら L2、誰も更新できる人がいないなら L3 検討
  • 外部リンク先がほぼ全部死んだ: 情報の検証可能性が失われた → L3 にして注記
  • 後継ページが完成した: 旧ページに「→ 新ページへ」のリンクを残して L3 へ
  • ユーザーから「これもう不要」の明示: L3 か L4 を判断
  • 機密情報の混入が判明: 即 L4（物理削除）+ git history も書き換え検討（force push が必要なら別 ADR）

例: 4/17 MA デモの扱い（実例）

  1. イベント終了（2026-04-17）
  2. 1 ヶ月放置後（2026-05-25）、トップ中段バナー 2 本が陳腐化していることに気付く
  3. 選択肢を A/B/C で提示し、ユーザーが「バナー削除 + demos/ フォルダ自体は残す」を選択（ADR-005 / ADR-006）
  4. demos/ma-demo-2026.html は L3 として保持、demos/index.html の「イベント終了済み」セクションに分離表示
  5. 物理リネームは見送り（リンク切れリスク回避）

このパターンが本ハブのアーカイブ運用の典型例。
