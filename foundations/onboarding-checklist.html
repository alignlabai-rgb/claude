Onboarding Checklist — 新セッションの最初の10分

新しい Claude / Codex セッション（または久しぶりに戻ってきた人）が、このハブで作業を始めるまでに踏むべき具体ステップです。 CLAUDE.md が「何を読むべきか」を示すのに対して、このページは「何をするか」を時系列で示します。

所要時間: 通常作業前で 5-10分。大きな構造変更の前は + 5-10分。

Phase A最初の 3 分 — Git とブランチ状態の把握
1

作業ディレクトリと git の状態を確認

git status
git fetch origin
git log --oneline -10
  • untracked / modified が残っていないか — 前回作業の残骸がないか確認
  • "behind" 表示があれば即 pull — 並走作業の取り込み（→ 並走プロトコル）
  • 最近10コミットの傾向 — 誰が・何を更新中か把握

→ なぜ：自分の作業が古い状態で進んで、後でコンフリクトする事故を防ぐ。AP-001 / RP-001 で実証済み。

2

並走ブランチの存在を確認

git branch -r | grep "claude/"
  • claude/laughing-cannon-* 等の自動命名ブランチがあれば、別セッションが同時稼働している可能性
  • 並走を検出したら 並走プロトコル を必ず読む
Phase B最初の 5 分 — このハブの「現在地点」を把握
3

必読ファイル 4 点をチェック

  • CLAUDE.md — 目的・フォルダ規則・編集方針
  • ALIGN Lab Context — ハブが何のために存在するか（ALIGN_Lab レポは別。このページが ALIGN_Lab の自己紹介を兼ねている）
  • Agent Protocol — エージェントとして作業する時のルール
  • Next Actions — 直近の TODO・優先タスク

→ なぜ：このハブの「何を達成しようとしているか」が変わることがある。前回の前提のまま動くと、すでに変わった方針と衝突する。

4

運用ダッシュボードで全体の健全性を確認

  • Hub Health Dashboard — 各カテゴリの鮮度・要対応 ALERT を一目で
  • 直近の四半期レビュー — Q の達成・ミス・次方針

→ なぜ：「次に何を更新するか」は気分で決めない。ダッシュボードで ALERT が出ているカテゴリを最優先に。

Phase C最初の 10 分 — 過去の判断と失敗を把握
5

直近の決定ログ（ADR）を斜め読み

  • decisions.html の上から 3-5 件を読む
  • 「なぜ今この構造なのか」を理解する。納得できなくても、まずは現状を尊重
  • 覆したくなったら、新しい ADR を書く（既存を上書きしない）

→ なぜ：構造はだいたい意図的にそうなっている。背景を知らずに「整理」すると、過去の決断を踏み潰す。

6

アンチパターンと用語集に目を通す

  • anti-patterns.html の AP-001〜006 を斜め読み（5分以内）— 過去エージェントの典型ミス
  • glossary.html — 知らない用語が出たら都度ここを引く

→ なぜ：同じ失敗を繰り返さない。「ありそうな URL を書く」「日付を混同する」等の典型ミスは避けられる。

7

今やる作業のカテゴリを決める

  • 変更が 制作・技術コア（Creator System / Claw Stack / Tech Workbench / LLM 個別深掘り）か
  • ナレッジ・資料（Industry Trends / Briefings）か
  • ハブ運用（Foundations / Strategy / Logs）か

→ なぜ：カテゴリを決めずに変更すると、トップ index.html での配置がブレる。CLAUDE.md のフォルダ規則を参照。

状況別フロー — 迷ったらここ

IF リンク切れを見つけた

  1. 該当ページを消さない。代わりに正しいリンクに修正する
  2. 修正できないなら、いったん logs/next-actions.html に「TODO: X.html リンク切れ修正」として残す
  3. リンク先を勝手にリネームしない（ADR-005 参照）

IF どこに置くか分からない

  1. CLAUDE.md の Folder Rules を見る
  2. 該当しなければ、用語集 で類似カテゴリを探す
  3. それでも分からなければ、カテゴリを新設せず、いったん近いカテゴリの下に置いて ADR で「暫定配置」と記録
  4. 新カテゴリ追加判断は ADR-002（3カテゴリ構造）を参照してから

IF 並走を見つけた

  1. 即 並走プロトコル を読む
  2. 相手の作業ブランチを消さない・上書きしない
  3. 自分の作業が重複している可能性を疑う（同じトピックを書いてないか）

IF 大きな構造変更をしたくなった

  1. その変更が「戻せるか」を考える。物理リネーム・フォルダ削除・カテゴリ統合は要注意
  2. 選択肢を 2-3 個用意してユーザーに提示（A/B/C 形式）
  3. 決まったら必ず ADR を書く。書くコストより後で読み返す価値の方が大きい

IF 情報の鮮度が分からない（古いかも？）

  1. ページ末尾の 最終更新: YYYY-MM-DD を確認
  2. 無い場合は git log -1 --format="%ai" -- <file> で確認
  3. Hub Health で対応するカテゴリの ALERT 状況を見る

IF URL や外部情報が必要

  1. 記憶ベースで URL を書かない（AP-002 の典型ミス）
  2. WebSearch / WebFetch で実在確認してから記載
  3. 確認できないなら 「Source: メディア名（日付）」のテキストだけにしてリンクを張らない

セッション終了前のチェック

作業を切り上げる前に以下を確認すると、次のセッションが困らない。

✓

編集したファイルの整合性チェック

  • ☑ 最終更新 / last-update の日付を更新したか（grep で全箇所同期）
  • ☑ 新規ファイルは親 index からリンクされているか
  • ☑ 重複コンテンツが残っていないか（AP-005 防止）
  • ☑ 外部リンクは実在確認済みか
✓

意図を残す

  • ☑ 構造変更があれば decisions.html に ADR 追加
  • ☑ 失敗・救済の事例があれば anti-patterns.html に記録
  • ☑ 新用語が出たら glossary.html に 1-2 行追加
  • ☑ 重い作業をしたら logs/sessions/YYYY-MM-DD.html でセッションログ（Phase 4 で運用復活予定）
✓

残作業を引き継ぐ

  • ☑ 途中で止めたタスクは next-actions.html に追加
  • ☑ commit する場合、明確なメッセージで（雑な「update」は禁止）
  • ☑ push する前に必ず git fetch && git status で並走確認
