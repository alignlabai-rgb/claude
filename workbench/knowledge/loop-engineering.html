ループエンジニアリングとは何か

「You don't prompt a coding agent once. You design loops that run autonomously. A loop with nothing to push back is the agent just agreeing with itself.」
── Loop Engineering の核心原則（Boris Cherny / Anthropic, 2026）

プロンプトエンジニアリングが「1 回の指示をどう書くか」、コンテキストエンジニアリングが「何を見せるか」だとすれば、ループエンジニアリングは 「エージェントがどう反復するか」 を設計します。

4 つの規律の進化を振り返ると：

規律問い確立時期設計対象
Prompt Engineeringどう頼むか2020〜1 回の指示文
Context Engineering何を見せるか2025年6月〜コンテキストウィンドウの中身
Harness Engineeringどう組むか2026年2月〜ツール・メモリ・検証の環境
Loop Engineeringどう回すか2026年6月〜自律反復サイクル全体

「ループ設計のないエージェントは、タスクを受け取り、1 回実行し、終わる ── つまり自動化スクリプトと変わらない。本当の意味でのエージェントは、フィードバックを受け取り、自分で判断し、次の行動を決める」という思想が基盤にあります。

「Reflect → Plan へのフィードバック」がループを閉じます。フィードバックゲートがないループはエージェントが自己承認を繰り返すだけです。終了条件（done-condition）の設計も同様に重要です。

軍事・認知科学から来た OODA ループとの対応

OODA（John Boyd, 1970s）Agent Loop（2022〜）役割
Observe（観測）Observe（ツール出力・環境状態）現実を知覚する
Orient（方向付け）Reflect（評価・判断）状況を解釈する
Decide（決定）Plan（次アクション決定）行動を選択する
Act（行動）Act（ツール実行）環境に影響を与える

AI エージェントループは OODA の直接の派生ではなく並行発展ですが、構造的に一致しています。

学術的系譜 ── 論文で辿るループの進化

ReAct: Synergizing Reasoning and Acting in Language Models
Yao et al. (Princeton / Google Research), arXiv 2022年10月
LLM に「思考（Reason）+ 行動（Act）を交互に実行させる」設計を提案。Thought → Action → Observation のサイクルが現在のエージェントループの原型。HotpotQA・ALFWorld で従来手法を上回る精度を実現。
Reflexion: Language Agents with Verbal Reinforcement Learning
Shinn et al. (Northeastern / MIT), arXiv 2023年3月
「言語フィードバックによる自己改善」を実現。タスク失敗後に自然言語で反省文を生成し、次のループに注入することで精度を向上。HumanEval でパス率 91% 達成（GPT-4 ベース）。
Self-Refine: Iterative Refinement with Self-Feedback
Madaan et al. (CMU / Yann LeCun Group), arXiv 2023年3月
同一モデルが生成・評価・改善を繰り返す「自己改善ループ」。追加学習なしに品質向上が可能なことを示す。数学・コード・要約など 7 タスクで平均 +20% の品質向上。
Tree of Thoughts: Deliberate Problem Solving with LLMs
Yao et al. (Princeton), arXiv 2023年5月
Chain-of-Thought を「木」に拡張。複数の思考経路を並列探索し、バックトラックを可能にする。ループの分岐・探索概念の先駆け。Game of 24 で GPT-4 を 4% → 74% に向上。
AgentBench: Evaluating LLMs as Agents
Liu et al. (THU / UC Berkeley), arXiv 2023年8月
エージェントとしての LLM を 8 環境で評価する統一ベンチマーク。ループ実行能力（長期整合性・自己修正・探索）の差がモデル選択で重要になることを示す。
SWE-bench: Can LMs Resolve Real-World GitHub Issues?
Jimenez et al. (Princeton), arXiv 2023年10月〜（継続更新）
実際の GitHub Issue 解決を評価するベンチマーク。エージェントがコード読解 → 修正 → テスト実行のループを何度回せるかが性能に直結。GLM-5.2 が OW 首位（62.1%）を取得。

ループ設計の 5 パターン

エージェントループには用途に応じた複数の設計パターンがあります。

① 単純反復ループ（Until-Condition）

「条件を満たすまで繰り返す」最もシンプルな形。終了条件の設計が全て。

# Claude Code パターン
until [ "$(npm test)" = "PASS" ]; do
  # Claude が自律的に修正を試みる
  sleep 2
done

適用: バッチ処理・フォーマット変換・単純な修正タスク

② TDD ループ（テスト駆動エージェント）

テストを先に書き、テストが通るまで実装を繰り返す。品質担保と終了条件が一体化した優れた設計。

# 1. テストを書く（人間 or エージェント）
# 2. 実装する（エージェント）
# 3. テスト実行（ハーネス）
# 4. 失敗 → Reflect → 再実装
# 5. 全テスト GREEN → 完了

適用: 機能実装・バグ修正・リファクタリング

③ 評価ループ（Eval Loop / LLM-as-judge）

生成 → 評価 → 改善を繰り返す。評価者と生成者が同一モデルでも分離したモデルでも機能。

for i in range(max_rounds):
    output = generator.generate(task)
    score, feedback = judge.evaluate(output)
    if score >= threshold:
        break
    task = enrich_with_feedback(task, feedback)

適用: コンテンツ品質向上・翻訳精度向上・レポート生成

④ 並列ループ（Parallel Agent Swarm）

複数のエージェントが独立した作業を並列実行。オーケストレーターが結果を統合。

# オーケストレーター
tasks = decompose(goal)
results = await asyncio.gather(*[
    agent.run(task) for task in tasks
])
final = synthesize(results)

適用: 大規模コンテンツ生成・マルチリサーチ・コードベース全体修正

⑤ 階層ループ（Orchestrator-Worker）

高レベル計画エージェント（オーケストレーター）が低レベル実行エージェント（ワーカー）を管理する 2 層構造。

class Orchestrator:
    def run(self, goal):
        plan = self.plan(goal)
        for step in plan:
            worker = Worker(step.type)
            result = worker.execute(step)
            self.update_state(result)
            if self.goal_met(): break

適用: 複雑な長期タスク・Kanban エージェント・マルチモーダルパイプライン

05 クリエイター Obsidian HEARTBEAT パターン ── Vault を定期的に自律更新するループ

// heartbeat.ts — 定期実行エージェント
async function heartbeat() {
  const pendingNotes = await vault.search("status: draft");
  for (const note of pendingNotes) {
    const enriched = await claude.enrich(note.content);
    await vault.update(note.path, enriched);
  }
}

// 毎朝 6:00 に実行
cron.schedule("0 6 * * *", heartbeat);

「下書きノートを毎朝エージェントが自動補完する」というクリエイターのワークフロー。ループが止まらない設計（cron）とエラー時の安全な停止設計が重要。

07 クリエイター 小説執筆エージェントループ ── プロット→章→段落→推敲の階層ループ

長編小説の自動執筆は階層ループ（⑤）の最も深い実装例の一つです。4 層の入れ子ループで構成されます：

# 層1: 物語全体ループ（終了条件: 全章完了）
for chapter in story.chapters:

    # 層2: 章ループ（終了条件: 章の一貫性スコア >= 0.85）
    while chapter.coherence_score < 0.85:
        scenes = planner.decompose_chapter(chapter)

        # 層3: シーンループ（終了条件: 段落数 + キャラクター整合）
        for scene in scenes:
            draft = writer.draft_scene(scene, story.memory)

            # 層4: 推敲ループ（終了条件: editor スコア >= 0.8）
            for _ in range(max_polish=3):
                score, notes = editor.review(draft)
                if score >= 0.8: break
                draft = writer.revise(draft, notes)

            scene.content = draft

        chapter.coherence_score = judge.evaluate_chapter(chapter)

各層の終了条件が独立しているため、章単位でのチェックポイント保存が容易になります。物語記憶（story.memory）をループをまたいで引き継ぐことが長期整合性の鍵です。キャラクターの言動・伏線・世界設定が矛盾しないよう、専用の長期記憶バッファを設計します。

パターン: 階層ループ ④×⑤ 組み合わせ
08 クリエイター SNS コンテンツカレンダー自動生成ループ ── 30日分を並列生成→評価→スケジュール

30 日分の SNS 投稿を一括で生成・評価・スケジュールするパイプラインです。並列ループ（④）と評価ループ（③）の組み合わせ：

import asyncio

async def generate_calendar(brand_voice, topics_30):
    # フェーズ1: 30日分を並列生成（④ 並列ループ）
    drafts = await asyncio.gather(*[
        writer.generate_post(
            topic=t,
            voice=brand_voice,
            platform="instagram"
        )
        for t in topics_30
    ])

    # フェーズ2: 品質評価ループ（③ 評価ループ）
    approved = []
    for draft in drafts:
        score = await judge.evaluate(
            draft,
            criteria=["engagement", "brand_fit", "hashtags"]
        )
        if score >= 0.75:
            approved.append(draft)
        else:
            # リジェクトされた投稿は再生成（最大2回）
            for _ in range(2):
                revised = await writer.revise(draft, score.feedback)
                score = await judge.evaluate(revised)
                if score >= 0.75:
                    approved.append(revised)
                    break

    # フェーズ3: スケジューリング
    calendar = scheduler.assign_dates(approved)
    return calendar

並列生成で速度を確保し、評価ループで品質を担保する二段構えが特徴。生成コストを抑えるため、草案生成には軽量モデル（Haiku 相当）、品質評価には高精度モデル（Sonnet 相当）を使い分けます。

生成速度: 30投稿 約90秒（並列化なしの4倍速）
09 クリエイター 動画編集指示ループ ── Premiere Pro / DaVinci Resolve への自動指示

映像編集ソフトへのエージェント自動指示は、「生成→プレビュー→評価→修正」の評価ループ（③）です：

# ExtendScript / DaVinci Scripting API を通じた制御
loop_state = {
    "target_duration": 90,  # 秒
    "pacing": "dynamic",
    "color_grade": "cinematic_warm"
}

for iteration in range(max_iter=5):
    # Act: 編集指示を生成してスクリプト実行
    edit_script = claude.generate_edit_instructions(
        footage_manifest,
        loop_state
    )
    premiere.execute(edit_script)  # ExtendScript 実行

    # Observe: 書き出しプレビューを取得
    preview = premiere.export_preview(quality="low")

    # Reflect: マルチモーダル評価（映像を直接評価）
    feedback = claude.review_video(
        preview,
        criteria=["pacing", "cut_smoothness", "color"]
    )

    if feedback.score >= 0.85:
        break  # 完了

    # 次ループへのフィードバック注入
    loop_state.update(feedback.adjustments)

マルチモーダル LLM がプレビュー映像を直接評価することで、「カットのテンポが速すぎる」「カラーグレードが青みすぎる」といった主観的なフィードバックを定量化してループに注入します。Adobe ExtendScript・DaVinci Scripting API・FFmpeg いずれでも同様の構造が適用できます。

11 エンジニア Reflexion 実装 ── 言語フィードバックによる自己改善ループ

Reflexion パターンの最小実装：

def reflexion_loop(task, max_trials=5):
    memory = []  # エピソード記憶
    for trial in range(max_trials):
        # 過去の反省を注入してから実行
        context = "\n".join(memory) if memory else ""
        result = agent.run(task, context=context)

        # 外部評価（テスト / LLM-judge）
        success, feedback = evaluate(result, task)
        if success:
            return result

        # 失敗した場合、自然言語で反省文を生成
        reflection = llm.reflect(
            f"タスク: {task}\n試行結果: {result}\n失敗理由: {feedback}"
        )
        memory.append(reflection)  # 次のループに引き継ぐ

    return None  # max_trials 超過

記憶（memory）への反省文の蓄積がループを賢くします。trial を重ねるごとに「何をすべきでないか」の知識が増えます。

12 エンジニア Grok Build ── 8 並列サブエージェントのオーケストレーターループ

xAI の Grok Build は並列ループ（④）+ 階層ループ（⑤）の組み合わせです：

def run_ci_loop(max_iterations=5):
    gates = [
        Gate("pytest", cmd="pytest tests/ -x -q"),
        Gate("mypy",   cmd="mypy src/ --strict"),
        Gate("ruff",   cmd="ruff check src/"),
    ]

        if not failures:

            return True

            failures=failures

        git.push()

    return False  # max 超過 → 人間にエスカレーション

17 エンジニア データクレンジングループ ── 異常検知→修正提案→承認→適用の反復

大量のデータセットに対して「異常を検知し、修正案を提示し、人間の承認を経て適用する」ループです。人間承認ゲート（⑥）を持つ半自律ループの実装例：

import pandas as pd

def data_cleaning_loop(df: pd.DataFrame, human_approval=True):
    cleaned = df.copy()
    iteration_log = []

    for iteration in range(max_iter=10):
        # Act: 異常検知
        anomalies = detector.find_anomalies(cleaned)
        if not anomalies:
            break  # 異常なし → 完了

        # Observe: 各異常に対して修正案を生成
        proposals = []
        for anomaly in anomalies[:20]:  # バッチサイズ制限
            fix = claude.propose_fix(anomaly, cleaned)
            proposals.append(fix)

        # Reflect: 人間承認ゲート（オプション）
        if human_approval:
            approved = review_ui.show(proposals)  # UI で承認
        else:
            approved = [p for p in proposals if p.confidence > 0.9]

        # Apply
        for fix in approved:
            cleaned = fix.apply(cleaned)

        iteration_log.append({
            "iteration": iteration,
            "anomalies_found": len(anomalies),
            "fixes_applied": len(approved)
        })

    return cleaned, iteration_log

人間承認ゲートを confidence > 0.9 の自動承認に切り替えることで、完全自律化と半自律の中間点を設計できます。金融・医療データなど高精度が要求される領域では人間ゲートを必須にし、ログデータなど低リスク領域では自動承認に切り替えるという使い分けが現実的です。

パターン: 評価ループ（③）+ 人間承認ゲート（⑥）

パターン: 並列④ + 評価③ + 単純① の多層合成

信頼できるループを作る 7 つのフィードバックゲート

「フィードバックのないループはエージェントが自分に同意しているだけ」── ゲートがループを機能させます。

① テストスイート（最強）

ユニットテスト・統合テストが通るかどうか。バイナリ（合格/不合格）でエージェントの主観を排除。TDD ループの要。

② 型チェッカー

TypeScript の tsc・Python の mypy など。エラーゼロを終了条件にすると収束が安定。

③ Linter / Formatter

ESLint・Prettier・Ruff など。コードスタイルの客観的評価。低コストで即座にフィードバックが得られる。

④ LLM-as-judge

別の LLM（または同一モデル）が出力を評価するゲート。主観的品質（文章の自然さ・論理性）の自動評価に有効。スコアに閾値を設定。

⑤ ビジュアル差分

スクリーンショット比較・ピクセル差分。UI 実装・デザイン生成ループで人間の目を代替。Percy / Chromatic などで自動化可能。

⑥ 人間レビューゲート

特定ステップで人間の承認を必須にする。コスト・安全性に関わる操作や「確信が持てない場合」に配置。Claude Code の permission system が実装例。

⑦ 上限カウンター（Safety）

最大反復回数・最大トークン使用量・最大実行時間のハードリミット。すべてのループに必須。無限ループ防止の最後の砦。

ループのデバッグ手法

ループが失敗・停滞した時に「何が起きたか」を診断する技術。ループ設計と同等の重要性を持ちます。

失敗パターンの分類

失敗パターン①: コンテキスト枯渇

ループを重ねるうちにコンテキストウィンドウが埋まり、初期の指示や状態が「見えなくなる」。後半のループで突然方向性が変わる症状が出ます。

診断方法: 各反復の入力トークン数をログに記録。急激な増加があれば Context Bloat が原因。

# 診断コード
for i, loop_state in enumerate(loop_history):
    print(f"[ITER {i}] input_tokens={loop_state.input_tokens}, "
          f"context_ratio={loop_state.input_tokens / CTX_LIMIT:.1%}")

失敗パターン②: ツール失敗カスケード

1 つのツール呼び出しが失敗すると、その失敗を「前提」として次のツール呼び出しも誤った方向に進む連鎖。エラーをコンテキストに注入し続けると加速します。

診断方法: ツール呼び出し履歴を「成功/失敗/リトライ」でタグ付け。失敗ツールのパターンを可視化。

# ツール呼び出しログのスキーマ
{
  "iter": 3,
  "tool": "run_tests",
  "status": "FAIL",
  "error": "ModuleNotFoundError: numpy",
  "retry": 1,
  "downstream_tools": ["fix_imports", "reinstall_deps"]
}

失敗パターン③: 近似無限ループ（Near-Infinite Loop）

終了条件に近づくが届かない状態で振動するパターン。テストが 9/10 成功の状態で残り 1 件を直しては別の 1 件を壊す「モグラ叩き」が典型例。

診断方法: 各イテレーションのゲートスコア推移をプロット。スコアが一定範囲で振動していれば Near-Infinite の可能性大。

# スコア推移の検出
scores = [loop.gate_score for loop in history]
variance = statistics.stdev(scores[-5:])  # 直近5回
if variance < 0.02 and max(scores[-5:]) < threshold:
    raise NearInfiniteLoopError(
        f"Score oscillating around {mean(scores[-5:]):.2f}"
    )

ループデバッガー実装

上記トレース形式を自動生成する軽量なロガークラスです。既存のエージェントコードに最小限の変更で組み込めます。

import time, textwrap
from dataclasses import dataclass, field
from typing import Literal

@dataclass
class IterRecord:
    iter_num: int
    input_tokens: int = 0
    plan: str = ""
    tool_calls: list = field(default_factory=list)
    observations: list = field(default_factory=list)
    gate_score: float = 0.0
    decision: Literal["CONTINUE", "SUCCESS", "MAX_ITER", "ERROR"] = "CONTINUE"
    elapsed_ms: int = 0

class LoopTraceLogger:
    def __init__(self, task: str, max_iter: int):
        self.task = task
        self.max_iter = max_iter
        self.records: list[IterRecord] = []
        self.start_time = time.time()
        self.total_cost_usd = 0.0

    def begin_iter(self, iter_num: int) -> IterRecord:
        rec = IterRecord(iter_num=iter_num)
        rec._t0 = time.time()
        self.records.append(rec)
        return rec

    def end_iter(self, rec: IterRecord):
        rec.elapsed_ms = int((time.time() - rec._t0) * 1000)

    def log_tool(self, rec: IterRecord, tool: str, status: str, output_preview: str):
        rec.tool_calls.append({"tool": tool, "status": status,
                               "preview": output_preview[:120]})

    def print_trace(self):
        width = 66
        header = f"LOOP TRACE  task={self.task}  max_iter={self.max_iter}"
        print(f"╔{'═'*width}╗")
        print(f"║  {header:<{width-2}}║")
        print(f"╚{'═'*width}╝")
        for r in self.records:
            print(f"\n[ITER {r.iter_num}/{self.max_iter}] "
                  f"{'─'*40} tokens: {r.input_tokens:,}")
            print(f"  PLAN  → {r.plan[:80]}")
            for tc in r.tool_calls:
                status_icon = "✓" if tc["status"] == "OK" else "✗"
                print(f"  ACT   → tool={tc['tool']} {status_icon}  {tc['preview']}")
            for obs in r.observations:
                print(f"  OBS   → {obs[:80]}")
            print(f"  REF   → score={r.gate_score:.2f}  decision={r.decision}")
        elapsed = time.time() - self.start_time
        last = self.records[-1] if self.records else None
        result = last.decision if last else "UNKNOWN"
        print(f"\n{'══'} RESULT: {result} in {len(self.records)}/{self.max_iter} "
              f"iterations {'═'*20}")
        print(f"   elapsed={elapsed:.1f}s  cost=${self.total_cost_usd:.4f}")

トークン効率とループコスト最適化

ループは反復するほどコストが積み上がります。「1 回のループをいくら使うか」を意識した設計がなければ、10 反復で予想の 10 倍のコストが発生します。

反復コストの計算モデル

ループの総コストは単純な反復回数 × 単価ではなく、コンテキスト蓄積によって指数的に増加します。

基本コスト計算

def estimate_loop_cost(
    base_ctx_tokens: int,    # 初期コンテキスト
    avg_output_tokens: int,  # 1反復あたりの出力
    iterations: int,
    input_price: float,      # $/1M tokens
    output_price: float,
    ctx_growth_rate: float = 0.8  # 出力の80%がctxに蓄積
) -> float:
    total = 0.0
    ctx = base_ctx_tokens
    for i in range(iterations):
        # 入力: 現在のコンテキスト全体
        input_cost = ctx * input_price / 1_000_000
        # 出力: 今回の生成
        output_cost = avg_output_tokens * output_price / 1_000_000
        total += input_cost + output_cost
        # コンテキスト成長
        ctx += int(avg_output_tokens * ctx_growth_rate)
    return total

早期終了（Early Stopping）

信頼度が閾値を超えた時点でループを打ち切る戦略。「完璧を求めて 10 回回す」より「80% の品質で 3 回で止める」ほうがコスト効率が良いケースが多い。

def loop_with_early_stopping(
    task,
    confidence_threshold=0.85,
    max_iter=10
):
    for i in range(max_iter):
        result = agent.run(task)
        confidence = evaluator.score(result)

        # 閾値超えで即終了
        if confidence >= confidence_threshold:
            return result, i+1  # 使用反復数も返す

        # 残りコストの見積もり
        remaining_budget = budget.remaining()
        projected_cost = estimate_next_iter_cost(i)
        if projected_cost > remaining_budget:
            log.warn("Budget limit: stopping early")
            return result, i+1

    return result, max_iter

同一の入力に対するツール呼び出し結果をキャッシュして、ループ内の重複実行を排除します。高コストな外部 API・DB クエリ・ファイル読み取りに特に効果的。

import hashlib, functools

class CachedToolRunner:
    def __init__(self):
        self._cache = {}

    def run(self, tool_name: str, **kwargs) -> str:
        # キャッシュキー = ツール名 + 入力のハッシュ
        key = hashlib.md5(
            f"{tool_name}:{sorted(kwargs.items())}".encode()
        ).hexdigest()

        if key in self._cache:
            return self._cache[key]  # キャッシュヒット

        result = tools[tool_name](**kwargs)
        self._cache[key] = result
        return result

分散ループ・スケールアウト設計

単一ループで処理できる限界を超えた時、ループをどうスケールするか。「1 エージェント × N 反復」から「N エージェント × M 反復」への進化です。

単一ループの限界ライン

以下のいずれかに該当したら、スケールアウトを検討するサインです。

時間的限界

1 つのループが完了するまでに 30 分以上かかる。ユーザー体験・コスト・エラーリカバリのいずれにも悪影響が出ます。

コンテキスト的限界

扱うべき情報量がモデルのコンテキストウィンドウを超える。1M ctx を持つモデルでも、コードベース全体・長期ログ・大規模データセットは収まらないことがあります。

独立性的限界

タスクが本質的に独立したサブタスクに分解できる。「30 本の記事生成」「100 ファイルのフォーマット変換」などは並列化で線形にスケールします。

ファンアウトパターン（1 オーケストレーター → N 並列ループ）

基本ファンアウト構造

import asyncio
from typing import Callable

async def fan_out_loop(
    orchestrator_task: str,
    worker_fn: Callable,
    max_workers: int = 8,
):
    # オーケストレーター: タスクを分解
    subtasks = await orchestrator.decompose(
        orchestrator_task,
        max_subtasks=max_workers
    )

    # ワーカー: N 個のループを並列起動
    semaphore = asyncio.Semaphore(max_workers)
    async def bounded_worker(subtask):
        async with semaphore:
            return await worker_fn(subtask)

    results = await asyncio.gather(*[
        bounded_worker(st) for st in subtasks
    ], return_exceptions=True)

    # 失敗したワーカーを再試行
    failed = [(i, st) for i, (st, r) in
              enumerate(zip(subtasks, results))
              if isinstance(r, Exception)]
    for i, st in failed:
        results[i] = await worker_fn(st)  # 再試行

    # オーケストレーター: 結果を統合
    return await orchestrator.synthesize(subtasks, results)

チェックポイント + プロセス再起動対応

長時間ループはプロセスクラッシュ・タイムアウト・デプロイによって中断されます。チェックポイントにより「続きから再開」を実現します：

class ResumableLoopRunner:
    def __init__(self, job_id: str, checkpoint_dir: str):
        self.job_id = job_id
        self.cp_path = f"{checkpoint_dir}/{job_id}.json"

    def run(self, task, max_iter=10):
        # 既存チェックポイントがあれば再開
        start_iter, state = self.load_checkpoint()

        for i in range(start_iter, max_iter):
            state = agent.step(state, task)
            # 各反復後に保存
            self.save_checkpoint(i + 1, state)

            if state.is_done:
                self.cleanup_checkpoint()
                return state.result

        return state.result  # max 超過

    def save_checkpoint(self, iter_num, state):
        with open(self.cp_path, "w") as f:
            json.dump({"iter": iter_num,
                       "state": state.to_dict()}, f)

    def load_checkpoint(self):
        if os.path.exists(self.cp_path):
            with open(self.cp_path) as f:
                cp = json.load(f)
            log.info(f"Resuming from iter {cp['iter']}")

アンチパターン 5 選

① 無限ループ（Infinite Loop）

終了条件が未定義、または達成不可能な条件を設定してしまう。最も危険なアンチパターン。APIコスト・時間が無限に消費される。

✅ Fix: max_iterations・max_tokens・timeout を必ず設定。loop 開始前にログで可視化。

② 自己承認ループ（Echo Chamber Loop）

エージェントが自分で生成し、自分で評価し、自分で合格とする。外部フィードバックゲートがないため、品質が改善されない。

✅ Fix: 評価は必ず外部（テスト・別モデル・人間）が行う。自己評価のみに頼らない。

③ コンテキスト肥大化（Context Bloat in Loop）

ループを重ねるたびに会話履歴・ツール出力が蓄積し、コンテキストウィンドウを圧迫。後半のループで初期の判断を「忘れる」。

✅ Fix: N ループごとに状態を要約圧縮。重要な状態のみ Task State（層⑦）として明示的に管理。

④ 過剰ループ（Over-Engineering the Loop）

1 回で十分なタスクに複雑なループを設計する。オーバーヘッドが大きく、シンプルな実装より遅く高コスト。

✅ Fix: まず単純実装で試す。反復が本当に必要かを検証してからループを導入。

⑤ フィードバックラグ（Slow Feedback Gate）

フィードバックゲートの実行に時間がかかりすぎてループが遅い。E2E テスト全件実行をすべてのループで行う等。

✅ Fix: 高速ゲート（型チェック・単体テスト）を先に配置。遅いゲート（E2E）は最終ループのみに。
