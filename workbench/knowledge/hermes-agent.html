Hermes Agent：学習をスキルと記憶へ変える運用設計

最終更新・公式情報確認：2026-10-13。確認日は発表日ではありません。本文の教材・評価案は筆者の提案であり、実行済み成果や導入保証ではありません。

Hermes Agent は Nous Research のエージェント基盤である。重要なのは「使うほど賢くなる」という一言より、経験をどこへ保存し、次回どの条件で再利用するかである。CLI、Gateway、ツールの backend、保存層を組み合わせるため、モデルの文章能力と、手順を育てる運用能力を別々に評価する。Hermes Agent 公式リポジトリ 本記事は特定組織の常設構成や採用状態を記載しない。

スキルは成功の認定ではない

公式 Skills System は、必要に応じて読み込む知識文書を説明し、ローカルのスキルへ追加や変更を行えるとしている。Hermes Skills System 便利な手順を保存できることと、その手順が安全で再現可能なことは違う。生成したスキルを自動的に推奨手順と扱わず、対象、前提、禁止効果、完成判定を読んで評価する。

教材例として、三つの架空の更新告知を比較した後、根拠の段落を取り違えた失敗をスキルの検査項目へ変える。次回は「モデル名」「提供面」「確認日」を別列にし、同じ名前の API と Web 機能を混ぜない。失敗したプロンプト全文の保存より、どの誤りを防ぐ条件かを残す方が再利用しやすい。

メモリは原本の代わりにしない

公式 Persistent Memory は MEMORY.md と USER.md による、量を制限した整理済みの記憶を説明する。開始時にはスナップショットとして読み込まれ、同じ Hermes home を複数プロセスで共有しないよう注意している。Hermes Persistent Memory 保存した短い結論には原本への参照と観測日を付け、古い判断を無期限の事実へ変えない。

覚えるべきものは、今後の作業に必要で、保存してよい情報だけである。利用者の秘密を便利だからという理由で記憶へ写す必要はない。業務の証拠、会話の履歴、安定した好み、再利用する手順を同じ箱へ混ぜると、どこを訂正するか分からなくなる。記憶から消したことと、ログや元資料から消したことも分ける。

実行 backend は別の判断

公式 architecture は、入口から AIAgent へ進み、provider resolution と tool dispatch、さらに保存とツール backend を分ける構造を示す。Hermes Architecture 同じ会話画面でも、ホスト上の terminal と隔離した実行環境では到達できる対象が違う。モデル名や personality の変更から、この境界を推測しない。

試行では作業用の合成ディレクトリを一つに限定し、何を書けるか、外へ何を送れるか、どのプロファイルの状態を使うかを記録する。コンテナを使う場合も mount と通信先を確認する。手元で推論すること、ホストでツールを動かすこと、チャットサービスへ結果を返すことは独立した選択になる。

承認はモードと実行面で読む

確認した公式 Security は危険コマンドの承認モードと、cron・単発・無人の実行面における別の設定を説明している。規則の照合は OS の完全な能力隔離ではないとも注意する。Hermes Security 本稿は承認を外す手順を薦めない。拒否された操作は、言い換えて通すのではなく、許可された課題へ戻すか運用者が要件を見直す。

通知からスキル更新までを一続きで自動化する前に、原稿の下書き、採用、外部送信を別段階にする。スキルを保存したいというモデルの提案は、人間や組織の採用判断ではない。省力化したい段階だけを自動化し、権限を持たない段階は候補のまま止められるようにする。

学習の価値を測る三つの問い

  • 同じ失敗入力で、根拠を取り違える回数が減ったか。
  • 正しい例だけでなく、保留や停止が正しい入力にも対応できるか。
  • 更新したスキルを戻した場合、挙動の差を説明できるか。

回答の長さや保存したスキルの数は価値そのものではない。変更前後の手順、入力、評価を一組にし、解決した失敗と新しい失敗を残す。これは筆者の評価提案であり、Hermes の性能測定結果ではない。経験が蓄積される基盤だからこそ、誤った経験を次回へ持ち越さない編集の仕組みが必要になる。
