Claude API実装 — 応答より先に失敗を設計する

Messages APIとClaude Codeを区別し、tool・stream・再開を堅牢なアプリへ結びます。

旧情報は固定旧版の全文へ分離しています。以下の例・試験案は未実行の教材です。

APIが担当すること、アプリが担当すること

Messages APIはモデルへ入力を渡して応答を受ける入口です。Claude Codeという完成した作業環境を呼ぶこととは違います。利用者の認証、資料の取得権限、操作の実行、結果の保存、UIの状態はアプリ側で設計します。toolが使えるモデルを選んでも、すべての処理が自動的に安全に完了するわけではありません。

現行のrequestとresponseはCreate a Messageで確認します。旧SDKの例をコピーする際は、model ID、parameter、content block、error handlingを現行版と照合します。この記事の概念手順は未実行で、API keyや課金設定の操作を行いません。

入力と出力の契約を先に置く

教材の公開仕様抽出アプリでは、入力は許可された資料と確認日、出力は製品・surface・仕様・出典・未確認点です。金額がない場合に推測値を返すのでなく、未確認を正しい状態にします。JSONらしい文字列が得られたことではなく、必須field、型、単位、禁止値を検査してから利用します。

長い資料を渡すときは、資料IDと元の段落が結果から追えるようにします。取得失敗で入力が空になった場合、通常の要約が生成されても成功扱いにしません。input validation、model response validation、domain validationという異なる検査を一つのAI自己評価へまとめないことが重要です。

tool往復には実行ownerがいる

モデルが返すtool_useは、実際の外部作用が完了したreceiptではありません。client側toolではアプリが呼び出しを検証し、tool_resultとして結果を戻します。Tool use overview。送信・変更するtoolは読取toolと分離し、必要な範囲の入力だけを受け付けます。

例えば「資料を検索する」と「資料を削除する」を同じ曖昧なtoolへまとめない設計にします。許可された操作でもtimeout後に結果不明になる可能性があるため、操作IDと結果照会を用意します。同じtool callを再送することが安全かをmodelの言葉だけで判断せず、外部システムの仕様と保存済みreceiptで判断します。

streamは途中の状態である

streamingでは複数のeventが段階的に到着します。文字が表示されたから完成したと扱うと、途中切断やtool結果待ちを最終結果にしてしまいます。Streaming messages。UIは受信中、tool実行中、完了、失敗、結果不明を分け、最終messageまで照合します。

未実行の試験案では、途中のnetwork切断、toolのerror、空content、非常に長い出力を入力にします。進捗表示と保存データが一致するか、errorが消えて完了色に変わらないかを確認します。streamの断片を全量保存する場合にも、秘密の混入とretentionを別に検討してください。

移行と費用をrequest単位で見る

現行Opus・Sonnetの移行ではthinking、forced tool use、tool間の表示等が変わっています。Opusの互換性／Sonnetの互換性。model名だけを置換し、既存requestがたまたま通った一件で全移行完了としないでください。

費用は標準入力、出力、cache write/read、server tool等を別に記録します。retryを含む一案件の総量も残し、成功した最後の一回だけを比較しません。常に上位modelを呼ぶより、分類は限定的な小モデル、重大な判断は別の評価条件、という段階を設計できますが、実測なしに節約率を断定しません。

完成条件と運用上の出口

人工fixtureで通常、入力不足、矛盾資料、tool拒否、timeout、途中切断を試します。どの失敗が再試行でき、どれは人やownerの判断を要するかを決めます。permission拒否は自動再試行して通す対象ではありません。結果不明の操作は状態を確認してから進めます。

評価ではschema適合と事実正確性を別に点検し、出典のない値を止められるかを重視します。運用記録にはrequest設定の版、資料版、結果、費用単位、未確認を残します。汎用のAPIガイドから読者の契約・保存要件への適合を確定することはできないため、個別の導入判断は対象環境のownerに残します。

境界テストを三つ用意する

合成のツールを使い、正常な結果、形式不正の結果、同じ要求への重複応答をアプリに渡す教材を作ります。正常時だけでなく、結果をどの依頼へ結び付けるか、欠けたフィールドをどう扱うか、再試行で副作用を二重にしないかを確かめます。モデルが補完した値をアプリ側の事実として保存しないことが重要です。

ストリームが途中で切れた出力は、画面に文字が見えていても完成済みとは扱いません。確定した応答と暫定表示を分け、利用者が再開するときにも未完了状態が残るように設計します。教材のログには架空の要求IDと合成値を用い、認証ヘッダーや実データを混ぜずに検証できます。
