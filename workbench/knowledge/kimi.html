Kimiの長時間タスク設計 — 履歴契約・視覚・再開

長いcontextと自律実行は、同じ話ではありません。Kimiのモデル、API、Kimi Code、Webの成果物作成機能を分け、途中で失敗しても根拠を残して再開できる仕事を設計します。

1. 現行モデルとアプリを切り分ける

公式Kimi K3 repositoryはfull weights公開、ネイティブmultimodal、長いcontext、API名kimi-k3を説明しています。ライセンスは固有のKimi K3 Licenseです。「昔のKimiはModified MITだった」という理解を現行artifactへ引き継がないようにします。K3公式repository

同じブランドのWebアプリが資料やスライドを作ることと、APIだけでその全機能が利用できることは別です。UI、検索、ファイル変換、agent orchestrationが付いている場合、成果はモデル単体の能力だけではありません。API比較は同じtoolsで行い、アプリ比較は完成物を評価する別の試験にします。

2. 履歴は表示用の文章だけではない

K3は常時thinkingで、effortはlow/high/max。multi-turnとtool利用では返されたassistant message全体を次のmessagesへ戻すよう公式が指定しています。contentだけ抜き出すと、reasoning_contentやtool callsを落とします。K3公式quickstart

設計上は「ユーザーに見せる回答」と「API状態」を分離します。前者は必要な答えと根拠、後者は次requestのために保存するmessage構造です。状態を保存することは、そのまま全ログを広く共有することではありません。データ分類、保持期限、閲覧者を設定し、公開記事には必要な公開根拠だけを出します。

# 架空のagent状態例。providerは呼び出さない
conversation_state = {
  "messages": "provider契約に必要な完全message列",
  "task_version": "example-r1",
  "last_verified_artifact": "draft-section-2",
  "pending_tools": [],
  "remaining_budget": "caller側で定義"
}
reader_output = {
  "answer": "人が読む結論",
  "evidence": "公開sourceの該当箇所",
  "uncertainty": "まだ確認していない事項"
}

圧縮やmemory生成もAPIの履歴契約と同一ではありません。履歴を要約する場合は、残すべきtool callの対応関係や未完了処理を壊さない移行方法を検証します。見た目の短縮だけを目標にすると、継続時に同じ仕事を再実行することがあります。

3. Long-horizonを小さな受入へ分割する

長いtaskを「全部完成させて」で始めると、最後まで誤りに気づかない危険があります。本ハブの提案では、入力の理解、最小成果、拡張、検証、受渡しの区切りを作ります。各区切りで実物と未解決点を残し、次工程に必要な情報だけをまとめます。

架空の公開データ分析では、まずCSVの列と欠損を説明し、次に一つの集計を作り、次に可視化し、最後に元データと数字を照合します。グラフが魅力的でも計算が違えば分析としては失敗です。taskの大きさではなく、どの段階から正しく再開できるかを評価します。

停止点も先に決めます。入力が欠けている、source間の矛盾が解けない、toolが拒否された、同じ失敗が試行上限まで続いた時は、勝手な代替経路を探すのではなく実物と不足を返します。自律性は止まらないことではなく、許された範囲で次行動を選べることです。

4. 視覚から制作判断へ

公式quickstartはvision inputをcontentの配列として渡し、動画ファイル参照、structured outputを説明します。structured outputで制約するのは最終のcontentであり、reasoning文字列をJSONとして解釈しないよう案内しています。Vision・structured output仕様

画面評価なら、入力の版と画像を対応させ、modelに「観察」「問題」「修正案」を別々に出させます。観察には目に見える情報だけを入れ、操作結果の推測は区別します。たとえばボタンが見えることは、そのボタンが実際に動く証拠ではありません。画像QAと機能testを分けると、成功の偽装を防げます。

5. 公開重みを持つことの意味

K3は大規模MoEで、公式cardには総規模とactive規模が別に記されています。active値から単一PCの必要memoryを断定せず、重み、量子化、cache、runtime、通信を含めて見積ります。full weights公開は、手元環境での可動性やAPIとの完全一致を証明しません。model summary・deployment

自前運用の試験は、同じprompt templateでの短い応答、tool形式、画像処理、長context、再開を順に確認します。APIとlocalで差があった時は、先にtokenizer、template、sampling、runtime版を調べ、すぐに「modelが悪い」と一般化しません。

6. 導入評価の完了条件

評価記録には完成率だけでなく、初回の誤り、修正回数、人の読解時間、未解決点、再開成功を残します。providerのbenchmarkは候補選択の参考ですが、自分の資料形式・日本語・workflowの適合証拠ではありません。

並列agentを使う場合も、成果の重複、矛盾、引用の一致を親側で統合する工程が必要です。作業数が増えても最終原稿が整わなければ価値は増えません。本記事の手順は架空の設計例であり、Kimiを使った試験や採用の実績を主張しません。
