VS Code — 編集・実行・AI支援を混ぜずに使う

VS Codeはコードを読む、編集する、差分を確認するための土台です。言語runtime、debugger、Git、AI extensionはそれぞれ別の部品です。「エディタをinstallしたので全部動く」と期待せず、一つのprojectで保存からテストまでを確かめると、AIが増えても作業が見えなくなりません。

最終更新: 2026-10-13 · 公式資料の確認日。手順例は未実行の教材です。

ファイル一枚よりworkspaceを開く

workspaceの単位でfolderを開くと、検索、設定、terminal、Gitの対象を揃えやすくなります。何を開いたかを確認しないまま広いfolderでagentを動かすと、不要な資料まで文脈へ入り得ます。小さなprojectを明示的に開くことが筆者の推奨です。個人の好みはUser settings、project共有の必要条件はWorkspace settingsに分け、秘密を設定ファイルへ入れないでください。

VS CodeのGit機能はcommit、branch、diffなどの操作を画面から行う入口です。Gitの履歴や共有先を別の仕組みへ変えるものではありません。Git本体とrepo設定が必要であり、status barのbranch名とSource Controlの差分を確認します。公式: Source Control overview

知らないprojectは実行する前に読む

Workspace Trustは、見知らぬprojectに対してRestricted Modeで自動実行に関わる機能を制限する仕組みです。extensionがuntrusted workspaceでどのように動くかも宣言します。ただし「信頼」とクリックすれば、そのprojectのコードが無害になるわけではありません。公式: Workspace Trustの設計

最初にREADME、package scripts、tasks、debug設定、install時の処理を読みます。生成されたprojectにも実行可能な設定が含まれます。AIが「テストを実行してください」と書いた場合でも、そのtest commandがnetworkや外部serviceを使わないかを先に確認してください。読み取り、依存取得、実行、公開を別の段階にします。

extensionを少なく始める理由

extensionは文字色を変えるだけとは限りません。VS Code公式のsecurity説明はextensionの信頼、publisher、署名などを扱います。表示名や人気だけでなく、publisherの出所、権限に関わる機能、更新、依存serviceを確認します。公式: extension runtime security

最初は言語支援とformatterを一つずつ選び、機能が重複するformatterやAI assistantを大量に足さない方が切り分けは簡単です。remote環境を使う場合はextensionの実行場所も確認します。手元のエディタから操作していても、terminalやファイルの実体はremote側ということがあります。

教材例: HTMLを一ページ直す最小loop

  1. 公開してよい練習用folderを開き、元ページをbrowserで表示する。
  2. h1と説明文を一箇所変更する。保存前後のdiffを読む。
  3. 再読み込みして見出し、文字化け、リンク、狭い画面での折り返しを確認する。
  4. Source Controlで意図したファイルだけが変更されたか確認する。
  5. formatterが全体を書き換えたなら、意味の変更と整形を分けてreviewする。

この例は実施結果ではなく練習設計です。preview extensionの追加は必須ではありません。静的HTMLならbrowserで確認でき、scriptやbuildが必要なら、そのprojectの公式手順を読みます。エラー表示のない文章でもリンク先や事実が誤るため、editorの診断とsource auditは別に行います。

AIに頼む範囲を差分で定義する

良い依頼は「よくして」より、対象ファイル、変更理由、変更してはいけない部分、test方法を明示する形です。たとえば「このHTMLの表をmobileで読めるようにし、本文の意味とURLを変えず、CSSの差分を示す」と書きます。AIの返答ではなく、保存されたファイルとdiffを成果として確認します。

実行の失敗では、Problems panelの診断、terminalの出力、debuggerの停止位置を分けます。構文エラーなら言語支援、import失敗ならruntimeと依存、期待と違う値ならtestとdebuggerです。複数のAI assistantが同じファイルを直す場合はownerと順番を決め、互いの未保存変更を上書きしないようにします。

選択と評価

多言語の編集、Git review、既存toolchainを自分で組みたいならVS Codeが有力です。AIの統合workflowを主にしたいならCursorなども比較対象ですが、エディタUIが似ていても契約、データ配送、agent実行条件は別です。初心者ほど「何のprocessが実行しているか」を説明できる環境を選びます。

評価条件は、同じprojectを開き直せる、対象runtimeが明確、不要なextensionなし、testが再現する、意図した差分だけをcommit候補にできる、の五つです。このページでは利用者のextension一覧、Git設定、AI契約、実機のtest結果を確認していません。利用者の内部設定や個人情報は掲載していません。
