Qwen選択ガイド — API・公開重み・Qwen Code

Qwenは一つのモデルではなく、商用API、サイズの異なる公開重み、画像・音声系モデル、開発ツールが重なるエコシステムです。ブランドからartifactへ選択単位を移すことが実務の第一歩です。

1. 目的に合わせて入口を分ける

Model Studioの現行catalogはqwen3.8-max、qwen3.7-plus、qwen3.8-omni-flashを掲載し、理解系と画像・動画生成を別カテゴリにしています。API名は同名のlocal weightsが存在する証拠ではありません。Alibaba Cloud公式catalog

対話ならWebアプリ、アプリ組込みならModel Studio、自前推論ならmodel card、repository編集ならQwen Codeや他harnessから検討します。ログ、権限、課金、再現性、運用責任は別。チャット契約がAPIを含むとは考えません。画像を理解するmodelを選ぶ時も、画像を生成するmodelと同じ名前で管理しないようにします。

2. familyから運用artifactへ降りる

公式repositoryはQwen3.8-2.4T-A95BとQwen3.8-27Bの公開を記録しています。同じfamilyでも大規模MoEと27Bでは運用対象が違います。Qwen Studio、Qoder、QwenWorkも別入口として案内されています。Qwen3.8公式repository

local候補は最大モデルではなく、入力長、視覚能力、待ち時間、出力用途から選びます。文章分類なら小さい候補と人の確認を組み合わせられます。長いrepository変更ならcontext容量だけでなくtool callと差分の質が重要です。長文を入れられることと、必要な根拠を使えることを分けます。

量子化版は別artifactです。配布者、元revision、方式、chat template、tokenizerを記録し、元名だけで比較しません。第三者の変換済みファイルが公式の性能・license・runtime検証を自動的に引き継ぐわけではありません。

3. Licenseを一括化しない

Qwen3.8-27B cardはApache-2.0、Qwen3.8-Flash-Next cardはqwen-community-1.0と表示します。「QwenはApache」と一括して再配布や商用利用を判断せず、使用weightsのLICENSE本文を読みます。27B card / Flash-Next card

重み再配布、改変物表示、禁止用途、商用条件、noticeを別に確認します。API規約、repository codeのlicense、weightsのlicenseは別欄。これは契約の結論を自動生成する仕組みではなく、判断に必要な文書の取り違えを防ぐ整理です。公開モデルと聞いても、すべての条件が消えるわけではありません。

4. Qwen Codeは実行基盤

現行READMEはterminal、editor、desktop、browser、chat向けagentとして説明し、複数protocol、第三者providerやlocal model、MCP、subagentを案内します。harness機能であって、接続modelが同じ精度で使える保証ではありません。Qwen Code公式repository

harnessとmodelを同時変更すると改善原因がわかりません。まず同じharnessでmodelだけ比較し、次に同じmodelでharnessを比較します。自動memoryやskillsも検査可能な形にし、古いtask前提が持ち越されないようにします。サブエージェント数ではなく、最終差分の一貫性と再作業量を測ります。

# 架空の試験仕様。導入／接続は実行しない
task: CSV読込みの境界条件を修正
allowed: sandbox読書き、既存test実行
forbidden: 公開、原本削除、credential変更
evidence: patch、test command、result、未解決条件
comparison: 同一harness／異なるmodel

5. Local導入はcontextを伸ばして測る

RAM増設だけで特定modelの可動性は断定しません。weights容量、KV cache、画像処理、runtime作業領域、CPU/GPU転送、同時利用を測ります。MoEのactive規模が小さくても、非active expertsを保持・読込みする仕組みが必要です。

最小入力でchat templateを確認し、短文生成、実用途のcontext、同時実行へ段階的に進みます。memory不足とtokenizer不一致を同じ「遅い」で処理せず、first-token待ち、総時間、失敗理由を分けます。大きいmodelが動くことより、必要taskが許容時間で終わることを完了条件にします。

6. 日本語実務と失敗経路を評価する

公開表の欠落抽出、短いbugfix、画像注記を保つ要約を使います。日本語が自然でも固有名や数量が違えば抽出では失敗、綺麗な画面でも例外処理が壊れれば開発では失敗です。難しい問題だけでなく、単純な指示を確実に守れるかも含めます。

出典不明、曖昧な指示、tool拒否、依存関係不足を試験に含め、止まるべき場面で止まれるかを見ます。評価をQwen全体の評判に拡張せず、artifact・runtime・task・権限の組合せに限定します。このガイドは採用設計であり実測ランキングではありません。
