エージェントの工程設計 — 分担より受渡しを先に作る

担当ごとの証拠と編集境界を結び、並列結果を一つの完成物へ統合します。

旧情報は固定旧版の全文へ分離しています。以下の例・試験案は未実行の教材です。

一つの大仕事を、検証可能な工程へ

複数agentを起動する前に、どの成果が次の工程の入力になるかを決めます。調査、実装、review、公開を同時に走らせても、未確定仕様を実装し、未確認結果を公開するなら速さが品質を損ないます。依存関係のある工程と、独立して進められる調査を分けます。

Claude Codeはsubagent、別session、worktree、agent teams等の異なる並列手段を案内しています。公式の機能索引。それらを一つの万能swarmと呼ばず、継続する文脈、書込対象、会話の戻り方、停止条件を比較します。

引き継ぐのは説明だけでなく実物

受渡しには対象pathや版、目的、許可範囲、完成条件、出典またはtest結果、未解決を含めます。親の長い会話を読めると期待して、短く「続きを」とだけ渡す方法は、対象と前提がずれやすくなります。summaryから元の証拠へ戻れる参照を付けます。

調査workerは見解、実装workerは差分、reviewerは反例と指摘という異なる出力を持ちます。全員に同じ長文reportを要求するより、次工程が必要な情報を指定します。受領、引受け、成果確認、採用は別なので、messageを送った時点で責任を空けない設計が必要です。

編集対象は排他的にする

未実行の教材例は、フォームの入力検証を改善する仕事です。Aは仕様と既存反例をread-only調査、Bは対象moduleの実装、Cは別test fileの追加、親が共有configと統合を所有します。依存する変更があるなら、契約を固めてから後段へ渡します。

worktreeは同時sessionの変更を分ける手段です。Worktrees。分離したbranchでも同じ外部DBや送信先を使えば副作用は競合し得ます。共有resourceのownerを一人にし、独立fixtureと使うportなども明示します。

reviewの独立性を設計する

reviewerへ実装者の「全部成功」というsummaryだけを渡すと、確認対象が狭まります。実diff、仕様、変更前の失敗、未実行の検査を渡し、反証を求めます。複数model系統であっても、同じ不十分な入力では同じ漏れが起きるため、人数を独立性の証明にしません。

レビューは指摘の根拠を返す工程で、修正や採用は対象ownerが判断します。重大な問題、再現条件、任意の改善を分類すると、何を今直すべきか分かります。「好みが違う」だけの指摘を大量に戻すより、完成条件の不達を具体的に示す方が役立ちます。

停止・結果不明・重複を扱う

workerが終了したことと担当仕事が完了したことは違います。不足資料、permission拒否、tool障害、結果不明を短く残し、再開条件を示します。止まった担当を無確認で別workerへ再実行させると、同じファイルや外部操作が二重になります。

subagentの文脈とtoolは専用に設定できますが、返答が正しいことを保証しません。Subagents。親は対象成果を照合し、受渡しの失敗か内容の失敗かを分けます。拒否された操作を別担当に迂回させることは、工程上の解決ではありません。

並列化の価値を測る

測るのは起動数でなく、統合後の完成時間、重複調査、競合、訂正量、見つかった実害です。小さい案件ではcoordination costが勝つことがあります。三人が同じ説明を読んだ時間も総負荷に含め、単独のbaselineと比べます。

採用できた分担は適用条件を残します。「独立した複数module」「共有stateなし」「review入力が固定」等が条件です。次の案件で依存が増えたら同じ人数を自動で起動せず、単独または順次工程へ戻します。工程の縮小も、品質を保って仕事を閉じる有効な改善です。

統合失敗を先に試す

架空の改修を調査、実装、レビューへ分け、同じファイルを二人が変更するケース、レビュー対象が古いケース、入力が未完了なのに後工程を起動するケースを教材にします。並列度を上げる前に、これらを検知して停止できるかを確認します。

各担当の完了報告を集めるだけでは全体の受入にはなりません。最終的な対象版、依存していた入力版、残った競合を統合者が照合します。速く終わった担当の待ち時間を悪とせず、誤った入力で進む仕事を減らす方が有益な場合もあります。この比較は設計上の論点で、速度改善の実績値ではありません。
