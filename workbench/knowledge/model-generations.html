モデル世代の読み方：名前から、使える条件へ

モデルの「最新」だけでは、正しい選択になりません。識別子、入口、提供段階、license、試験条件までを一つの候補として扱います。

最終更新・公式資料確認: 2026-10-13 / provider別現行行はLLM Tracker、確認根拠はmodel ledger。

モデルは、一つの名前ではなく一組の条件

ニュースに「新モデル登場」と書いてあっても、model ID、app内のモード名、API alias、weights artifact、coding harnessのどれかで意味が変わります。同じブランドの最新版でも、画像が読めるもの、文章だけを返すもの、動画を生成するもの、検索vectorを返すものは同じ仕事をしません。

候補の識別票（教材）
provider / family / exact model ID
surface: app | API | partner API | weights
version or alias / provisioning stage
input → output / tool protocol
license or contract / region / account conditions
official URL / publication date / checked date
unconfirmed conditions / next test

この識別票がない比較は、モデルだけでなく環境や契約も一緒に変えている可能性があります。たとえば同じmodelでも検索toolを付けた場合と付けない場合は、最新情報の正解率を同じ条件で比べたことになりません。

正式提供・preview・deprecatedを分ける

Previewは試せる機能の紹介である一方、変更の扱いが正式版と違う場合があります。MistralはモデルlifecycleでLabs/Previewのsilent update、GAの変更方針、aliasとfixed versionを説明しています。Mistral lifecycle。この方針を全providerに一般化するのではなく、採用候補ごとに同じ項目を調べます。

Deprecatedは利用終了と同じではありません。AnthropicのSonnet4.5は11月30日のretirement予定を持ちます。公式deprecations。一方、旧DeepSeek Flashのmodelがretiredでも、旧IDのrequestが新modelへroutingされる説明があります。公式更新。成功応答だけでは旧modelが継続稼働している証拠になりません。

予定日を過ぎたこと、停止の告知、実endpointの失敗、後継への移行は四つの観測です。このページはendpointを実行していません。未来の期限は日付とtimezone、対象surfaceを残し、予定を既成事実にしないでください。

contextの大きさを品質の証明にしない

長いcontextは大きな入力を渡す余地を作りますが、重要箇所の読取、矛盾の発見、根拠の保持を保証しません。出力上限、cache、長文料金の閾値、tool messageの保存条件も確認します。Kimi K3の継続tool処理ではassistant messageを適切に戻す手順があり、単純に履歴を短くすればよいとは限りません。公式quickstart。

評価は「長い資料を全部入れた」ではなく、必要な章、矛盾する章、関係のない章を混ぜた合成資料で始めます。答えに必要な根拠を正しい版から引いたか、根拠がない質問を保留したかを確認します。context engineeringは容量を使い切る競争ではなく、判断に必要な状態を設計する仕事です。

licenseはfamily名ではなくartifactへ結び付ける

同じproviderのweightsでもlicenseが異なることがあります。Qwen3.8 27BのApache2.0とFlash-Nextのqwen-community-1.0、Llama4のCommunity Licenseは同一ではありません。27B card / Flash-Next card / Llama4 license。公開weights、open source、商用利用可という言葉を交換しないでください。

実務では、exact artifact/version、用途、再配布の有無、model outputの扱い、契約と追加条件を切り分けます。このページは個別用途の法的適合を判定しません。導入前の確認項目を示す解説です。APIの請求契約とweights licenseの検査も別にします。

限定試験から、導入候補へ進む

  1. 用途を一つに固定する。例えば公開仕様から移行条件を抽出する。
  2. 正解例だけでなく、旧版、日付なし、surface違い、矛盾する条件を含むfixtureを作る。
  3. model/effort/harness/toolの変更を別々に比較する。
  4. 正答率、危険な誤昇格、修正量、総時間・費用を同じ単位で記録する。
  5. 失敗条件が分かるまで実データや外部作用へ拡大しない。

これは未実行の試験手順案です。提供者benchmarkの値を自分の受入基準へそのまま使うより、取り返しのつかない誤りを先に定義する方が判断しやすくなります。採否は、その用途を担当する人が証拠と制約を読める状態で行います。

現行表は一か所、解釈は各記事へ

このページに全model名の第二の表を複製すると、次回更新で矛盾が生まれます。現行行はLLM Tracker、差分と期限は日付付きsnapshot、利用方法は各guideへ分離します。速報から得た新しい名前は候補として残し、sourceを確認してから現行表へ入れます。

現行世代は永遠のSSOTではなく、確認範囲付きの参照です。Baichuanや01.AIのようにcurrent catalogが確定できない行も隠しません。新しい根拠が出たときに調べ直す場所が分かることが、単に行を埋めるより有益です。
