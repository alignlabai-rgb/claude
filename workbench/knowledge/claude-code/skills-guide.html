Claude Code Skills — 繰り返す方法を再利用する

一回の長い依頼を、適用条件と反例を持つ小さな方法へ変えます。

旧情報は固定旧版の全文へ分離しています。以下の例・試験案は未実行の教材です。

Skillに向く仕事、向かない仕事

毎回同じ手順を貼り付ける、確認の順番を忘れる、資料の所在が固定されている、といった仕事はSkill候補です。毎回異なる緊急判断や、十分に試されていない長い依頼をそのままSkillへしても、再利用できる方法にはなりません。まず同じ手順が有用な条件を特定します。

公式のSkillはSKILL.mdを入口に、補助資料やscriptを含める構成です。Skills reference。SkillをロードすることとMCPへの接続、実行権限の取得は別です。この章の例は方法設計の教材で、実際のSkillをインストールするものではありません。

入口はいつ使うかを伝える

名前とdescriptionは、どの仕事でSkillが選ばれるかを左右します。「あらゆる仕事を改善」では適用範囲が広すぎます。例えば「公開API仕様の比較で、製品・利用面・日付・料金の出典を照合する」とすれば、用途と確認項目が明確になります。

本文は目的、入力、手順、出力、停止条件に分けます。詳細資料をすべて入口へ貼り付けず、必要なreferenceへの道順を示します。file pathを絶対の内部hostへ固定すると他環境で使えなくなるため、案件内の相対参照や利用者が決める入力に分けます。

成功例だけで方法を固定しない

未実行の教材Skill案では、公式資料二件の比較を正常例にし、料金未記載、同名の別製品、旧日付の仕様、資料中の命令文を反例にします。出典のない値を埋めず、未確認が出力へ残るかを確認します。文章が自然な正常例だけで合格にしません。

失敗したときは、Skillの指示不足、入力資料の不足、tool障害、modelの判断誤りを分けます。すべてを新しい禁止文として追加すると方法が肥大化します。どの条件で再利用すべきかを見直し、不要な一般論を減らして次版へ反映します。

副作用を分離する

調査・下書き・公開を一つのSkillにまとめると、途中の結果が外部へ送られやすくなります。読者が必要なのは記事候補なら、公開toolの呼び出しは含めず、採用判断へ渡します。送信や課金を含む場合は、それぞれの明示的な権限を持つ別段階へ分けます。

設定上のtool制限も万能なsecurity boundaryではありません。promptの指示、Codeのpermission、OS・接続先の権限を分け、実際の拒否を迂回する手順を埋め込みません。Permissions。Skillにscriptが付くなら、それも実行コードとしてレビューします。

配布範囲と版を設計する

個人、project、plugin、account sync等の配置は利用面と影響範囲が異なります。公式の現在の配置表を確認します。Skillの保存場所と適用。個人の試作をrepositoryへ置くことは、他の利用者へも方法を配る変更です。採用前に秘密と環境依存を点検します。

更新では、変更理由、対象fixture、旧版との違い、戻し方を残します。名前だけ同じで中身が変わると再現が難しくなるため、実行時の方法版や参照先を記録します。読者のjobが旧版に依存しているなら、勝手に消したり全員へ一括更新したりしません。

方法の価値を確かめる

同じ作業をSkillなしとありで比べ、見落とした確認、追加質問、訂正時間、出典への到達を観察します。起動回数やtoken消費は方法の有用性ではありません。実際に下流の人が成果を使えるか、反例でも境界を守れるかを見ます。

数回の成功を全分野の万能手順と一般化しないでください。方法の適用条件、除外対象、未検証の利用面を短く明記し、新しい資料やtool schemaの変更があれば再評価します。使われないSkillを残すより、必要な方法だけが見つかる小さなtoolkitへ縮めることも改善です。

方法の採用と撤回を設計する

合成資料の照合Skillなら、正しい資料対、片方が欠けた資料対、出典が似ている別資料対を試します。採用する条件はきれいな説明文ではなく、必要な根拠を示し、欠損や取り違えを成功にしないことです。テストの期待値は実行者の出力を見る前に書きます。

更新では、手順、参照資料、適用範囲のどれを変えたかを明示します。以前の結果が再現できない場合は、利用者が旧版へ戻るための手がかりも残します。Skillを増やすこと自体を成果にせず、一つの方法で判断の再現性が改善したかを確認すると、似た長文手順の乱立を防げます。
