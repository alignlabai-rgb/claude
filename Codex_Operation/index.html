権限と安全性

SandboxとApprovalを別々に理解する

Sandbox

技術的にどこまで読める・書ける・通信できるか。read-only、workspace-write、danger-full-accessがあります。

Approval policy

どの操作で人に確認するか。通常の対話はon-request、安定した非対話処理は制約付きのneverを検討します。

用途推奨理由
調査・計画read-only変更を発生させない
通常開発workspace-write + on-request作業領域内は自動、外部は確認
CI・自動処理限定workspace + never人待ちを避けつつ境界を維持
Full access外部隔離環境のみホスト上での常用は危険
codex --sandbox workspace-write --ask-for-approval on-request
codex --sandbox read-only --ask-for-approval on-request
--yolo: 承認とサンドボックスを迂回します。外部で強固に隔離した環境以外では使いません。

Git・Worktree

ユーザー変更を守りながら公開する

Commit意図的にstage
Push追跡設定
git status --short --branch
git fetch origin --prune
git diff
git add path/to/intended-file
git commit -m "Concise change summary"
git push -u origin HEAD

Worktreeを使う

長い変更、複数案、並列作業を本体から隔離できます。無視ファイルは自動で引き継がれないため、必要なら.worktreeincludeやセットアップスクリプトを使います。

既存変更を守る

他人の変更を勝手にrestoreしません。同じファイルなら内容を読んで共存させ、無関係ならstage対象から外します。

競合時: まずバックアップ枝を作り、base/ours/theirsの意味を確認します。リベース中のoursは更新先、theirsは再適用中コミットになる点に注意します。
