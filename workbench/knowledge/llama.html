Core Specs

Latest Model Llama 4 Scout / Maverick
Architecture MoE・Native Multimodal
Context Scout: 10M / Maverick: 1M
Strength Ecosystem & Tooling

Llama は Meta が公開するオープンウェイトのファミリーです。現行 Llama 4 は MoE（Mixture-of-Experts）× ネイティブマルチモーダルに進化。Scout（17B active / 16 experts・10M コンテキスト）と Maverick（17B active / 128 experts・1M コンテキスト）の2モデルが公開済み。最大の価値は単体ベンチの高さではなく、エコシステムの厚み——情報・派生モデル・量子化版・推論ツールのどれを取っても一番揃っている「枯れた安心感」にあります。

The Open Standard: なぜ"標準"なのか

Llama は「いちばん賢いモデル」ではなく、「いちばん多くの人が触っているモデル」です。それがそのまま実用上の強さになります。

  • 情報量が最大: 動かし方・トラブル事例・チューニング知見がネット上に最も多く、詰まったときに解決策が見つかりやすい。
  • ツールが揃う: Ollama / llama.cpp / vLLM など主要な推論エンジンが軒並み第一級でサポート。"動かない"がほぼ起きない。
  • 派生の土台: 多くのファインチューン版・特化版が Llama をベースに作られており、その上に乗るだけで選択肢が広がる。

Why "Open Weights"?

Llama は重み（Weights）が公開されているため、クラウド API に依存せず自社インフラで完結させられます。これがローカル/オンプレ運用の定番たる理由です。

Local & On-Prem

外部サーバーにデータを出せない機密プロジェクトでも、ローカル GPU やプライベートクラウドで動かせます。トークン課金から解放され、大量・反復タスクのコストを大きく圧縮できます。

Fine-tuning

ベースが公開されているため、社内用語・特定ドメイン・特殊な言語に追加学習させやすい。多くの研究・派生モデルがこの「土台」の上で育っています。

主な用途

  • ローカル / オンプレ運用: API にデータを出せない・出したくない環境での定番。オフラインでも動く。
  • ファインチューン基盤: ドメイン特化モデルを自前で育てるときのベースモデル。
  • 研究・派生モデルの土台: 新手法の検証や派生モデル構築の出発点として広く使われる。

他との使い分け

  • vs Qwen: Qwen は多言語とコーディング・理数に鋭く、MoE で効率も高い。「日本語コメント込みのコード生成」や算法系は Qwen が一歩リード。Llama はエコシステムの厚みと汎用バランスで選ぶ。
  • vs Gemma: Gemma は Google 系の軽量・端末寄りの構成が得意。極小サイズで端末に乗せるなら Gemma、情報量・ツール・派生の豊富さを取るなら Llama。
  • vs Mistral: どちらもオープンウェイトだが、Mistral は欧州発・用途特化のスリムなモデル群が持ち味。汎用の"安全牌"としては Llama が無難。

Deep Dive: ローカル運用の"安全牌"として

Llama を選ぶ最大の理由は「迷ったときに最も外しにくい」点です。性能首位を狙う場面では他モデルに譲ることもありますが、オープンウェイト × 最大のエコシステム × ツール対応の厚みという三拍子で、ローカル運用の出発点として最も安定しています。（以下はオープンウェイト運用一般の考え方）

どこで動かすか（推論エンジン）

  • Ollama: 最も手軽。個人・検証用に1コマンドで起動。
  • LM Studio: GUI で試したいとき。
  • vLLM: バッチ並列でスループット最大。量産向き。
  • llama.cpp: 低 VRAM / CPU フォールバック。名前の通り Llama 系との相性が深い。

VRAM と量子化

ローカルで動くか／何枚 GPU が要るかは、ほぼ VRAM と量子化で決まります。目安として FP16（無圧縮）は「param 数 × 約2GB」、INT4 量子化なら「× 約0.5GB」と VRAM を 1/2〜1/4 に圧縮できます。フォーマットは GGUF（Ollama / LM Studio / llama.cpp 向け）、AWQ / GPTQ（vLLM 向け）が定番。Llama はこれらの量子化版が最も豊富に出回っているため、手元のハードに合わせた版を見つけやすいのが強みです。

Deep Dive: API（従量） vs ローカルの損益分岐

「自前で安い」が成立する条件をコストの形で捉えると判断が速くなります（普遍的なローカル運用の考え方）。

API（従量）

トークン量 × 単価で使うほど比例増。初期投資ゼロ・即起動・最新モデルにすぐ乗れる。低頻度・最高品質・試作向き。

ローカル（OSS Llama）

GPU 初期投資 ＋ 電気代で事実上使い放題。一定の月間トークン量を超えると単価が API を下回る。大量・反復・オフライン/機密向き。

現実解＝ハイブリッド: 下書き・分類・整形・要約のような大量反復工程はローカル Llama で安く回し、質の最終判断だけ Claude（Opus 4.8 / Sonnet 4.6）や GPT-5.5 等のフラッグシップ API に通す。これがコスト最適のパターンです。

注意: ローカルは「無料」ではない。電気代・GPU の減価・運用/保守の手間も“コスト”。完全自前に振り切るより、まずは「量産工程だけローカル Llama」から始めるのが安全。
