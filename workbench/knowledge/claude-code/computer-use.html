Computer Use — APIと実際の画面操作を分ける

スクリーンの観察、操作の実行、結果の確認を切り分けてGUI作業を評価します。

旧情報は固定旧版の全文へ分離しています。以下の例・試験案は未実行の教材です。

同じ名前で異なる提供面を混ぜない

Computer use APIでは、modelが操作を提案し、開発者側が画面取得や操作を行う環境を用意します。API toolの仕様。Claude Codeの組込みscreen操作やCoworkのUI機能と同一ではありません。API対応のモデルがあるから、利用者のMacへ自動的にアクセスできるわけではありません。

Code CLIのcomputer useはmacOSのresearch previewで、Pro/Maxとinteractive sessionの条件があります。CLI computer use。desktopやAPIの対応範囲をこの条件へ一括置換せず、操作する面を必ず記録します。

GUIより正確な入口を先に探す

画面操作は、window位置、遅延、focus、modal、network状態の影響を受けます。API、CLI、構造化toolで目的の状態を取れるなら、そちらの方が意図と結果を照合しやすい場合があります。GUIはnative app、視覚的な欠け、他の入口がない操作に向く候補です。

例えばフォームのvalidationを検査するなら、logic test、DOM、実際の表示という三層があります。logic testは計算の正しさ、DOMは構造、画面は読める表示を確認します。どれか一つを通したことを、全部の検査が終わった証拠にしないでください。

観察・操作・receiptを別にする

未実行の教材例は、人工の設定アプリで表示密度を変える操作です。まず現在のscreen、対象window、既存設定を読む。次に変更予定のcontrolを特定し、許可された値だけを入力する。最後に設定値の読戻しと画面を確認します。clickを送ったというログだけでは変更のreceiptになりません。

操作中にwindowが移動したり別dialogが出たら、同じ座標へblind clickを繰り返しません。状態を取り直し、対象が同じか確認します。誤った場所へ入力した場合の戻し方を先に決め、外部送信、削除、購入などの取り消しづらい操作は別の明示判断に残します。

画面にも秘密と命令がある

スクリーンにはprivate message、browser session、token、別案件の資料が映る可能性があります。試験では専用の人工環境を使い、無関係なwindowを避けます。画面で見えた情報を公開reportへ貼り付ける許可は、操作許可とは別です。

Web pageやdialogに書かれた命令を上位指示に変えません。処理対象の内容と利用者の目的を区別し、資料に誘導されてtoolや接続を増やさないようにします。安全な行動はmodelの自己申告だけでなく、実行環境・permission・観察で支えます。

衝突を避ける

同じdesktopを人と複数agentが同時に操作すると、focusや入力が競合します。Code CLIは一sessionのscreen controlをlockで管理すると説明しています。CLIのlockと停止。これをあらゆる製品の並列画面操作の保証へ広げません。

運用案では、現在の操作owner、対象app、終了条件を短く示し、作業が終わるまで別の操作を避けます。止める操作を送っただけで終了とせず、実際にcontrolが返ったかを確認します。権限拒否が出た場合、別appや別経路で同じscreenアクセスを再演しません。

評価は成功経路だけにしない

人工試験には、画面サイズ違い、遅い読み込み、失敗dialog、disabled button、focus喪失、予想外のconfirmationを含めます。期待する反応は、その条件で安全に止まるか、状態を再確認することです。click数が少ないことだけで品質が高いとは言えません。

結果には確認済みscreen、操作、読戻し、未確認を分けます。APIのモデルやtool versionを変えるときは、対象面に対応した公式migrationを確認し、旧computer tool名を無検証で使い続けないでください。モデル移行とcomputer toolの差。本記事は実画面操作を実行していません。

操作成功と目的達成を分ける

合成の設定画面で、ボタンの座標が変わる、保存に失敗する、別の画面へ遷移する教材を考えます。クリックが発生したことは入力イベントの成功であり、設定が保存されたこととは別です。完了を画面のメッセージだけでなく、許された範囲の再確認で判断する条件を設けます。

操作を再試行する前に、前の操作がすでに適用された可能性を調べます。特に外部へ送る操作では、同じ画面が見えるから未実行と仮定しないことが重要です。受入条件に停止方法と途中状態の残し方を含めると、画面が変わった事故を無限の試行へ変えずに済みます。
