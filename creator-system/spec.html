モジュール構成

6つのコアモジュール

各モジュールは独立したOpenClaw Skillとして実装され、メッセージキューで非同期連携します。

0

topic-generator

トレンド収集・LLM展開・スコアリングを経て構造化されたネタJSONを生成し、パイプラインキューへ投入するシステム最上流モジュール。詳細は topic-generator.html。

Input: trigger（cron or manual）
Output: queued_topics: TopicJob[]
SLA: バッチ 〜5分（15本）
1

topic-analyzer

ネタ文章を受け取り、ジャンル・ターゲット・難易度を分析してメタデータを付与する。topic-generatorのステップ2で内部呼び出しされる分析サブモジュール。

Input: raw_text: string
Output: topic_data: TopicMeta
SLA: <10秒
2

video-pipeline

topic_data からスクリプト生成・画像生成・音声合成・動画合成を行う。

Input: topic_data: TopicMeta
Output: video: ContentArtifact
SLA: ショート 8〜15分
3

manga-pipeline

topic_data からコマ割り・キャラ生成・セリフ配置・ページ合成を行う。

Input: topic_data: TopicMeta
Output: manga: ContentArtifact
SLA: 8ページ 20〜40分
4

content-evaluator

生成コンテンツをスコアリングし、公開可否フラグと改善提案を返す。

Input: artifact: ContentArtifact
Output: result: EvalResult
SLA: <5秒
5

monetization-manager

評価通過コンテンツを指定プラットフォームに投稿し、収益データを記録する。

Input: artifact: ContentArtifact, score: number
Output: publish: PublishResult
SLA: <60秒
型定義

共通データ型

TopicMeta

type TopicMeta = { id: string // UUID v4 raw_text: string // 元ネタ文章 genre: string // "comedy"|"horror"|... target_age: string // "teen"|"adult"|"all" difficulty: number // 1–5 keywords: string[] // タグ候補 created_at: string // ISO 8601 }

ContentArtifact

type ContentArtifact = { id: string type: "video" | "manga" file_path: string // GCS / S3 パス thumbnail: string // サムネイルURL duration_sec: number// 動画の場合 page_count: number // 漫画の場合 topic_id: string // TopicMeta.id size_bytes: number created_at: string }

EvalResult

type EvalResult = { artifact_id: string score: number // 0–100 decision: string // PUBLISH|IMPROVE // |REVIEW|DISCARD breakdown: { visual: number content: number seo: number safety: number engagement: number } suggestions: string[] evaluated_at: string }

PublishResult

type PublishResult = { artifact_id: string platforms: { name: string url: string published_at: string status: "success"|"failed" }[] revenue_est_jpy: number tracking_id: string }

JobCheckpoint （v0.5で追加 — ジョブ状態管理・再開用）

type JobCheckpoint = { job_id: string pipeline: "video" | "manga" step: string // 完了済み最終ステップ名 step_index: number idempotency_key: string // 同一ステップの二重実行を防止 state: "pending" | "running" | "succeeded" | "failed" | "compensating" retry_count: number last_error: string | null checkpoint_data: Record<string, unknown> // 中間データのGCS参照等 updated_at: string }

Redis にジョブ単位で保持し、ステップ完了ごとに書き込む。プロセス再起動時は最後の step から再開し、idempotency_key で外部API呼び出しの二重発火を防ぐ（詳細は 実行アーキテクチャ）。

実行アーキテクチャ

オーケストレーション方式と
状態管理・耐障害性設計

v0.4までは「メッセージキューで非同期連携する」という粒度の記述に留まっていました。v0.5では、 OpenClaw がどのオーケストレーションパターンを採用しているか、ジョブ状態をどう永続化し、 失敗時にどう回復するかを明文化します。ここで扱うのは設計方針であり、 Phase 3進行中のため実装が方針に追いついていない箇所は「実装中」と明記します。

採用パターン: Supervisor–Workers

2026年時点でよく整理されるマルチエージェント/パイプライン構成は 「単一エージェントループ」「Supervisor–Workers」「階層型」「Peer-to-Peer」の4パターンに大別される （報告ベース・業界一般の整理であり本ハブ独自の分類ではない）。 本システムは OpenClaw を中央コントローラとする Supervisor–Workers 型 を採用する。 理由は、公開判定（評価スコア・コスト上限）という「必ず一箇所で強制したいゲート」が存在し、 Peer-to-Peer型のような分散判断だと閾値の一貫性を保証しづらいため。

  • OpenClaw = Supervisor（分解・委譲・集約・ゲート判定）
  • topic-analyzer / video-pipeline / manga-pipeline / evaluator / monetization-manager = Workers
  • Worker間の直接通信は無し。全て Supervisor 経由（暗黙のPeer-to-Peer結合を防止）
  • Worker はステートレス設計。状態は Redis の JobCheckpoint に一元集約

状態管理・チェックポイント

動画生成は8〜15分、漫画生成は20〜40分かかる長時間ジョブのため、途中でWorkerプロセスが落ちても 最初からやり直さないことがコスト・SLA双方で重要。各ステップ完了時に JobCheckpoint をRedisへ書き込み、再起動時は step_index から再開する。

# 擬似コード: チェックポイント付きステップ実行 def run_step(job_id, step_fn, step_name): cp = redis.get_checkpoint(job_id) if cp.step_index >= step_registry[step_name].index: return cp.checkpoint_data # 完了済みはスキップ（冪等） try: result = step_fn(idempotency_key=cp.idempotency_key) redis.save_checkpoint(job_id, step_name, "succeeded", result) except RetryableError: redis.increment_retry(job_id) except FatalError: redis.mark_compensating(job_id) # Saga的な補償処理へ

冪等性・リトライ・回路遮断（Circuit Breaker）

2026年半ばの一般的なAIパイプライン運用では、「一時的失敗はリトライ、恒久的失敗はフォールバック、 連続失敗は回路遮断で以降の呼び出しを止める」という三層構造が定石とされる（報告ベース）。 本システムも同じ三層で外部API呼び出し（RunwayML / Kling / ElevenLabs 等）を保護する。

状態条件挙動
CLOSED直近のエラー率が正常範囲通常通り呼び出す
OPEN同一サービスで3回連続失敗即座にフォールバック先へ切替。一定時間（目安60秒）呼び出し自体を停止
HALF_OPENOPEN経過後の試験的復帰1件だけ試行。成功でCLOSEDへ、失敗で再度OPENへ
  • リトライ: exponential backoff + jitter（初回1s→2s→4s、最大5回、ジッターで同時再送を回避）
  • フォールバック: RunwayML→Kling AI、Midjourney→DALL-E 4 など既存の代替ツール表（ツール選定参照）をそのまま利用
  • Saga的補償: 動画合成の途中で漫画側が失敗しても、既に課金済みの音声・画像生成コストは記録として残し「部分成果物」を tmp/ に保持（完全ロールバックはしない＝二重課金より二重生成の方が安いという判断）
  • エスカレーション: 3ステップ連続失敗、または同一ジョブで合計5回リトライ後は自動リトライを止め、Signal通知で人間判断に切り替える
⚠️ 実装状況（目安）: JobCheckpoint によるステップ再開とexponential backoffは実装済み。回路遮断（Circuit Breaker）とSaga的補償処理はPhase 3で設計中・一部Workerのみ実装（2026-07時点、報告ベース）。

ファイル管理と
GCS パス構造

生成中ファイルはローカルSSD、完成後はGCSへ移動。 評価通過後のみ長期ストレージへ格納し、未通過ファイルは48時間で自動削除します。

# GCS バケット パス構造 gs://ai-creator-hub-prod/ ├── tmp/ # 生成中ファイル（48h TTL） │ ├── video/{job_id}/ │ └── manga/{job_id}/ ├── artifacts/ # 評価待ちコンテンツ │ ├── video/{YYYY-MM}/{id}.mp4 │ └── manga/{YYYY-MM}/{id}.pdf ├── published/ # 公開済み（永続保存） │ ├── video/{YYYY-MM}/{id}/ │ │ ├── final.mp4 │ │ └── thumbnail_{A,B,C}.jpg │ └── manga/{YYYY-MM}/{id}/ │ ├── final.pdf │ └── final.epub └── lora/ # LoRAモデル（永続） └── characters/{name}_v{n}.safetensors

ライフサイクルルール

tmp/ — 48時間後に自動削除
評価未通過・エラー終了ファイルを含む全一時ファイル。コスト削減のため厳格に管理。
artifacts/ — 評価後7日で移動 or 削除
評価通過 → published/ へ移動。未通過 → 7日後に削除。
published/ — 永続保存（Nearline Storage）
収益化済みコンテンツ。90日後にColdlineへ自動移行してコスト削減。
lora/ — 永続保存（Standard）
LoRAモデルは頻繁にアクセスされるため Standard Storage で保持。バージョン管理必須。

モジュール間認証

内部モジュール間の通信はJWT Bearer tokenで認証します。 OpenClawがマスターキーを管理し、各Skillの起動時に短期トークンを発行します。

# 内部API認証ヘッダー Authorization: Bearer <JWT_TOKEN> # JWT payload { "sub": "skill:video-pipeline", "aud": "skill:content-evaluator", "exp": 1748000000, // 1時間有効 "scope": ["ingest"] }

Webhook署名検証

# OpenClaw → Skill へのWebhookを検証 import hmac, hashlib def verify_webhook(payload, signature, secret): expected = hmac.new( secret.encode(), payload, hashlib.sha256 ).hexdigest() return hmac.compare_digest( f"sha256={expected}", signature )

コード意味原因対処
400リクエスト不正必須フィールド欠損・型不一致ペイロードのバリデーションを確認
401認証失敗JWTトークン無効・期限切れOpenClawから新しいトークンを取得
409冪等キー重複同一 idempotency_key で二重実行を検知先行ジョブの結果をそのまま返却（再実行しない）
422コンテンツ生成失敗AIサービスのエラー・プロンプト問題fallbackモデルへ自動切り替え後リトライ
429APIレート制限外部APIのquota超過exponential backoff + jitter（最大5回） + フォールバック
451コンテンツフィルタ除外不適切コンテンツ検知ネタを修正して再投入。パターンをDBに記録
503外部サービス障害RunwayML / ElevenLabs等の障害・回路遮断OPEN状態代替サービスへ自動フォールバック
504ステップタイムアウト単一ステップが想定時間（目安: SLAの2倍）を超過JobCheckpointから該当ステップのみ再試行。連続超過でエスカレーション
507ストレージ不足GCSバケット上限 or ローカルディスク満杯tmpファイルを即時クリーンアップ + アラート
