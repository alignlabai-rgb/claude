GitHub Copilot：コード変更をreview可能な仕事にする

補完、IDEのagent、cloud agent、code reviewを役割で選ぶ。現在のAI Credits、repo範囲、実行時間、権限とテストを分けて理解する。

最終更新：2026-10-13 / 公式一次資料確認。実環境の機能・契約検査は未実施。

補完からbackground作業まで、同じ仕事ではない

GitHub Copilotはコード補完、chat、IDEでのagent利用、GitHub上のcloud agent、review等を持つ開発サービスだ。cloud agentは一時的なcloud開発環境でrepo調査、計画、編集、testを行い、branchやcommit、pushの作業を進める。現行GitHub.comでの体験。自分の端末のIDE agentと、cloudに委任する作業を同一視しない。

公開repoへコードを出すこと、PRを作ること、mainへmergeすること、deployすることは別の作用だ。記事を読んだだけでそのすべてをagentに許可したことにはならない。repo policyやbranch保護がある環境では、その条件を安全機能として維持し、動かないからという理由で迂回しない。

2026年秋の費用：premium requestsだけで数えない

公式billingはAI creditsという従量単位を使い、1 credit＝0.01 USDと説明する。個人planとorganization/enterpriseでは含まれる枠やpoolの仕組みが異なる。GitHub Copilot billing。旧記事のpremium request回数だけでagent作業の費用を見積もらない。

現行のplan比較ではchat、agent、review、CLI等のAI Credits消費が説明され、code reviewのActions minutesも別に扱われる。modelとtaskの大きさによって消費は変わる。GitHub AI CreditsをCopilot StudioのCopilot CreditsやMicrosoft365のライセンスへ交換可能な共通通貨と考えない。購入時の単価・包含枠・追加使用設定を確かめる。

委任するissueを、実装の契約にする

筆者の提案は、目的、対象file、禁止範囲、期待動作、test、終了条件、返却物を短いissueへ結ぶことだ。「全部改善」より、特定のbugを再現し正常動作へ戻す仕事を最初にする。入力の欠落をagentが想像で補えば、実装が立派でも本来の問題を解いていない可能性がある。

目的：公開ページの相対リンク検査を直す。
対象：検査scriptと専用testだけ。
禁止：記事本文、認証設定、workflowの権限変更。
完了：正常、欠落、外部URL、anchorのtestが通る。
返却：変更理由、実行したtest、未確認事項。
merge/deployは今回の作業から分離する。

これは未実行の教材issueで、このrepoの実作業命令ではない。依存の更新を含む時は、lockfileと対応runtime、migrationの必要性を明示する。多数のfileにまたがる変更は、人がreviewできる単位へ分ける。

cloud agentの制限を工程設計に使う

現行公式docsには、一task一repo、一度に一branch、一task一PR、session最大59分等の制限がある。複雑な仕事は小さく分けるよう案内される。cloud agentの現行制限。制限を超えるために安全条件を変えるのでなく、入力と完了範囲を減らす。

長い仕事を分割する時は、中間branchの差分、test結果、残る不確実性を渡す。最初のagentが「完成」と言ったことを、次のagentの採用済み前提にしない。コードの版が変わったら、前のtestやreviewの対象も変わる。指示fileやskills、MCPを接続する場合は、使えるtoolsと資料の利用範囲を同時に確認する。

code reviewとtestは異なる反証

AI reviewは構造やriskの候補を探す補助として使えるが、すべてのbugや脆弱性を発見する保証ではない。testは指定した入力と条件に対する反証であり、未試験の動作を証明しない。人はdiffと重要な実行経路を読み、追加dependency、network呼出し、秘密の記録、危険なfile操作を確認する。

reviewを役割として独立させるなら、変更の目的と対象版をreviewerへ渡し、producerの自己評価だけで通さない。指摘がなかったことと、riskがないことは違う。CIがない場合は「CI通過」と書かず、実行したlocal testと未確認項目を明示する。

採用の評価

比較するのは生成行数ではなく、再現したbugが解消したか、意図しない変更がないか、review時間が短くなったか、再発がないかだ。小さなtaskで失敗原因を記録し、task定義の不足、環境構築、実装判断、test不足を分ける。より高価なmodelへ変える前に、仕事の契約や試験を直せるかを見る。

agentがPRまで進めても、公開物や本番へ入れる責任は残る。許可済みの範囲でmergeとdeploymentを扱い、結果が不明ならremoteを照合する。コードを書いたという実績ではなく、検証して使える差分を残すことが開発支援の価値になる。
