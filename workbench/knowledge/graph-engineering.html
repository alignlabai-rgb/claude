Graph Engineering
知識と実行を混同しない

関係を辿る知識グラフと、仕事を進める状態グラフは別物です。両者を結びつける価値は、情報を大量に蓄えることより、根拠を追え、途中から再開でき、誤った遷移を止められることにあります。

Graph Engineeringは本ハブで使う横断的な実務ラベルであり、単一の標準規格ではありません。旧版の「14時間→45分」「精度96.5%」「破壊修正率0%」等、元実験を確認できない成果主張を除去し、説明用設計と実測を分けました。

1. グラフにする前に、エッジの意味を決める

種類ノード／エッジ用途例
知識グラフ対象／意味のある関係依存、由来、関連の探索モデル→提供surface→公式根拠
状態・処理グラフ状態や処理／遷移条件実行順、分岐、待ち、再試行収集→検証→草稿→評価→完了
依存グラフ成果物や部品／必要条件変更の波及や実行順の計算共通ライブラリ→利用モジュール→テスト

「担当者Aが製品Bを知っている」という関係は、「AがBを導入してよい」という遷移許可ではありません。意味をオントロジーで明示し、実行条件は別のpolicyとしてコード化します。グラフに書かれた関係も、sourceなしなら未確認情報です。

2. 状態は進捗より、再開に必要な情報で設計する

架空の技術調査を次の状態機械にします。これは説明用の設計例です。レビュー待ちは停止状態であり、黙って承認済みへ進めません。

COLLECTED → VALIDATED → DRAFTED → REVIEW_PENDING
    │            │                  │
    └→ HELD      └→ HELD            ├→ REJECTED
                                    └→ REVIEWED → DELIVERED
                        （公開・契約・本番反映はこのグラフの外）
字段必要な理由守る条件
task_id / revision別案件や旧版を取り違えない一意ID、更新の競合検出
artifact_ref / content_hash何をレビューしたか固定成果物が変わればレビューを無効化
evidence_ids根拠の由来を復元必要sourceへ辿れる
attempts / failure_class同じ失敗の無限反復を防ぐ上限と終了理由を保持
review生成と評価を分離判断者・判定・対象hash
effect_receipt配送等の実行を追跡予定と実行結果を別記録

巨大な本文や画像は状態へ複製せず、参照とhashを持たせます。LangGraphのPersistenceは、thread内のcheckpointと、threadをまたぐStoreを区別します。RAMだけのcheckpointerはプロセス再起動を越えて残らないため、本番の復旧とは別に扱います。

3. 再開できることと、一度だけ実行されることは違う

LangGraphのInterruptsでは、再開時にinterruptを呼んだノードを再実行します。承認待ちの前でメール送信・課金・追記を済ませていると、再開で重複する危険があります。

  1. 読み取り、草稿生成、承認、外部操作を別ノードにします。
  2. 承認対象のhash、操作先、具体的な値を固定します。
  3. 外部操作の直前で対象と承認の一致を再検証します。
  4. 可能なら操作先にidempotency keyを渡し、receiptを保存します。
  5. 通信断で結果が不明なら、再送前に操作先を照会します。

checkpointだけでは外部APIのexactly-onceを保証しません。「送信成功だがreceipt保存前にクラッシュ」の隙間があります。transactional outboxや操作先の重複排除などを検討し、結果不明という状態を残します。本稿のオフラインコードの重複排除は、メモリ内の疑似配送に限るものです。

並列処理にも合流規則が必要

複数workerの結果をリストへ追加するだけでは、同じIDの矛盾や再試行の重複が残ります。安定したIDで重複を識別し、同一IDで内容が違う時はconflictとして保留します。部分失敗、timeout、入力欠落の各経路を定義します。

4. GraphRAGは、質問の構造に合わせて使う

Microsoft GraphRAGの公式資料は、Local、Global、DRIFT、Basicの検索方式を説明します。特定entityの問いと全体を俯瞰する問いは同じ検索ではありません。全体集約にはresource-intensiveな処理もあり、単純なFAQへ無条件に導入するものではありません。

問い最初に試す方法注意
このAPIのmodel IDは？公式catalogの文字列検索グラフ推論でIDを生成しない
この廃止が何に影響する？依存関係と元sourceの探索エッジの更新日と漏れを検査
文書群全体の共通課題は？community report等の集約要約の過程と少数の例外を追えるか
あるentityと広い周辺論点を調べるLocal／DRIFT等を比較展開しすぎたノイズを評価

LLMが抽出したエッジは「確定事実」ではなく候補です。元文書・該当箇所・時点を保ち、誤抽出を訂正できるようにします。権限フィルタは検索前にも適用し、他ユーザーのグラフやcommunity summary経由で情報が漏れないかを確かめます。

5. 正しい経路より、危険な経路を先にテストする

  • 根拠なしの記録がVALIDATEDへ到達できない。
  • レビュー対象hashが変わるとDELIVEREDへ進めない。
  • producer本人の自己承認ではレビュー待ちを越えない。
  • 再実行しても同じ疑似配送receiptが二つにならない。
  • retry上限を越えると、失敗理由を持って停止する。
  • 未知の状態・判定値は暗黙の成功ではなくrejectされる。

標準ライブラリだけの実験コードには、このうち根拠選択、hashに結びつくレビュー、producer／reviewerの分離、疑似配送の重複排除のテストを含めています。DB永続化・ネットワーク・実モデルは使いません。LangGraphの互換性テストや本番の承認基盤を名乗るものではありません。

python3 workbench/knowledge/examples/evidence_pipeline.py
# 内蔵の架空fixtureを検証し、選ばれた根拠IDとテスト結果を表示
# ファイル変更、API呼び出し、外部送信はしません

6. グラフ化を見送る判断も設計

単純な直列処理なら、通常の関数とログが読みやすい場合があります。条件分岐、長い待ち、並列処理、再開、監査が現実に必要になった部分をグラフ化します。ノード数やagent数を価値指標にしません。

導入判断では、失敗後にどこから再開できるか、外部操作を重複させないか、入力から出力まで根拠を追えるかを比較します。GraphRAGの効果は、同じ質問集合で通常検索と比較するまで未検証です。
