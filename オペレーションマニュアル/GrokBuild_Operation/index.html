Grok Build
完全オペレーション

Grok Buildを「速いコード生成」で終わらせず、調査、実装、検証、レビュー、引き渡しまで一つの運転手順にするための実務マニュアル。Grok Build 0.1の256KコンテキストとxAI API互換運用を前提にしています。

最終確認 2026-06-20対象: Build / xAI API基準: 公式Docs・Changelog

概要と導入

最初に役割と運転境界を決める

Best at

高速な実装ループ

小さく仕様を切り、生成、実行、修正を短い周期で回す。待ち時間を減らして試作数を増やす用途に向きます。

Not enough

検証は別工程

速度と正しさは別です。テスト、型検査、セキュリティ、差分レビューを完了条件に含めます。

Context

256Kを設計して使う

大量投入より、対象ファイル、仕様、失敗ログ、完了条件に絞るほうが再現性が上がります。

1. Scope変更範囲を限定
2. Inspectコードと仕様を読む
3. Build小さく実装
4. Verifyテストと差分
5. Ship説明して引き渡す

導入チェック

運用原則: Grok Buildの速度は、タスクを小さくし、検証コマンドを先に渡したときに最大化します。曖昧な大仕事を一発で任せる運用にはしません。

日常オペレーション

毎回同じ開始・終了手順を通す

Start

セッション開始

  1. git statusで未保存変更を確認
  2. 対象機能と非対象を一文で定義
  3. 関連ファイルを先に読ませる
  4. 完了条件と検証コマンドを提示
Finish

セッション終了

  1. テスト・lint・buildを実行
  2. git diffをレビュー
  3. 残課題と未確認事項を列挙
  4. 意味のある単位でコミット

標準プロンプト

目的: [達成したい状態]
対象: [変更してよいファイル/機能]
非対象: [触らない領域]
制約: [言語、依存、互換性、性能]
完了条件:
- [ユーザーから見える結果]
- [テスト/lint/buildコマンド]
- 差分を自己レビューし、リスクを報告

最初に実装せず、関連コードと既存パターンを確認してください。
局面人が決めることGrok Buildへ任せること
企画価値、優先順位、禁止事項選択肢、技術調査、試作案
実装受入条件、設計境界コード変更、テスト追加、反復修正
レビュー許容リスク、公開判断差分要約、潜在バグ、回帰確認

指示とコンテキスト

速さを壊さない情報設計

ファイルで渡す

長い仕様を会話へ貼り続けず、README、設計書、テスト、サンプルへ固定します。

失敗ログを短く渡す

コマンド、終了コード、最初の原因行、期待結果をセットにします。

1ターン1判断

設計変更と大量実装を混ぜず、確認ポイントごとに区切ります。

良い依頼: 「この失敗テストを通す最小変更を行い、既存APIを変えず、同じ回帰テストを追加してください」。
避ける依頼: 「全部いい感じに刷新して」。範囲、判断基準、終了条件がなく、速度が手戻りへ変わります。

実践ワークフロー

用途別の再現可能な手順

Feature

機能追加

  1. 既存の類似機能を特定
  2. 最小のデータフローを図示
  3. 失敗するテストを先に追加
  4. 実装してテストを通す
  5. 公開APIとUI回帰を確認
Bug

障害修正

  1. 再現コマンドを固定
  2. 原因候補を最大3つに絞る
  3. 観測ログを追加
  4. 最小修正
  5. 再現テストを残す
Refactor

リファクタリング

  1. 振る舞いテストを確保
  2. 構造変更を小分け
  3. 各段階でテスト
  4. 性能・bundle差を比較
Review

PRレビュー

  1. 仕様との不一致
  2. 境界値とエラー処理
  3. 認証・権限・秘密情報
  4. テスト欠落
  5. 運用・移行リスク
この差分をレビューしてください。要約ではなく、
1. 実害のあるバグ
2. セキュリティ/権限リスク
3. 回帰テスト不足
4. ロールバック困難性
の順で、ファイルと理由を示してください。

API・ツール連携

xAI APIで反復処理へ組み込む

APIキー

環境変数またはシークレットストアで管理します。リポジトリ、HTML、ログ、スクリーンショットへ含めません。

$env:XAI_API_KEY="..."

モデル指定

モデルIDとコンテキスト上限は公式Modelsページで確認し、コード中の既定値は一箇所へ集約します。

model = "grok-build-0-1"
base_url = "https://api.x.ai/v1"

復旧と安全運用

速い失敗を安全に戻す

変更が広がった

git diff --statで範囲を確認し、生成を止めます。必要ファイルだけ残し、未関係の変更はバックアップ後に除外します。

テストが不安定

同じコマンドを複数回実行し、時刻・ネットワーク・共有状態への依存を切り分けます。

コンテキストが崩れた

新しいセッションで目的、現在差分、失敗ログ、次の一手だけを再提示します。

秘密情報を貼った

即時にキーを失効・再発行し、ログと履歴の保存範囲を確認します。削除だけでは無効化になりません。

git status --short
git diff --stat
git diff
git log --oneline -5
禁止: 状況を確認せずに git reset --hard、強制push、再帰削除を実行させないこと。まずバックアップ枝またはstashを作ります。

逆引き

困ったときの最短入口

最速で試作したい画面1枚、API1本、受入条件3つに限定する。
既存コードを壊したくない類似実装と回帰テストを先に読ませる。
回答が散らかる実装前に計画と変更ファイル一覧だけ出させる。
同じ失敗を繰り返す失敗コマンドと原因をREADMEまたは運用ログへ固定する。
本番へ出したいテスト、差分、migration、rollbackの4点を人が確認する。
最新仕様を確認したいxAI ModelsとBuild Changelogを確認する。
