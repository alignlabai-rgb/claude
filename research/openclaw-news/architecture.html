状態のアーキテクチャ：受付・結果・配送を分離して復旧する

最終更新・公式情報確認：2026-10-13。news という旧 URL は維持し、本文は用途別の現行ガイドへ刷新しました。確認日は発表日ではありません。

例と評価案は筆者の設計提案で、未実行です。性能測定・本番導入・安全認定・正式採用の実績を示すものではありません。

基本の Gateway 構造は アーキテクチャ入門 に譲り、この章では途中停止した仕事の状態を扱う。常設処理が難しくなるのは、モデルが文章を生成できないときだけではない。結果があるのに完了と分からない、通知したか分からない、再開で重複する、といった曖昧な境界が問題になる。

三つの確定点を置く

筆者の設計案では受付、成果保存、配送確認を別々の確定点へする。OpenClaw の公式構造にも、runId 付きの受付と後の最終結果がある。OpenClaw Gateway architecture 受付が完了したから成果物も完成した、としない。人が採用する判断は、その三つの後にある別の工程になる。

合成例は、告知二件の比較表を作り、チャットへ一枚返す仕事である。比較表が保存された直後に通信が切れた場合、モデルをもう一度動かさず、既存結果を返せる状態を理想にする。どの状態を OpenClaw が持ち、どの状態を自分の成果物台帳が持つかを対応させる。

仕事の ID と試行の ID

同じ資料を処理する仕事と、その仕事を実行した一回の試行を分ける。資料の ID と版が同じなら同じ仕事として比較できる一方、モデルや設定を変えた試行は別の観測になる。試行を新しくすることを、同じ結果をもう一度外へ送る理由にしない。

入力、受付、結果、配送を同じキーへ結び、失敗時に最後の確認点を記録する。ID を付けただけで exactly-once を保証するわけではない。処理中の重複、再起動後の重複、長く経った後の再実行は別の試験条件である。

定期処理の期限と再開

公式 lifecycle はジョブと実行履歴の永続化、Gateway の稼働、実行の期限、再起動時の扱いを説明する。OpenClaw Automation lifecycle 時刻が来たこととモデルの呼び出しが終わったことを一つのイベントへしない。期限を越えた結果を今も届けるべきかは業務の要件として決める。

教材では五分で価値を失う速報と、一週間有効な仕様比較を分ける。どちらも同じ再開方針なら、古い速報を新しいものとして送る可能性がある。結果に対象の時刻を含め、時間切れなら保留または期限切れへできる設計にする。

複数 agent に分ける状態

公式 multi-agent は agent ごとの workspace と状態、session の範囲を説明するが、plugin の保存が自動で全て分割されるとはしない。Multi-agent routing 作業を分担するときは、各成果物の責任と共有する保存先を別に決める。名前が違う agent を作っただけで、結論の独立性や秘密の分離が成立したとは言えない。

調査担当の結果と編集担当の原稿には別の状態を持たせる。調査が未完了でも編集は見出しを作れるが、その見出しを完成原稿として採用しない。途中成果を活かすことと、途中を完成と呼ぶことは違う。

障害注入の順序

合成入力で、受付直後、結果保存直後、配送要求直後にそれぞれ停止する条件を検討する。一度に全部を止めると原因が分からない。復旧後に残る結果、重複、不明な状態を記録し、必要な検査だけを再実行する。

完成した設計図には、成功の一本道だけでなく、どの状態から再開できず人の判断を要するかを入れる。失敗を隠す全初期化より、残る証拠を使った局所的な回復を優先する。これが常設を小さな業務の積み重ねとして運用する土台になる。

状態の反例を作る

比較表の保存先が存在していても、前日の古い表なら今日の完成証拠にはならない。ファイル名だけでなく入力の版と今回の結果を結びつける。通知先にメッセージがあっても、途中の ACK なら完成通知ではない。受付と結果の文章を似せない設計にすると、読者も途中の状態を誤解しにくい。
