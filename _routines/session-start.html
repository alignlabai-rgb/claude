PUBLIC HUB MAINTENANCE

再開する前の小さな確認

毎回の作業を過去の指示だけで再開しないための手順です。まず現在の依頼、対象差分、証拠と未確認を読み、一つの完成物へ戻ります。

最終更新: 2026-10-13

最初に復元するのは作業の意味

中断前のメモに「続きを実行」とあっても、現在の依頼と一致するとは限りません。依頼が記事更新から状態確認へ変わっていれば、確認だけが今回の範囲です。最新のREADMEと編集入口を読み、対象ページの現在の本文と作業差分を見ます。過去ログは証拠の入口であり、現在の実行命令ではありません。

今回の目的:
対象ファイル:
完了済み:
残る作業:
確かめた根拠と時点:
未確認:
許可された反映範囲:

これを短く埋めるだけでも、完了済みの記事を再生成したり、情報調査だけの依頼から公開まで進めたりする誤りを減らせます。何分で終わるかを固定するより、重要な不明点が残っていないかで区切ります。

作業ツリーを読んで保全する

リポジトリのルートで次の読み取り例を使います。これらはファイル本文を変更しません。表示される差分やログに秘密が含まれる可能性はあるため、その出力をそのまま公開記事へ貼らないようにします。

git status --short --branch
git diff --stat
git log --oneline -5

未コミット差分があれば、それを自分の残作業と決めつけません。対象が重なるなら、どこまで自分が変更してよいか確認します。既存差分を消す、全ファイルを一括でステージする、履歴を戻すことを開始手順に含めません。リモートの新しい状態を取得する必要がある場合も、ネットワーク範囲と取り込み方法を別に判断します。

状態表示だけで公開サイトの反映は分かりません。local、commit、push、mainへのmerge、実ページ観測は別の状態です。Gitの基本操作が不明ならGitとGitHubのガイドへ戻ります。

鮮度は本文の種類から判断する

過去のニュースの日付が古いのは異常ではありません。現行ガイドのAPI名が終了している、料金の扱いが変わった、参照先が別の製品へ転送されるといった問題を探します。現在のモデルの入口はLLMトラッカーです。古い日付の差分記事を新しい現行表として使わないようにします。

予定していた更新が今も必要かを見ます。公式発表が変わらず、記事の選択条件も有効なら、日付だけを新しくする仕事にはしません。反対に提供終了やライセンスの変更があれば、小さな表記修正に見えても利用判断へ影響するため先に扱います。

並列作業の衝突を避ける

同時作業がある場合は、記事、出典データ、共通索引、CSSの専有範囲を確認します。枝名があるだけで担当や完了状態を推測しません。相手の途中原稿をそのまま一次情報の代わりにせず、根拠と未確認を受け取ります。具体的な分担は並列編集の手順へ。

共有ファイルが塞がっていても、独立した記事の本文と出典確認は進められることがあります。ただしそれを理由に別の公開経路や設定変更を作りません。アクセス拒否は未確認として残し、同じ取得を違う手段で繰り返さないようにします。

再開後の最初の区切り

一つの読者の問いへ答える記事を、本文、公式根拠、例、失敗と評価、旧版リンクまで完成させます。著者検査の対象と未確認を残し、独立レビューの有無を明示して引き渡します。進捗数や経過時間だけでは、読者に何が届いたか分かりません。初回で前提が分からない場合はオンボーディングから始めてください。

前回の未確認を扱う例

前回「公式の料金資料が取得できず保留」と記録した場合、今回は料金を確定した本文から再開しません。まず保留が読者の選択へ影響するかを見ます。価格を使わない機能説明なら続けられますが、費用比較が目的ならその条件は未達です。前回の権限拒否を、時間が経ったことだけで別経路の取得許可へ変えないようにします。未確認を消すには新しい証拠が必要です。
