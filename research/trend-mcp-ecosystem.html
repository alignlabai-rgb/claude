MCP エコシステムの 2026年中間総括
9,000 サーバー、月間 DL 9,700万、そして RCE 実証開示まで

Anthropic が 2024 年末に公開した Model Context Protocol（MCP）は、わずか 1 年半で AI エージェントとツール間の事実上の標準プロトコルになりました。 2026 年 5 月時点で公式レジストリのサーバー登録は 9,000 件超、 月間ダウンロードはローンチ比 4,750% 増の 9,700 万回超。 Claude / ChatGPT / Gemini のいずれも MCP を取り込み、JetBrains・Adobe・Intuit・Docusign など 主要ベンダーが公式コネクターを提供する状況にあります。

一方で 5/18、OX Security が 6 つの本番プラットフォームで MCP の設計上の欠陥を悪用した RCEを実証開示し、 Anthropic はプロトコルレベルでの修正は行わない方針を表明しました。 本稿は、普及指標とリスク、そして Anthropic 側の周辺整備（MCP tunnels / Self-hosted sandboxes / Memory）を一度に並べ、 技術リードが「いま自社で MCP をどこまで踏み込んで使うか」を判断するための見取り図を提示します。

TL;DR — 中間総括の要点

  • 普及面は勝負あり。公式レジストリ 9,000+ サーバー、月間 DL 9,700 万超、主要 LLM ベンダーすべてが MCP をネイティブサポート。「採用するか否か」ではなく「どこから入れるか」のフェーズへ移行。
  • セキュリティ面は未解決。OX Security が本番 6 製品で RCE 実証、Anthropic はプロトコルレベルでは修正しない方針。接続側（サーバー実装・gateway・組織側）にガバナンス責任が降りてきている。
  • Anthropic は「プロトコルは薄く、運用は厚く」。MCP tunnels（社内ネットワーク到達）・Self-hosted sandboxes（実行隔離）・Memory（状態保持）と、周辺レイヤを Managed Agents として揃えた。
  • 2026 後半の論点は、Connector のガバナンス（誰が監査するか）と課金フロー（API 料金以外の経済圏）、そしてエンタープライズ gateway 標準の三点に集約される。
  • 技術リードへの実務メモは末尾参照。「公式コネクター」と「自前 MCP サーバー」の境界線を社内で線引きしておくことが、向こう半年で最大のレバレッジになる。

1. MCP の現在地 — 普及指標と対応モデル

まず、ベンチマークになる数字を並べます。MCP は 2024 年 11 月に Anthropic がオープンソースで公開したプロトコルで、 当初は「Claude Desktop 上で外部ツールを使えるようにする」程度の認識でした。それが 2026 年に入って、 以下のようなクロスベンダーのデファクトに育っています。

9,000+ 公式レジストリ登録サーバー数

2026-05-25 時点。JetBrains が TeamCity 2026.1 を投入したタイミングで MCP Ecosystem Report が達成を公表。

9,700 万 / 月 MCP 関連パッケージ月間 DL

ローンチ時比 4,750% 増。Cyber Strategy Institute（2026-05-18）報告。

200+ Claude 公式コネクター対応アプリ

Uber・Spotify・Instacart・Adobe・Booking.com など。コンシューマー＋エンタープライズの両層を含む。

1.1 「採用するか」ではなく「どこから入れるか」

2025 年半ばまでは「MCP を採用するベンダーが増えるかどうか」が論点でした。2026 年 5 月時点では、 Anthropic（Claude）・OpenAI（ChatGPT / Codex）・Google（Gemini / Antigravity）・Microsoft（Copilot 系列）・ JetBrains・Atlassian・Adobe・Intuit・Docusign・Thomson Reuters など、AI 側もツール側もほぼ全員が MCP を実装済みです。 論点は「どのレイヤから MCP を組み込むか」に移りました。

  • SaaS 利用者層：Claude / ChatGPT / Gemini のチャット UI から「公式コネクター」を有効化するだけ
  • 開発者層：Claude Code・Codex・Gemini CLI・Antigravity から自前 MCP サーバーを参照
  • エンタープライズ層：Self-hosted sandboxes・MCP tunnels・社内 MCP gateway で、外部ネットを通さずに使う

1.2 なぜ 1 年半でデファクトになれたのか

MCP は意図的に薄いプロトコルです。JSON-RPC ベースで、リソース（read）・ツール（call）・プロンプト（template）の 3 種類のプリミティブしかなく、新しい認証スキームや独自のスキーマ言語は持ち込みません。 この「薄さ」が、競合ベンダーが追加実装する障壁を下げ、結果としてクロスベンダー採用を加速させました。

MCP の本質は「ツールの呼び出し方法を統一する」というより、 「ツール側が自分自身の仕様を AI に自己申告するプロトコル」である点にあります。 従来の OpenAPI / Function Calling と違い、ツール側がランタイムに自己記述するため、 AI 側は事前に何も知らなくてもサーバーに接続した瞬間に使えるようになる。

2. Claude / ChatGPT / Gemini の MCP 対応比較

三大ベンダーすべてが MCP をサポートしていますが、「MCP を中核に据える」のは Anthropic だけです。 OpenAI と Google は、自前のエコシステム（Codex プラグイン / Antigravity）を主軸に据えつつ MCP を 「外部ツール接続の標準口」として併用するスタイルを取っています。

ベンダー MCP の位置づけ 主な接続経路 差別化
Anthropic（Claude） プロトコルそのものの提唱者。全プロダクト共通の標準。 Claude Desktop / Claude.ai / Claude Code / Managed Agents / Cowork、全てで MCP がネイティブ。 200+ 公式コネクター。MCP tunnels で社内ネット到達。Self-hosted sandboxes で実行隔離。
OpenAI（ChatGPT / Codex） Codex プラグインを主軸、MCP は「外部ツール接続の互換口」。 Codex から MCP サーバーを参照可能（Codex Changelog 5/10 で MCP diagnostics 強化）。Workspace Agents は独自プラグイン形式。 Atlassian Rovo・GitLab・CircleCI など 90+ プラグインを GPT-5.5 と同時追加。SaaS への直接接続は MCP と独自プラグインのハイブリッド。
Google（Gemini / Antigravity） Antigravity の Managed Agents と Workspace ディープ統合が主軸。MCP は「外部ツール用」。 Gemini CLI / Antigravity Desktop（IDE）から MCP サーバーを参照。Workspace 統合は Google 独自の API レイヤ。 Gmail / Docs / Slides に Spark でディープ統合。OS レベル（Android 17 / Android XR）まで降りていく戦略。

2.1 「中核」と「互換口」の差は何を生むか

Anthropic にとって MCP はプロダクトの一部です。Claude for Legal（5/12）は 12 プラグインに加えて Docusign / Box / Thomson Reuters（Westlaw）など 20+ MCP コネクターを提供しており、 コネクター追加が「製品差別化そのもの」になっています。クリエイティブ系も同じ構造で、4/28 に Adobe・Blender・Ableton など 9 本の MCP コネクターを一斉公開しています。

対照的に OpenAI と Google は、MCP に「外部接続の互換性」だけを求めています。コア体験は Codex プラグイン（90+）や Workspace ディープ統合で作り、その外側に MCP を置く。 この差は、「サードパーティ MCP サーバーが増えれば増えるほど直接得をするのは Anthropic」 という構図を生みます。エコシステムの成長と自社製品の魅力が同期するのは、現状 Anthropic だけです。

3. MCP RCE 脆弱性と Anthropic の判断

3.1 5/18 の実証開示 — 何が起きたか

2026 年 5 月 18 日、セキュリティベンダーの OX Securityが、本番運用されている 6 つの MCP 対応プラットフォームで、 MCP の設計上の欠陥を悪用したリモートコード実行（RCE）を実証する報告を公開しました。 詳細はベンダー間の協調修正が進む間は伏せられていますが、報告の核は次の三点です。

  • ツール記述の信頼境界が曖昧：MCP サーバー側が AI に「ツール定義」を渡すとき、その内容を AI が無検証で取り込む構造。サーバー側を侵害すれば、AI に任意のプロンプトを実質的に注入できる。
  • ツール出力からの indirect prompt injection：サーバーが返す結果テキストにエージェント向けの指示が混入していると、AI が後続ツールを呼び出して任意コードを実行しうる。
  • 接続ホスト側の権限管理が薄い：MCP の信頼モデルは「ユーザーが許可した接続は信頼する」が前提で、サンドボックス・最小権限化はホスト実装に委ねられている。

3.2 Anthropic の判断 — プロトコルレベルでは修正しない

Anthropic は、これに対しプロトコルレベルでは修正を行わない方針を表明しました。理由は表向きには示されていませんが、 構造から読み取れるロジックは次の通りです。

  1. プロトコルを厚くすると採用が止まる。MCP がここまで広がったのは「薄さ」が理由。認証や権限制御を本体に組み込むと、現在の 9,000 サーバーの多くが互換性を失う。
  2. 脆弱性の根は「実装の信頼境界」。プロトコル仕様を変えても、ホスト実装がサンドボックス化していなければ同じ問題は再発する。本質的にはホスト責任。
  3. Anthropic 自身が「ホスト側」で答えを出している。Self-hosted sandboxes・MCP tunnels・Memory は、まさにこの問題への回答。プロトコルではなく Managed Agents 側で守る、という設計思想。
この判断は「IETF 的な仕様主義」と「プラットフォーム的な運用主義」の分岐点と読めます。 Anthropic は明確に後者を選んだ。プロトコルは公開・共有財として薄く保ち、自社の差別化はホストレイヤの安全運用で出す、という二層戦略。

3.3 接続事業者・利用組織への影響

この方針が意味するのは、「MCP サーバーを公開する側」「MCP サーバーを使う組織」の双方が、独自にセキュリティ責任を負うということです。 現状、運用上の最小ラインは以下です。

  • MCP サーバー側：ツール出力に外部入力をそのまま含めない／署名付き応答／最小権限の API キー
  • ホスト側：Self-hosted sandbox・コンテナ実行・ネットワーク隔離・人手承認ゲート（Claude Code の Auto Mode 承認フローなど）
  • 組織側：許可リスト方式の MCP gateway／コネクターの監査ログ集約／秘密情報の保持境界明示

4. Connector エコシステムの構造

Connector（コネクター）という呼称は Anthropic が広めましたが、実体は「公式に動作確認・配布された MCP サーバー」の通称です。 ここでは公式 / サードパーティ / エンタープライズ gatewayの三層に整理します。

① 公式コネクター

Anthropic / OpenAI / Google が直接配布・保証するもの。Claude では 200+ アプリに対応。Adobe・Blender・Docusign・Westlaw・QuickBooks・Intuit などの業務基幹アプリを網羅。

保証範囲：基本動作・OAuth フロー・ベンダー側との合意。セキュリティ保証は限定的。

② サードパーティ MCP サーバー

公式レジストリの 9,000 件超のうち、大多数はコミュニティ・スタートアップ・SaaS 各社による自前提供。「カタログには載っているが品質はバラバラ」な状態で、選定責任は利用組織側にある。

選定軸：メンテナの継続性・依存パッケージのセキュリティ・出力サニタイズの実装。

③ エンタープライズ MCP gateway

2026 年に立ち上がりつつあるレイヤ。社内の許可されたコネクターだけを束ね、AI からの呼び出しを監査ログ・レート制限・秘密情報マスキング付きで中継する。Big Four の Digital Gateway 系はこの設計思想に近い。

参考：KPMG × Anthropic Digital Gateway / PwC × Anthropic 統合。

4.1 公式コネクターの「2 種類」

Claude の 200+ コネクターは、実は機能的に大きく二系統に分かれます。

  • コンシューマー寄り：Uber・Spotify・Instacart・Resy・StubHub・Tripadvisor・AllTrails など、Claude が文脈に合わせて「最適なアプリ」を自動提案するライフスタイル系（4/24 公開、5/23 拡張）。
  • エンタープライズ寄り：Docusign・Box・Thomson Reuters（Westlaw）・QuickBooks・HubSpot・PayPal・Canva・Google Workspace・Microsoft 365 など、Claude for Legal / Claude for Small Business に紐づく業務系（5/12 / 5/13）。

この二層化は、MCP が「個人向け生活アプリ」と「業務基幹アプリ」の両方に同時に染み込んだことを示します。 2025 年までは開発者向けの色合いが強かったプロトコルが、半年で UX まで降りてきた点が今期最大の変化です。

4.2 課金フロー — 次の論点

現状、ほとんどの MCP コネクターは「AI 側の API 料金＋ツール側の既存課金（ユーザーが既に契約している SaaS）」で動いており、 コネクター自体は無償。しかし、Connector を提供することが集客に直結し始めると、 いずれ「コネクター経由のトランザクション課金」「優先表示の枠課金」といった経済圏が立ち上がる可能性が高い。 Uber / Booking.com / Tripadvisor のような「予約系」コネクターは、その最有力候補です。

5. Anthropic 側の周辺進化 — MCP tunnels / Self-hosted sandboxes / Memory

前述したように、Anthropic は「プロトコルは薄く、ホストレイヤで守る」という二層戦略を取っています。 その「ホスト側」が、Code with Claude London（5/19〜20）で public beta に揃った 3 つの機能です。

Memory public beta

セッションをまたぐファイルベースの記憶層。Netflix・Rakuten・Wisedocs・Ando などで初回エラー97%減・処理速度30%向上の実績。MCP 経由で取得した情報を「次回も覚えている」状態にすることで、毎回の MCP 呼び出し回数を構造的に減らす。

Self-hosted sandboxes public beta

機密データ・社内サービスを自社インフラに留めたまま、エージェントループのオーケストレーションのみ Anthropic 側で実行。MCP サーバーの実行を自社境界内に閉じ込められる。RCE リスクへの実質的な回答。

MCP tunnels research preview

パブリックインターネットを介さず、社内システムへ到達するセキュアトンネル。社内 ERP・CRM・コードベースに MCP 接続する際の「インターネット晒し」を回避できる。エンタープライズ採用の最大のブロッカーを外す機能。

5.1 三点セットが解いている問題

この 3 機能は、それぞれ独立しているように見えますが、まとめて読むと「MCP を本番で使うときに残っていた 3 つの壁」に対応しています。

  • 状態の壁 → Memory（毎回ゼロから始まらない）
  • 実行の壁 → Self-hosted sandboxes（任意コード実行を自社境界に閉じる）
  • 到達の壁 → MCP tunnels（社内ネットに公衆網を晒さず届く）

プロトコル本体には手を入れず、運用上の「壁」を Managed Agents 側で順に解いていく戦略は、 OpenAI が Codex のサンドボックス（Windows サンドボックス・Mac アプリ）で取っているアプローチと近い構造を持ちます。 違いは、Anthropic の場合これらが全て MCP を前提に組まれている点です。

6. 次の論点 — ガバナンス、セキュリティ標準、課金

6.1 ガバナンス — 誰が「公式」を保証するのか

9,000 サーバーが乱立する状態は、利用組織にとって「カタログにある＝安全」では決してありません。 公式レジストリは登録の場であって監査の場ではない。今後、以下のいずれかが必要になります。

  • Anthropic / Google / OpenAI 各社による「公式 verified」のティア分けと署名済みコネクター
  • 第三者監査機関によるMCP サーバー認証（SOC2 / ISO 27001 の MCP 版）
  • エンタープライズ gateway による許可リスト運用（事実上の私的監査）

5/18 の RCE 開示以降、この「監査」の不在は構造的リスクとして可視化されました。 2026 後半に、いずれかの形で着地点が見える可能性が高い。

6.2 セキュリティ標準 — MCP-Sec のような追加層

Anthropic がプロトコル本体に手を入れない以上、補完層が必要です。すでにコミュニティでは 署名付きツール定義・呼び出し ID の改ざん検証・呼び出しの監査トレースといった追加仕様が議論されています。 これらが「公式 MCP の派生」ではなく「MCP の上に乗る追加プロファイル」として標準化されると、 プロトコルの薄さを保ったまま運用安全性を上げられます。

6.3 課金フロー — Connector 経済圏

現状、AI 側のトークン課金しかマネタイズ経路がない MCP に対して、 Connector 経由の予約・購入・サブスクリプションのリベニューシェアは技術的に組み込み可能です。 Anthropic は Claude.ai 内で Uber・Spotify・Booking を提案するところまで来ており、 次の半年で「AI 経由のコンバージョンに対する手数料」フェーズに進むかどうかが注目されます。

7. 技術リード向け実務メモ

ここまでの整理を踏まえ、向こう 3〜6 ヶ月で技術リード・エンジニアリング企画担当が手を動かすべき項目を列挙します。

A. 「公式コネクター」と「自前 MCP サーバー」の境界線を決める

  • SaaS 系（Slack・Docusign・QuickBooks・Westlaw）は公式コネクター優先。OAuth と監査ログがベンダー側で整っている。
  • 社内基幹システム（ERP・社内 CRM・社内ナレッジ）は自前 MCP サーバーを Self-hosted sandbox + MCP tunnels の組合せで隔離して提供。
  • コミュニティ製サーバーをそのまま本番投入しない。fork して依存をフリーズし、出力サニタイズを追加する運用を標準化。

B. ホスト側のセキュリティ最小ライン

  • サンドボックス実行（Self-hosted sandboxes / Windows サンドボックス / コンテナ）をデフォルト ONに。
  • ツール出力を AI に渡す前にHTML / コード / リンクのエスケープを行う indirect prompt injection 対策。
  • Auto Mode などの自動承認パスを使う場合は呼び出し回数・予算上限・対象パスのハードリミットを必ず設定。

C. ガバナンス側

  • 社内で「許可コネクターリスト」を明示し、CISO / 情シスがレビューするフローを整備。
  • MCP gateway を1 個に集約し、すべての AI クライアントはそこ経由でツールにアクセスする構成（gateway パターン）を推奨。
  • 監査ログを既存の SIEM に流し込み、「いつ・誰の AI が・どのツールを・どのパラメータで呼んだか」を残す。

D. 開発側のスタンス

  • 新規ツール統合は「MCP サーバーとして書く」を基本に。OpenAPI / Function Calling 専用実装は避ける（互換性が AI 側で失われる）。
  • 社内向け MCP サーバーには「ツール定義の自己説明」を厚く書く。AI 側の精度がここで大きく変わる。
  • Claude Code・Codex・Gemini CLI のいずれでも動くように、クライアント非依存のサーバー実装を心がける。
要するに、「プロトコルとしての MCP」は安定し、勝負はホスト側に移った。 2026 後半に差がつくのは、サンドボックス・gateway・監査ログを当たり前に運用できる組織かどうかです。
